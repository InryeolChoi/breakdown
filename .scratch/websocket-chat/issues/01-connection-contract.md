# WebSocket 접속·메시지·종료 계약

Type: grilling
Label: wayfinder:grilling
Status: resolved
Assignee: Codex
Blocked by: none

## Question

익명 사용자 준비, 방 접속 조건, 메시지 형식, 방 종료와 오류 및 쿠키 갱신을 어떻게 연결하며 사용자와 AI의 구현 경계를 어디로 잡을까?

## Comments

2026-10-11: 사용자 답변으로 아래 방향을 확인했다.

- 접속 전 기존 HTTP 익명 사용자 API로 쿠키를 준비한다. 핸드셰이크는 새 사용자를 생성하지 않으며 유효한 쿠키와 운영 중인 방을 확인한다.
- 클라이언트는 본문만 담은 JSON을 전송한다. 방은 접속 주소, 작성자는 쿠키로 판단한다. 응답은 서버가 생성한 메시지 ID·닉네임·본문·시각을 포함한다.
- 방 운영 종료 시 종료 안내 후 연결을 종료한다. 메시지 작성 시에도 기존 Service에서 운영 시간을 재검증한다.
- 사용자는 Handler를 작성하고 AI는 핸드셰이크·JSON 변환·설정 및 전송 지원·테스트를 지원하는 분담안을 제시했다.

미답변 질문:

- 입력 오류는 보낸 연결에만 오류를 보내고 유지하되 사용자 만료·차단·방 종료는 종료할 것인가?
- 각 방 접속 전 기존 HTTP 익명 사용자 API로 쿠키를 갱신하고, 메시지 작성에서는 DB 방문 시각을 갱신하는 것으로 시작할 것인가?

계약 전체와 구현 분담을 함께 확인한 뒤 해결한다. 아직 Java 코드 변경은 시작하지 않았다.

## Answer

2026-10-11: 사용자는 추가 질문에도 추천안을 선택했다. 입력 오류는 보낸 연결만 오류 JSON으로 안내하고 연결을 유지한다. 사용자 만료·차단·방 종료는 안내 후 종료한다. 방 접속 전 HTTP 익명 사용자 API로 쿠키를 갱신한다. 정책은 docs/decisions.md에 반영했다.

사용자의 다음 작성 지점은 ChatWebSocketHandler.handleTextMessage의 메서드 틀과 방 ID·payload 읽기다. 최종 핵심 흐름은 본문 변환 → ChatService.create → 성공한 결과의 방별 방송이다. JSON 변환·핸드셰이크·설정·동시 전송 보호·검증 코드는 AI 지원 범위로 두고 아직 Java 구현은 시작하지 않았다.
