## Question

메시지를 보내지 않는 연결도 자신이 입장한 운영 구간의 종료 안내를 받고 닫히려면, 종료 감지 주기와 종료 직전에 수락한 메시지의 처리 순서를 어떻게 정할까?

## Comments

2026-10-11: 다음 frontier로 선택하고 Codex가 담당한다. 기존 정책의 종료 안내·연결 종료 자체를 다시 묻지 않고 아직 정하지 않은 시간·경합 경계만 확인한다. Java 구현은 진행하지 않는다.

단일 기존 서브에이전트가 로컬 코드를 읽기 전용으로 확인했다.

- `Room.currentClosingTime(now)`는 열린 운영 구간의 날짜가 포함된 종료 시각을 이미 계산한다. 자정을 넘는 운영도 처리한다.
- 핸드셰이크 속성은 현재 roomId/rawToken뿐이다. 입장 구간의 종료 시각은 없다. 다음 운영 시간이 시작된 뒤 isOpen만 확인하면 이전 연결과 새 구간을 구분할 수 없다.
- Registry에는 register/unregister/broadcast만 있다. 방송과 Handler의 오류 전송·종료는 동일한 세션 객체를 잠근다.
- 스케줄링 활성화와 주입 Clock, 테스트용 MutableClock을 재사용할 수 있다. 기존 60초 정리 작업은 DB 삭제용이다.
- 기존 방 종료 테스트는 시간 변경 후 메시지를 보내야 종료된다. 유휴 연결의 자동 종료를 확인하지 않는다.

사용자에게 확인할 현재 질문:

1. 정상 실행 중 1초마다 종료 대상 연결을 확인하는 방식으로 시작할까? 작성 거절은 기존 운영 시간 검증을 유지하며, 안내·물리적 종료는 검사 시점에 수행한다. 주기 값은 서버 부하·전송 지연까지 포함한 엄격한 최대 지연 보장은 아니다.
2. 종료 직전에 수락했지만 종료 후 DB 커밋이 끝난 메시지 때문에 연결 종료를 기다릴까? 종료 우선이면 저장은 성공해도 전달되지 않을 수 있다. 수락한 메시지 전달 우선이면 종료가 늦어질 수 있다.

추천은 1초 검사와 종료 우선이다. 사용자 답변 전에는 정책으로 확정하거나 구현하지 않는다. 종료 안내·연결 종료에 이미 사용 중인 오류 JSON/1008 형식은 재사용 후보이며 새 계약이 필요하면 별도로 확인한다.

## Answer

2026-10-11: 사용자는 두 질문에 각각 ‘1초 주기’, ‘방 종료 우선’을 선택했다.

- 정상 실행 중 1초 주기로 종료 대상 연결을 확인한다. 이 값은 최대 지연 보장이 아니며 작성 시의 운영 시간 검증을 유지한다.
- 종료 직전에 수락했어도 종료 시각 이후 커밋된 메시지의 전달을 기다리지 않는다. DB 저장 성공과 실시간 전달 성공은 구분한다.
- 종료 시각 이후 새 방송 전송을 시작하지 않도록 방송의 세션별 잠금 안에서도 종료 여부를 판단한다. 이미 시작된 전송을 회수한다는 뜻은 아니다.
- 연결은 자신이 입장한 운영 구간에 속한다. 다음 날 방이 다시 열려도 이전 연결의 종료 기한을 새 운영 구간으로 연장하지 않는다.

구현에 넘길 순서: 핸드셰이크에 종료 시각 속성 준비 → Registry의 종료 대상 확인·안내·등록 해제·종료 경계와 방송 직전 검사 → 주입 Clock을 사용하는 1초 스케줄링 연결 → 메시지를 보내지 않는 실제 연결과 종료 경계 검증. 기존 오류 JSON의 방 종료 403·종료 코드 1008을 재사용한다. Java 구현과 새로운 테스트는 아직 작성하지 않았다. 첫 학습 과제는 사용자가 핸드셰이크 속성에 `closesAt`을 추가하는 것이다.
