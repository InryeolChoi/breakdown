# Message DB 임시 보관 — 검토 초안

상태: 2026-10-05 Q1~Q7 합의, 2026-10-06 V10 및 Java 저장/신고/정리 경로 전환 완료. 이 문서는 검토 이력이며 최신 정책은 [decisions.md](../decisions.md), ERD는 [erd.dbml](../erd.dbml)을 따른다.

## 설계 트리

- 일반 메시지를 DB에 임시 보관: 사용자 합의 완료
  - 기존 확정 정책 유지: 이전 대화 미제공, 최대 140 코드 포인트, 수정/사용자 삭제 없음, 신고 가능 기한은 최대 15분 또는 운영 구간 종료, 신고 증거 30일
  - 사용자 확인 완료: 재시작 이후에도 원래 기한까지 신고 가능 / 원본 확인 시점에 유효하면 커밋이 만료 후 완료되어도 접수
  - 사용자 확인 완료: DB 전환에서 기존 10,000개 전역 상한 제거
  - 사용자 확인 완료: 해당 운영 구간 종료 10분 후 원본 삭제 / 원본 삭제와 독립된 Report 증거(FK 없음)
  - 사용자 확인 완료: 기존 최대 15분 또는 방 종료의 신고 기한 유지
  - 사용자 확인 완료: 삭제 대상 row를 실행 완료 후 1분 간격으로 정리
  - AWS 운영 설계에서 별도 확정: 백업/WAL 보존 기간. 이번 ERD 합의는 백업의 즉시 삭제를 보장하지 않음
  - 합의 후: ERD/정책 반영 → V10 → Entity/Repository → 기존 Service 전환 → 테스트

Wayfinder 검토 목적지는 **DB 임시 Message의 정책·ERD 합의**로 제한한다. 현재는 한 세션에서 검토할 수 있는 작은 설계여서 별도 지도/트래커 이슈를 만들지 않았다. 관리자 신고 검토·자동 차단은 사용자가 언급한 향후 요구이며 이번 전환에는 구현하지 않는다. 신고 증거 보관과 실제 신고 가능 기한은 서로 다르다. 서버 재시작이 원본의 15분 기한을 연장하지 않는다.

### 1차 답변 반영

- Q1: 서버 재시작 후에도 원본의 남은 유효 시간 동안 신고를 받는다. 원본 만료 후에는 Report에 보관된 증거만 관리자 검토에 사용할 수 있다.
- Q2: DB 전환에서 기존 10,000개 전역 상한을 제거한다(사용자 확인). 기존 상한은 Map의 메모리 증가를 막는 장치였다. 제거가 무제한 자원을 뜻하지는 않으며, 만료 정리·전송 제한·디스크 모니터링은 운영 준비에서 검토한다. 현재 Map의 상한 코드는 DB 전환 시 함께 제거하며 지금은 유지한다.
- Q3: 원본을 확인할 때 기준 시각을 구해 유효성을 판단한다. 만료 전에 확인한 원본이면 증거 저장의 커밋이 만료 후 끝나도 신고를 받는다.
- Q4: 사용자 답변은 "한번 채팅방이 종료되고 10분 후에 삭제"다. 실제 삭제 기한은 해당 운영 구간 종료 + 10분으로 변경한다. 이것이 기존 15분 신고 가능 기한까지 변경하는 뜻인지는 아직 확인하지 않았다. 정리 스케줄 간격과 앱 정지 시 삭제 지연도 별도 검토한다.
- Q5: 사용자는 원본 삭제 후에도 Report 증거가 남는 구조에 동의했다. Report.message_event_id는 Message FK 없이 유지한다.
- Q6: 기존 신고 기한(작성 후 최대 15분 또는 방 종료 중 빠른 시각)을 유지한다(사용자 확인). 원본의 실제 삭제 기한만 해당 운영 구간 종료 + 10분으로 분리한다.
- Q7: 삭제 작업은 1분 간격이며 삭제 대상 기한 이후 다음 정리 때 실제 삭제한다(사용자 확인). 앱 정지 중에는 삭제가 지연될 수 있다.

## 관계와 컬럼

Room 1:N Message, AnonymousUser 1:N Message. Report는 여전히 Room과 신고자/대상 사용자를 참조한다. Report.message_event_id는 Message.id의 값을 복사하지만 DB 외래 키는 아니다.

| Message 컬럼 | 역할 |
| --- | --- |
| id uuid PK | 서버 생성 메시지 식별자. 기존 메시지 UUID/API 유지 |
| room_id integer FK | 작성된 방 |
| anonymous_user_id integer FK | 서버 쿠키로 검증한 작성자 |
| nickname varchar(30) | 작성 당시 닉네임. 기존 메모리 객체가 보관하던 의미 유지 |
| content varchar(140) | 서버 검증 후 앞뒤 공백을 제거한 원문 |
| sent_at timestamp | 서버가 기록하는 작성 시각 |
| expires_at timestamp | 신고 가능 기한: min(sent_at + 15분, 해당 운영 구간 종료) |
| delete_after timestamp | 해당 운영 구간 종료 + 10분. 실제 정리 DELETE 대상이 되는 시각 |

UUID는 서버에서 생성한다. 클라이언트가 ID/작성자/만료 시각을 정하지 않는다. UUID를 비밀번호나 권한으로 취급하지 않는다. timestamp는 기존 서울 기준 LocalDateTime과의 일관성을 위한 초기안이다. 향후 Instant/timestamptz 전환 여부는 전체 시각 모델과 함께 판단한다.

nickname은 새 닉네임 변경 기능을 추가하려는 것이 아니라 기존 ChatMessage가 작성 당시 값을 보관하던 의미를 유지하기 위한 컬럼이다. Report는 현재와 같이 사용자 ID·본문·작성 시각을 보관하며 닉네임 증거 보관 요구는 아직 없다.

메시지 본문은 Java String / PostgreSQL varchar(140)를 제안한다. 자유로운 자연어라는 의미의 비정형성과 DB row의 필드 구성이 불규칙하다는 의미는 구분한다. 현재 메시지의 방·작성자·본문·작성 시각은 일정한 구조다. JSON 객체 내부의 유동적인 키를 저장/검색할 요구가 없으므로 jsonb나 별도 NoSQL은 필요하지 않다. HTTP JSON 요청 형식과 DB 컬럼 타입은 별개의 선택이다.

## DB가 보장할 것과 Service가 판단할 것

- DB: PK, 필수 컬럼, 방/작성자 FK, 최대 길이, 비어 있지 않은 본문에 대한 보조 CHECK, expires_at > sent_at CHECK. 삭제 정리를 위해 delete_after 인덱스를 제안한다. 신고는 PK 조회 후 기한을 확인하므로 expires_at 인덱스는 현재 요구에 필수가 아니다.
- Service: ACTIVE 쿠키 사용자, 방 열림, Unicode 코드 포인트 140자/공백 검증, 현재 운영 구간의 종료 계산, 현재 시각에 따른 메시지 유효성, 자기 신고 거절.
- 현재 시각이 지나면 자동으로 상태가 바뀌어야 하므로 CHECK에 now()를 넣어 TTL을 구현하지 않는다. 조회 조건과 삭제 작업이 담당한다.
- PK로 신고 원본 한 건을 찾으므로 room_id 단독 인덱스나 대화 목록용 복합 인덱스는 현재 추가하지 않는다. 새 조회 기능이 생기면 실행 계획에 따라 검토한다.
- DB btrim은 Java isBlank/strip과 동일한 모든 Unicode 공백 규칙을 보장하지 않는다. 서버 검증을 유지한다.

## Report와 Message 사이에 FK를 걸지 않는 이유

11:00 작성한 메시지가 11:15에 만료되어 삭제되어도, 11:10 접수한 신고 증거는 접수 후 30일 동안 남아야 한다. FK RESTRICT면 원본 삭제를 막고, CASCADE면 신고 증거도 삭제한다. nullable FK와 별도 UUID를 함께 둘 수도 있지만 현재 추적용 UUID와 증거 복사만으로 충분하다. 사용자/방 관계의 기존 FK는 유지한다. 사용자/방 물리 삭제 기능은 이번 범위에 없다.

## 트랜잭션과 경계 사례

방문 시각 변경과 메시지 INSERT를 같은 Service 트랜잭션에 묶는다. 미커밋 Message는 PostgreSQL의 일반 Read Committed 조회로 다른 트랜잭션에 보이지 않는다. DB 커밋 이후에만 실시간 전달한다. DB 커밋과 WebSocket 전달까지 원자적으로 보장되는 것은 아니다.

신고는 서버 DB 원본의 방/작성자/본문을 확인해 Report에 복사한다. 정리 DELETE가 먼저 끝나면 원본을 찾지 못해 신고를 거절한다. 원본 조회 시점의 기준 시각으로 expires_at이 이후인지 판단한다. 이미 읽은 유효 원본으로 신고를 작성하는 동안 정리 DELETE가 진행되거나 만료 시각을 지나도 신고 저장을 허용한다(Q3 사용자 확인). Report에 Message FK가 없으므로 복사된 증거를 저장할 수 있다. 이 요구를 위해 비관적 행 잠금이나 격리 수준 변경을 도입하지 않는다.

신고 가능 기한과 실제 삭제 기한을 구분한다. 사용자 Q4/Q6에 따라 expires_at은 기존 신고 기한을 유지하고, delete_after는 해당 운영 구간 종료 + 10분으로 둔다. 예: 10:00 작성 / 방 11:30 종료라면 신고 만료는 10:15, 삭제 기한은 11:40이다. 앱이 꺼져 있으면 실제 정리는 늦어지며, DB 백업/WAL에 남는 기록까지 이 TTL이 삭제하는 것은 아니다. 운영 전 백업 보존 정책을 별도로 확인한다.

## 확인할 테스트

- 방문 시각과 메시지 INSERT의 함께 롤백, 커밋 전 다른 트랜잭션에 메시지 미노출
- 140자/이모지, 서버 원본과 쿠키 기반 작성자, 잘못된 방/자기 신고/동시 중복
- 정확한 만료 시각, 방 종료, 다음 운영 구간에서 이전 메시지 부활 금지
- Message 삭제 후 Report 내용/중복 기준 유지, 만료 Report 30일 정리
- 재시작 후 잔여 유효 원본 신고 허용, 전역 10,000개 상한 로직 제거 확인

V9는 이미 적용되었으므로 수정하지 않는다. 사용자 합의 뒤 새 V10을 작성한다. 파티셔닝, Redis, 추가 메시지 브로커는 현재 제안에 없다.
