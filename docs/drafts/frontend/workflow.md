# GitHub Issues와 PR 작업 흐름 초안

상태: 작은 기능 이슈 하나 / PR 하나의 기본 작업 단위는 사용자 승인됨. 실제 setup 적용·게시·세부 저장소 설정은 확인 전이다. 이 문서는 설치된 스킬의 원본을 변경하지 않는다.

## 스킬별 역할과 이번에 멈추는 경계

| 스킬 | 역할 | 확인/실행 경계 |
| --- | --- | --- |
| setup-matt-pocock-skills | tracker·triage·도메인 문서 소비 규칙 설정 | 적용할 파일 내용 확인 후 활성 설정 작성. 이번에는 setup 초안만 준비 |
| wayfinder | 결정을 풀어 명세까지 갈 경로 찾기 | 디자인·연결 방식 같은 미결정을 질문 티켓으로 관리. 구현 티켓과 구분 |
| to-spec | 이미 논의한 내용을 명세로 합성 | 새 인터뷰를 대신하지 않음. 테스트 경계를 사용자에게 확인한 뒤 명세 게시 |
| to-tickets | 독립적으로 검증 가능한 작은 기능으로 분할 | 분할 크기·의존 관계 승인 후 게시 |
| implement-spec | 전체 명세를 통합 브랜치에서 구현 | 여러 구현 worktree/서브에이전트와 통합 리뷰를 거쳐 전체 PR. 지금 실행하지 않음 |
| pr | 검토자가 이해할 PR 본문 작성 | Summary / Evidence / Merge Danger 사용. PR 게시·생성과는 별개 |
| code-review | 기준 준수와 명세 충족을 독립적으로 검토 | 비교 기준과 명세를 먼저 고정. 실제 리뷰 시 두 축의 서브에이전트 사용 |

## 기본 제안: 작은 기능 이슈 하나당 PR 하나

1. 디자인/기술 결정이 남으면 wayfinder 질문을 먼저 해결한다.
2. to-spec 명세와 테스트할 사용자 경계를 확인한다.
3. to-tickets 분할과 의존 관계를 확인하고 GitHub에 게시한다.
4. 미해결 결정을 가진 이슈는 준비 완료로 표시하지 않는다. 승인된 범위와 의존 이슈 완료가 확인된 작업만 착수한다.
5. 최신 main 기준으로 기능 브랜치를 만든다. 이름은 `codex/<기능 이름>`을 기본으로 사용한다.
6. 해당 이슈의 사용자 동작 하나를 구현·검증한다. 필요한 환경 준비는 그 기능과 함께 묶고 서버/화면/테스트별 수평 이슈로 쪼개지 않는다.
7. origin/main의 비교 SHA와 해당 이슈/명세를 고정해 code-review를 수행한다. 같은 변경을 보는 동안 기준 SHA를 바꾸지 않는다. 아직 커밋하지 않은 변경은 리뷰 범위에 명시하거나 먼저 기능 브랜치에 커밋한다.
8. 실제 증거를 PR 본문에 넣고 Draft PR을 만든다. 완료 기준과 필요한 검증이 충족되면 검토 준비 상태로 바꾼다.
9. 사용자가 설명·데모·리뷰를 확인한 뒤 머지한다. 기본 제안은 squash merge다.
10. 기본 브랜치로 머지된 이슈만 완료된다. 부모 명세는 일부 기능 PR로 닫지 않는다.

브랜치/이슈 수보다 한 PR을 읽고 무엇이 바뀌는지 이해할 수 있는 크기를 우선한다. 하나의 기능이라도 규모가 커지면 기존 동작을 깨지 않고 독립 검증할 수 있는 동작으로 다시 나눈다.

## implement-spec과 차이

| 기준 | 이슈 하나 / PR 하나 | implement-spec 원형 |
| --- | --- | --- |
| 완료 단위 | 작은 사용자 기능 | 전체 명세 |
| 작업 브랜치 | 기능 브랜치 → main | 티켓별 branch/worktree → 통합 브랜치 → main |
| main에 보이는 시점 | 기능마다 머지 | 전체 통합 PR 머지 시 |
| 리뷰 | 작은 diff를 순서대로 | 통합된 전체 diff |
| 장점 | 사용자가 이해·검토하기 쉽고 문제를 좁혀 되돌리기 쉬움 | 여러 독립 티켓을 병렬로 구현하고 전체로 검증하기 좋음 |
| 비용 | 매 PR의 인계·CI·머지와 실제 의존 관계 관리 | 전체 diff·충돌·통합 검증이 커짐; 사용자의 중간 학습 지점이 줄 수 있음 |
| 이슈 종료 | 해당 PR 머지 후 기능 이슈만 | 전체 PR 머지로 명세·관련 티켓 종료 |
| 이번 제안 | 기본 | 예외: 별도 명세와 사용자 요청이 있을 때 |

설치된 implement-spec을 그대로 호출하면서 이슈마다 PR이 생성된다고 설명하지 않는다. 원본 스킬을 몰래 수정하지도 않는다. 기본 방식은 승인된 티켓을 한 번에 하나 구현하도록 범위를 지정하고 TDD/리뷰/PR 스킬을 조합한다. 통합 방식이 필요하면 사용자가 명시적으로 선택한다.

GitHub의 `Closes #번호`는 기본 브랜치를 대상으로 하는 PR에서 닫힘 관계를 만든다. 통합 브랜치 대상의 내부 PR이 먼저 머지됐다고 이슈가 완료된 것으로 처리하지 않는다. [GitHub PR 연결 규칙](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue).

## 구현 인계의 최소 정보

- 해당 이슈와 상위 명세의 제목·링크.
- 준비 완료된 범위, 제외 범위, 미결정이 없는지.
- 실제 blocking 관계와 완료된 선행 작업.
- 테스트할 공개 동작 및 정상·실패·경계 상황.
- 비교할 main SHA와 현재 작업 트리 상태.
- 서버 계약은 [API 메모](api-contract.md)와 원본 코드를 함께 확인.

### 한 기능 구현을 맡길 때 쓸 문구 초안

> 승인된 기능 이슈 하나만 구현한다. 연결된 명세·기존 서버 정책을 먼저 읽고 정상·실패·경계 상황을 확인한다. 테스트할 사용자 경계를 합의한 뒤 작은 TDD 루프로 구현한다. 다음 이슈나 미결정 디자인까지 확장하지 않는다. 완료하면 실행한 검증과 미확인 범위를 보고하고 기준 SHA/명세로 리뷰한다. PR 게시 및 머지는 그 시점의 사용자 권한을 확인한다.

### 두 축 리뷰를 맡길 때 쓸 문구 초안

> 비교 기준은 <main SHA>, 대상은 <기능 브랜치>의 커밋이다. 명세는 <기능 이슈 제목·링크> 및 연결된 spec이다. code-review의 Standards와 Spec을 분리해 검토한다. 테스트 결과만으로 명세 충족이나 운영 준비 완료를 주장하지 않는다.

이번에 이러한 구현·리뷰를 실행한 것은 아니다.

## 기존 세션 스킬과 연결

현재 session-end는 현재 브랜치를 커밋·푸시한다. PR 작업을 시작하면 기능 브랜치에서 세션을 진행해야 한다. main 보호를 켠 뒤 기존처럼 main에서 종료 커밋을 바로 푸시하면 막힐 수 있다.

후속 적용 시 session-start/end의 브랜치 처리도 함께 검토한다. 세션 종료를 자동 머지 권한으로 해석하지 않으며, 사용자의 당일 작업 제한이 세션 자동화보다 우선한다. 이번처럼 문서 초안만 요청한 날에는 자동 커밋·푸시를 실행하지 않는다.
