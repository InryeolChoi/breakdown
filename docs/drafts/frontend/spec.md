# 잠깐 쉬러 들어와 채팅하는 프런트 — 명세 초안

상태: 2026-10-15 [GitHub 명세 이슈](https://github.com/InryeolChoi/breakdown/issues/2) 발행 / 구현 착수 조건은 아직 미충족. 사용자 지정 Next.js + TypeScript는 확정이고 나머지 질문은 [questions.md](questions.md)를 따른다.

## Problem Statement

현재 서버는 익명 사용자·열린 방·채팅·신고를 제공하지만 사용자가 브라우저에서 이 흐름을 직접 이용할 화면이 없다. 접속한 직장인이 짧은 시간에 무엇을 할 수 있는지 알아보고 가볍게 대화할 수 있어야 한다.

## Solution

로그인 없이 이용하는 Next.js + TypeScript 프런트를 기존 Spring 서버에 연결한다. 사내 카페에서 잠깐 쉬는 느낌을 살리고 열린 방·채팅이라는 행동을 눈에 보이게 한다. 게시판 중심이나 메타버스 이동 UI는 도입하지 않는다.

첫 기능은 열린 방을 확인하는 작은 경로다. 그다음 익명 사용자 준비와 실제 채팅·신고를 연결한다. 탁 트인 창문이 보이는 라운지에 들어온 듯한 느낌을 목표로 한다. 디자인 도구는 Stitch부터 사용하며 첫 화면·세부 레이아웃은 미결정이다.

## User Stories

1. 방문자로서, 접속 직후 지금 할 수 있는 일을 알아볼 수 있어 짧은 휴식 시간을 쓰고 싶다.
2. 방문자로서, 현재 열린 방을 확인해 대화할 공간을 고르고 싶다.
3. 방문자로서, 열린 방이 없을 때 그 상태를 알아야 기다릴지 나갈지 판단할 수 있다.
4. 방문자로서, 목록을 불러오는 중임을 알아야 고장으로 오해하지 않는다.
5. 방문자로서, 요청 실패 후 명시적으로 다시 시도해 서비스에 접근하고 싶다.
6. 새 익명 사용자로서, 닉네임 입력을 생략하고도 서버가 만든 이름으로 참여하고 싶다.
7. 새 익명 사용자로서, 원하는 닉네임을 선택 입력해 참여하고 싶다.
8. 재방문 사용자로서, 유효한 쿠키로 기존 사용자로 참여하고 싶다.
9. 차단된 사용자로서, 참여할 수 없음을 안내받고 싶다.
10. 참여자로서, 열린 연결에서 메시지를 보내고 같은 방의 메시지를 실시간으로 보고 싶다.
11. 참여자로서, 다른 방의 메시지가 내 방에 표시되지 않기를 바란다.
12. 참여자로서, 잘못 입력한 메시지의 이유를 보고 다시 입력하고 싶다.
13. 참여자로서, 방 종료·식별 만료·차단 후 입력이 막히고 종료 안내를 받고 싶다.
14. 참여자로서, 연결 실패·끊김과 서버가 확인한 성공을 구분하고 싶다.
15. 참여자로서, 화면을 떠난 뒤 예전 방의 연결이나 이벤트가 계속 남지 않기를 바란다.
16. 신고자로서, 남의 메시지를 증거로 그 사용자를 신고하고 접수·실패 결과를 확인하고 싶다. 첫 공개 범위에 포함한다.
17. 모바일/키보드 사용자로서, 방 선택과 채팅·오류 안내를 작은 화면과 키보드로 이용하고 싶다. 모바일 360px와 데스크톱 1280px를 함께 검토한다.

## Implementation Decisions

확정한 내용:

- Next.js + TypeScript. Spring이 API·익명 식별·운영 판단·메시지 저장·신고 검증을 소유한다.
- 같은 저장소 루트의 frontend 디렉터리에 프런트를 두고 기존 Spring 구조를 유지한다. 사용자 승인된 위치이며 프로젝트 생성은 아직 하지 않았다.
- 작은 기능 이슈 하나당 PR 하나로 구현한다. 첫 공개에는 채팅과 기존 신고 API 연결을 포함한다.
- 탁 트인 창문이 보이는 라운지 분위기를 목표로 하며 모바일 360px/데스크톱 1280px를 함께 검토한다.
- 기존 서버 정책과 ERD를 유지한다. 프런트 편의만을 위해 Message 보관 기한이나 새 이력 조회 API를 만들지 않는다.
- 작성은 양방향 WebSocket을 사용한다. HTTP는 익명 사용자 준비·방 목록·신고에 사용한다.
- 프런트가 쿠키 토큰을 읽어 JSON/스토리지에 복사하지 않는다.
- 정책·데이터 계약은 decisions/ERD와 서버 원본을 기준으로 확인한다. 현재 계약 메모는 [api-contract.md](api-contract.md)에 있다.
- 추가 MCP 범위는 디자인 도구이며 Stitch부터 사용하기로 선택했다. 아직 연결 검증은 하지 않았다.

확인 대기인 제안:

- 브라우저에서 같은 출처로 HTTP/WS 접근할지와 실제 연결 경로.
- 첫 화면과 닉네임 준비 순서, 구체적인 라운지 표현과 배치. Stitch의 실제 인증·연결 작업도 남아 있다.
- App Router·패키지 관리자·배포 방식·구체 Next 버전. 코드 착수 전에 필요한 항목만 확인하고 공식 문서 기준으로 선정한다.
- 자동 재연결 여부·재시도 제한·전송 중 표시와 미확인 메시지 처리. MVP 제안은 명시적 재접속, 자동 재전송 없음이다. 서버에 중복 제거용 client ID 계약이 없기 때문이다.

## Testing Decisions

첫 브라우저 테스트 경계는 사용자 동의를 받았다. 후속 기능의 세부 검증 방식은 구현 인계에서 확인한다:

- 가장 높은 공개 경계인 브라우저 사용자 동작을 중심으로 검증한다. 첫 경계는 열린 방 목록·빈 상태·오류와 재시도다.
- 목록의 HTTP 경계에 정상 배열/빈 배열/오류/지연 응답을 통제해 화면 결과를 검증한다. 내부 hook 호출 횟수나 컴포넌트 구현 모양을 고정하지 않는다.
- 실제 Spring API에 붙이는 정상 경로도 별도로 확인해 stub만 통과한 것을 계약 검증으로 주장하지 않는다.
- 쿠키·Origin·WebSocket의 실제 연결은 독립된 브라우저 컨텍스트 두 개와 실제 서버로 검증한다. Node/JDK 클라이언트 테스트만으로 브라우저 정책 통과를 주장하지 않는다.
- 종료·만료·중복 신고는 격리된 테스트 데이터/서버 시간 조건으로 재현한다. 실제 시간대에 맞춰 테스트 결과가 바뀌거나 운영 DB에 테스트 방을 영구 seed하지 않는다.
- 기존 백엔드의 handshake/broadcast/transaction/report 테스트를 참고해 서버 검증은 유지한다. 프런트 변화마다 관계없는 전체 검증을 불필요하게 반복하지 않는다.
- 레이아웃·포커스·키보드·텍스트 표시를 승인한 기기 기준에서 확인한다.

이번에는 테스트 코드를 만들거나 앱 테스트를 실행하지 않았다.

## Out of Scope

현재 사용자 요청으로 문서 커밋·푸시와 GitHub 명세/티켓 발행은 진행한다. 프런트 코드, 의존성/도구 설치, 계정 연결, 활성 설정 변경, PR·머지는 이번 작업에서 실행하지 않는다.

첫 프런트 MVP 후보: 게임/랭킹, 관리자 화면·자동 차단, 과거 대화 조회, 메시지 수정·삭제, 로그인, 3D 메타버스, 게시판, Redis/STOMP 등 새 서버 기술, AWS 배포 구현. 별도 사용자 요청으로 범위를 다시 정할 수 있다.

## Further Notes

디자인 질문과 구현 티켓은 다르다. 도구나 라운지 표현을 정했다고 사용자 기능이 구현된 것은 아니다. 소스 없는 참석자 수·다음 개장 카운트다운·과거 메시지를 장식용으로 만들어 보여주지 않는다.

기존 사용자는 닉네임을 새 요청 값으로 덮어쓰지 않는다. 핸드셰이크 실패 HTTP 코드와 연결 후 ERROR 메시지를 같은 UI 계약으로 취급하지 않는다. 상세는 API 메모의 주의점을 따른다.
