# 첫 작업과 기능 이슈 분할 초안

상태: 2026-10-15 사용자 요청으로 [기능 이슈를 발행](../../frontend-issues.md)했다. 작은 기능 분할 방향과 첫 테스트 경계는 동의 받았으며 첫 화면·접속 경로·세부 setup의 선행 작업은 열려 있다. 아래 1~4는 준비 순번이고 GitHub issue 번호가 아니다. UI·API·테스트를 따로 개발하는 수평 분할 대신, 한 사용자 동작이 완성되는 경로로 분할한다.

## 구현 전 준비

setup 설정·triage 매핑·PR 흐름 승인을 먼저 받는다. 디자인 질문은 [questions.md](questions.md)에서 해결한다. 실제 이슈 생성 후 parent와 blocking을 연결한다. 명세의 자식이라는 이유만으로 모든 이슈에 같은 선행 관계를 만들지 않는다.

## 1. 브라우저에서 지금 열린 방 확인

**What to build:** 실제 방 조회 API를 연결한 첫 Next.js + TypeScript 화면에서 열린 방, 불러오는 중, 빈 목록, 실패 후 재시도를 구분한다. 같은 저장소 루트의 프런트 위치와 첫 테스트 경계는 승인됐고 첫 UI 구조/HTTP 접근 방식을 확인한 뒤 구현한다.

**Blocked by:** 첫 화면 범위·HTTP 접속 방식에 대한 결정. 저장 위치·첫 테스트 경계는 더 이상 미결정 blocker가 아니다. 다른 구현 티켓은 없음.

**Acceptance criteria 제안:**

- [ ] 승인한 프로젝트 위치에서 설치·개발 실행·typecheck·build 방법을 재현할 수 있다.
- [ ] 실제 `GET /rooms` 정상 응답의 방 ID·이름·운영 시각을 화면에 반영한다.
- [ ] 빈 배열은 '지금 열린 방이 없음'으로 보여주고 서버 고장으로 표시하지 않는다.
- [ ] 요청 실패와 불러오는 중을 구분하며 명시적 재시도가 정상 목록으로 회복한다.
- [ ] 실패 중 이전 목록을 계속 선택 가능한 최신 방으로 제시하지 않는다. 재요청이 겹쳐 오래된 결과가 최신 상태를 덮지 않는다.
- [ ] 모바일 360px·데스크톱 1280px와 키보드에서 방 정보·안내가 읽힌다.
- [ ] 아래 정상·실패·경계의 자동 검증과 실제 API 정상 연결 증거를 남긴다.
- [ ] fake 참가자 수·닫힌 방 전체 목록·다음 개장 카운트다운·채팅 이력을 만들지 않는다.
- [ ] 서버 정책·ERD·Flyway 변경 없음. UI가 동작해야만 필요한 연결 설정 변경은 범위와 근거를 먼저 설명한다.

### 정상·실패·경계

| 구분 | 입력/상황 | 기대 결과 | 검증 후보 |
| --- | --- | --- | --- |
| 정상 | 열린 방 한 개/여러 개 | 응답의 이름·시각·ID를 사용하는 화면 | 브라우저 + 실제 API 정상 경로 |
| 실패 | 연결 불가/HTTP 5xx | 오류 안내와 재시도; 열린 방 없음과 구분 | HTTP 경계 통제 |
| 실패 | 잘못된 JSON/기대 shape와 다른 응답 | 목록을 성공처럼 표시하지 않음 | HTTP 경계 통제 |
| 실패 | 응답 지연 | 로딩 표시; 승인한 제한시간 이후 회복 가능한 오류 | HTTP 경계 통제, 제한시간 수치는 구현 전 확인 |
| 경계 | `200 []` | 빈 상태 | 주말/운영 시간 밖과 동일한 화면 결과 |
| 경계 | 재시도를 빠르게 반복, 역순 응답 | 오래된 응답이 최신 결과를 덮지 않음 | 브라우저 동작 |
| 경계 | 자정을 넘는 운영 시각 | 야간 구간을 일관되게 읽을 수 있음 | 응답 fixture + 화면 검토 |
| 경계 | 화면 이탈 중 응답 도착 | 이전 화면 상태로 돌아가거나 경고가 남지 않음 | 사용자 이동 동작 |

**완료 증거:** 정상·빈·오류 화면, 실행 명령·결과, 실제 API 연결 확인, 미확인 범위를 PR에 남긴다. 첫 PR에 익명 사용자·WebSocket·신고·완성 디자인 전체를 넣지 않는다. 방 선택 시 실제 채팅으로 이동하는 동작은 다음 티켓이다.

## 2. 닉네임 준비 후 열린 방에 입장

**What to build:** 승인된 진입 흐름으로 익명 사용자를 준비·갱신하고 선택한 방에 실제 WebSocket 연결을 연다. 입장 상태와 입장 실패가 사용자에게 보인다. 메시지 작성 입력은 아직 제공하지 않는다.

**Blocked by:** '브라우저에서 지금 열린 방 확인' — 실제 방 선택 화면을 재사용. 익명 준비 순서·쿠키/WS 출처 경로 결정도 필요.

- [ ] 새 사용자의 선택 입력/서버 자동 닉네임과 유효 재방문을 반영한다.
- [ ] `200` 응답이어도 `status=BANNED`이면 입장 가능 사용자로 처리하지 않는다.
- [ ] 쿠키를 JS에서 읽거나 별도 토큰을 요청 JSON/localStorage에 넣지 않는다.
- [ ] 실제 브라우저에서 Set-Cookie와 handshake를 이어 확인한다.
- [ ] 목록을 본 뒤 방이 닫힌 경우·쿠키 미준비·연결 실패를 성공 입장처럼 표시하지 않는다.
- [ ] 화면 이탈/방 이동 시 이전 연결을 정리한다.

핸드셰이크 실패 원인의 HTTP status를 browser WebSocket onerror에서 읽을 수 있다고 가정하지 않는다. UI 안내 문구는 원인을 확인할 수 있는 HTTP 결과와 일반 연결 실패를 구분한다.

## 3. 같은 방의 실시간 채팅과 종료 안내

**What to build:** 입장한 방에서 본문을 보내고 같은 방에 서버가 전달한 메시지를 표시한다. 입력 오류는 수정할 수 있고, 방 종료·식별 만료·차단·연결 끊김에서는 안전하게 입력 상태를 바꾼다.

**Blocked by:** '닉네임 준비 후 열린 방에 입장' — 실제 연결과 사용자 상태가 필요.

- [ ] 서로 다른 사용자 컨텍스트 두 개로 같은 방 송수신과 다른 방 미수신을 확인한다.
- [ ] 정상 응답의 서버 UUID로 동일 메시지를 중복 표시하지 않는다.
- [ ] 본문만 전송하고 ID·방·작성자·시각을 프런트가 위조해 채워 넣지 않는다.
- [ ] 공백·Unicode 코드 포인트 140/141자와 잘못된 입력을 기존 서버 검증과 일치시킨다.
- [ ] `ERROR/status=400`은 보낸 화면에 안내하고 연결을 유지한다.
- [ ] `401/403` 안내와 종료 코드 `1008`을 받으면 입력을 막는다. 유휴 연결의 방 종료도 포함한다.
- [ ] 네트워크 종료와 정책 종료를 가능한 증거 범위에서 구분한다. 모든 `1008`을 방 종료라고 단정하지 않는다.
- [ ] 서버 성공 응답 전 미확인 전송을 확정 성공으로 표시하지 않는다.
- [ ] 재연결/재전송 정책은 승인 후 적용하며 끊긴 메시지를 몰래 자동 재전송하지 않는다.
- [ ] 이전 대화 조회 없이 입장 이후 수신만 표시한다. 메시지는 HTML로 실행하지 않고 텍스트로 표시한다.

성공·오류·종료가 한 연결의 기본 사용 경로이므로 초기 제안에서는 함께 묶는다. 이 크기가 과하다면 서버 연결 상태를 깨지 않고 독립 검증 가능한 방식으로 나눌지 사용자와 확인한다.

## 4. 수신한 메시지로 사용자 신고

**What to build:** 다른 사용자의 수신 메시지에 신고 사유를 입력하고 서버에 신고를 접수하며 성공·중복·만료·실패를 구분한다.

**Blocked by:** '같은 방의 실시간 채팅과 종료 안내' — 수신 UUID와 작성자 정보가 필요. 첫 공개의 신고 포함은 사용자 승인됐다.

- [ ] 방 ID, messageId, reason만 기존 신고 계약으로 사용한다. 증거 본문·대상 사용자는 서버가 판단한다.
- [ ] 자기 메시지 신고를 화면에서 막고 서버 거절도 처리한다.
- [ ] 201 접수, 409 중복, 410 신고 기한 만료와 400/401/403/404 등 실패를 실제 계약에 맞게 표시한다.
- [ ] 15분 또는 방 종료 중 먼저 도래하는 신고 기한을 실제 서버 결과로 최종 판단한다.
- [ ] 실패한 신고를 접수 완료로 표시하지 않고 중복 클릭 중 불필요한 요청을 막는다.
- [ ] 자동 차단·관리자 판단까지 구현하거나 신고 내용을 다른 사용자에게 공개하지 않는다.

## 분할 방향 동의 후 인계에서 점검할 것

1. 위 작은 기능 분할 방향은 사용자 동의를 받았다. 구현 중 규모가 커지면 독립 검증 가능한 경로로 다시 나눈다.
2. 실제 선행 관계만 연결했는가? 디자인 MCP 연결이 단순 목록 조회의 기술적 선행 조건은 아니다.
3. 첫 공개의 신고 포함은 확정됐다. 채팅 정상·오류·종료를 함께 묶는 세부 작업 크기는 실제 연결 경로를 정한 뒤 점검한다.

실제 이슈 번호·링크·native 선행 관계는 인계 문서에서 확인한다. 작업을 claim하기 전 담당자를 확인하고, 프런트 명세는 전체 기능 확인까지 열린 상태로 유지한다.
