# 사용자에게 모아둔 질문

상태: 2번 작업 단위, 3번 저장 위치, 4번 방 선택·닉네임 동시 표시, 5번 스킬 우선·Stitch 연결 보류, 6번 분위기 방향, 7~9번은 사용자 답변을 반영했다. 1번·3번 접속 방식과 세부 저장소 설정·화면 배치는 미정이다. 추천은 결정을 대신하지 않는다.

## 작업 흐름·설정

1. **기본 triage 라벨을 그대로 쓸까? — 설명 후 확인 대기.** GitHub 이슈에 붙이는 작업 분류표다. `needs-triage`=검토 필요, `needs-info`=답변/정보 대기, `ready-for-agent`=AI 구현 가능, `ready-for-human`=사용자 참여/직접 작업 필요, `wontfix`=진행하지 않음. 설치된 스킬이 이 이름으로 작업을 찾으므로 기본값 사용을 추천한다. `wontfix`는 이미 있다. 사용자는 의미를 물었고 사용 승인이나 라벨 생성은 아직 하지 않았다.
2. **작은 기능 이슈 하나 / PR 하나 — 승인.** 사용자가 제안한 작업 단위에 동의했다. [작업 흐름](workflow.md)에 반영했다. [setup 내용](repo-settings.md)의 main 보호·squash·브랜치 삭제와 실제 설정 적용은 이 답변으로 일괄 승인된 것이 아니며 별도 확인 대상이다.
3. **저장 위치 확정 / 접속 방식은 어떤 안을 검증할까?** 사용자는 같은 저장소 루트의 `frontend/`를 승인했다. 기존 Spring 구조는 유지한다. 남은 질문은 HTTP API와 WebSocket을 브라우저에서 같은 출처로 접근할지다. 같은 출처 안을 고르면 쿠키·HTTP·WebSocket Upgrade가 실제 통과하는 연결 방식을 후속 작업에서 검증해야 한다. Next.js 설정만으로 무조건 해결된다고 확정하지 않았다.

## 디자인에서 결정

4. **방 선택과 닉네임 입력을 한 화면에 함께 — 2026-10-15 사용자 결정.** 별도의 닉네임 선행 화면으로 나누지 않는다. 구체적 배치와 재방문 사용자의 표시는 구성안 비교에서 정한다. 현 서버에서 재방문 사용자의 닉네임을 변경하는 기능은 없으므로 '언제든 닉네임 수정'을 화면 약속에 포함하지 않는다.
5. **frontend-design 스킬부터 사용 / Stitch 연결 보류 — 2026-10-15 승인.** Anthropic 공식 스킬을 설치했고 디자인 계획부터 비교한다. Stitch 조사 결과는 유지하며 계정 인증·등록·연결 검증은 보류한다. Figma는 필요해지면 검토한다. [조사 메모](../../research/design-mcp-comparison.md).
6. **분위기 방향 — 사용자 수정 반영.** 커피 컵 중심이 아니라 탁 트인 창문이 보이는 라운지에 온 듯한 느낌을 원한다. 구체적인 화면 배치·첫 행동은 미정이며 라운지 느낌이 3D 이동/메타버스 도입을 뜻하지 않는다. 디자인 용어보다 사용자에게 원하는 느낌·불편한 느낌을 확인하고 구체적 시안으로 비교한다.
7. **모바일 360px + 데스크톱 1280px — 승인.** 두 기준을 함께 검토한다. 과한 애니메이션 없이 키보드·포커스·텍스트 대비와 빈 상태도 함께 확인한다.

## 구현에서 확인

8. **첫 공개 범위: 채팅 + 신고 버튼 — 승인.** 기존 신고 API를 연결한다. 게임·관리자·자동 차단은 뒤로 둔다. 첫 방 목록 PR에서 신고까지 구현하자는 의미는 아니다.
9. **첫 기능·테스트 경계와 작은 기능 분할 방향 — 승인.** [첫 티켓](tickets.md)의 '브라우저에서 열린 방/빈 상태/오류 후 재시도를 확인' 경계에 동의했다. 후속은 익명 준비·채팅·신고의 사용자 동작 단위다. 필요한 화면/연결 결정과 구체 blocking을 맞춘 뒤 게시하며, 동의가 모든 후속 테스트 방법·GitHub 게시 권한까지 확정한 것은 아니다.

남은 확인은 1번 라벨·세부 setup 설정, 3번 접속 방식, 4번 구체 배치·재방문 표시다. Stitch 연결은 보류했으며 방 목록 API 계약 검토를 막지는 않는다. 분위기는 정해졌지만 구체적인 시안을 선택한 상태는 아니다.

## 질문을 구분한 이유

디자인에서 정할 것은 첫인상, 진입 흐름, 사물의 역할, 정보 배치, 기기 기준이다. 구현에서 정할 것은 저장소 위치, 쿠키/출처/WS 연결, 테스트 경계와 완료 기준이다. 따뜻한 카페 분위기를 선택했다고 자동 로그인·재연결·신고 정책까지 확정되는 것은 아니다.

답변 없는 질문을 AI가 HITL 티켓의 답변으로 작성하거나 해결 완료로 닫지 않는다. 2026-10-15 사용자 요청으로 [실제 설계/준비 티켓](../../frontend-issues.md)을 발행했다. 해결된 방향과 미결정을 구분하고 최신 작업 상태는 GitHub를 확인한다.
