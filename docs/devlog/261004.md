# 2026-10-04 — AnonymousUser 생성 API 검증

## DTO에서 Controller까지 JSON 요청 흐름 확인

선택 입력인 nickname을 `AnonymousUserCreateRequest`로 받고, Controller에서 `@RequestBody`로 JSON을 DTO에 바인딩한다. `@Valid`는 DTO의 `@Size(max = 30)`을 실행한다. `{}`를 보내면 nickname은 null로 Service에 전달되어 자동 생성 규칙을 따른다. 31자 입력은 Service 호출 전에 HTTP 400으로 거절된다.

MockMvc 테스트로 두 경우를 확인했고 `./gradlew test` 전체가 통과했다. 이번 테스트는 HTTP/JSON/검증 경로를 검사하며, Service의 자동 닉네임 생성은 기존 Service 테스트가 담당한다.

## 요청 데이터를 DTO 클래스로 받는 경험

처음으로 클라이언트가 보낸 JSON 데이터를 전용 Java 클래스로 받는 흐름을 연결했다. DTO는 요청 필드와 입력 제약을 표현하고, `@RequestBody`가 JSON을 객체로 바꾸며, `@Valid`가 제약을 실행한다. Controller는 검증된 입력을 Service로 전달한다. 다음에는 Postman으로 `{}`, 닉네임 입력, 길이 초과 요청을 직접 보내 응답을 확인한다.

## 세션을 다시 시작하며

`make`가 처음에는 `open -a Docker` 단계에서 앱을 찾지 못해 실패했다. `docker desktop start`로 Docker Desktop을 시작한 뒤 `make`를 다시 실행해 PostgreSQL 컨테이너를 올렸다. API 코드는 직전 커밋 `df673b9`에 있으며, 전체 Gradle 테스트와 JSON 바인딩·선택 닉네임·30자 검증 MVC 테스트가 통과한 상태다.

다음은 Postman에서 닉네임을 생략하거나 입력한 요청, 30자와 31자 경계값을 직접 호출해 HTTP 응답과 저장 결과를 확인하는 것이다. 그다음 응답 DTO가 브라우저에 필요한 값만 내보내는지 검토하고, AnonymousUser 생성 API 수직 슬라이스를 마무리한다.

## Postman에서 405 Method Not Allowed가 나온 이유

요청 주소와 서버는 도달했지만, Postman이 `GET /anonymoususer`를 보냈다. Controller 매핑은 `@PostMapping("/anonymoususer")`이므로 허용되지 않는 메서드라는 HTTP 405 응답이 정상이다. Postman에서 메서드를 POST로 바꾸고 URL은 `/anonymoususer`로 두며, Params의 `nickname` 대신 Body → raw → JSON에 `{"nickname":"오리"}`를 넣는다. Headers의 `Content-Type`은 `application/json`이어야 한다. 닉네임을 생략하려면 본문 `{}`를 보낸다.

POST로 바꾼 뒤에도 400이 발생한 화면을 다시 확인했다. URL에 `?nickname=오리`와 Params 값이 그대로 있고 Body가 비어 있었다. 현재 Controller의 `@RequestBody`는 JSON 본문을 요구하므로 query parameter만 보낸 요청은 필요한 본문이 없어 400 Bad Request가 된다. URL에서 `?nickname=오리`를 지우고 Params 체크를 끈 뒤, Body 탭의 raw/JSON에 `{"nickname":"오리"}`를 입력해야 한다. raw/JSON을 선택하면 Postman이 `Content-Type: application/json` 헤더를 설정한다.

## 길이 검증은 되는데 왜 한국어 오류 문구는 안 보일까?

31자보다 긴 nickname을 보내자 Postman은 HTTP 400을 받았다. 이는 `@Valid`와 `@Size(max = 30)` 검증이 실패해 요청을 거절했다는 뜻이다. 응답 본문에 `timestamp`, `status`, `error`, `path`만 보이는 이유는 Spring Boot의 기본 오류 응답이 현재 설정에서 필드 검증의 세부 메시지를 반환하지 않기 때문이다. 이후 DTO의 `@Size`에 `message = "이름은 30자 이하로 입력해주세요."`를 지정했다.

사용자 지정 메시지를 HTTP 응답에 넣으려면 `@RestControllerAdvice`에서 `MethodArgumentNotValidException`을 처리해 필드 오류의 `defaultMessage`를 꺼내 응답 본문에 담는다. 검증을 통과시키거나 Service에서 예외를 던지는 작업이 아니라, 이미 발생한 검증 오류를 API 응답 형식으로 바꾸는 단계다.

### 예외 처리 클래스 초안을 리뷰하다

`@RestControllerAdvice`가 붙은 클래스는 `com.breakground` 하위라 component scan 대상에 들어가는 위치가 맞다. 다만 현재 handler가 모든 `Exception`을 잡고, `printStackTrace()`만 호출하며 `ResponseEntity<String>`를 반환하지 않아 컴파일되지 않는다. 모든 예외를 한꺼번에 잡으면 버그나 DB 오류까지 검증 오류처럼 처리할 위험이 있다. `MethodArgumentNotValidException`만 구체적으로 받아 `getBindingResult().getFieldError().getDefaultMessage()`를 응답 본문에 담고 `ResponseEntity.badRequest()`로 반환해야 한다. 클래스 이름도 예외 객체처럼 보이는 `AnonymousUserException`보다 `GlobalExceptionHandler`가 역할을 잘 나타낸다.

### 예외 처리를 AnonymousUserController에만 한정할 수 있을까?

가능하다. `@RestControllerAdvice(assignableTypes = AnonymousUserController.class)`로 Advice 적용 대상을 지정하면 해당 Controller에서 발생한 예외만 이 처리기가 맡는다. 또는 Controller 클래스 안에 `@ExceptionHandler` 메서드를 둘 수도 있다. 현재처럼 API 하나에서만 시작할 때는 범위를 좁혀도 되고, 여러 Controller에서 같은 오류 응답 정책을 쓸 때 Advice를 공통 처리기로 넓힐 수 있다. 어느 경우든 `@ExceptionHandler(MethodArgumentNotValidException.class)`로 처리할 예외 종류도 구체화한다.

Advice 메서드 안에서는 `MethodArgumentNotValidException`의 binding result에서 첫 field error를 얻고, 그 error의 `defaultMessage`를 꺼내 응답에 담는다. JSON 응답이면 `ResponseEntity<Map<String, String>>`와 `Map.of("message", message)`를 사용할 수 있고, 상태는 `ResponseEntity.badRequest()`로 400을 지정한다. 흐름은 검증 예외 → 사용자 정의 메시지 추출 → JSON body에 넣기 → 400 반환이다.

## AnonymousUser는 이제 끝났을까?

선택 닉네임 입력, 미입력 시 자동 생성, PostgreSQL 저장, JSON 응답, 길이 검증까지의 생성 API 수직 슬라이스는 거의 완성됐다. 검증 오류 문구를 응답하는 Advice를 추가했으므로 전체 테스트와 31자 요청을 다시 확인하고, 응답 DTO에 브라우저에 필요한 필드만 노출되는지 점검해야 이 단계를 마칠 수 있다.

제품 관점의 AnonymousUser 기능은 아직 끝나지 않았다. 현재 DB primary key는 row를 식별하지만, 같은 브라우저의 다음 요청이 같은 사용자를 다시 찾게 해주지는 않는다. 익명 사용자를 계속 식별하려면 cookie/token 발급·저장·재방문 조회 정책을 다음 별도 단계로 구현해야 한다. 따라서 지금 완료를 선언할 범위는 “익명 사용자 생성 API”이고, “브라우저 익명 식별”은 후속 작업이다.

### 같은 브라우저의 재방문을 어떻게 식별할까?

재방문 기능은 숫자 DB primary key를 cookie에 넣는 것이 아니라, 서버가 생성한 예측하기 어려운 토큰을 cookie에 보내고 DB에는 그 해시를 저장하는 흐름으로 설계한다. 다음 요청에서 cookie 토큰을 다시 해시해 Repository로 AnonymousUser를 찾는다. 만료 기간은 논의 당시 미정이었으나, 이후 사용자가 마지막 방문 후 7일 동안 활동이 없으면 만료하기로 결정했다.

사용자가 마지막 방문 후 7일 동안 활동이 없으면 익명 식별을 만료하기로 했다. 유효한 재방문에서 `last_seen_at`을 갱신하고 쿠키의 7일 유효 기간도 다시 설정하는 rolling 만료로 해석한다. ERD에는 아직 브라우저 식별 토큰 해시 컬럼이 없으므로, 다음 구현 단계에서 사용자가 이를 DBML에 추가하고 V7 migration으로 옮긴다.

다시 세션을 시작해 개발 환경을 켰다. `make`의 `open -a Docker`는 앱 이름을 찾지 못했지만 `docker desktop start`는 이미 실행 중임을 확인했고, 권한이 있는 `make` 실행으로 PostgreSQL 컨테이너가 정상 상태임을 확인했다. 이번 구현의 첫 학습 작업은 `AnonymousUser` ERD에 토큰 해시를 저장할 컬럼을 추가하는 것이다. DB에 이미 존재하는 cookie 없는 이전 사용자 row와 null 제약의 관계를 고려해 본다.

### 쿠키 토큰의 해시를 DB에 저장하면 안전할까?

DB에는 암호학적으로 강한 난수 토큰 원문 대신 그 해시를 저장한다. DB를 읽기만 할 수 있는 공격자가 해시 컬럼을 가져가도 원문 토큰을 그대로 쿠키처럼 재사용할 수 없고, 충분한 엔트로피의 난수는 해시에서 역산하기 어렵다. 이때 토큰은 사람이 정한 비밀번호가 아니라 서버가 생성한 고엔트로피 비밀값이므로, OWASP 세션 지침은 이런 verifier에 빠른 SHA-256 해시를 사용할 수 있고 비밀번호용 Argon2/bcrypt 같은 느린 해시는 불필요하다고 구분한다. 토큰은 CSPRNG로 최소 128비트 이상 생성해야 하며 이 프로젝트에서는 256비트를 권장한다.

해시 저장이 쿠키 탈취까지 막아주지는 않는다. 원문 토큰을 훔친 공격자는 만료 전까지 해당 브라우저 사용자처럼 요청할 수 있다. 따라서 원문은 HttpOnly 쿠키로 전달하고 로그에 남기지 않으며, 운영에서는 HTTPS와 Secure, SameSite 쿠키 속성을 적용한다. SameSite는 CSRF의 방어층이지 단독 해결책은 아니다. OWASP Session Management Cheat Sheet는 토큰 저장소 유출과 쿠키 탈취를 별도 위협으로 구분하고, Secure/HttpOnly/SameSite 및 서버 저장 verifier를 설명한다.

### 해시 컬럼 설계를 다시 검토하다

고엔트로피 토큰의 SHA-256 해시를 DB에 저장하는 방식은 유지할 만하다. 하지만 이 보호는 DB를 읽기만 하는 유출 상황에 한정된다. 서버는 반드시 cookie 원문을 해시해 컬럼과 조회해야 하고, 컬럼에 저장된 해시 자체를 cookie 값으로 받아들이거나 응답 DTO에 포함해서는 안 된다. 후속 Message·Report·GamePlay 쓰기 요청에서 클라이언트가 전달한 `anonymousUserId`를 작성자 권한으로 신뢰하면 쿠키 식별을 구현한 의미가 없으므로, 서버가 cookie에서 사용자를 찾아야 한다.

7일 비활성 만료만 적용하면 탈취자가 주기적으로 토큰을 사용해 유효 기간을 계속 연장할 수 있다. OWASP 세션 지침도 idle timeout의 이 한계와 별도의 absolute timeout을 설명한다. 이 서비스의 위험 수준과 사용자 기록 유지 정책에 맞는 절대 만료 또는 토큰 교체 여부는 구현 전에 별도로 판단한다. 쿠키를 지운 사용자가 새 AnonymousUser를 만드는 것도 막을 수 없어, BANNED는 브라우저 단위의 제한일 뿐 실제 사람의 확실한 차단은 아니다.

### 로그인 없는 서비스에서 지금 브라우저 식별을 구현해야 할까?

로그인이 없더라도 브라우저 cookie로 익명 사용자를 기억하는 것은 가능하다. 이는 실제 사람의 신원을 확인하는 계정 로그인과 다르고, 브라우저에만 연결된 임시 식별자다. 다만 cookie가 없으면 매번 새 AnonymousUser가 만들어질 수 있어 Message 작성자 연결, 같은 사용자의 중복 신고 방지, BANNED 상태 적용, GamePlay 누적이 불안정해진다.

현재는 Message/Report/GamePlay API가 아직 없으므로, persistent cookie 구현을 당장 미루는 편이 학습 범위를 줄일 수 있다는 의견을 검토했다. 다만 실제 사용자와 운영 데이터를 받기 전에, 특히 Message 작성 API에서 작성자를 안전하게 연결하기 전에 구현해야 한다. 이는 아직 최종 정책 변경이 아니라 시점에 대한 제안이다.

이번 handler의 흐름은 `MethodArgumentNotValidException` 받기 → `exception.getBindingResult().getFieldError().getDefaultMessage()`로 `@Size`에 적은 문구 꺼내기 → `ResponseEntity.badRequest().body(Map.of("message", message))`를 반환하기다. 이러면 Postman 응답은 HTTP 400과 JSON `{"message":"이름은 30자 이하로 입력해주세요."}`가 된다. 다른 종류의 오류는 이번 handler에서 넓게 잡지 않고, 필요가 생길 때 각각 정책을 정한다.

## 해시 문자열을 DB에 저장할 때 암호화도 해야 할까?

SHA-256은 암호화가 아니라 한 방향 해시다. 32바이트 digest를 hexadecimal 문자열로 표현하면 64글자이므로 Java `String`과 PostgreSQL `varchar(64)`로 저장할 수 있다. 매 요청에서 쿠키 원문에 같은 SHA-256을 적용해 계산한 값으로 unique 해시 컬럼을 조회한다. DB에서 다시 복호화하지 않으므로 컬럼 암호화는 이 조회 흐름에 필요하지 않다. DB 디스크/백업 암호화(at rest)는 별도 방어층이며, 논리적 DB 읽기 권한으로 덤프가 유출되는 경우에는 해시 저장이 직접 도움을 준다. 토큰이 CSPRNG가 만든 256비트 난수라면 비밀번호처럼 느린 Argon2/bcrypt 또는 salt를 붙일 필요는 없다. OWASP는 고엔트로피 random verifier에는 빠른 SHA-256이 충분하다고 설명한다.

구현 순서는 요청 cookie 읽기 → 없거나 만료된 경우 SecureRandom으로 새 32바이트 토큰 생성 → raw token은 Set-Cookie로만 보내고 SHA-256 hex를 저장 → 기존 cookie면 같은 방식으로 hash를 계산해 Repository 조회 → 7일 idle 제한을 `last_seen_at`으로 서버에서 확인 → 유효하면 last_seen_at과 cookie 만료를 갱신해 기존 사용자 응답 순서다. 만료를 판단하기 전에 last_seen_at을 갱신하면 안 된다. 해시 컬럼은 unique여야 하며 응답 DTO나 로그에 노출하지 않는다.

이미 V5/V6를 적용한 DB에는 cookie hash가 없는 사용자 row가 있을 수 있다. V7에서 새 컬럼을 즉시 `NOT NULL`로 추가하면 기존 row 처리 계획이 필요하다. 기존 브라우저에 사용 가능한 token을 배정할 수 없으므로 migration에서 기존 사용자 데이터를 어떻게 다룰지와 nullable 전환을 ERD 리뷰 때 검토한다.

### 쿠키를 CreateRequest에 넣어야 할까? 재방문 식별 로직은 어디에 둘까?

쿠키는 JSON 요청 본문이 아니라 HTTP 요청 헤더의 `Cookie` 값이다. 따라서 `AnonymousUserCreateRequest`에는 사용자가 선택적으로 보내는 `nickname`만 두고, 쿠키는 Controller의 `@CookieValue`로 읽는다. Controller는 HTTP 쿠키를 읽고 응답의 `Set-Cookie`를 설정하며, Service는 닉네임 생성·토큰 해시 조회·7일 비활성 여부 판단·사용자 생성/재사용이라는 유스케이스를 수행한다. Repository는 해시로 사용자를 찾는 일을 맡는다.

Service의 흐름은 다음과 같다. 쿠키가 있으면 토큰을 해시해 사용자를 찾고, `last_seen_at`이 현재 시각으로부터 7일 이내인지 갱신 전에 확인한다. 유효하면 방문 시각을 갱신하고 기존 사용자를 반환한다. 쿠키가 없거나 해시 조회 결과가 없거나 만료됐다면 새 난수 토큰을 만들고 해시만 DB에 저장한 새 사용자를 만든다. 원문 토큰은 Service 결과로 Controller까지 전달해 쿠키로만 응답하고 JSON 응답 DTO·DB·로그에는 넣지 않는다. 그러므로 토큰 자체는 CreateRequest나 Response DTO의 필드가 아니다.

현재 초안의 `id_hash`는 어떤 값을 해시한 것인지 의미가 불분명하므로 `token_hash`처럼 목적을 드러내는 이름이 낫다. DBML의 `[not null]` 표기는 DBML 문법이지 PostgreSQL SQL 문법이 아니다. 또한 이미 존재하는 사용자 row가 있을 수 있어 `ALTER TABLE ... ADD ... NOT NULL`을 바로 적용할 수 있는지 먼저 확인해야 한다. 기존 사용자에게 토큰 원문을 복원해 줄 수 없으므로, V7의 기존 row 처리와 최종 nullability를 함께 설계하고 해시에는 `UNIQUE` 제약을 둔다.

### token_hash 초안과 Controller 작성 중 리뷰

ERD에서 `id_hash`를 `token_hash`로 바꾼 것은 의미가 명확해졌다. 다만 DBML에는 해시가 중복되지 않도록 unique index도 표현해야 한다. V7 SQL은 `[not null]` 같은 DBML 옵션 표기를 쓰지 않고 SQL 문법으로 작성해야 하며, 기존 사용자 row가 있으면 `NOT NULL` 컬럼을 즉시 추가할 수 없다. 기존 row를 유지한다면 먼저 nullable로 추가하고 새 사용자부터 값을 넣는 등 migration 전략을 결정한다.

Entity에는 아직 `token_hash` 필드가 없고 Repository에도 해시 조회 메서드가 없으며 Service는 매번 새 사용자만 생성한다. 이 세 부분이 다음 구현 단계다. Controller 초안의 `@CookieValue(required = true)`는 쿠키 없는 첫 방문을 Spring이 Controller 진입 전에 400으로 거절하게 만든다. 쿠키 부재가 새 사용자 생성 경로여야 하므로 값은 선택 사항이어야 한다. 또한 쿠키 이름은 `token_hash`가 아니라 브라우저가 보관할 원문 토큰의 용도를 나타내는 이름(예: `anonymous_user_token`)으로 두고, DB 컬럼에만 `token_hash`를 쓴다. Controller에는 쿠키 이름과 값을 나타내는 `String`을 주입하면 되고, 아직 빈 메서드가 반환값을 만들지 않아 현재 코드는 컴파일되지 않는다.

`/anonymoususer/create`와 `/anonymoususer/token`을 별개로 만들기보다, 익명 사용자 준비 요청 하나에서 쿠키 확인과 재사용/생성을 함께 처리하는 흐름이 단순하다. Controller는 쿠키 입력과 `Set-Cookie` 응답만 다루고 Service가 유스케이스를 조정한다. 새 토큰 원문을 Controller로 돌려주려면 Service 결과에 사용자와 원문 토큰을 함께 담아야 하지만, 이를 JSON 응답 DTO에 넣지 않고 HTTP 쿠키로만 내보낸다.

### V7 SQL과 Entity 수정 리뷰

현재 서비스는 로컬 개발 단계라면 기존 익명 사용자 데이터 보존이 필수는 아니다. DB가 폐기 가능한 개발 데이터인지 확인하고, 필요하다면 기존 row를 비운 뒤 `NOT NULL` 컬럼을 추가하는 전략을 택할 수 있다. 다만 Flyway V7은 로컬 DB에서 실제 적용 전 검토하고, 이미 성공 적용한 migration 파일은 수정하지 않는다.

Entity에 `tokenHash` 필드를 추가하고 `@Column(name = "token_hash", nullable = false, unique = true)`로 선언한 것은 의도에 맞다. 현재 V7 SQL은 `ALTER TABLE AnonymousUser`라 PostgreSQL에서 이름이 소문자로 접혀 `anonymoususer` 테이블을 찾게 된다. 실제 테이블명은 V5에서 만든 `anonymous_user`이므로 이 이름으로 고쳐야 한다. 개발 DB에 기존 row가 남아 있으면 `NOT NULL` 추가도 실패하므로 row 수를 확인하거나 로컬 데이터를 정리해야 한다. SQL constraint 이름은 camel case보다 `uq_anonymous_user_token_hash` 같은 이름이 읽기 쉽다.

Entity 필드를 추가한 것만으로 저장 흐름이 완성된 것은 아니다. 현재 생성자는 tokenHash를 받지 않고 Service도 기존처럼 저장하므로, V7 적용 뒤 새 row 저장 시 DB의 `NOT NULL` 제약 위반이 발생한다. 다음으로 토큰 해시를 생성자에 전달하는 경로와 Repository의 해시 조회를 연결해야 한다. ERD에도 token_hash의 unique 제약을 함께 표현한다.
