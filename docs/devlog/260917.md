# 2026-09-17 — Room 테이블에서 JPA 엔티티까지

오늘은 테이블 하나 만들고 클래스로 연결했다. 코드 양은 많지 않은데, DB와 Java 사이에서 누가 무슨 일을 하는지 질문이 많이 나왔다.
블로그로 옮기기 전에 처음 생각했던 것과 답을 듣고 이해한 내용을 정리해 둔다.

## 오늘 한 것

- Docker PostgreSQL 실행 문제를 확인하고 복구했다.
- Spring에서 PostgreSQL 연결이 되는 것을 확인했다.
- Room의 운영 시간, 필수값, ID 생성 방식을 정하고 ERD에 반영했다.
- `V1__create_room.sql`을 작성하고 Flyway 적용 성공을 DBeaver에서 확인했다.
- `Room` 클래스에 필드, getter, JPA 매핑을 작성했다.
- `ddl-auto: validate`를 설정했고, 기존 Spring 기동 테스트가 통과했다.

아직 Repository, Service, Controller, API는 만들지 않았다.

## 1. Makefile이 실패한 이유

Docker Desktop을 열고 DB를 실행하도록 Makefile을 만들었는데 실패했다.
확인해 보니 Makefile 문법 문제가 아니라 기존 컨테이너가 사라진 Docker 네트워크를 참조하고 있었다.
`make: *** [up] Error 1`은 그 앞의 Docker 명령이 실패했다는 결과였다. 네트워크가 왜 사라졌는지까지는 확인하지 못했다.

DB 데이터 볼륨은 유지하고 컨테이너만 재생성해서 복구했다.

```bash
docker compose up -d --force-recreate postgres
```

이후 make와 DB 쿼리가 성공했다. 컨테이너가 실행되는 것과 Spring이 DB에 연결되는 것은 별도로 확인해야 했다.

## 2. Flyway가 뭐 하는 건데?

**Q. DBeaver에 들어가서 DDL을 실행해야 하는 거 아닌가?**

직접 실행해도 테이블은 만들어진다. 다만 이번에는 SQL을 파일로 남기고 Flyway가 실행하도록 했다.
내가 SQL을 작성하는 건 같고, 실행과 이력 관리를 Flyway에 맡기는 것이다.

`src/main/resources/db/migration/V1__create_room.sql`을 만들었다.
현재 설정에서는 Spring이 시작할 때 Flyway가 migration을 실행한다.
적용한 버전은 `flyway_schema_history`에 기록된다. DBeaver에서 버전 1, 설명 create room, success가 true인 것을 확인했다.

처음에 나온 `No migrations found`는 SQL 파일이 없어서 나온 경고였다.
`Schema is up to date`만 보고 테이블 설계가 끝났다고 생각하면 안 된다. 실행할 migration이 없을 때도 나오는 메시지다.

**Q. 일종의 DB판 Git인가? 컬럼을 추가하면 로컬과 AWS에 모두 적용되나?**

변경에 버전과 이력을 붙인다는 점에서는 비슷하다. DB끼리 실시간 동기화하거나 데이터를 복사하는 도구는 아니다.

1. 컬럼 추가 SQL을 V2 파일로 작성한다.
2. 로컬에서 실행하면 로컬 DB에 적용된다.
3. 그 파일이 포함된 앱을 AWS에 배포하고 실행하면 AWS DB에도 적용된다.

각 DB가 자기 이력을 보고 미적용 migration만 실행한다.
공유하거나 배포한 V1을 수정하기보다 V2, V3로 변경을 추가한다. Git처럼 자동으로 이전 상태로 돌아가는 것도 아니다.
DBeaver는 테이블 확인, SELECT, 쿼리 실험에 계속 사용한다.

## 3. Room DDL을 작성하며 고민한 것

처음에는 DBML 내용을 거의 그대로 SQL로 적었다. 컬럼 사이 쉼표가 빠졌고 PostgreSQL에 없는 `String` 타입도 사용했다.
문자열에는 `varchar(n)`이나 `text`를 사용할 수 있다.

**Q. ID는 GENERATED AS IDENTITY 아니면 SERIAL을 쓰라는데?**

이번에는 IDENTITY를 선택했다. 정확한 문법은 두 가지다.

| 선언 | ID를 직접 지정한 일반 INSERT |
| --- | --- |
| `GENERATED ALWAYS AS IDENTITY` | 거부한다. 명시적으로 재정의하는 별도 구문은 있다. |
| `GENERATED BY DEFAULT AS IDENTITY` | 직접 지정한 값을 사용한다. |

둘 다 내부적으로 시퀀스를 사용한다. ID 생성은 DB가 맡게 하려고 ALWAYS를 선택했다.
자동 생성과 유일성 보장은 별개라 PRIMARY KEY도 유지했다.

**Q. 운영 시간은 필수지만, 이름은 거의 고정 아닌가?**

이름이 바뀌는 빈도와 필수 여부는 별개다. 이름 없는 방은 허용하지 않으므로 이름에도 NOT NULL을 붙였다.
이름은 최대 10자로 정했다. NOT NULL은 NULL을 막을 뿐 빈 문자열이나 공백까지 막지는 않는다.

**Q. 짧게 보관할 대화인데 날짜가 필요한가?**

Room의 운영 시간을 time으로 정한 이유는 매일 반복되는 일정이기 때문이다.
메시지를 짧게 보관하기 때문은 아니다.

- Room.open_at: 매일 12시에 열린다는 반복 일정
- Message.created_at: 특정 날짜의 12시 3분에 작성됐다는 발생 시점

삭제가 누락되면 어제 메시지와 오늘 메시지를 구분해야 하므로 메시지 작성 시점에는 날짜도 의미가 있다.
정책도 하루가 지나면 삭제가 아니라 방이 닫히면 삭제다.

**Q. 야근방처럼 자정을 넘는 방도 만들고 싶다. 어떻게 반영하지?**

23:00~02:00 같은 운영 시간을 허용하기로 했다. 현재 time 컬럼으로 저장할 수 있으므로 SQL에 추가할 것은 없었다.
단순히 open_at < close_at 제약을 넣으면 이런 방을 막아 버린다.
열림 여부는 이후 Spring에서 판단한다. 열림과 닫힘 시각이 같은 경우의 의미는 아직 미정이다.

설계 원본인 docs/erd.dbml과 docs/decisions.md에 반영하고 dbdiagram.io에도 동기화했다.
DBML의 increment는 자동 증가 의도이고, PostgreSQL의 정확한 ALWAYS 정책은 migration에 명시했다.
SQL에서 따옴표 없이 ROOM이라고 썼으므로 실제 테이블 이름은 소문자 room이다.

## 4. Spring 클래스는 어떤 순서로 만드는가?

처음 정리했던 목록은 이랬다.

```text
DB → domain → repository → service → dto → controller → 프론트
                          └ filter (로그인 시 필요?)
```

구현 순서와 각 클래스의 역할이 섞여 있었다. 다시 정리했다.

| 구분 | 역할 |
| --- | --- |
| DB | 데이터 저장과 PK, FK, NOT NULL 같은 제약 보장 |
| domain | 서비스의 개념과 규칙 표현. JPA 엔티티라면 테이블에도 매핑 |
| repository | 엔티티 저장과 조회 |
| service | 사용 사례 처리, 도메인과 Repository 조합, 트랜잭션 경계 설정 |
| DTO | 요청과 응답에 필요한 데이터를 담는 객체 |
| controller | HTTP 요청을 받고 처리 결과를 HTTP 응답으로 반환 |
| 프론트 | 화면, 사용자 상호작용, API 호출 |

Filter는 Service 아래가 아니다. HTTP 요청이 Controller에 도달하기 전후에 공통 처리를 하는 위치다. 로그인에만 쓰는 것도 아니다.
DTO는 변환 처리 자체가 아니라 데이터를 담는 구조다.
Domain도 단순한 테이블 복사본보다 넓은 개념이다. Room의 운영 규칙을 어디에 둘지도 나중에 고민한다.

```text
이번 구현 순서: DB → Room 엔티티 → Repository → 필요한 Service·DTO → Controller
요청 처리 흐름: 프론트 → Filter → Controller → Service → Repository → DB
```

엔티티와 DTO는 요청이 통과하는 실행 단계가 아니라 각 단계에서 사용하는 객체다.
Room은 관련 기능을 모으기 위해 com.breakground.room 패키지에 만들었다.

## 5. Java 필드 타입을 고른 이유

**Q. java.sql.Time을 그대로 쓰면 안 되나?**

쓸 수는 있다. JDBC 타입이라는 이유만으로 금지하는 건 아니다.
Time은 java.util.Date를 상속하는 오래된 타입이다. 날짜 없는 시각인데도 날짜 관련 메서드가 남아 있고 일부는 호출하면 예외가 난다. 객체 자체도 변경할 수 있다.

LocalTime은 날짜와 시간대 없이 시각을 표현하는 불변 객체다.
운영 시간을 비교하고 계산하기에 적합해서 선택했다.

```java
LocalTime opening = LocalTime.of(12, 0);
LocalTime delayed = opening.plusMinutes(30);
// opening은 12:00 그대로, delayed는 12:30
```

**Q. 필드는 왜 private으로 두는가?**

접근 제어자를 생략하면 같은 패키지에서 직접 변경할 수 있다.
private으로 두고 허용한 방법을 통해 변경하도록 통제한다. getter는 추가했지만 setter는 만들지 않았다.
private이어도 변경 가능한 객체를 getter로 그대로 반환하면 외부에서 그 객체의 내용을 바꿀 수 있다. LocalTime은 불변이라 이 문제가 없다.

**Q. Integer는 그냥 기능이 많아서 고른 건데?**

처음에는 별생각 없이 참조형을 골랐다. 이번에는 저장 전 ID의 미할당 상태를 null로 표현할 수 있다는 근거가 생겼다.
횟수처럼 0이 자연스러운 값에는 int가 적합할 수 있다. 참조형이 항상 좋은 건 아니다.
null인 Integer를 int로 자동 변환하면 NullPointerException이 날 수 있다.

## 6. DB 설계와 JPA 매핑 연결하기

**Q. DB의 primary key가 Java의 id에 대응되는 건가?**

필드 이름이 id라서 기본 키가 되는 건 아니다. JPA는 @Id가 붙은 필드를 엔티티 식별자로 본다.
DB는 PK로 행을 구분하고 JPA는 식별자로 엔티티를 구분한다. 이번에는 room.id와 Room.id를 연결했다.

**Q. 자동 생성은 PostgreSQL에서 정했는데 왜 JPA에도 설정하나?**

- SQL의 GENERATED ALWAYS AS IDENTITY: PostgreSQL이 ID를 생성하도록 설정한다.
- JPA의 @GeneratedValue(strategy = GenerationType.IDENTITY): DB가 생성한 ID를 받아 사용하도록 설정한다.

ALWAYS와 BY DEFAULT 모두 JPA에서는 IDENTITY로 대응할 수 있다. 직접 지정한 ID를 허용하는지는 DB의 세부 정책이다.

**Q. openAt과 closeAt의 NOT NULL도 알려줘야 하는 것 아닌가?**

@Column으로 컬럼 이름과 필수 여부를 표현했다. name에는 length = 10도 설정했다.

```java
@Column(name = "open_at", nullable = false)
private LocalTime openAt;
```

| 설정 | 역할 |
| --- | --- |
| DB의 NOT NULL | 어떤 저장 경로든 DB가 NULL을 거부 |
| @Column(nullable = false) | 매핑 정보. Java 필드에 null을 대입하는 것 자체를 막지는 않음 |
| Validation의 @NotNull | 검증을 실행하는 시점에 값이 있는지 검사 |

Flyway가 스키마를 관리하므로 어노테이션만 바꿔도 기존 DB 제약이 바뀌는 것은 아니다.

**Q. 그런데 PK에는 왜 @Column을 안 쓰나?**

PK에도 쓸 수 있다. 지금은 Java 필드와 DB 컬럼이 모두 id라 기본 매핑으로 충분하다.
@Id는 식별자 지정, @GeneratedValue는 생성 방식, @Column은 컬럼 이름과 옵션을 정하는 역할이다.
DB 컬럼이 room_id라면 @Column(name = "room_id")를 같이 쓸 수 있다.
PK 자체가 DB에서 NOT NULL과 유일성을 보장하므로 그것을 위해 추가할 필요도 없다.

**기본 생성자와 validate 설정**

@Entity를 붙여 Room을 엔티티로 등록했다.
JPA 엔티티에는 public 또는 protected인 인자 없는 생성자가 필요하다.
현재는 생성자를 작성하지 않아서 Java가 public 기본 생성자를 만든다.
인자를 받는 생성자를 추가하면 자동 기본 생성자가 사라지므로 JPA용 기본 생성자도 명시해야 한다. 그때 protected로 둘 예정이다.

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

이 설정으로 재시작했고 기존 Spring 기동 테스트도 통과했다.
validate는 스키마를 수정하지 않고 매핑을 검사한다. 모든 길이, NOT NULL, 제약조건을 완전히 비교해 주는 것은 아니므로 ERD와 SQL 리뷰도 필요하다.

## 7. Java 클래스로 DB를 만들면 안 되나?

**Q. 엔티티를 먼저 만들고 그대로 DB로 옮기는 게 기술적으로 불가능한가?**

가능하다. Hibernate가 엔티티 매핑을 바탕으로 DDL을 실행할 수 있다.

| ddl-auto | 동작 |
| --- | --- |
| validate | 매핑 검사 |
| create | 매핑 대상 테이블을 삭제하고 다시 생성. 기존 데이터가 사라질 수 있음 |
| create-drop | 생성하고 종료 시 삭제 |
| update | 매핑에 맞춰 스키마 변경 시도 |

Flyway를 쓰는 이유는 데이터가 이미 있는 DB의 변경 의도와 순서를 명시하기 위해서다.
필드를 name에서 title로 바꿨을 때 기존 컬럼 이름을 바꾸려는 것인지 별개의 컬럼을 추가하려는 것인지, 최종 클래스만으로는 충분히 알기 어렵다.

객체를 먼저 설계해도 된다. 그 설계에 맞춰 ERD와 migration을 작성하면 된다.
이번에는 테이블 하나부터 시작해서 Java 객체와 연결해 봤다.

## 8. Hibernate는 뭐더라?

Hibernate는 Java 객체와 관계형 DB를 연결하는 ORM(Object-Relational Mapping) 라이브러리다.
이름들이 비슷해서 헷갈렸는데 역할을 나누면 이렇다.

| 이름 | 역할 |
| --- | --- |
| JPA | 객체를 저장하고 조회하기 위한 표준 API와 규칙 |
| Hibernate | JPA를 실제로 구현한 라이브러리 |
| Spring Data JPA | JPA를 사용하는 Repository의 반복 코드를 줄여주는 도구 |
| JDBC | Java에서 DB에 접근하는 API. Hibernate 아래에서도 사용 |
| Flyway | DB 변경 SQL 실행과 적용 이력 관리 |

@Entity, @Id, @Column은 JPA 어노테이션이다.
현재 프로젝트에서는 Hibernate가 매핑을 읽어 SQL을 준비하고 JDBC로 실행하며 결과를 엔티티로 구성한다.

## 9. RoomRepository는 어디에 쓰나? JDBC와 DAO는 괜히 배웠나?

**Q. RoomRepository는 무슨 일을 하나?**

Room을 저장하고 조회하는 통로다. 앞으로 Service에서 방 목록을 요청할 때 사용한다.
Spring Data JPA가 기본 CRUD 구현을 제공하므로 기본 조회마다 SQL과 구현체를 직접 작성할 필요는 없다.
테이블 생성은 Flyway, 그 테이블의 데이터 접근은 Repository가 담당한다.

**Q. Java_101에서 만들었던 DAO는 어떻게 된 건가?**

[Java_101의 MemberDao](https://github.com/InryeolChoi/Java_101/blob/main/StartJdbc/src/main/java/com/java101/jdbc/step4/MemberDao.java)를 다시 확인했다.
findById에서 다음을 직접 하고 있었다.

1. SELECT SQL 작성
2. Connection 준비
3. PreparedStatement에 ID 설정
4. SQL 실행
5. ResultSet에서 컬럼 값 읽기
6. new Member(...)로 객체 만들기

지금도 DB에서 SQL이 실행된다는 사실은 같다. Hibernate가 매핑 정보를 이용해 SQL 실행과 객체 구성 등의 일을 맡는다.

```text
예전: 호출 코드 → MemberDao → JDBC → DB
지금: Service → RoomRepository → Spring Data JPA → Hibernate → JDBC → PostgreSQL
```

DAO와 Repository는 설계 개념이 완전히 같지는 않지만, 지금은 Service에서 데이터 접근을 분리하는 역할로 연결해 이해했다.
이름이 비슷한 메서드도 동작은 확인해야 한다.

| MemberDao에서 작성한 메서드 | Spring Data JPA |
| --- | --- |
| findById: 없으면 null 반환 | findById: 빈 Optional 반환 |
| findAll: SQL에 ORDER BY id ASC 명시 | findAll: 정렬이 필요하면 별도 지정 |
| save: 항상 INSERT, 영향받은 행 수 반환 | save: 엔티티 상태에 따라 저장 처리, 엔티티 반환 |

[트랜잭션 실습](https://github.com/InryeolChoi/Java_101/blob/main/StartJdbc/src/main/java/com/java101/jdbc/step6/MemberTransactionBoundaryMain.java)에서는 setAutoCommit(false), commit(), rollback()도 직접 사용했다.
이 경험은 나중에 @Transactional을 배울 때 연결된다.

JDBC 공부가 사라진 건 아니다. 직접 작성하던 일 중 어떤 부분을 라이브러리에 맡기는지 배우고 있다.
예상보다 많은 SQL이 실행되거나 트랜잭션 문제가 생기면 실제 SQL과 DB 동작을 이해해야 한다.
