- domain은 테이블 매핑뿐 아니라 서비스의 개념과 규칙을 표현한다.
- repository는 저장과 조회를 담당하고, service는 사용 사례를 처리하며 트랜잭션 경계를 정한다.
- filter는 service 아래가 아니라 HTTP 요청이 controller에 도달하기 전후에 공통 처리를 하는 위치다. 로그인에만 쓰는 것도 아니다.
- DTO는 변환 처리 자체가 아니라 요청과 응답에 필요한 데이터를 담는 객체다.

먼저 문법입니다.
- 컬럼 정의 사이에 쉼표(,)가 필요합니다.
- PostgreSQL에는 기본 타입으로 String이 없습니다. 길이 제한을 정한다면 varchar(n), 정하지 않는다면 text를 사용할 수 있습니다. 문자열 타입 문서
1) ID 자동 생성: 이번에는 IDENTITY를 추천합니다.
   정확한 문법은 두 가지입니다.
   GENERATED ALWAYS AS IDENTITY
   GENERATED BY DEFAULT AS IDENTITY
   둘 다 내부적으로 시퀀스라는 번호 생성 객체를 사용합니다. 차이는 직접 ID를 넣었을 때입니다.
   방식	INSERT에서 ID를 직접 지정하면
   ALWAYS	일반적인 INSERT에서는 거부
   BY DEFAULT	직접 지정한 값을 사용


“ID는 DB가 생성한다”는 의도라면 ALWAYS가 자연스럽습니다. 자동 생성과 유일성 보장은 서로 다른 역할이므로 PRIMARY KEY도 유지하세요. Identity 문서
2) 이름이 고정인 것과 필수인 것은 별개입니다.
   ‘점심방’이라는 이름이 거의 바뀌지 않아도, 그 값을 저장할 필요는 있습니다. 현재 결정도 점심방·간식방을 각각 Room 행으로 관리하는 것이고요.
   판단 기준은 **“이름 없는 방을 유효한 데이터로 허용할 것인가?”**입니다. 허용하지 않는다면 이름에도 NOT NULL을 붙이면 됩니다. 운영 시간도 같은 이유로 NOT NULL이 필요합니다.
   다만 NOT NULL은 NULL만 막습니다. 빈 문자열 ''까지 막는 것은 아니라는 점도 기억해 두세요.
3) Room 운영 시간에 time을 쓰는 결론은 맞지만, 이유는 ‘매일 반복되는 일정’이기 때문입니다.
- Room.open_at: 매일 12:00에 열린다 → 날짜 없는 시각
- Message.created_at: 9월 16일 12:03에 작성됐다 → 날짜를 포함한 발생 시점
  메시지를 짧게 보관하더라도 작성 시점의 날짜가 불필요해지는 것은 아닙니다. 서버 장애로 어제 메시지 삭제가 누락됐을 때, 시각만 저장하면 오늘 메시지와 구분하기 어렵습니다.
  또한 현재 정책은 하루가 지나면 삭제가 아니라, 방이 닫히면 즉시 삭제입니다. Room의 반복 일정과 Message의 보관 수명은 나누어 생각해야 합니다.

5) DB 설계랑 JPA 매핑 연결하기

**Q. DB의 primary key가 Java의 id에 대응되는 건가?**

필드 이름이 id라서 기본 키가 되는 건 아니다. JPA에서는 `@Id`가 붙은 필드를 엔티티 식별자로 본다.
DB에서는 PK로 행을 구분하고, JPA에서는 이 식별자로 엔티티를 구분한다.
이번에는 `room.id`와 `Room.id`를 연결했다.

**Q. DB가 ID를 자동 생성하는 건 PostgreSQL에서 정했는데, JPA에도 설정해야 하나?**

둘은 연결되어 있지만 역할이 다르다.

- SQL의 `GENERATED ALWAYS AS IDENTITY`: PostgreSQL이 ID를 생성하도록 설정한다.
- JPA의 `@GeneratedValue(strategy = GenerationType.IDENTITY)`: INSERT 시 DB가 생성한 ID를 받아 사용하도록 설정한다.

앞에서 고민한 `ALWAYS`와 `BY DEFAULT`는 ID를 직접 지정해서 INSERT할 때의 정책이다.
`ALWAYS`는 일반적인 직접 지정을 거부하고, `BY DEFAULT`는 직접 넣은 값을 허용한다.
둘 다 JPA에서는 `GenerationType.IDENTITY`로 대응할 수 있다. 세부 정책은 Flyway SQL에 남는다.

**Q. openAt, closeAt이 NOT NULL인 것도 JPA에 알려줘야 하는 거 아닌가?**

맞다. 컬럼 이름과 필수 여부도 매핑에 표현했다.

```java
@Column(name = "open_at", nullable = false)
private LocalTime openAt;
```

`closeAt`에도 같은 방식으로 설정하고, `name`에는 `length = 10`, `nullable = false`를 설정했다.
다만 비슷해 보이는 설정들의 역할을 구분해야 한다.

- DB의 `NOT NULL`: 어떤 경로로 저장하든 DB가 NULL을 거부한다.
- JPA의 `@Column(nullable = false)`: 매핑 정보다. Java 필드에 null을 대입하는 것 자체를 막지는 않는다.
- Validation의 `@NotNull`: 검증을 실행하는 시점에 값이 있는지 검사한다. 요청 DTO를 만들 때 더 다룰 예정이다.

이 프로젝트에서는 Flyway가 스키마를 관리한다. 어노테이션만 고친다고 기존 DB 제약조건이 바뀌지는 않는다.

6) Room 매핑 리뷰 후 알게 된 것

- `@Entity`로 Room을 JPA 엔티티로 등록했다.
- `@Id`와 `@GeneratedValue`로 기본 키와 ID 생성 방식을 연결했다.
- `@Column`으로 이름 길이, 필수 여부, 운영 시간 컬럼 이름을 맞췄다.
- 필드와 컬럼 이름이 같은 `@Column(name = "name")`의 name 설정은 생략할 수도 있다.

JPA 엔티티에는 public 또는 protected인 인자 없는 생성자가 필요하다.
지금은 생성자를 하나도 작성하지 않아서 Java가 public 기본 생성자를 만들어 준다.
나중에 인자를 받는 생성자를 추가하면 자동 기본 생성자는 사라지므로, JPA용 기본 생성자를 protected로 직접 선언해야 한다.

`application.yml`에는 아래 설정을 추가하고 앱을 재시작했다.

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

Flyway는 실제 스키마를 만들고, Hibernate는 엔티티와 실제 테이블의 매핑을 검증하도록 역할을 나눴다.
`validate`는 테이블을 수정하지 않는다. 그렇다고 모든 NOT NULL, 길이, 제약조건을 완전히 비교해 주는 것도 아니므로 ERD와 SQL 리뷰는 계속 필요하다.
