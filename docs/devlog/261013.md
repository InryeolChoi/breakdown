## 목적과 시작 상태

Next.js + TypeScript 프런트를 구축하기 전에 스킬 설정·GitHub Issues·PR 작업 방식을 준비한다. 사용자가 자러 가므로 필요한 질문은 모아두고 독립적으로 작성 가능한 초안까지 진행한다. 프런트 코드, 도구 설치·계정 연결, GitHub 게시·설정 변경, 커밋·푸시·PR 생성·머지는 이번 요청 범위에서 제외한다.

시작 브랜치는 main / a92cbab이다. 앞선 작업의 전체 97개 테스트 통과 기록이 있지만 오늘 재실행하지 않았다. 시작 시 breakground.zip 삭제와 .DS_Store 미추적 변경이 있었고 그대로 보존했다. 문서 준비에 필요한 파일·GitHub 상태만 읽고 Docker/DB/앱을 시작하지 않았다.

## 질문과 답변 — 스킬을 어떤 순서로 쓰는가?

setup-matt-pocock-skills, wayfinder, to-spec, to-tickets, implement-spec, pr, code-review의 실제 설치 파일을 읽었다. setup은 issue tracker·triage·도메인 문서 소비 규칙을 확인받아 적용한다. wayfinder는 미결정을 해결하는 단계이고, to-spec은 이미 논의한 명세를 합성하며 테스트 경계를 확인받는다. to-tickets는 사용자 동작을 끝까지 완성하는 작은 기능으로 나누고 크기·의존 관계 승인을 받은 뒤 게시한다. implement-spec은 전체 명세를 통합 브랜치로 구현하며, pr은 본문을 쓰고 code-review는 Standards/Spec 두 축을 따로 검토한다.

설치 파일을 읽었다는 것이 setup 적용·wayfinder HITL 결정 완료·실제 code-review 실행을 뜻하지는 않는다. setup의 "Let them edit before writing.", to-spec의 "Check with the user that these seams match their expectations.", to-tickets의 "Iterate until the user approves the breakdown." 경계에 따라 활성 설정·명세 게시·티켓 게시 전에서 멈춘다. 사용자는 자는 동안 초안을 충분히 준비하도록 허용했지만 답변 없는 선택을 대신 확정하거나 외부 게시를 허용하지 않았다.

## 질문과 답변 — 이슈 하나당 PR 하나인가, 통합 PR인가?

기본 제안은 작은 기능 이슈 하나에 PR 하나다. 기능별 diff와 검증 결과를 사용자가 읽고 이해하며 순서대로 머지할 수 있다. 설치된 implement-spec은 티켓별 worktree 작업을 하나의 integration branch에 합쳐 전체 명세 PR을 만드는 방식이다. 두 흐름을 동일하다고 설명하거나 원본 스킬을 몰래 바꾸지 않는다. 통합 작업이 필요하면 별도로 선택한다.

GitHub의 Closes 관계는 기본 브랜치 대상 PR에서 동작한다. 부분 기능 PR이 부모 명세까지 닫지 않도록 하고, 통합 브랜치의 내부 PR 머지를 전체 완료로 취급하지 않는다. 이슈의 부모 관계와 실제 선행 blocking 관계도 구분한다.

## 프런트에서 놓치기 쉬운 서버 계약

- 방 목록은 현재 열린 방만 반환한다. 닫힌 방/다음 개장/참가자 수를 아는 것처럼 디자인하지 않는다.
- 익명 준비는 BANNED 사용자도 200과 상태 데이터로 반환할 수 있다. 응답 status를 확인한다.
- 쿠키는 HttpOnly이며 JS에서 읽어 토큰 JSON/localStorage로 옮기지 않는다.
- 채팅 WebSocket은 기본 같은 출처 허용이다. echo wildcard를 채팅 계약으로 착각하지 않는다. 개발 포트 분리는 쿠키와 Origin/HTTP CORS/WS 경로 확인이 필요하다.
- 브라우저 onerror는 handshake HTTP status를 직접 전달하는 계약이 아니다. 서버의 JDK 클라이언트 테스트와 실제 브라우저 확인은 구분한다.
- 정상 채팅 응답에는 type 필드가 없고 오류만 ERROR/status/message다.
- 닉네임/신고 사유 길이는 Java UTF-16 검사이고 메시지는 코드 포인트 검사다. 프런트에서 한 가지 길이 계산을 모두에 적용하지 않는다.
- 시각 응답에 offset이 없고 Clock과 LocalDateTime.now 호출이 섞여 있다. 브라우저 시간으로 최종 운영/만료 판단을 대체하지 않는다.

기존 API와 소스 근거, 공식 문서 링크는 docs/drafts/frontend/api-contract.md에 정리했다. 이번에 이 문제들을 코드로 고치거나 서버 정책을 변경한 것은 아니다.

## 프런트 파일 위치를 조정해야 하는가?

**질문:** 프런트가 들어갈 파일 위치도 조정해야 하나?

프런트 위치는 정해야 하지만 기존 Spring 파일을 모두 옮길 필요는 없다. 현재 루트의 src/main, src/test, build.gradle, gradlew는 그대로 유지하고 같은 저장소 루트에 frontend 디렉터리를 추가하는 안을 추천했다. Next.js의 package.json·소스·의존성은 해당 디렉터리에 두면 서버와 프런트의 작업·검증 범위를 한 저장소에서 연결할 수 있다. backend/frontend로 전체를 재배치하는 안도 가능하지만 지금은 서버 경로·실행·문서·테스트 설정을 함께 바꿀 필요성을 찾지 못했다.

추후 실제 생성할 때 프런트 의존성·빌드 결과·비밀 환경 파일의 Git 제외 규칙과 실행 위치를 맞춘다. 이는 이번에 이미 적용한 변경이 아니다. 같은 저장소에 두는 것과 브라우저에서 같은 출처로 접근하는 것은 다른 결정이며 쿠키·HTTP·WebSocket 접속 경로는 별도로 정한다. 현재 설명은 위치 추천이고 사용자 승인 전이다. 디렉터리 생성·코드 이동·GitHub 게시를 하지 않았다.

**사용자 답변:** 제안한 구조로 진행하는 것이 좋겠다.

같은 저장소 루트 frontend에 Next.js + TypeScript를 두고 기존 Spring 구조를 유지하는 위치 결정을 확정했다. decisions.md와 관련 초안·NEXT.md를 갱신하고 첫 작업에서 저장 위치를 미결정 blocker로 제거했다. 위치 선택의 승인을 프로젝트 생성·설치·접속 경로·다른 setup 선택 승인으로 확대하지 않았다. 다음에 정할 기술 결정은 HTTP/쿠키/WebSocket 접속 방식이다.

## 아홉 질문에 대한 답변과 라운지 방향

사용자는 1번 라벨의 뜻과 3번 연결 방식의 뜻을 물었다. 2번은 작은 기능 이슈 하나 / PR 하나로 승인했다. 4번 첫 화면은 더 생각하고 5번 디자인 도구는 아직 잘 모르겠다고 했다. 6번은 커피 컵이 아니라 실제로 탁 트인 창문이 보이는 라운지에 온 느낌으로 수정했다. 7번 모바일 360px·데스크톱 1280px, 8번 채팅과 신고 버튼의 첫 공개 범위, 9번 목록 기능·첫 브라우저 테스트 경계와 작은 기능 분할 방향에 동의했다.

triage 라벨은 GitHub 이슈의 분류표다. needs-triage는 검토 필요, needs-info는 정보/답변 대기, ready-for-agent는 AI 구현 가능, ready-for-human은 사용자 참여/직접 작업 필요, wontfix는 수행하지 않음이다. 설치 스킬이 이 이름으로 작업을 찾으므로 기본값 사용을 추천하지만 의미 설명 요청을 사용 승인으로 처리하지 않는다.

연결 방식은 파일 위치가 아니라 브라우저 요청이 어느 주소를 거쳐 Next.js/Spring으로 도착하는지를 정하는 것이다. 개발에서는 두 프로그램이 서로 다른 포트로 실행될 수 있다. 한 사이트 주소 아래 화면은 Next.js, 방 목록·익명 준비·신고와 WebSocket은 Spring으로 전달하는 안을 추천했다. 중간 전달 구성은 프록시라고 부르며 쿠키와 WS Upgrade가 실제 통과하는지 후속 검증이 필요하다. 같은 출처 구성을 확정하거나 코드로 적용하지 않았다.

디자인은 사용자에게 전문 용어로 완성안을 정하도록 요구하지 않는다. 탁 트인 창문·라운지라는 원하는 느낌을 기준으로 자연광·넓은 여백·실내외 풍경 같은 후보를 구체화해 비교할 수 있다. 이는 레이아웃·색·시안을 확정한 것이 아니며 3D 이동 공간을 도입하는 결정도 아니다. 첫 화면과 도구는 미정으로 유지했다.

확정 답변은 decisions.md와 질문/명세/티켓/지도/인계 초안에 반영했다. 작업 단위 동의를 main 보호·라벨·계정·게시·머지의 일괄 권한으로 확대하지 않았다. 변경은 문서에 한정하고 GitHub 게시나 앱 구현을 시작하지 않았다.
