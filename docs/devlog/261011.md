## 테스트에서 실제 채팅 연결 구축으로 넘어가기

**질문:** 다음은 무엇인가? 테스트보다 다른 것을 구축해야 하는 것 아닌가? WebSocket 서버 방 구축이 많이 남았는가?

현재 Registry 테스트 네 가지가 통과했으므로 다음 목표는 실제 ChatWebSocketHandler 연결 구축으로 잡는다. 남은 닫힌 연결 분기 검증은 후속 작업으로 두고, 이를 먼저 끝내야만 Handler를 작성할 수 있는 것은 아니다. Room 테이블은 이미 방 정보를 저장하고 Registry는 실행 중인 서버의 연결 목록을 관리한다. 새 방 테이블이나 서비스 전체를 다시 만들 필요는 없다.

구축 순서는 실제 접속을 방별로 등록·종료 시 해제, 받은 메시지를 기존 ChatService로 검증·DB 저장 후 커밋된 메시지 방송, 두 실제 클라이언트로 같은 방 수신·다른 방 격리를 확인하는 세 단계다. 지금 접속 가능한 것은 /ws/echo이고 Echo는 보낸 연결에만 돌려준다. Registry는 실제 Handler와 아직 연결되지 않았다.

첫 사용자 작성 과제는 com.breakground.chat에 ChatWebSocketHandler를 만들고 TextWebSocketHandler를 상속해 공용 Registry를 생성자 주입하는 틀과 afterConnectionEstablished/afterConnectionClosed 메서드를 준비하는 것이다. 연결 시 검증된 roomId로 register, 종료 시 같은 roomId로 unregister하도록 연결한다. 방 ID와 익명 쿠키를 연결 속성에 전달하는 준비, 설정에 Handler를 명확한 타입으로 등록하는 코드, 세션별 동시 전송 보호는 AI가 지원할 부분으로 제안한다. 연결별로 새 Registry를 만들면 사용자끼리 목록을 공유하지 못한다.

채팅 주소 /ws/rooms/{roomId}는 제안이며 아직 코드·정책에 반영하지 않았다. 다른 Handler를 추가할 때 현재 WebSocketHandler 타입 필드는 두 후보 중 어떤 Bean인지 명확히 하도록 설정도 조정해야 한다. 사용자에게 작은 작성 지점을 안내했으며 Java 코드는 변경하지 않았다.

## roomId가 연결 콜백의 파라미터에 없는 이유

**질문:** afterConnectionEstablished나 afterConnectionClosed 파라미터에 roomId가 없는 것 같은데 왜인가?

이 메서드는 직접 설계한 Controller 메서드가 아니라 Spring WebSocketHandler 계약에 따라 프레임워크가 호출하는 콜백이다. 연결 성공에는 WebSocketSession, 연결 종료에는 WebSocketSession과 CloseStatus를 받도록 시그니처가 정해져 있다. roomId 파라미터를 추가하면 다른 메서드가 되어 @Override가 성립하지 않고 Spring도 그 메서드를 연결 콜백으로 호출하지 않는다.

방 ID는 접속 URL에서 읽거나, 핸드셰이크 시 서버가 추출·검증한 값을 session attributes에 저장한 뒤 Handler가 꺼내는 방식으로 전달한다. 제안 흐름은 /ws/rooms/1 접속 → HandshakeInterceptor가 roomId=1을 검증하고 attributes에 저장 → 연결 성공 Handler에서 Integer roomId=(Integer)session.getAttributes().get("roomId")로 읽어 Registry에 등록하는 것이다. 종료 때도 같은 연결 속성을 읽어 해제한다. session.getId()는 연결 식별자이며 DB 방 ID와 다르다.

roomId 키는 Spring이 URL을 보고 자동으로 채워 주지 않는다. 해당 값을 넣는 핸드셰이크 준비 코드는 아직 없으므로 지금은 읽기 예제만 안내했다. Java 소스를 변경하거나 테스트를 실행하지 않았다.

참고: [WebSocketHandler 콜백 계약](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/socket/WebSocketHandler.html), [WebSocketSession 연결 속성](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/socket/WebSocketSession.html)

## ChatWebSocketHandler 초안 검토 — 객체의 수명과 소스 위치

**질문:** Handler를 다 만들었다. 다음은 무엇인가?

실제 작성 파일은 src/test/java/com/breakground/chat/ChatWebSocketHandler.java에 있었다. 콜백 메서드 시그니처는 맞지만 운영용 Handler는 src/main/java/com/breakground/chat로 옮겨야 한다. test 소스는 테스트용이며 기본 애플리케이션 빌드의 운영 클래스에 포함되지 않는다.

접속과 종료 메서드 안에 각각 new RoomSessionRegistry()가 있다. 접속마다 빈 목록을 새로 만들고 종료 시에도 별개의 빈 목록을 만들어 기존 연결을 해제하지 못한다. Handler 필드에 final Registry를 두고 생성자로 전달받아 두 메서드가 같은 객체를 사용하도록 안내했다. 실제 Spring 연결에서는 공유 Registry와 Handler를 Bean으로 구성하는 준비도 필요하다.

접속 메서드는 속성에서 roomId를 읽고도 register(1, session)으로 등록한다. register(roomId, session)으로 사용해야 종료의 unregister(roomId, session)과 일치하며 모든 연결이 방 1로 섞이는 것을 피한다. roomId 속성을 넣는 핸드셰이크 준비 코드가 아직 없으므로 이 수정만으로 실제 접속이 완성되지는 않는다.

Java 소스는 이동·수정하지 않았고 테스트도 실행하지 않았다. 현재 작은 과제는 소스 위치, 공유 객체의 생성자 주입, 등록 방 ID를 먼저 바로잡는 것이다. 그 다음 핸드셰이크 속성 전달과 WebSocket 설정 연결로 진행한다.

## 생성자 주입은 기존 방 등록 내역을 조회하는 것인가?

**질문:** Handler 생성자로 Registry를 받으면 기존 방 등록 내역을 가져오는 것이 맞는가?

이미 연결을 등록한 같은 Registry 객체를 받는다면 그 객체가 가진 목록을 그대로 사용할 수 있다. 다만 DB에서 조회하거나 Map을 복사하는 동작은 아니다. this.registry=registry는 전달받은 객체의 참조를 필드에 저장한다. 접속과 종료 콜백은 이 같은 객체의 register/unregister를 호출한다.

첫 접속의 alice가 방 1에 등록되고 다음 접속의 bob이 같은 객체에 등록되면 그 Registry의 방 1 목록은 alice와 bob을 모두 가진다. alice가 종료되면 동일한 목록에서 alice를 제거하고 bob은 남는다. 매번 new Registry를 만드는 방식에서는 목록이 각각 분리된다.

생성자 문법만으로 공유가 보장되는 것은 아니다. 실제 설정에서 공유 Registry Bean을 만들고 Handler에 주입해야 하며 이 준비는 아직 남아 있다. Registry 목록은 현재 서버 메모리에 있는 살아 있는 연결 모음이다. PostgreSQL Room 테이블의 방 정보와 다르고 서버 재시작 때 연결 목록을 DB에서 복원하는 것도 아니다. Java 변경과 테스트 실행은 하지 않았다.

**추가 질문:** 방 등록 내역을 어딘가에 따로 저장해야 하는 것 아닌가?

현재 연결 등록 내역의 저장소가 이미 RoomSessionRegistry의 roomSetMap 필드다. 방 ID를 키로, 해당 방에 연결된 WebSocketSession의 Set을 값으로 가진다. register가 이 Map을 수정하고 broadcast/unregister가 같은 Map을 사용한다. 방 이름·운영 시간은 PostgreSQL Room에, 지금 접속한 실제 연결은 서버 메모리 Map에 저장한다. Handler 생성자는 이 Map을 가진 Registry 객체의 참조를 받으므로 같은 객체가 유지되는 동안 기존 등록 내역도 유지된다. 서버가 재시작되면 연결과 메모리 목록은 새로 시작하며 다시 접속할 때 등록한다. 이미 있는 동일 질문 기록에 이 저장 위치 설명만 보완했다.

## 연결 속성의 roomId와 전체 구현 지도

**질문:** session.getAttributes().get("roomId")는 어디에서 방 ID를 가져오는가? 언제 넣었는가? 전체적으로 얼마나 구현했는지 인터랙티브하게 보고 싶다.

현재 저장소에는 roomId 속성을 넣는 코드가 없다. getAttributes는 연결에 붙은 Map을 반환하고 get은 그 Map의 키를 읽을 뿐이다. Spring이 URL의 방 ID를 자동으로 채워 주는 것이 아니므로 지금은 null이 나온다. 다음 작은 작업은 HandshakeInterceptor가 접속 URL의 방 ID와 익명 쿠키를 검증하고 attributes에 roomId를 저장하도록 준비하는 것이다. 이후 공유 Registry/Handler Bean과 채팅 URL을 설정에 연결한다. 사용자는 Handler를 main 소스로 이동하고 공유 Registry 생성자 주입, 등록·해제에 roomId 사용까지 수정했다.

프로젝트의 구현 지도를 만들었다. 개발 환경·방·익명 사용자·HTTP 메시지 저장·신고·Echo·Registry는 구현 근거가 있고, ChatWebSocketHandler는 초안이며 핸드셰이크와 실제 채팅 전송 연결은 남아 있다. 프론트·게임·관리자 신고 처리·AWS 운영은 후속 단계다. 각 항목을 선택하면 현재 동작, 검증 근거, 다음 작업을 볼 수 있도록 구성했으며 전체 완성률을 임의의 숫자로 표현하지 않았다. Registry 테스트 4개 통과는 오늘의 실행 결과이고 Echo 및 전체 통합 테스트는 기존 기록의 검증 날짜를 구분했다.

지도는 브라우저에서 항목 선택과 상세 내용 변경을 확인했다. Java 코드는 변경하지 않았고 이 요청으로 테스트를 추가 실행하지 않았다. 현재 위치는 백엔드 기반과 HTTP 기능을 만든 뒤 실제 WebSocket 채팅을 연결하는 단계다.

## WebSocket 구현 분담과 첫 정책 질문

**요청:** wayfinder와 grill-me를 사용해 Handler는 직접 작성하고 핸드셰이크·메시지 연결은 속도를 높이고 싶다.

Handler의 연결 등록·해제는 사용자 코드로 준비되어 있고 메시지 수신 메서드는 아직 없다. 사용자는 Handler의 핵심 수신·서비스 호출·방송 흐름을 작성하고 AI는 핸드셰이크 검증·세션 속성 전달, Bean·URL 설정, JSON 변환과 동시 전송 보호, 테스트를 지원하는 분담안을 제시했다. 실제 분담 세부 경계와 정책은 아직 협의 중이며 Java 코드는 변경하지 않았다.

읽기 전용 사실 확인을 서브 에이전트에 맡겼다. ChatService.create는 원문 토큰·방 ID·본문을 받아 사용자와 운영 시간 및 본문을 검증하고 메시지를 저장하는 트랜잭션이다. 쿠키 이름은 anonymous_user_token이며 HTTP 작성 성공 때 쿠키를 7일로 갱신한다. WebSocket의 쿠키 갱신 경로는 별도로 정해야 한다. 기존 결정인 양방향 WebSocket과 커밋 이후 전달은 유지한다.

grilling 첫 질문은 다음과 같다. 아래는 추천안이며 사용자의 답변 전에는 확정 정책이 아니다.

1. 접속 조건: HTTP API로 익명 쿠키를 준비한 뒤 운영 중인 방에만 연결하고, 쿠키가 없거나 방이 닫히면 핸드셰이크를 거절할 것인가? 새 사용자를 핸드셰이크에서 자동 생성하는 대안과 비교한다.
2. 메시지 형식: 본문만 담은 JSON을 보낼 것인가, 일반 문자열을 보낼 것인가? JSON 추천안은 방과 작성자를 서버가 접속 주소·쿠키로 판단하고 메시지 ID·닉네임·본문·시각을 응답한다.
3. 방 종료: 종료 안내 후 연결까지 끊을 것인가, 연결은 유지하고 작성만 거절할 것인가? 종료 안내 후 연결 종료를 추천했으며 메시지 작성 시 운영 시간 재검증은 기존 Service를 재사용한다.

답변을 받은 뒤 오류 응답과 익명 쿠키 갱신 등 남은 경계를 구체화한다. wayfinder는 계획을 먼저 정하는 흐름으로 적용하며, 별도로 설정된 이슈 트래커가 없어 필요하면 로컬 Markdown 결정 지도를 사용한다. 이번 질문에서는 구현이나 테스트를 실행하지 않았다.

**사용자 답변:** HTTP로 익명 사용자 준비 후 접속, 본문만 담은 JSON, 방 종료 안내 후 연결 종료의 세 추천안을 선택했다. 해당 정책을 decisions.md에 기록했다. 로컬 결정 지도는 .scratch/websocket-chat/map.md이며 접속·메시지·종료 계약 티켓 하나를 진행 중으로 두었다.

**질문:** 이제 직접 해야 할 것은 무엇인가?

다음 사용자 작성 지점은 ChatWebSocketHandler의 handleTextMessage(WebSocketSession, TextMessage)다. TextMessage.getPayload는 JSON 자체가 아니라 JSON 형식의 문자열을 반환한다. 최종 흐름은 연결 속성의 방 ID·토큰 읽기, 본문 JSON 변환, ChatService.create로 검증·저장, 성공한 메시지 응답을 같은 방 Registry에 방송하는 것이다. 지금 준비할 수 있는 작은 부분은 override 메서드의 틀과 방 ID·payload 읽기다. JSON 변환과 토큰 속성 전달 지원 코드는 아직 없으므로 존재하지 않는 헬퍼를 호출하도록 안내하지 않는다.

후속 grilling 질문도 기록했다. Q4는 잘못된 JSON·빈 본문·길이 초과에 대해 보낸 연결만 오류 안내 후 유지하고 만료·차단·방 종료는 연결을 종료할지다. Q5는 방 접속 전 HTTP 익명 사용자 API로 7일 쿠키를 갱신하는 방식으로 시작할지다. 둘 다 추천안이며 아직 답변 전이다. 열린 WebSocket에서는 HTTP 400 응답 대신 오류 메시지를 보내야 하므로 오류 전달 경로가 HTTP Controller와 다르다. 정책 질문 중에는 Java 코드를 수정하거나 테스트를 실행하지 않았다.

**후속 답변:** Q4와 Q5도 추천안을 선택했다. 입력 오류는 보낸 연결만 안내 후 유지하고, 만료·차단·방 종료는 안내 후 종료한다. 각 방 접속 전 기존 HTTP API로 쿠키를 갱신한다. decisions.md에 반영하고 접속·메시지·종료 계약 티켓을 해결 상태로 기록했다. 사용자에게는 handleTextMessage의 메서드 틀과 roomId·payload 읽기를 첫 작성 과제로 안내하고 JSON 변환·핸드셰이크·전송 보호는 AI 지원 범위로 정리했다. Java 코드는 아직 변경하지 않았다.

## payload는 어디에 쓰는가?

**질문:** 안내한 수신 메서드를 작성했다. payload는 어디에 쓰는가?

작성한 Handler에는 handleTextMessage와 TextMessage import, roomId·payload 읽기가 들어갔다. 추가된 registry.broadcast(roomId, message)는 클라이언트의 원래 TextMessage를 그대로 방송하므로 payload 변수를 사용하지 않는다. 메서드 틀은 맞지만 이 상태에서는 ChatService의 본문·작성자·운영 시간 검증과 DB 저장을 건너뛴다. 따라서 아직 합의한 실제 채팅 흐름이 아니다.

message는 Spring이 전달한 TextMessage 객체이고 payload는 그 객체에서 꺼낸 문자열이다. 클라이언트가 {"content":"안녕"}을 보내면 payload에는 JSON 문서 전체가 문자열로 담긴다. 다음에 JSON을 기존 MessageCreateRequest 형태로 변환하면 request.content()가 본문 "안녕"을 반환한다. 이 본문을 방 ID·원문 토큰과 함께 ChatService.create에 전달하고, 성공한 ChatMessage 결과를 응답 JSON으로 바꿔 방송해야 한다. 방송할 것은 검증·저장 전 원래 요청이 아니라 서버가 생성한 ID·닉네임·시각을 포함한 결과다.

작은 다음 과제는 Handler에 ChatService를 Registry처럼 생성자 주입하는 것이다. JSON 변환 지원 코드는 아직 없고 AI 지원 범위로 남아 있다. 검토와 설명만 수행했고 Java 소스 변경이나 테스트 실행은 하지 않았다.

## ChatService 주입 확인과 JSON 변환 지원 코드

**요청:** ChatService를 넣었다.

사용자가 final ChatService 필드와 생성자 인자·대입을 올바르게 작성했다. 추가한 chatService.create() 호출은 방 ID·원문 토큰·본문 세 인자가 없으므로 아직 컴파일 오류다. 기존 요청 message를 바로 broadcast하는 줄도 남아 있어 서비스의 반환 결과로 바꿔야 한다. 사용자 작성 중인 Handler는 AI가 수정하지 않았다.

합의한 AI 지원 범위에서 ChatMessageCodec을 추가했다. decode(payload)는 JSON 객체의 문자열 content를 기존 MessageCreateRequest로 변환한다. 문법 오류·객체가 아닌 값·누락/문자열이 아닌 content·뒤에 이어진 두 번째 JSON은 400 상태의 ResponseStatusException으로 표현한다. 예외를 실제 WebSocket 오류 JSON으로 전송하는 Handler 지원은 후속 작업이다. 빈 본문·140자 등 비즈니스 검증은 ChatService에 유지한다. encode(saved)는 서버의 ChatMessage 결과를 기존 ChatMessageResponse와 TextMessage로 변환하며 문자열 따옴표·줄바꿈을 직접 조립하지 않는다.

프로젝트에 설치된 Jackson 3.1.5 API와 Spring Boot의 JsonMapper 자동 설정을 확인해 변환 클래스가 JsonMapper를 생성자 주입받도록 했다. HTTP @RequestBody와 달리 TextWebSocketHandler가 받은 문자열은 직접 변환해야 하며 요청 DTO의 @NotBlank도 이 경로에서 자동 실행되는 것은 아니다. 빈 본문 검증이 기존 Service에 있으므로 이 경계에서도 검증이 유지된다.

참고: [Spring Boot JSON 자동 설정](https://docs.spring.io/spring-boot/reference/features/json.html).

**검증:** 일반 ./gradlew test --tests com.breakground.chat.ChatMessageCodecTest 실행은 Handler 37줄의 인자 없는 create() 때문에 compileJava에서 실패했다. 테스트에는 도달하지 않았다. 이후 저장소 설정이나 Handler를 변경하지 않고, 임시 Gradle 초기화 스크립트로 이번 실행에서만 해당 Handler 소스를 제외해 JSON 변환 테스트 17개를 실행했다. 최신 XML 기준 실패·오류·건너뜀 0개다. 정상 JSON·숫자/배열 등의 잘못된 타입·잘못된 문법·후행 JSON·서비스 검증 경계·서버 응답 ID와 시각·따옴표/줄바꿈 보존을 확인했다. 임시 스크립트는 검증 후 삭제했다. 전체 프로젝트 컴파일, Spring Bean 주입 및 실제 채팅 연결 성공을 검증한 것은 아니다.

다음 사용자 작성 지점은 Codec을 생성자 주입하고 MessageCreateRequest request=codec.decode(payload)를 연결하는 것이다. 서비스에는 roomId, 핸드셰이크에서 전달할 rawToken, request.content()를 넘기고 반환된 ChatMessage를 encode해 방송해야 한다. rawToken 연결 속성을 넣는 핸드셰이크는 아직 없으므로 실제 접속 검증은 그 지원 코드와 함께 진행한다.

## 구현 지도 갱신과 요청 DTO 위치

**요청:** 전체 진도를 다시 인터랙티브하게 보여 달라. 작업 중 MessageCreateRequest 클래스가 없는 것 같다고 질문했다.

MessageCreateRequest는 src/main/java/com/breakground/chat/dto에 이미 있는 public record다. Handler의 com.breakground.chat과 DTO의 com.breakground.chat.dto는 다른 패키지이며 하위 패키지의 타입이 자동으로 import되는 것은 아니다. import com.breakground.chat.dto.MessageCreateRequest를 안내했고 사용자가 추가한 것을 확인했다. Codec 생성자 주입과 decode(payload) 연결도 사용자가 작성했다. 현재 create 호출에는 방 ID를 쓰기 시작했지만 토큰·본문 인자가 미완성이고 원래 요청을 방송하는 줄이 남아 있다.

진도 지도에는 JSON 변환 구현·단독 테스트 17개 통과, 최신 Handler 작성 상태, 확정된 핸드셰이크·종료·오류 정책을 반영했다. 종료·오류 처리와 실제 채팅 검증을 별도 항목으로 표시해 코드 구현·정책 합의·실행 검증을 구분했다. 브라우저에서 항목 선택과 상세 내용 변경 및 화면 배치를 확인했다. 코드 리뷰 시점의 상태를 표시했으며 이번 요청으로 Java 소스를 바꾸거나 테스트를 다시 실행하지 않았다.

## decode 다음은 저장 결과를 방송하기

**질문:** 이제 그다음 무엇을 해야 하는가?

최신 Handler는 Codec 주입·요청 DTO import·decode까지 작성되어 있다. create(roomId, )는 토큰과 본문 인자를 작성하는 중이며 원래 요청을 바로 방송하는 줄이 남아 있다. 다음 사용자 과제는 연결 속성에서 rawToken을 읽고 방 ID·토큰·request.content()로 서비스를 호출하여 반환된 ChatMessage를 변수로 받는 것이다. 그 결과를 Codec.encode로 TextMessage로 바꾸어 같은 방 Registry에 전달한다.

핸드셰이크가 roomId와 rawToken 연결 속성을 준비하는 내부 경계로 안내했다. rawToken은 서버가 접속 쿠키에서 읽을 값이며 메시지 JSON의 입력 필드가 아니다. 속성을 넣는 핸드셰이크는 AI 지원 범위로 아직 구현 전이라 지금 읽으면 null이며 실제 채팅 접속 성공은 아직 확인할 수 없다. Handler에서 원문 요청을 방송하면 서버가 생성한 UUID·작성자·시각과 DB 검증을 반영하지 못하므로 저장 결과를 방송해야 한다. 현재 Handler가 상위 트랜잭션 없이 주입된 Service 프록시를 호출하는 구성에서는 정상 반환 때 트랜잭션 커밋이 끝난 뒤 방송하도록 순서를 연결한다.

이번에는 사용자 작성 힌트와 다음 경계만 정리했다. Java 코드 변경·테스트 실행·새 정책 결정은 하지 않았다.

## ChatMessage를 TextMessage로 바꾸는 과정

**질문:** 방송은 TextMessage를 받는데 저장 결과는 ChatMessage다. 어떻게 바꾸는가?

사용자가 rawToken 속성 읽기, 요청 decode, 세 인자를 전달하는 ChatService.create, 반환값 ChatMessage saved까지 올바르게 작성했다. 현재 broadcast의 두 번째 인자를 작성하는 중이다.

이미 준비된 ChatMessageCodec.encode(saved)는 ChatMessage를 기존 응답 DTO로 옮기고 JsonMapper.writeValueAsString으로 JSON 문자열을 만든 뒤 new TextMessage(json)으로 전송 객체를 생성한다. 반환 타입이 TextMessage이므로 TextMessage response=chatMessageCodec.encode(saved)를 받고 registry.broadcast(roomId,response)에 전달하면 된다. ChatMessage 자체의 타입을 바꾸는 캐스팅이 아니라 같은 메시지 정보를 JSON으로 직렬화하여 새 전송 객체에 담는 과정이다.

ChatMessage에는 서버가 생성한 메시지 ID·작성자·본문·시각이 있고 TextMessage는 WebSocket으로 보낼 문자열을 담는다. 이 변환 경계는 앞서 Codec 단독 테스트에서 서버 정보와 따옴표·줄바꿈 보존까지 확인했다. 이번에는 타입 흐름 설명과 두 줄 힌트만 제공했고 Java 변경이나 새 테스트 작성·실행은 하지 않았다. TDD 새 테스트 경계는 따로 합의한 뒤 진행한다.

## handleTextMessage 전체 실행 순서

**질문:** 작성한 handleTextMessage의 모든 과정을 순서대로 설명해 달라.

사용자가 저장 결과의 encode와 broadcast까지 직접 작성한 것을 소스에서 확인했다. 아래는 핸드셰이크와 설정으로 접속이 준비된 상태를 가정한 흐름이다. 현재는 그 준비 코드가 아직 없다.

1. Spring이 해당 연결의 텍스트 메시지를 받으면 Handler 콜백을 호출한다. session은 계속 유지되는 연결, message는 이번에 받은 메시지다. void이므로 HTTP처럼 반환값으로 응답하지 않고 실제 소켓 전송을 호출한다.
2. session.attributes의 roomId를 읽는다. Map 값의 타입은 Object이므로 Integer로 캐스팅한다. 서버가 핸드셰이크에서 준비할 값이며 이 줄은 DB 조회를 하지 않는다.
3. message.getPayload()로 {"content":"안녕"} 전체 JSON 문자열을 읽는다. 아직 본문만 꺼낸 상태는 아니다.
4. attributes의 rawToken을 String으로 읽는다. 서버가 접속 쿠키에서 확보할 원문 토큰이며 요청 JSON에서 받지 않는다. 아직 속성을 넣는 코드가 없으므로 실제 현 상태의 Map에서는 null이 나온다.
5. Codec.decode가 JSON 문법과 content의 문자열 타입을 확인하고 MessageCreateRequest를 생성한다. request.content()는 "안녕"이다. 문법이나 구조 오류면 예외가 나고 서비스·방송으로 진행하지 않는다. DTO의 @NotBlank가 여기서 자동 실행되는 것은 아니며 본문 비즈니스 검증은 Service가 담당한다.
6. ChatService.create가 토큰의 SHA-256 해시로 익명 사용자를 조회하고 차단·비활성 만료를 검사한다. 사용자 방문 시각을 갱신하고 Room의 존재·운영 시간 및 본문의 공백·NUL·140자 제한을 확인한다. 신고 가능 기한과 원본 삭제 기한을 계산하여 JPA Message를 저장하고 결과를 ChatMessage record로 옮긴다. 방문 갱신과 INSERT는 같은 트랜잭션이다. Handler에서 상위 트랜잭션 없이 Spring Service 프록시를 호출하므로 정상 반환과 커밋이 끝나야 saved가 반환값을 받는다. save 호출 순간과 모든 SQL의 flush/커밋 완료 시점은 다를 수 있다.
7. Codec.encode가 saved를 응답 DTO, JSON 문자열, 새 TextMessage로 변환한다. 서버가 확정한 UUID·작성자·닉네임·본문·시각을 담으며 토큰은 응답에 포함하지 않는다. 이 줄은 추가 DB 저장을 하지 않는다.
8. Registry.broadcast가 메모리 Map에서 해당 방의 연결 Set을 찾아 열린 각 연결의 sendMessage를 호출한다. 작성자도 같은 Set에 등록되어 있으면 받으며 다른 방에는 보내지 않는다. 현재 Registry는 닫힌 연결이나 IOException으로 실패한 연결을 Set에서 제거하고 다른 연결 전송을 계속한다. 메서드가 끝난 뒤 화면에 표시하는 일은 프론트가 담당한다.

**실패와 경계:** 검증·저장·커밋이 실패하면 encode와 broadcast는 실행되지 않는다. 저장 커밋 후 encode 또는 소켓 전송이 실패해도 이미 커밋된 DB 행이 자동 취소되지는 않는다. throws Exception은 예외를 밖으로 전달하도록 선언할 뿐이며 오류 JSON 전송 코드는 별도로 필요하다. Registry 세션별 동시 전송 보호와 HandshakeInterceptor·Bean·URL 연결도 남아 있다.

참고: [Spring 트랜잭션 프록시](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html), [트랜잭션 전파](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html).

설명과 다음 상태 기록만 수행했다. Java 변경이나 테스트 실행은 하지 않았으며 실제 채팅 연결을 검증한 결과는 아니다.

## 핸드셰이크를 왜 해야 하는가?

**질문:** 핸드셰이크를 왜 해야 하는가?

WebSocket 프로토콜의 연결 협의와 프로젝트에서 추가하는 접속 검증을 구분했다. 현재 Spring 구성에서 브라우저의 WebSocket 접속은 HTTP 핸드셰이크 요청으로 시작하고 서버가 수락하면 WebSocket 통신으로 전환된다. 이 프로토콜 처리는 Spring과 서버가 담당하며 이미 Echo 접속에서도 수행됐다. 직접 프로토콜 협의 코드를 만드는 것이 아니다.

추가할 HandshakeInterceptor는 그 연결 협의 전에 실행하는 애플리케이션의 접속 검사다. 접속 URL의 Room이 존재하고 운영 중인지, 쿠키의 익명 사용자가 유효하고 차단되지 않았는지 확인한다. 통과한 연결에 roomId와 rawToken 속성을 준비한다. 실패하면 연결 수립을 거절하며 통과하면 연결 성공 콜백이 그 속성으로 Registry에 등록한다. 사용자 Handler는 이 속성을 읽는 쪽까지만 작성했으므로 현재 준비 코드가 없으면 값은 null이다.

즉 프로토콜의 핸드셰이크는 WebSocket 연결의 필수 과정이고 사용자 정의 Interceptor는 프로젝트 접속 정책과 연결 정보 전달을 위한 선택한 확장 지점이다. 접속 시 확인만으로 이후의 권한이 보장되지는 않는다. 방 종료·차단·사용자 만료가 연결 이후 발생할 수 있으므로 메시지 작성 때 기존 Service 검증을 유지한다.

참고: [Spring WebSocket 핸드셰이크와 Interceptor](https://docs.spring.io/spring-framework/reference/web/websocket/server.html), [HandshakeInterceptor API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/socket/server/HandshakeInterceptor.html).

현재 코드와 공식 문서를 확인해 설명했고 Java 코드 변경이나 테스트 실행은 하지 않았다.

## 핸드셰이크 TDD 시작 준비

**요청:** TDD로 핸드셰이크 구현을 시작하자.

TDD 스킬과 tests.md·mocking.md 및 GLOSSARY를 읽고 공개 경계를 먼저 합의하도록 질문했다. 추천 경계는 실제 WebSocket 접속이며 첫 행동은 쿠키 없는 /ws/rooms/1 접속을 HTTP 401로 거절하는 것이다. 대안은 Interceptor의 공개 메서드를 직접 검증하는 것이다. 경계 합의 전에는 테스트를 작성하지 않는다. 실제 경계를 선택하면 실패를 먼저 실행하고 최소 구현한 뒤, 유효한 쿠키로 운영 중인 방에 접속하는 다음 행동을 같은 경계에서 검증하는 방향으로 제안했다.

세션 시작 규칙에 따라 make를 실행했고 Docker 엔진과 PostgreSQL 컨테이너가 정상 실행 중임을 확인했다. 사용자 Handler를 포함한 ./gradlew compileJava도 BUILD SUCCESSFUL이다. 앞선 미완성 코드로 인한 컴파일 오류는 해결됐다. 테스트 실행과 실제 채팅 핸드셰이크 구현은 아직 시작하지 않았고 질문 답변을 기다리는 상태다.

## 실제 접속으로 핸드셰이크를 TDD 구현하기

**질문:** 어떻게 하라는 건지 모르겠다.

테스트 경계를 고른다는 설명을 더 구체적으로 바꿨다. "내가 실제 Spring 서버에 WebSocket으로 접속하는 테스트를 만들고, 쿠키가 없으면 401로 거절되는지부터 확인해도 될까?"라는 뜻이었다. 사용자가 진행에 동의했다. 테스트 경계는 실제 `/ws/rooms/{roomId}` 접속과 수신 응답이다. Interceptor 내부 호출 횟수나 private 메서드를 검사하지 않는다.

**구현 순서와 실패 증거:**

1. 쿠키 없는 접속의 기대값은 HTTP 401이었다. 첫 실행에서는 채팅 URL이 없어 404가 나왔고 테스트가 실패했다. 채팅 URL·공유 Registry/Handler Bean·Interceptor를 연결해 401로 거절하도록 한 뒤 통과했다.
2. HTTP `/anonymoususer`로 익명 쿠키를 준비한 사용자가 열린 방에 접속하고 메시지를 보내면, 서버 응답에 실제 방 ID·작성자 ID·본문이 있어야 한다. 당시 모든 접속을 거절하던 구현에서는 정상 접속도 실패했다. 쿠키 검증과 연결 속성 준비를 추가한 뒤 실제 메시지 왕복까지 통과했다.
3. 10:30에 닫히는 방은 정확히 10:30에 접속을 거절해야 한다. 처음에는 연결이 수락되어 테스트가 실패했다. Room 존재·운영 시간 검사를 추가한 뒤 HTTP 403으로 거절되어 통과했다.
4. 잘못된 토큰 401, 마지막 방문 후 정확히 7일인 사용자 401, 차단 사용자 403, 없는 방 404, 숫자가 아닌 방 번호 400도 실제 접속 경계에서 확인했다. 이 다섯 경우는 기존 검증을 재사용한 뒤 추가한 회귀 검증이며, 각각의 red 단계를 확인했다고 주장하지 않는다.

**왜 이제 Handler에서 roomId를 읽을 수 있나?**

`WebSocketConfiguration`이 채팅 URL에 `ChatHandshakeInterceptor`를 등록한다. Spring이 연결 전 `beforeHandshake`를 호출하면, Interceptor가 접속 주소에서 방 번호를 읽고 HTTP 쿠키에서 원문 토큰을 꺼낸다. 쿠키 누락을 확인하고 방 존재·운영 시간 검사, 기존 `AnonymousUserService.requireActiveUser`의 해시 조회·7일 만료·차단 검사를 통과해야 `attributes.put("roomId", roomId)`와 `attributes.put("rawToken", rawToken)`을 실행한다. Spring은 이 속성을 연결 세션으로 전달하고, 사용자가 작성한 `afterConnectionEstablished`가 해당 방의 공유 Registry에 연결을 등록한다.

실패 시 HTTP 상태를 설정하고 `false`를 반환하여 WebSocket 연결 전환을 거절한다. 통과하면 `true`를 반환한다. 원문 토큰을 DB나 메시지 응답에 추가하지 않으며, 핸드셰이크에서 새 익명 사용자를 생성하거나 쿠키를 갱신하지 않는다. 기존 Service 재사용으로 허용된 접속의 DB 방문 시각은 갱신된다. 잘못된 방·닫힌 방은 사용자 검증 호출 전에 거절하므로 방문 시각을 갱신하지 않는다.

Handler와 Registry에 `@Component`를 붙여 Spring이 공유 객체를 만들도록 했다. 설정에서는 Echo/Chat Handler 타입을 명시하여 두 Handler Bean 사이의 주입 모호성을 피했다. 사용자 Handler의 decode → create → encode → broadcast 성공 흐름은 유지했다. 새 채팅 경로에는 Origin 전체 허용을 추가하지 않았다.

**실행 검증:**

- `ChatWebSocketHandshakeTest`: 실제 Spring 랜덤 포트·PostgreSQL·JDK WebSocket 클라이언트로 8개 통과. 정상 접속은 HTTP 쿠키 발급부터 메시지 작성·응답 수신까지 확인했다.
- Echo·Codec·Registry와 함께 실행한 대상 테스트: 30개 통과. Codec도 Handler 제외 없이 정상 빌드에서 통과했다.
- 최종 `./gradlew test`: 전체 78개, 실패·오류·건너뛰기 0. Spring Bean 추가에 따른 기존 HTTP·JPA 기능 영향도 함께 확인했다.
- `git diff --check` 통과. 테스트용 메시지·방·사용자만 정리하고 소켓도 종료한다.

**아직 확인하거나 구현하지 않은 것:** 실제 두 클라이언트 사이의 방송, 세션별 동시 전송 보호, 연결 이후 오류 JSON, 운영 종료 시 기존 연결 안내·종료는 남아 있다. Registry 단위 테스트가 통과한 것과 이 실제 연결 동작이 완성된 것은 구분한다. 다음에는 같은 방의 두 클라이언트 수신을 확인하고, 동시 전송 보호를 작은 단계로 추가한다.

**읽어볼 포인트:** `beforeHandshake`의 `true`/`false`는 사용자 JSON 응답이 아니라 Spring에게 연결 전환을 진행할지 알려주는 값이다. `attributes.put` 두 줄과 Handler의 `session.getAttributes().get` 두 줄을 나란히 읽으면 정보가 어디서 들어와 어디서 사용되는지 연결된다.

## 실제 두 사용자 방송·방 분리·재접속 검증

**요청:** 계속 테스트를 진행해 달라.

세션 시작 스킬에 따라 make로 PostgreSQL 실행 상태를 확인했고 같은 날짜의 devlog를 이어 썼다. 앞서 합의한 실제 WebSocket 접속·수신 경계에서 `ChatWebSocketBroadcastTest`를 추가했다. 내부 Registry나 ChatService를 모의 객체로 바꾸지 않고 실제 Spring 랜덤 포트와 PostgreSQL, JDK WebSocket 클라이언트를 사용했다. 테스트 하나를 추가하고 실행한 뒤 다음 행동을 추가했다. 세 테스트 모두 기존 구현에서 바로 통과했으므로 이번 작업은 red 단계를 확인한 새 기능 구현이 아니라 회귀 검증이다. 서버 코드는 변경하지 않았다.

1. **같은 방의 두 사용자:** Alice와 Bob이 각각 HTTP 익명 사용자 API에서 다른 쿠키를 발급받고 같은 방에 접속한다. Alice의 메시지를 두 연결이 받아 동일한 서버 UUID·작성자·닉네임·본문으로 전달되는지 확인했다. Bob이 수신한 메시지의 작성자는 Alice여야 하므로 단순 Echo와 구분된다.
2. **다른 방의 수신 분리:** A방에 Alice·Bob, B방에 Carol을 연결했다. A방의 두 연결이 A 메시지를 받은 뒤 B방도 자신의 메시지를 정상 수신하는지 확인했다. 각 연결의 정상 응답을 소비한 뒤 500ms씩 추가 메시지나 연결 오류가 없는지도 확인했다. 따라서 연결이 끊겨 못 받은 것을 방 분리 성공으로 오인하지 않는다. 미수신 검증은 이 관찰 시간 내의 결과이며 임의로 오래 지연된 전달까지 증명하지는 않는다.
3. **종료 후 재접속:** Bob이 정상 Close 프레임으로 종료하고 서버의 Close 응답을 받은 뒤 같은 쿠키로 다시 접속한다. 계속 연결된 Alice와 새 Bob 연결이 새 메시지를 함께 받는지 확인했다. 내부 Set에서 종료된 연결이 제거되는 정확한 순간을 검사하는 테스트는 아니다.

**테스트 클라이언트의 역할:** Listener는 onText의 문자열 조각을 모아 마지막 조각에서 하나의 JSON을 큐에 넣고, 다음 메시지 수신을 요청한다. 오류·예상하지 않은 종료도 큐에 담아 테스트가 실패하도록 한다. 접속·전송·수신·종료 대기는 각각 3초로 제한했다. 연결 직후 Ping/Pong 왕복을 확인한 뒤 본문을 보내며, 종료 시 소켓과 해당 테스트가 생성한 DB 데이터만 정리한다. HTTP 익명 사용자 생성은 시스템 시간을 쓰고 채팅은 주입된 Clock을 쓰므로 준비 데이터의 방문 시각을 고정 테스트 시각에 맞췄다.

**실행 결과:** 새 방송 테스트를 하나씩 추가한 실행에서 1개 → 2개 → 3개가 통과했다. 최종 `./gradlew test`는 전체 81개 통과, 실패·오류·건너뛰기 0이다. `git diff --check`도 통과했다.

**다음에 생각할 점:** 두 사람이 접속해 한 명이 보낸 메시지를 함께 받는 것과, 두 사람이 동시에 메시지를 보내는 것은 다른 상황이다. 두 방송이 같은 수신 연결의 sendMessage를 동시에 호출할 수 있으므로 세션별 전송 보호는 별도 검증·구현으로 남아 있다. 연결 후 오류 JSON과 운영 종료 안내·연결 종료도 아직 남아 있다.

## 동시 전송 문제를 고치는 첫 TDD 단계

**질문:** 리뷰에서 발견한 문제를 TDD로 어떻게 고치나?

직전 review-agent 검토는 읽기 전용이라 파일을 수정하지 않았다. 기존 전체 테스트 81개를 캐시 없이 다시 실행해 통과했고, 파일을 만들지 않는 Java 메모리 실행으로 두 문제를 재현했다. 실제 Registry와 전송이 겹치면 거절하는 모의 WebSocketSession에서 동시 호출·IllegalStateException을 확인했다. 실제 Handler·Codec과 Spring ExceptionWebSocketHandlerDecorator에 잘못된 JSON을 전달했을 때 오류 메시지는 0건, 연결 종료 코드는 1011이었다. 실제 네트워크 동시 부하 검증과 구분한다.

이번 TDD 단계는 먼저 동시 전송 하나로 제한했다. 이전에 사용자와 합의한 Registry의 공개 register/broadcast 경계를 그대로 사용한다. AI는 `concurrentBroadcastsDeliverBothMessagesWithoutOverlappingSends` 테스트를 추가하고, 사용자가 서버 코드를 먼저 고칠 수 있도록 힌트를 제공했다. 입력 오류 테스트를 한꺼번에 추가하지 않았다.

**Red 증거:** 첫 방송의 소켓 전송을 latch로 붙잡아 둔 동안 두 번째 스레드가 같은 방으로 방송한다. 외부 전송 경계인 모의 소켓은 중첩 전송을 실제 컨테이너처럼 거절한다. 전송 해제 후 두 Future가 성공하고 두 본문이 모두 전달되어야 한다. 전송을 관찰하는 테스트이며 내부 Map이나 잠금 구현을 검사하지 않는다. 현재 구현으로 단일 테스트를 실행하니 두 번째 Future에서 `ExecutionException → IllegalStateException: 동일한 연결에 전송이 겹쳤습니다.`로 실패했다. 아직 서버 코드 수정이나 green 검증은 하지 않았다.

**사용자가 고칠 위치와 이유:** `RoomSessionRegistry.broadcast`의 try 안에서 isOpen 검사·sendMessage·닫힌 연결 제거 구간을 `synchronized (s)`로 감싼다. 각 연결 객체의 모니터를 사용하므로 같은 s를 대상으로 하는 두 방송 중 하나가 전송 중이면 다른 방송은 잠금 해제를 기다린다. 보호할 대상은 공유 Map 구조가 아니라 소켓의 전송 동작이다. 이미 등록한 세션 객체를 그대로 사용하므로 이번 최소 수정에서는 컬렉션·등록/제거 방식·Handler·Service·DB를 변경할 필요가 없다. 기존 IOException 처리도 유지한다.

`synchronized`는 DB 트랜잭션이나 스레드 생성 기능이 아니다. JVM 안에서 같은 모니터를 쓰는 코드 구간에 동시에 진입하지 못하게 한다. 추후 입력 오류 응답을 직접 전송할 때에도 같은 세션의 전송 보호를 공유해야 한다. 느린 연결의 대기 시간·버퍼 한도까지 관리하는 Spring ConcurrentWebSocketSessionDecorator는 후속 개선 후보이며 이번 힌트에는 새 제한 정책을 추가하지 않았다.

**다음 순서:** 사용자가 잠금 구간을 작성하면 새 동시 방송 테스트와 기존 Registry 테스트를 실행한다. 통과 후에 입력 오류를 보낸 연결만 JSON 안내받고 같은 연결로 정상 메시지를 다시 보낼 수 있는 다음 테스트로 넘어간다. 가장 최근 전체 81개 통과는 새 red 테스트 추가 전의 결과다.

## 테스트를 위임하고 연결 후 오류 처리를 완성하기

**요청:** 서브에이전트에게 테스트를 맡기고, 다음 고칠 부분에 집중한다. 수정이 끝나면 Git에 커밋한다.

단일 서브에이전트가 기준 커밋 `8b0883d2cafab2bed8844a49d392dc16a48494d8` 이후 staged·unstaged·untracked 변경을 읽기 전용으로 검토하고 테스트했다. 사용자가 Registry에 넣은 `synchronized (s)` 덕분에 동시 방송 테스트를 포함해 전체 82개가 통과했다. 남은 지적은 Handler의 `decode/create`에서 발생하는 `ResponseStatusException`이 처리되지 않아, 잘못된 입력도 오류 JSON 없이 1011로 연결이 닫힌다는 것이었다.

**입력 오류의 red → green:** 실제 WebSocket 경계에 잘못된 JSON·공백 본문·141자 입력 테스트를 추가했다. 세 경우 모두 오류 JSON 대신 1011 종료를 받아 먼저 실패했다. Handler에서 예상한 검증 예외를 잡고, Codec이 `{"type":"ERROR","status":400,"message":"..."}`를 만들도록 수정하니 세 테스트가 통과했다. 오류는 보낸 연결만 받고 다른 연결에는 전달되지 않는다. 같은 연결에서 재입력한 정상 메시지는 두 사용자가 함께 받았다.

**종료 오류의 red → green:** 접속 이후 방문 시각을 7일 전으로 바꾸거나 차단 상태를 설정하거나 방 종료 시각으로 Clock을 옮기는 테스트를 추가했다. 오류 JSON은 받았지만 연결이 계속 열려 있어 종료 대기에서 세 경우 모두 실패했다. 입력 오류인 400은 재입력할 수 있게 유지하고, 만료 401·차단/방 종료 403은 안내 후 방송 목록에서 제거하고 WebSocket 종료 코드 1008로 닫도록 수정했다. 세 테스트가 통과했고 안내는 다른 연결에 방송되지 않았다.

**try/finally와 잠금의 역할:** 정상 메시지는 기존 서비스 검증과 DB 트랜잭션이 성공한 뒤 방송한다. 오류 응답은 해당 연결에 직접 보내므로 방송과 동일한 `session` 모니터를 잠가 서로 전송이 겹치지 않게 한다. 종료가 필요한 오류라면 안내 전송이 실패해도 `finally`에서 방송 목록 제거와 종료를 시도한다. 예상한 `ResponseStatusException`만 처리하며 예상하지 못한 서버 오류는 Spring의 기본 오류 처리에 맡긴다. JSON의 status는 오류 분류값이지 WebSocket 연결 안에서 HTTP 400 응답을 보내는 것은 아니다.

**검증 결과:** 동일한 서브에이전트가 수정 후 `./gradlew test --rerun-tasks`를 실행해 전체 88개 통과, 실패·오류·건너뛰기 0을 확인했다. 최종 코드 리뷰는 Standards 0건·Spec 0건의 actionable 지적이며 `git diff --check`도 통과했다. 새 테스트는 공개 네트워크 동작을 확인한다. 오류 안내 전송 실패와 방송/오류 응답의 혼합 동시 전송은 이번에 별도 실행 테스트를 추가하지 않았으며 같은 세션 잠금을 쓰는 코드를 검토했다.

**다음 학습 지점:** 현재 운영 종료 처리는 사용자가 메시지를 보낼 때 적용된다. 아무 메시지도 보내지 않는 연결도 방 종료 시 자동으로 안내·종료하는 것은 다음 단계다. 느린 수신자에 대한 전송 시간·버퍼 제한도 아직 구현하지 않았다. `finally`가 안내 실패 시에도 필요한 이유를 먼저 코드에서 확인해보자.

## Wayfinder로 유휴 연결의 방 종료를 설계하기

**요청:** 다음 단계로 나아가자.

작업 재개 흐름으로 `make`를 실행해 PostgreSQL이 실행 중임을 확인하고 오늘 파일을 이어 썼다. wayfinder·grilling·domain-modeling을 적용해 다음 결정인 ‘방 운영 종료 감지와 연결 종료 시점’을 기존 로컬 지도에 연결하고 담당했다. 아직 구현은 하지 않는다.

방 자체와 한 번의 운영 구간을 구분했다. 같은 Room도 다음 날 다시 열리므로 다음 운영 시간에 `isOpen(now)`만 확인하면 이전 구간부터 남아 있던 연결을 놓칠 수 있다. 기존 `currentClosingTime`은 날짜가 포함된 종료 시각을 계산하지만 핸드셰이크는 아직 이를 연결에 보관하지 않는다. 이 값과 주입 Clock, 기존 세션별 전송 잠금을 재사용하는 방향을 제안했다.

**미확정 질문:** 종료 대상 연결을 1초마다 확인해 안내·종료할지, 종료 직전에 수락한 메시지가 종료 후 커밋되면 전달을 기다릴지 확인한다. 추천은 1초 검사와 종료 우선이며 사용자 답변을 기다린다. 검사 주기는 엄격한 최대 지연 보장이 아니며, 종료 이후 새 메시지의 거절은 기존 Service의 운영 시간 검증을 유지한다. DB 메시지 삭제는 기존 운영 종료+10분 정책과 별개다.

테스트는 이번 설계 단계에서 다시 실행하지 않았다. 직전 전체 88개 통과 결과를 유지하며 Java·DB 변경은 없다.

**Q1 — 방 종료를 1초마다 확인할까?** 사용자 답변은 ‘1초 주기’였다. 다음 검사에서 안내·종료하되 부하로 인한 지연까지 엄격히 1초로 보장하는 정책은 아니다. 새 메시지 작성 거절은 기존 서비스 검증으로 유지한다.

**Q2 — 종료 직전 수락한 메시지의 커밋이 늦으면 전달을 기다릴까?** 사용자 답변은 ‘방 종료 우선’이었다. 저장이 성공해도 닫힌 구간의 연결에는 실시간 전달되지 않을 수 있다. 방송 직전에도 같은 세션 잠금 안에서 종료 시각을 확인해야 다음 주기 전의 틈에 새 전송이 시작되지 않는다. 이미 전송을 시작한 프레임을 회수한다는 의미는 아니다.

결정 티켓을 해결하고 지도·decisions·NEXT를 갱신했다. 다음 사용자 과제는 기존 ChatHandshakeInterceptor에서 `closesAt` 연결 속성을 준비하는 것이다. 값은 Room의 열린 운영 구간을 기준으로 계산하며 LocalDateTime이다. roomId는 방 자체를 식별하고 closesAt은 그 연결이 참여한 구간의 종료 기한을 나타낸다. 새로운 DB 컬럼은 필요하지 않다.

## closesAt은 try와 catch 중 어디에 넣는가?

**질문:** 왜 catch문 안에 넣는가?

앞서 AI가 준 파일 링크가 catch 시작 줄을 가리켜 혼동을 만들었다. 정정하면 closesAt 준비는 정상 접속 흐름인 try 안에서 roomId/rawToken과 함께 넣으며 return true 직전이다. catch 안에 넣는 작업이 아니다. 현재 저장된 소스에는 closesAt이 아직 없다.

try에서는 쿠키·방 운영·사용자 상태를 검증하고 통과하면 연결 속성을 준비한다. 검증 과정에서 예외가 발생하면 남은 try 코드를 건너뛰고 해당 catch로 이동한다. catch는 HTTP 오류 상태를 지정하고 false를 반환해 핸드셰이크를 거절한다. 실패한 연결에 정상 접속용 종료 시각을 준비할 이유가 없다. room과 now는 try 블록 안의 지역 변수이므로 catch에서는 직접 사용할 수도 없다.

사용자가 추가할 줄의 값은 기존 room.currentClosingTime(now)이며 LocalDateTime이다. Java 소스나 테스트를 대신 수정하지 않았고 이번 설명 때문에 테스트를 다시 실행하지 않았다.

## closesAt 작성 확인과 Registry 종료 테스트의 red

사용자가 ChatHandshakeInterceptor의 정상 접속 경로에 `attributes.put("closesAt", room.currentClosingTime(now))`를 작성했다. roomId/rawToken 준비 뒤, return true 앞에 있어 위치와 반환 타입이 맞다. 같은 서브에이전트가 기존 핸드셰이크 테스트만 실행해 8개 통과를 확인했다. 이 기존 테스트들은 새 속성이나 유휴 연결 종료를 직접 검증하지 않는다.

다음은 이전에 합의한 Registry 공개 메서드 경계의 첫 종료 행동으로 제한했다. AI가 `closeExpiredSessions(LocalDateTime now, TextMessage notice)`의 빈 틀만 준비하고, 정확히 종료 시각에 호출하면 해당 연결에 안내를 보낸 다음 코드 1008로 닫는 테스트 하나를 추가했다. 실제 Registry와 외부 전송 경계인 모의 WebSocketSession을 사용하며 내부 Map 내용이나 잠금 구현을 검사하지 않는다.

**실행 결과:** 서브에이전트가 `./gradlew test --tests 'com.breakground.chat.RoomSessionRegistryTest.notifiesThenClosesConnectionExactlyAtItsOperatingPeriodEnd'`를 실행했다. 컴파일은 성공했지만 안내 전송이 호출되지 않아 WantedButNotInvoked로 1개 실패했다. 의도한 red이며 종료 메서드의 핵심 로직은 아직 없다. 전체 88개 통과는 이 테스트 추가 전의 결과다.

**사용자 작성 힌트:** Map의 entrySet에서 방 ID와 연결 목록을 꺼내고 각 연결의 closesAt 속성을 LocalDateTime으로 읽는다. `!now.isBefore(closesAt)`로 정각 포함 종료를 판단한다. 대상 연결의 모니터를 잠가 안내·등록 해제·close를 처리하며, 전송 실패가 다른 연결의 종료를 막지 않도록 연결마다 오류를 처리한다. 목록 정리·실패·종료 전 유지와 실제 스케줄링은 첫 행동이 통과한 뒤 하나씩 검증한다.

## 종료 메서드가 어려울 때 순회부터 나누기

**질문:** 이건 좀 어렵다.

현재 사용자 코드는 closeExpiredSessions 안에서 roomSetMap.entrySet()까지 작성했다. 이 호출은 방 ID와 연결 목록의 쌍들을 반환하지만, 반환값을 사용하지 않으면 연결을 순회하거나 종료하지 않는다. 앞선 과제에 Map/Set 순회·시간 비교·잠금·전송 오류 처리를 한꺼번에 넣어 부담이 컸으므로 순회 단계부터 나눴다.

Map의 한 entry에서 getKey()는 Integer 방 ID, getValue()는 Set<WebSocketSession> 연결 목록이다. 바깥 반복문은 방별 묶음을, 안쪽 반복문은 그 방의 연결을 하나씩 꺼낸다. var는 이때 entry의 타입을 컴파일러가 추론하게 하는 Java 문법이다.

전체 종료 구현 대신 이중 반복문과 지역 변수만 작은 예제로 설명했다. 이번 사용자 과제는 반복문을 작성하는 데까지다. 그 다음 안쪽에서 closesAt을 읽고 종료 여부를 판단한다. 같은 종료 행동의 red → green 과정 안에서 구현을 나눈 것이며 새 테스트나 리팩터링을 추가하지 않았다. Java 소스 수정과 테스트 실행은 하지 않았다.

## session에서 종료 시각을 읽는 방법

**질문:** session에서 closeat을 어떻게 바꾸는가?

사용자는 방·연결 이중 반복문을 작성했고 안쪽에 s.close()를 쓰는 중이었다. close는 종료 시각을 바꾸는 메서드가 아니라 WebSocket 연결 자체를 닫는 메서드다. 현재 단계는 핸드셰이크에서 저장한 종료 시각을 먼저 읽는 것이다.

`LocalDateTime closesAt = (LocalDateTime) s.getAttributes().get("closesAt");`로 꺼낸다. 키는 저장할 때 사용한 closesAt과 정확히 같아야 한다. 연결 속성은 Map<String, Object>로 여러 타입을 담으므로 get의 반환 타입은 Object이고, 실제 저장된 LocalDateTime 타입으로 캐스팅한다. 문자열을 날짜로 파싱하는 과정이 아니다. Room의 매일 종료 시간과 달리 이 값은 날짜까지 포함해 그 연결의 운영 구간을 구분한다.

이번에는 s.close() 줄을 종료 시각 읽기로 바꾸고 다음 단계에서 now와 비교하도록 안내했다. 연결 종료와 예외 처리는 그 뒤에 붙인다. 사용자 Java 코드는 수정하지 않았고 미완성 메서드 상태에서 테스트를 재실행하지 않았다.

## 종료 대상 판정과 CloseStatus 사용

**Q1 — 종료 대상임을 어떻게 표기하는가?** 사용자가 작성한 `if (!now.isBefore(closesAt))`가 이미 종료 대상을 판정한다. 종료 시각보다 이전이면 false, 정확히 같거나 이후이면 true다. 이번 흐름에서는 해당 조건문 안에서 바로 처리하므로 별도 DB 상태나 종료 대상 필드를 추가할 필요가 없다. 읽기 쉬운 이름이 필요하면 이 판정 결과를 지역 boolean 변수에 담을 수 있다.

**Q2 — close(CloseStatus.POLICY_VIOLATION)는 어떻게 쓰는가?** CloseStatus를 import하고 현재 연결 변수인 s에 `s.close(CloseStatus.POLICY_VIOLATION)`를 호출한다. 정책에 따른 종료 코드 1008로 연결 종료를 요청하는 API다. 호출에 전달하는 값은 종료 시각이 아니라 종료 사유 코드다.

현재 사용자의 `s.sendMessage()`는 인자가 없어 미완성이다. 메서드 인자로 받은 TextMessage notice를 전달한다. 정상 흐름은 안내 전송 → 등록 해제 → 정책 코드로 연결 종료다. sendMessage와 close에는 checked IOException 처리가 필요하므로 기존 방송처럼 연결별로 처리해야 한다. 안내 실패 시에도 등록 해제·종료를 시도하는 finally 구성은 다음 작성·리뷰 단계에서 함께 확인한다. AI는 소스를 수정하거나 테스트를 재실행하지 않았다.

## 종료 구현 리뷰와 finally의 배치

**요청:** 작성한 종료 로직을 검토하고, 괜찮으면 테스트를 진행한다. 모두 통과하면 커밋·푸시하고 WebSocket 완료 여부도 확인한다.

같은 서브에이전트가 HEAD 이후 staged·unstaged·untracked 변경을 읽기 전용으로 검토했다. 종료 시각 속성 준비와 비교 조건은 맞지만 sendMessage/close의 checked IOException을 처리하지 않아 컴파일이 실패한다(P1). 안내 전송이 실패하면 뒤의 등록 해제와 종료를 건너뛰는 흐름도 수정해야 한다(P2). 단순히 메서드에 throws IOException을 붙이면 한 연결의 실패가 다른 연결 처리를 중단시킬 수 있다.

**검증:** `./gradlew test --tests 'com.breakground.chat.RoomSessionRegistryTest'`는 compileJava에서 IOException 미처리 오류 2개로 중단됐다. 테스트 실행 0개이며 전체 테스트를 실행하지 않았다. 이는 앞서 빈 메서드에서 관찰한 assertion red와 구분해야 한다. 검증 통과 조건이 충족되지 않아 이번 커밋·푸시는 수행하지 않았다.

**질문:** finally를 어떻게 써야 할지 고민해보자.

정리 작업을 안내 전송 성공 여부와 분리한다. 세션 잠금 안의 try에서 열린 연결에 안내를 보내고, finally에서는 먼저 등록 해제한 뒤 연결이 열려 있으면 close를 시도한다. 바깥 try/catch는 안내 전송과 finally의 close에서 발생하는 IOException을 모두 잡아 한 연결의 실패가 다른 연결 처리까지 중단시키지 않도록 한다. 같은 try의 catch는 finally 자체에서 발생한 예외를 잡지 않으므로 바깥 catch 위치가 중요하다.

정상 흐름은 안내 → finally의 등록 해제/종료다. 안내가 예외를 던지면 finally 정리를 시도한 후 바깥 catch로 이동한다. already-closed 연결에는 안내를 보내지 않고 목록 정리만 한다. 전체 메서드를 대신 작성하지 않고 현재 synchronized 구간을 감싸는 작은 구조를 설명했다. Java 소스는 수정하지 않았다.

**WebSocket 남은 부분:** 기존 접속 검증·DB 커밋 후 방송·입력 오류와 메시지 작성 시 만료/차단/방 종료 처리는 구현돼 있다. closeExpiredSessions를 호출하는 1초 스케줄러, 방송 직전 운영 구간 종료 검사, 실제 유휴 연결 자동 종료 검증은 아직 없다. Registry 종료 테스트 하나의 통과만으로 전체 WebSocket 완료라고 할 수 없다.

## 종료 실패 로그와 green 확인

**요청:** 로그 기록은 AI가 코드로 작성하고 다음으로 진행한다.

사용자가 연결별 try/catch와 synchronized 안의 try/finally를 작성했다. AI는 정책과 정리 흐름을 바꾸지 않고 SLF4J LoggerFactory로 Logger를 만들고 비어 있던 catch에 WARN 로그를 추가했다. 로그는 roomId·WebSocket sessionId·IOException을 기록하며 쿠키 원문 토큰이나 메시지 본문을 인자로 넣지 않는다. `{}`는 로그 값의 자리표시자이고 마지막 예외 인자는 스택 추적을 남긴다.

같은 읽기 전용 서브에이전트가 HEAD 이후 변경을 재검토했다. IOException 컴파일 오류와 안내 실패 시 정리 누락은 사용자 구현으로 해결됐다. 최종 리뷰는 actionable 지적 없음이다. Registry 테스트는 6개 통과했고, `./gradlew test --rerun-tasks`는 전체 89개 통과·실패/오류/건너뛰기 0이다. Gradle 작업 네 개 모두 새로 실행했다. `git diff --check`도 통과했다.

새 테스트는 Registry를 직접 호출하여 정각에 안내를 먼저 보내고 정책 종료 코드로 닫는 정상 흐름을 확인한다. 종료 전 유지, 안내 전송 실패 시 정리·다른 연결 처리, 종료 후 방송 제외는 아직 별도 종료 테스트로 검증하지 않았다. 자동 호출·방송 직전 종료 검사·실제 유휴 연결 종료 검증도 남아 있다. 이번 green은 Registry 첫 종료 행동의 완료이며 WebSocket 전체 완료가 아니다.

검증 통과 조건을 충족하여 요청된 커밋·푸시를 진행한다. 다음 학습 지점은 기존 MessageCleanup처럼 주입 Clock과 스케줄링을 사용해 종료 메서드를 1초마다 호출하는 작은 컴포넌트다.

## RoomConnectionCloser에 @Component를 붙이는 이유

**질문:** @Component는 왜 넣고, 왜 RoomConnectionCloser에 붙이는가?

@Component는 이 클래스의 객체를 Spring이 생성하고 관리하도록 표시하는 어노테이션이다. Spring이 관리하는 객체를 빈(bean)이라고 한다. 프로젝트의 시작 클래스는 com.breakground에 있고 @SpringBootApplication의 컴포넌트 스캔이 그 아래 패키지를 탐색하므로 com.breakground.chat의 RoomConnectionCloser도 등록 대상이 된다.

이 클래스는 운영 구간이 끝난 연결을 주기적으로 정리할 담당자다. 생성자에 RoomSessionRegistry·ChatMessageCodec·Clock을 받도록 작성하면 Spring이 기존 빈을 주입할 수 있다. 특히 Registry를 직접 새로 만들지 않고 현재 Handler가 사용하는 공유 빈을 받아야 실제 등록된 연결 목록을 대상으로 정리할 수 있다. @Component만 붙이면 아직 정기 실행은 하지 않는다.

역할을 구분하면 클래스의 @Component는 빈 등록, 기존 ChatConfiguration의 @EnableScheduling은 정기 실행 기능 활성화, 앞으로 메서드에 붙일 @Scheduled는 실행 주기 지정이다. Spring의 스케줄링 처리는 관리되는 빈의 메서드를 대상으로 적용된다. 현재 파일은 빈으로 등록할 빈 클래스만 작성된 상태다.

@Service도 @Component를 포함하므로 빈 등록은 가능하다. 여기서는 주기적으로 연결 정리를 호출하는 보조 컴포넌트라는 역할을 나타내기 위해 일반 @Component를 선택했다. 모든 Java 클래스에 필요한 어노테이션은 아니며 @Bean 등 다른 등록 방법도 있다.

참고: [Spring 컴포넌트 스캔](https://docs.spring.io/spring-framework/reference/core/beans/classpath-scanning.html), [Spring 스케줄링](https://docs.spring.io/spring-framework/reference/integration/scheduling.html), [Spring Boot 시작 어노테이션](https://docs.spring.io/spring-boot/reference/using/using-the-springbootapplication-annotation.html).

이번 작업은 설명과 devlog 기록만 수행했다. Java 소스 수정이나 테스트 실행은 하지 않았다.

## @Component와 생성자 주입은 다른 역할

**질문:** 여기서는 왜 생성자 주입이나 @Autowired를 사용하지 않고 @Component를 사용하는가?

둘은 대체 관계가 아니다. @Component는 RoomConnectionCloser 자체를 Spring의 관리 대상으로 등록하는 표시이고, 생성자 주입은 그 객체가 필요한 Registry·Codec·Clock 등의 다른 빈을 전달받는 방식이다. 현재 클래스가 비어 있어 생성자 주입을 아직 작성하지 않은 것이며, 다음 단계에서 @Component와 생성자 주입을 함께 사용한다.

작은 예제로 @Component가 붙은 클래스에 final RoomSessionRegistry 필드와 그 값을 받는 생성자를 보여줬다. Spring은 클래스를 발견한 뒤 생성자 인자에 맞는 기존 Registry 빈을 찾아 전달하고 RoomConnectionCloser를 생성한다. 생성자가 하나이면 @Autowired를 생략해도 주입되며, @Autowired 자체가 클래스를 빈으로 등록하는 것은 아니다.

참고: [Spring @Autowired와 단일 생성자 규칙](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html). 이번에는 개념과 예제만 설명하고 사용자 Java 파일을 수정하거나 테스트하지 않았다.

## 등록과 주입을 다시 구분하고 Clock 타입 이해하기

**질문:** 언제 @Component, @Autowired, 생성자 주입을 쓰는지 아직 헷갈린다. Clock은 LocalDateTime 타입인가?

세 가지를 서로 대체하는 선택지로 보지 않는다. @Component는 클래스를 스캔해 Spring 관리 대상으로 등록하는 표시다. 생성자 주입은 그 관리 객체를 만들 때 필요한 다른 객체를 생성자 인자로 받는 방식이다. @Autowired는 주입 지점을 표시하는 어노테이션으로 생성자에도 붙일 수 있지만, 생성자가 하나이면 생략 가능하다. 현재 프로젝트에서는 @Component(또는 역할에 맞는 @Service/@RestController)로 등록하고 필요한 객체는 생성자에서 받는 패턴을 사용한다. @Autowired만 붙인다고 클래스 자체가 등록되지는 않는다.

Clock의 타입은 java.time.Clock이며 LocalDateTime이 아니다. Clock은 현재 시각을 얻는 기준과 시간대를 제공하고, LocalDateTime은 날짜·시간 값을 나타낸다. 따라서 필드는 private final Clock clock이고 생성자에서도 Clock을 받는다. LocalDateTime.now(clock)을 호출하면 그 시계 기준의 날짜·시간 값이 반환된다. 기존 ChatConfiguration의 applicationClock()이 서울 시간대 Clock 빈을 등록하므로 생성자에 해당 빈을 주입할 수 있다. 테스트에서는 고정 Clock을 전달해 운영 종료 정각을 재현할 수 있다.

설명용 예제에서는 @Component가 붙은 RoomConnectionCloser가 생성자에서 Clock을 받는 모습을 함께 보여줬다. Java 소스는 사용자 작성 중인 상태 그대로 두었고 테스트는 실행하지 않았다.

## 생성자 준비 후 다음 TDD 과제

**질문:** 이제 해야 할 일은 무엇인가?

RoomConnectionCloser에서 Registry·Codec·Clock의 final 필드와 생성자 대입까지 작성된 것을 확인했다. 다음 동작 하나는 메시지를 보내지 않는 연결도 운영 구간 종료 시각에 안내 후 자동 종료되는 것이다. 기존 Registry 종료 테스트는 closeExpiredSessions를 직접 호출하기 때문에 실제 정기 실행까지 증명하지 않는다.

테스트 경계는 이전에 사용자와 합의한 실제 WebSocket 접속·수신 경계를 이어서 사용한다. ChatWebSocketBroadcastTest의 기존 연결 도우미와 MutableClock을 재사용해 열린 방에 접속하고, Clock을 종료 정각으로 옮기되 메시지는 전송하지 않는다. 제한시간 안에 방 종료 오류 JSON과 종료 코드 1008을 받는지 확인하는 테스트 하나가 다음 red 대상이다. 내부 Registry 호출 횟수나 Spring 어노테이션 유무를 검증하는 테스트로 대체하지 않는다.

red를 확인한 뒤 사용자가 RoomConnectionCloser에 인자와 반환값이 없는 public void 메서드를 작성하고 1초 간격 @Scheduled를 붙인다. 메서드의 흐름은 LocalDateTime.now(clock)으로 현재 시각 읽기 → 기존 Codec의 encodeError로 방 종료 안내 만들기 → Registry.closeExpiredSessions(now, notice) 호출이다. 새 DB 변경이나 트랜잭션은 필요하지 않다. 종료 전 유지·전송 실패·늦은 방송 차단은 이 첫 동작이 통과한 뒤 별도 작은 단계로 진행한다.

이번 답변은 현재 코드 확인과 다음 과제 안내다. 새 테스트나 Java 메서드는 작성하지 않았으며 실행 결과도 새로 주장하지 않는다.

## RoomConnectionCloser 작성 리뷰와 컴파일 검증

**요청:** 작성한 코드가 맞는지 검토하고 테스트를 시작한다.

기존 동일 서브에이전트가 HEAD 이후 staged·unstaged·untracked 변경을 읽기 전용으로 리뷰하고 관련 테스트를 실행했다. RoomConnectionCloser의 @Component, 공유 Registry·Codec·Clock 생성자 주입, fixedDelay 1000의 연결은 이번 과제에 맞다. 다만 28번째 줄에서 encodeError에 문자열을 전달해 컴파일이 실패한다(P1). ChatMessageCodec.encodeError의 매개변수 타입은 ResponseStatusException이며 문자열이 아니다.

수정 힌트는 HttpStatus.FORBIDDEN과 방 종료 문구를 담은 ResponseStatusException 객체를 만들어 encodeError에 전달하는 것이다. 여기서는 예외를 throw하는 것이 아니라 기존 오류 JSON 변환 메서드의 입력값으로 전달한다. WebSocket 안내 JSON의 status 403을 만드는 것이며 이미 열린 연결에 새 HTTP 403 응답을 전송하는 의미는 아니다. 실제 연결 종료는 Registry가 수행한다.

**검증:** `./gradlew test --tests 'com.breakground.chat.RoomSessionRegistryTest' --tests 'com.breakground.chat.ChatWebSocketBroadcastTest'`가 compileJava에서 String을 ResponseStatusException으로 변환할 수 없다는 오류 1개로 중단됐다. 테스트 실행은 0개이며 전체 테스트는 실행하지 않았다. `git diff --check HEAD`는 통과했다. 이전 전체 89개 통과와 이번 결과를 구분한다.

실제 유휴 연결 자동 종료 테스트는 아직 추가되지 않았다. 컴파일 수정 후 해당 행동을 검증해야 한다. 또한 기존 방 종료 테스트가 다른 연결에는 아무 이벤트도 없어야 한다고 기대했던 부분은 방 전체를 자동 종료하는 정책에 맞게 확인할 필요가 있다. 사용자 Java 파일은 수정하지 않았고 커밋·푸시도 하지 않았다.

## WebSocket 오류에 HttpStatus.FORBIDDEN을 사용하는 이유

**질문:** WebSocket으로 보내는 오류인데 왜 HttpStatus.FORBIDDEN을 사용하는가?

WebSocket 오류에 HttpStatus가 반드시 필요한 것은 아니다. 현재 Codec이 기존 Service의 ResponseStatusException을 재사용하면서 상태 번호와 문구를 JSON으로 복사하도록 작성돼 있기 때문이다. encodeError는 getStatusCode().value()를 ChatErrorResponse.status에 넣고 직렬화한 문자열을 TextMessage로 반환한다. 따라서 FORBIDDEN은 여기서 JSON 안의 숫자 403을 만드는 데 사용되며 HTTP 응답 전송을 지시하지 않는다.

접속 전 핸드셰이크에서 방이 닫혀 있으면 실제 HTTP 403으로 연결을 거절할 수 있다. 이미 연결된 뒤에는 방 종료 안내 JSON {"type":"ERROR","status":403,"message":"지금은 닫힌 방입니다."}을 WebSocket 텍스트 메시지로 보내고, 별도의 Close 프레임으로 종료 코드 1008을 보낸다. JSON의 403은 프로젝트가 정한 오류 분류이고 1008은 WebSocket 프로토콜의 정책 위반 종료 코드다. 둘 사이에 자동 변환 규칙은 없다.

현재 설계는 기존 HTTP Service 예외와 오류 형식을 재사용하는 선택이라 동작은 가능하지만 HTTP 타입이 WebSocket 표현에 드러나 학습과 유지보수에 혼동을 줄 수 있다. 특히 스케줄러에서 예외를 던지지도 않는데 안내를 만들기 위해 예외 객체를 생성하는 점은 어색하다. 필요하면 추후 Codec이 ChatErrorResponse 같은 데이터 객체를 직접 받게 하거나 ROOM_CLOSED 등의 애플리케이션 오류 코드로 구분할 수 있다. 이번 질문에서는 리팩터링이나 정책 변경을 하지 않았다.

참고: [WebSocket 종료 코드 표준 RFC 6455 §7.4.1](https://www.rfc-editor.org/rfc/rfc6455.html#section-7.4.1). 로컬 Codec·Registry를 읽고 설명을 기록했으며 Java 수정·테스트 실행은 하지 않았다.

## 컴파일 수정 후 자동 종료와 기존 테스트 기대의 충돌

**질문:** 그 다음은 무엇인가?

사용자가 RoomConnectionCloser의 encodeError 인자를 FORBIDDEN 상태와 종료 문구를 가진 ResponseStatusException으로 수정했다. 기존 동일 서브에이전트가 후속 검증을 실행했다. Registry·Broadcast 대상 실행은 15개 통과했지만, 전체 `./gradlew test`에서는 89개 중 88개 통과·1개 실패, 오류·건너뛰기 0이었다. `git diff --check HEAD`는 통과했다.

실패는 ChatWebSocketBroadcastTest의 roomClosed 경우에 bob.assertNoFurtherEvents()를 호출하는 222번째 줄이다. 테스트 Clock을 방 종료 시각으로 옮기면 Alice뿐 아니라 같은 운영 구간의 Bob도 종료 대상이 된다. 새 정기 작업은 아무 메시지도 보내지 않은 Bob에게 방 종료 ERROR/status 403 안내를 보냈으므로 무이벤트 assertion이 실패했다. 이전에는 작성 요청을 보낸 Alice만 종료됐지만 이제 방 종료는 모든 연결에 적용된다. 대상 실행과 전체 실행의 차이는 스케줄러 실행 시점에 따라 기존 기대가 간헐적으로 통과할 수 있음을 보여준다.

다음 작은 수정은 사용자 만료·차단의 발신자 전용 오류와 방 전체의 운영 종료를 테스트에서 구분하는 것이다. roomClosed 경우 Bob도 종료 안내와 1008을 받는지 확인하고, expired/banned 경우에는 Bob 미수신 기대를 유지한다. 이후 메시지를 전혀 보내지 않은 연결이 자동 안내·종료를 모두 받는 전용 네트워크 테스트를 추가한다. 이번 실패에서 Bob의 안내 수신은 관찰했지만 Close 코드까지 유휴 종료 전체 계약을 검증한 것은 아니다.

AI는 사용자 Java나 테스트 파일을 수정하지 않았다. 현재 전체 테스트 결과는 통과가 아니며, 기록과 NEXT만 최신 상태로 반영했다. 방송 직전 종료 시각 검사는 이후의 별도 작은 구현으로 남아 있다.

## 오류 안내 생성 구조를 이번에 정리할지 결정하기

**질문:** 다음 작업을 정하자. 예외를 던지지도 않는데 ResponseStatusException을 만들어 안내하는 구조도 수정할까?

Wayfinder의 작은 결정 티켓 ‘WebSocket 오류 안내 생성 경계’를 열고 담당했다. 추천은 실패한 방 종료 테스트 복구 → Codec 입력을 ChatErrorResponse로 정리 → 유휴 연결 자동 종료 검증 순서다. 실패 중인 상태에서 구조 변경까지 섞으면 원인 구분이 어려워 먼저 현재 동작의 검증 기준을 확보한다.

추천 변경 범위는 Codec과 두 호출부다. Codec은 안내 데이터 객체를 JSON/TextMessage로 바꾸고, Handler는 실제 예외에서 상태·문구를 꺼내 안내 데이터로 변환한다. RoomConnectionCloser는 예외 객체를 만들지 않고 방 종료 안내 데이터를 직접 생성한다. Handler의 기존 기본 오류 문구는 보존해야 한다. 기존 ERROR/status/message 형식과 400/401/403 분류, 종료 코드 1008은 유지하며 Service 예외·DB·새 오류 코드 체계까지 확대하지 않는다.

**AI 질문:** 이 순서로 작은 수정을 포함할지, 지금은 종료 테스트만 완성할지 확인했다. 사용자 답변 대기 중이며 아직 확정 결정으로 기록하지 않았다. 이번 작업은 계획과 기록만 수행했고 Java/테스트 수정이나 실행은 하지 않았다.

## 오류 안내 데이터 분리와 유휴 연결 자동 종료 검증 완료

**질문/위임:** ‘Bob도 안내와 1008을 받도록 기대를 수정한다’는 말이 이해되지 않는다. 오류 안내 부분은 AI가 모두 수정한다.

테스트의 기대는 테스트 코드에 적힌 ‘정상이라면 이런 일이 일어나야 한다’는 조건이다. 이전 테스트에서는 Alice가 방 종료 후 메시지를 보낼 때 Alice만 오류를 받고 Bob에게는 아무 이벤트도 없어야 한다고 적었다. 새 정기 작업에서는 방이 닫히면 가만히 있는 Bob도 나가야 하므로 그 조건이 정책과 어긋났다. 사용자 만료·차단은 해당 사용자만 영향을 받고, 운영 종료는 같은 운영 구간의 연결 전체에 영향을 준다는 차이다.

AI가 만료·차단의 발신자 전용 테스트에서 방 종료 경우를 분리했다. 별도의 실제 네트워크 테스트 notifiesAndClosesIdleConnectionsWhenTheirOperatingPeriodEnds는 두 연결을 준비하고 테스트 Clock을 종료 정각으로 옮긴다. 채팅은 보내지 않으며 각 연결이 방 종료 ERROR/status 403 안내를 받은 뒤 코드 1008로 닫히는지 확인한다. 실제 Spring 정기 작업과 Registry를 사용하고 내부 메서드를 직접 호출하지 않는다. 기존 동일 서브에이전트가 리팩터링 전 Broadcast 9개 통과로 동작 기준을 확인했다. 이미 구현된 정기 작업의 회귀 검증이며 이 새 테스트 자체의 사전 red를 확인했다고 주장하지 않는다.

사용자 위임으로 안내 생성의 세 경로를 정리했다.

- ChatMessageCodec.encodeError는 ResponseStatusException 대신 ChatErrorResponse를 받아 JSON 문자열/TextMessage로 변환한다.
- Handler는 실제로 잡은 예외에서 상태 번호와 문구를 응답 데이터로 변환한다. reason이 null이면 기존 ‘메시지를 처리할 수 없습니다.’ 문구를 유지한다. 만료·차단·입력 오류의 연결 유지/종료 정책은 유지한다.
- RoomConnectionCloser는 ChatErrorResponse("ERROR", 403, "지금은 닫힌 방입니다.")를 직접 생성한다. 안내용 ResponseStatusException 생성과 해당 HTTP 타입 import를 제거했다.

Service와 잘못된 요청을 해석하는 Codec.decode는 실제 오류를 계속 예외로 전달한다. 오류 직렬화의 입력만 데이터로 정리한 것이며 모든 HTTP 관련 타입이나 모든 예외를 제거한 변경은 아니다. DB와 ERD는 바꾸지 않았다. Codec 테스트 3개는 400/401/403의 기존 JSON 세 필드와 따옴표·줄바꿈의 보존을 확인한다.

**최종 검증:** 같은 서브에이전트가 HEAD 이후 staged·unstaged·untracked 변경을 읽기 전용으로 검토했고 actionable 지적 없음이다. Codec·Broadcast·Registry 대상 실행은 35개(20+9+6) 통과했다. `./gradlew test --rerun-tasks`는 전체 92개 통과, 실패·오류·건너뛰기 0이며 Gradle 작업 4개가 모두 새로 실행됐다. `git diff --check HEAD`도 통과했다. 실제 유휴 두 연결의 안내·종료는 대상 실행과 전체 실행 모두 통과했다.

다음은 방송 직전 세션 잠금 안에서 운영 구간 종료 시각을 확인해 정기 검사 사이에도 만료된 연결에 새 방송을 시작하지 않는 것이다. Registry의 종료 전 유지·안내 전송 실패·종료 후 목록 제거 경계도 후속 검증이다. 현재 WebSocket 전체 완료로 기록하지 않으며 이번 커밋·푸시는 요청되지 않아 수행하지 않았다.

## 방송 직전 종료 시각 검사 작성 힌트

**질문:** 방송 직전 종료 시각 검사를 어떻게 작성하는가?

현재 RoomSessionRegistry.broadcast는 synchronized(s) 안에서 isOpen만 검사해 sendMessage를 호출한다. isOpen은 통신 연결이 아직 열려 있는지 확인하며 방 운영 구간이 종료됐는지 판단하지 않는다. 따라서 Registry도 Clock을 생성자 주입받고, 열린 연결에 전송하기 직전 closesAt과 현재 시각을 비교해야 한다. closesAt은 기존 핸드셰이크 속성을 그대로 읽으며 DB 조회는 추가하지 않는다.

작성 순서는 Clock 필드·생성자 준비 → 기존 isOpen 분기에 중괄호 추가 → 세션 잠금 안에서 closesAt 읽기와 LocalDateTime.now(clock) 계산 → 정각 포함 만료이면 해당 연결의 방송 건너뛰기다. for 반복문에서 continue는 현재 연결만 건너뛰고 다음 연결로 진행하며 return은 방 전체 방송을 종료한다.

시각을 잠금 밖에서 먼저 읽으면 잠금을 기다리는 동안 방 종료 시각을 지나도 오래된 now로 전송할 수 있다. 예를 들어 10:59:59에 읽고 잠금을 얻은 시각이 11:00:01이면 이미 만료됐지만 이전 값은 유효하다고 판단한다. 그래서 잠금을 얻은 뒤 전송 직전 읽는다.

이번 작은 단계에서 만료 연결은 방송만 건너뛰고 Registry에 남긴다. 기존 1초 종료 작업이 안내·등록 해제·1008 종료를 맡는다. 만료됐다는 이유로 방송 쪽에서 등록만 해제하면 종료 작업이 그 연결을 찾지 못해 안내·종료를 누락할 수 있다. 이미 물리적으로 닫힌 연결과 전송 IOException에 대한 기존 제거 처리는 유지한다.

테스트에서는 Registry 생성자에 테스트 Clock을 전달하고 모의 세션에도 closesAt을 준비해야 한다. 다음 검증의 목표는 종료 정각 이후 broadcast가 일반 채팅을 보내지 않는 행동이며 스케줄러를 먼저 호출하지 않아도 차단돼야 한다. 이번 답변에서는 Java·테스트 파일을 수정하거나 실행하지 않았다.

## Clock 생성자 변경에 맞춘 테스트 준비와 방송 종료 경계 검증

**질문/위임:** 방송 검사를 작성했는데 Clock이 들어가면서 문제가 생기는 것 같다. AI가 전부 해결할 수 있는가?

사용자가 RoomSessionRegistry에 Clock 필드·생성자를 추가하고 broadcast의 세션 잠금 안에서 closesAt/현재 시각을 읽어 정각 포함 만료 연결에 continue를 적용했다. 이 핵심 구현은 그대로 유지했다. 코드 확인 결과 기존 단위 테스트 6곳이 여전히 인자 없는 new RoomSessionRegistry()를 호출했다. Spring 없이 직접 new하는 테스트는 필요한 Clock을 직접 전달해야 한다. Spring으로 실행되는 앱은 기존 Clock 빈을 생성자에 전달하므로 이와 구분한다.

AI가 6곳에 테스트 MutableClock을 전달하고 기존 방송 테스트의 모의 연결에 closesAt 속성을 준비했다. 이전에는 시간 검사가 없어서 필요하지 않았던 속성이다. 사용자 코드를 고치거나 인자 없는 생성자를 추가해 문제를 숨기지 않았다. 이번에는 실패한 기존 상태를 별도로 실행해 red를 관찰했다고 주장하지 않는다.

추가 검증은 기존에 합의한 공개 Registry 경계를 사용한다. 11:29:59에는 방송하고 11:30:00/11:30:01에는 만료 연결에 보내지 않는 세 경우를 검증한다. 각 경우에서 유효한 다른 연결은 계속 수신한다. 별도 테스트는 방송에서 건너뛴 연결도 이후 종료 작업에 남아 안내 JSON과 1008을 받는지 확인한다. 내부 Map 상태나 메서드 호출 구조를 테스트하지 않는다.

**검증:** 동일 서브에이전트의 읽기 전용 리뷰는 actionable 지적 없음이다. Registry·Broadcast 대상은 19개(10+9) 통과했다. `./gradlew test --rerun-tasks`는 전체 96개 통과, 실패·오류·건너뛰기 0이며 Gradle 작업 4개 모두 새로 실행했다. `git diff --check HEAD`도 통과했다. 기존 실제 유휴 두 연결 자동 종료 테스트도 유지·통과했다.

이번 수정 파일은 RoomSessionRegistryTest이며, 사용자 production Clock/방송 검사는 유지했다. 실제 DB 커밋 지연과 잠금 대기 중 종료 시각 통과를 재현하는 실행 검증은 아직 없다. 종료 전 연결 유지·안내 전송 실패 시 다른 연결 정리 같은 추가 종료 경계도 후속 작업이다. 기록과 정책 문서의 구현 상태를 최신화했으며 커밋·푸시는 하지 않았다.

## 다음 작은 과제: 종료 안내 전송 실패에도 정리 계속하기

**요청:** 다음 단계로 넘어간다.

NEXT와 기존 설계 지도를 확인했다. 서비스 정책은 이미 확정돼 있어 새 결정 티켓이나 정책 질문은 만들지 않았다. 다음 작은 과제는 RoomSessionRegistryTest에서 Alice에게 종료 안내를 보내는 동안 IOException이 나도 Alice의 close를 시도하고 Bob의 안내·종료를 계속하는 행동 하나를 검증하는 것이다.

기존 정상 종료 테스트의 준비를 바탕으로 같은 방에 Alice/Bob을 등록하고 둘의 closesAt을 종료 정각으로 맞춘다. 기존 방송 실패 테스트에서 사용했던 doThrow(IOException)를 Alice의 sendMessage(notice)에만 적용한다. closeExpiredSessions를 한 번 호출하고 Alice의 1008 종료 시도, Bob의 정상 안내와 1008 종료를 확인한다. 외부 전송 경계인 WebSocketSession만 모의 객체로 사용하며 내부 Map·순회 순서·로그 문자열은 검증하지 않는다.

이 과제는 현재 사용자가 작성한 try/finally와 연결별 catch가 실패 상황에서도 의도한 정리를 수행하는지 확인하는 회귀 검증이다. 새로운 프로덕션 메서드를 먼저 만드는 작업은 아니다. 아직 테스트를 작성하거나 실행하지 않았으며, 전체 96개 통과는 직전 실행 결과다. 이후 최소 브라우저 채팅 화면을 연결하는 방향을 제안하되 프론트 구현 범위는 별도로 정한다.

## 종료 안내 전송 실패 회귀 테스트 작성·실행

**위임:** 해당 테스트는 AI가 작성하고 실행한다.

RoomSessionRegistryTest에 closesFailedNoticeConnectionAndContinuesClosingOtherConnections 테스트 하나를 추가했다. 같은 방의 만료된 Alice/Bob 연결을 준비하고 Alice.sendMessage(notice)만 IOException을 던지게 설정했다. 공개 closeExpiredSessions를 호출한 뒤 Alice에게 안내 전송을 실제 시도했는지, 실패해도 POLICY_VIOLATION 종료를 시도하는지, Bob에게는 정상 안내 이후 같은 종료 코드를 보내는지 확인한다. 모의 객체는 외부 전송 경계인 WebSocketSession에만 사용하며 Registry는 실제 객체다.

테스트 중 Alice의 전송 예외는 세션 잠금 안의 finally 정리를 거쳐 바깥 catch에서 WARN으로 기록된다. 연결별 catch이므로 한 연결의 실패가 다른 연결의 처리를 중단하지 않는다. 로그가 나오는 것이 예상된 행동이며 빌드 실패를 의미하지 않는다. 현재 구현에 이미 있는 동작의 회귀 검증이라 별도로 red 단계를 만들거나 통과한 코드를 일부러 깨뜨리지 않았다.

**검증:** 동일 서브에이전트의 읽기 전용 리뷰는 actionable 지적 없음이다. `./gradlew test --tests 'com.breakground.chat.RoomSessionRegistryTest'`는 Registry 11개 통과했고 `./gradlew test --rerun-tasks`는 전체 97개 통과·실패/오류/건너뛰기 0이다. Gradle 작업 4개 모두 새로 실행됐다. `git diff HEAD --check`도 통과했다. 실제 유휴 두 연결 자동 종료 테스트도 전체 실행에 포함돼 통과했다.

프로덕션 코드는 변경하지 않았다. 다음은 최소 브라우저 채팅 화면의 구현 범위를 정하는 논의다. 종료 전 연결 유지·close 자체 실패·정리 후 제거·실제 DB 지연 및 잠금 대기 경합 등 추가 검증과 운영 한도는 별도 후속 항목으로 남긴다. 이번 커밋·푸시는 하지 않았다.

## 최소 브라우저 채팅 화면이라는 말의 의미

**질문:** 그게 무슨 말인가?

다음 단계로 제안한 최소 화면은 지금 만든 백엔드에 실제 웹페이지를 연결해 사람 손으로 채팅을 사용하는 작은 프론트 화면을 뜻한다. 닉네임 입력 또는 자동 생성으로 익명 사용자를 준비하고, 열린 방 목록에서 방을 선택하고, 메시지를 입력하면 상대 브라우저 화면에 실시간으로 표시하며, 방 종료 안내가 오면 입력을 막는 흐름이다.

익명 사용자 준비는 기존 HTTP API, 방 목록은 기존 Room API, 채팅 송수신은 현재 WebSocket 서버에 연결한다. 지금까지의 테스트가 확인한 서버 동작을 화면에서 직접 사용하는 단계다. 처음부터 사이트 전체를 만드는 작업으로 확정한 것은 아니며 React/Next.js 선택과 구체적인 화면 범위는 별도로 논의한다. 이번에는 설명·기록만 했고 프론트 파일 생성이나 실행을 시작하지 않았다.

## 백엔드 전체 완료 여부와 진행 지도

**질문:** 그럼 백엔드에서 할 수 있는 건 다 한 건가? 진행상황을 인터랙티브하게 보여줘.

백엔드 전체를 완료한 것은 아니다. Room 운영 시간, 익명 사용자 생성·재방문, 메시지 임시 저장, 신고 증거 보존, 양방향 WebSocket과 방 종료 안내의 핵심 흐름을 구현하고 검증한 상태다. 작은 브라우저 채팅 화면을 연결해 볼 수 있는 단계이며, 전체 테스트 통과가 운영 준비 완료를 뜻하지는 않는다.

신고 접수와 임시 차단 수단은 있지만 관리자 검토·신고 누적 자동 경고/차단은 남아 있다. Game/GamePlay는 ERD 계획 단계다. 느린 수신자·연결/전송 한도, 추가 종료 경계와 실제 지연·경합 검증, AWS·HTTPS·운영 설정·백업 보존·모니터링도 후속 범위다. 프론트는 아직 구현하지 않았으며 React/Next.js 선택도 이번에 확정하지 않았다.

저장소와 NEXT.md를 바탕으로 항목을 선택하면 현재 구현·검증 범위·남은 일을 확인하는 진행 지도를 만들었다. 예전 진행표의 '채팅 메시지 연결 미구현' 상태와 섞이지 않도록 새 상태 버전을 사용한다. 임의의 완료율은 표시하지 않는다. 기존 테스트 결과 XML을 다시 확인한 집계는 97개 통과·실패/오류/건너뛰기 0이며, 이번에는 백엔드 테스트를 재실행하거나 프로덕션 코드를 변경하지 않았다. 다음 후보는 닉네임 준비 → 방 목록 → 채팅 송수신 → 종료 안내의 최소 브라우저 화면이다.

진행표는 로컬 브라우저에서 10개 항목 렌더링, 선택 시 상세 변경, 저장된 선택 복원, 오래된 상태 무시, 320px/736px 너비의 가로 넘침 없음과 실행 오류 없음을 확인했다. 이번 질문·답변도 당일 기록에 추가했다.

## 오늘 마무리

**사용자:** 연결·전송 동작은 프론트와 함께 확인해야겠다. 오늘은 여기까지.

브라우저 화면을 붙이면 실제 사용자의 연결·송수신·종료 흐름을 함께 확인할 수 있다. 다만 서버의 전송 한도 설계나 지연·경합 검증 자체가 모두 프론트를 필요로 하지는 않는다. 다음 시작 지점은 최소 화면 범위 결정과 기존 HTTP API/WebSocket 연결이며 NEXT.md 상단에 정리했다. 오늘 핵심 검증은 전체 테스트 97개 통과, 실패/오류/건너뛰기 0이다. 종료를 위해 테스트를 불필요하게 재실행하지 않았다.

종료 스킬에 따라 `make fclean`을 실행했다. PostgreSQL 컨테이너와 프로젝트 네트워크 제거, Docker Desktop 정상 종료 명령이 모두 성공했다. 데이터 볼륨 삭제나 강제 종료는 실행하지 않았다. 이번 코드·테스트·정책·학습 기록을 함께 커밋하고 현재 main 브랜치를 origin에 푸시한다.
