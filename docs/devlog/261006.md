# 2026-10-06 개발 기록

## 목표와 시작 상태

합의한 Message DB 임시 보관 설계를 V10부터 직접 구현한다. 정책과 ERD는 반영되었고 실행 코드는 아직 Map 방식이다.

## 파일 준비와 작성 역할

사용자는 V10__create_message.sql의 내용이 아닌 빈 파일만 AI가 만들어달라고 명확히 했다. 빈 파일을 만들었으며 SQL 작성·DB 적용은 하지 않았다. 앞으로도 학습용 구현 파일의 준비는 AI가 하고 핵심 내용은 사용자가 작성하는 방식을 따른다.

## V10 초안 리뷰 — 자동 증가와 N:1

사용자는 SQL 초안을 작성하고 increment 및 N:1 관계 표현을 질문했다. 현재 V10에는 integer id, message_event_id, reporter_user_id, reported_user_id, reason, evidence_content 등 Report용 컬럼이 들어 있었다. 먼저 Report와 Message를 구분해야 한다. Message는 대화 원본이고 Report는 신고 증거 기록이다. 확정 ERD의 Message는 UUID id, room_id, anonymous_user_id, nickname, content, sent_at, expires_at, delete_after다.

자동 증가와 관계는 별개다. DBML increment는 정수 ID를 DB가 자동 생성하는 PostgreSQL GENERATED ALWAYS AS IDENTITY 등으로 표현하지만, 이번 Message.id는 서버가 생성하는 UUID라 identity/increment를 사용하지 않는다. UUID id에는 PRIMARY KEY를 붙인다. N:1은 Message 쪽 room_id/anonymous_user_id가 부모 테이블 PK를 참조하는 REFERENCES로 표현한다. room_id에 UNIQUE를 붙이면 한 방당 Message가 한 개만 가능해져 의도한 1:N을 막는다. 기존 부모 id는 integer이므로 FK도 integer다. 마지막 CREATE TABLE 괄호 뒤에는 세미콜론이 필요하다. 완성 코드는 제공하거나 자동 수정하지 않고 컬럼 구분과 작은 FK 예시만 안내한다.

### V10 재검토 — FK 문법은 반영, 도메인 컬럼은 아직 Report

사용자가 수정한 파일을 다시 읽었다. REFERENCES 문법과 마지막 세미콜론은 반영되었다. 그러나 integer id와 UUID message_event_id를 함께 두고 reporter/reported user, reason, evidence_content, message_sent_at, created_at, evidence_expires_at 등 Report 컬럼이 남아 있다. Message의 id UUID PK 하나로 통일하고 신고자/신고 대상 대신 작성자 anonymous_user_id 하나, 본문 content, 작성 시각 sent_at, 신고 가능 기한 expires_at, 실제 삭제 기준 delete_after, 작성 당시 nickname이 필요하다. 이번에는 컬럼 대응 표로 변경할 부분을 안내하며 자동 수정/DB 적용은 하지 않는다. 인덱스와 CHECK는 기본 컬럼 정리 이후 검토한다.

## V10 작성 위임 — 확정 ERD에 맞춰 SQL 정리

사용자는 grill-me를 호출하며 이번 수정은 AI에게 맡겼다. grill-me와 grilling의 실제 지침을 읽었다. 새로운 정책 질문은 없으며 기존 Q1~Q7 합의와 이번 작성 요청에 따라 V10만 수정했다. Message를 UUID id PK, 방/작성자 FK, nickname/content, sent_at/expires_at/delete_after로 정리했다. 잘못 들어간 Report 컬럼과 정수 id는 제거했다.

필수 값과 varchar 길이, 본문/닉네임의 btrim 공백 보조 CHECK, expires_at > sent_at 및 delete_after > expires_at CHECK, 삭제용 delete_after 인덱스를 추가했다. 두 시간 CHECK는 순서를 보장할 뿐 15분/방 종료+10분을 계산하지 않으며 해당 계산은 Service가 담당한다. btrim은 Java의 모든 Unicode 공백 검증을 대신하지 않는다. UUID는 서버 생성이고 IDENTITY는 사용하지 않는다. Report와 연결하는 FK는 만들지 않았다.

ERD와 SQL을 대조하고 git diff --check로 공백 오류를 확인했다. DB 적용과 실제 PostgreSQL 실행 검증은 아직 하지 않았다. 다음은 파일 이해 확인 및 Flyway 적용이며 Java Entity/Repository와 저장 전환은 이후 별도 작은 단계로 진행한다.

## btrim과 공백만 있는 문자열 검사

사용자가 V10 CHECK의 btrim 의미를 질문했다. PostgreSQL btrim(text)는 기본적으로 문자열 양끝의 일반 스페이스를 제거한 결과를 반환한다. 예: '  안녕  '은 '안녕', '   '은 빈 문자열이 된다. CHECK (btrim(content) <> '')는 이 결과가 빈 문자열이 아니어야 한다는 제약이다. 따라서 NOT NULL만으로 막지 못하는 빈 문자열과 일반 스페이스만 있는 내용을 추가로 거절한다. CHECK는 검사만 하고 저장할 원문 자체를 바꾸지 않는다. 탭/줄바꿈 등 모든 공백 문자를 기본 btrim이 제거하는 것은 아니므로 Service의 isBlank/strip 검증도 유지한다. 공식 PostgreSQL 문자열 함수 문서를 확인했다.

## V10 Flyway 적용과 실제 DB 확인 완료

사용자가 /wayfinder와 함께 다음 작업 진행을 요청했다. 설계 질문은 이미 합의되어 있어 새로운 이슈 지도를 만들지 않고, 다음 작은 작업인 V10 적용·검증을 수행했다. make로 Docker/PostgreSQL을 준비하고 ./gradlew test를 실행했다. 테스트 애플리케이션 시작 시 Flyway가 V10을 적용했다.

검증 결과: BUILD SUCCESSFUL, 39개 테스트, 실패/오류/건너뜀 0. PostgreSQL flyway_schema_history에서 version=10, description=create message, success=true를 확인했다. 실제 public.message의 UUID PK, 필수 컬럼, 두 FK, 네 CHECK, ix_message_delete_after를 확인했다. SQL 파일은 적용 이후 수정하지 않았다.

이 검증은 migration 적용과 기존 기능의 회귀 확인이다. 실제 메시지 작성은 아직 Map을 사용하고 신규 Entity/Repository/삭제 작업은 미구현이다. 다음 작업은 Message Entity/Repository를 작성하고 JPA 매핑을 확인하는 것이다. NEXT와 정책 문서의 전환 상태를 이 사실에 맞췄다. 커밋·푸시와 앱 상시 실행은 이번 작업에 포함하지 않았다.

## Message Entity·Repository 구현과 GitHub 반영 요청

사용자는 grill-with-docs로 계속 진행하고 Git에 올리라고 요청했다. 실제 업데이트된 스킬과 연결된 grilling/domain-modeling 지침, 프로젝트 규칙을 읽었다. 이번 구현 범위는 합의된 다음 단계인 Entity/Repository와 DB 매핑 테스트로 제한했고 Service/Map 교체는 다음 단계로 남겼다. 추가 정책 질문은 없었으며 기존 Q1~Q7 답변을 유지했다.

Message는 chat 패키지의 JPA Entity로 만들었다. Room/작성자는 LAZY ManyToOne과 V10 컬럼 이름을 사용한다. 작성 당시 nickname을 복사하고 공개 setter를 두지 않으며 필드는 updatable=false로 매핑했다. 보호된 기본 생성자는 Hibernate용이고 새 메시지 생성자는 원문·시각 정보를 받는다. PostgreSQL V10의 UUID id에는 DEFAULT가 없지만 GeneratedValue(GenerationType.UUID)를 사용하면 서버의 JPA provider(Hibernate)가 UUID를 생성한다. 처음 id=null이라 Spring Data save는 새 객체를 persist하는 기본 경로를 사용한다. 현재 ChatService의 UUID.randomUUID 흐름은 아직 Map 경로이므로 그대로다.

MessageRepository의 findByIdAndExpiresAtGreaterThan은 기한이 정확히 도달하면 원본을 반환하지 않는다. deleteReadyForCleanup은 신고 기한이 아닌 delete_after <= now 기준의 벌크 JPQL DELETE다. 읽기는 readOnly 트랜잭션, 삭제는 쓰기 트랜잭션으로 선언했고 향후 Service 트랜잭션 안에서도 함께 참여한다. 벌크 삭제 후 기존 영속성 컨텍스트 상태는 자동 정리되지 않으므로 테스트에서 clear하여 DB 재조회했다. 스케줄러는 아직 추가하지 않았다.

PostgreSQL 통합 테스트 4개를 추가했다: 서버 생성 UUID와 FK/닉네임/140개 이모지 재조회, 정확한 신고 만료와 row 보존, 방 종료+10분 삭제 경계, 원본 삭제 후 Report 증거와 중복 키 유지. 시간 경계는 DB 마이크로초 정밀도에 맞췄다. 전체 ./gradlew test: 43개, 실패/오류/건너뜀 0. 테스트 데이터는 트랜잭션 종료 시 롤백한다. V10은 수정하지 않았다.

검토 포인트는 GeneratedValue(UUID)의 생성 주체와 expires_at/delete_after의 서로 다른 역할이다. 다음은 Service를 Map 대신 Repository로 연결하고 정리 작업을 추가하는 단계다. 이번 사용자 요청에 따라 저장소의 설계 기록·ERD·V10·Entity/Repository/테스트를 커밋·푸시한다. 개인 경로의 grill-with-docs 스킬 수정은 이 저장소 밖에 있으므로 해당 Git 커밋에는 포함되지 않는다.
