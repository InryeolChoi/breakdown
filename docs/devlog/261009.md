## WebSocket은 Gradle에 무엇부터 넣어야 할까?

**질문:** Java에서 WebSocket을 실제로 코딩해 본 적이 없다. 먼저 Gradle에 어떤 의존성을 넣어야 할까?

**답변:** 현재 프로젝트는 Spring MVC 기반이므로 `dependencies`에 다음 한 줄을 추가하면 된다.

```groovy
implementation 'org.springframework.boot:spring-boot-starter-websocket'
```

Spring Boot 플러그인과 dependency-management 설정이 이미 있으므로 의존성 버전은 별도로 적지 않는다. 기존 MVC 의존성은 유지한다. 지금 단계에서는 Redis나 메시지 브로커를 추가할 필요가 없다.

추가한 뒤 IntelliJ에서 Gradle 변경 사항을 불러온다. 처음에는 `TextWebSocketHandler`로 받은 문자열을 그대로 돌려주는 작은 echo 실습을 하고, `WebSocketConfigurer`로 접속 경로를 등록하는 흐름부터 익힌다. 이것은 학습용 첫 단계이며 실제 채팅의 송수신 방식이나 방 종료 정책을 확정하는 것은 아니다.

사용자가 직접 의존성을 추가하고 WebSocket 코드를 작성한다. AI는 환경 준비와 설명을 담당했다. 이번에는 애플리케이션 코드 변경이나 테스트 실행은 하지 않았다.

참고: [Spring Boot 공식 WebSocket 문서](https://docs.spring.io/spring-boot/reference/messaging/websockets.html)

## 전체 흐름과 다음 단계

**질문:** WebSocket을 도입할 때 전체 그림은 어떻게 될까?

**답변:** 지금은 클라이언트가 HTTP 요청을 보내면 Controller가 Service를 호출하고, Service가 사용자·방·본문을 검증한 뒤 Repository를 통해 PostgreSQL에 저장한다. WebSocket은 방에 연결된 다른 사용자에게 서버가 새 메시지를 즉시 보내는 통로를 추가한다. HTTP로 송신하든 WebSocket으로 송신하든 기존 Service의 검증과 저장을 재사용하고, DB 커밋에 성공한 메시지를 같은 방의 연결에 전달한다.

학습 순서는 echo → 두 연결 사이 전달 → 방별 연결 관리 → 기존 채팅 저장 흐름과 연결이다. 실제 채팅 전에는 쿠키 기반 연결 사용자 확인, Origin 검증, 차단·운영 시간 재검사, 연결 종료 처리를 정해야 한다. HTTP 송신을 유지할지와 방 종료 시 연결 종료 정책은 아직 미결정이다.

`TextWebSocketHandler`는 문자열 메시지 처리, `WebSocketConfigurer`는 접속 경로 등록을 맡는다. 이후 방별 `WebSocketSession` 관리는 애플리케이션에서 설계할 부분이다.

참고: [Spring Framework WebSocket API](https://docs.spring.io/spring-framework/reference/web/websocket/server.html)

## TDD로 echo를 구현할 때 만들 클래스와 메서드

**질문:** 무엇을 해야 할지 구체적인 힌트가 필요하다. 어디에 어떤 클래스를 만들고 어떤 메서드를 쓰면 될까?

**답변:** 사용자가 이미 만든 빈 `EchoWebSocketTest`와 `EchoWebSocketHandler`를 확인했다. 첫 테스트 경계로 실제 `/ws/echo` 연결에서 `안녕`을 보내고 같은 문자열을 받는 동작을 제안했다. tdd 스킬은 테스트 경계를 사용자와 확인한 뒤 테스트를 작성하도록 요구하므로, 이번에는 설계와 힌트만 제공하고 확인을 기다린다.

- 테스트: `src/test/java/com/breakground/chat/EchoWebSocketTest.java`. 임의 포트 서버를 띄우는 `@SpringBootTest(webEnvironment = RANDOM_PORT)`, `@LocalServerPort`, `@Test`를 이용한다. Java `HttpClient`의 WebSocket 클라이언트로 연결하고 문자열 수신 결과를 검증한다. 접속·수신 대기는 제한 시간을 두며 실패를 그대로 드러낸다.
- 처리: `src/main/java/com/breakground/chat/EchoWebSocketHandler.java`. `TextWebSocketHandler`를 상속하고 `handleTextMessage(WebSocketSession, TextMessage)`를 재정의한다. `session.sendMessage(...)`로 받은 메시지를 같은 연결에 돌려준다. 전송 중 IOException이 발생할 수 있어 재정의 메서드에서 throws로 선언할 수 있다.
- 등록: `src/main/java/com/breakground/config/WebSocketConfiguration.java`. `@Configuration`, `@EnableWebSocket`, `WebSocketConfigurer`, `registerWebSocketHandlers(WebSocketHandlerRegistry)`를 사용한다. `registry.addHandler(handler, "/ws/echo")`로 경로를 등록한다. 핸들러는 `@Component`로 Bean 등록하고 설정 클래스 생성자에 주입하는 방식을 제안한다.

진행 순서는 테스트 하나 작성 → 경로가 없어 연결 실패하는 red 확인 → 핸들러와 경로 등록 → 같은 테스트가 통과하는 green 확인이다. 지금 echo에는 Service, Repository, DB 저장, 쿠키 인증을 붙이지 않는다. 서비스용 채팅과 연결하기 전 사용자·Origin·방 검증을 따로 설계한다.

테스트 경계 확정과 실제 테스트 작성·실행은 아직 하지 않았다.

참고: [Spring WebSocket API](https://docs.spring.io/spring-framework/reference/web/websocket/server.html), [Java 21 WebSocket.Builder](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/WebSocket.Builder.html)

## 비동기 테스트와 Spring 클래스의 위치

**질문 1:** 테스트를 비동기로 작성해야 할까?

**답변:** JUnit 테스트 메서드는 일반 `void` 메서드로 작성한다. 선택한 Java WebSocket 클라이언트의 연결과 수신이 비동기이므로, 테스트 메서드는 결과가 도착할 때까지 제한 시간을 두고 기다린 후 assert한다. 수신 콜백이 문자열 결과를 `CompletableFuture`에 채우고 테스트가 `get(3, TimeUnit.SECONDS)`로 기다리는 구조를 사용할 수 있다. `Thread.sleep`으로 추측해서 기다리거나 테스트에 `@Async`를 붙일 필요는 없다. 기다리지 않으면 응답이 오기 전에 테스트 메서드가 끝날 수 있다.

**질문 2:** `TextWebSocketHandler`는 어디에 있을까?

**답변:** 프로젝트에서 새로 만드는 클래스가 아니라 Spring 라이브러리의 클래스다. 정확한 패키지는 `org.springframework.web.socket.handler.TextWebSocketHandler`다. Gradle 캐시에 `spring-websocket-7.0.9.jar`와 sources.jar가 내려받아진 상태를 확인했다. IntelliJ에서 import하고 클래스 선언으로 이동하면 라이브러리 소스를 볼 수 있다.

현재 사용자가 작성 중인 핸들러에는 `TextWebSocketHandler`, `WebSocketSession`, `TextMessage`, `IOException` import와 클래스/메서드를 각각 닫는 중괄호가 필요하다. 설명만 제공하며 사용자의 코드는 수정하지 않았다. WebSocket 연결 테스트는 아직 실행하지 않았다.

참고: [TextWebSocketHandler API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/socket/handler/TextWebSocketHandler.html), [CompletableFuture API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/CompletableFuture.html)

## 코드가 떠오르지 않으면 검색해야 할까?

**질문:** 처음 WebSocket 테스트를 작성하려니 코드가 떠오르지 않는다. 구글링을 해야 할까?

**답변:** 처음 쓰는 라이브러리의 클래스명·호출 방법은 문서나 예제를 찾아보면서 작성하면 된다. 목표 동작을 정하는 것과 API 문법을 기억하는 것은 별개다. TDD도 API를 암기하는 방법이 아니라, 원하는 동작을 테스트로 표현하고 실패에서 통과까지 확인하는 방법이다.

AI가 비동기 수신·Future·실제 서버 테스트를 한꺼번에 설명해 시작점을 복잡하게 만들었다. 그래서 다음 조각을 클라이언트와 접속 주소 준비로 줄였다.

```java
HttpClient client = HttpClient.newHttpClient();
URI uri = URI.create("ws://localhost:" + port + "/ws/echo");
```

`HttpClient`는 테스트가 서버에 접속할 때 사용하는 클라이언트이고, `URI`는 접속 주소다. `port`는 RANDOM_PORT로 시작한 서버의 실제 포트다. 다음에는 `client.newWebSocketBuilder()`의 연결 API를 문서에서 찾고, 수신 리스너를 작은 조각으로 살펴본다. 이번에는 테스트 파일이나 서버 코드를 수정하거나 테스트를 실행하지 않았다.

참고: [Java 21 HttpClient API](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.html)

## 첫 echo 코드 리뷰

**요청:** 현재 미커밋 코드를 리뷰하고 잘못된 점을 찾은 뒤, 잘 작성되었다면 테스트를 실행한다.

- 사용자와 리뷰 기준을 HEAD(`ce1dff9`) 이후 미커밋 변경으로 확인했다. 커밋 간 비교가 아니므로 `git diff HEAD -- <WebSocket 세 파일>`로 확인했다.
- code-review 스킬에 따라 Standards와 Spec 검토를 별도 서브 에이전트로 진행했다. 명세는 이 devlog의 echo 설명과 `NEXT.md`를 사용했다.
- Standards: 문서화된 작성 규칙 위반이나 의미 있는 코드 냄새는 발견하지 않았다. 학습용 작은 echo 범위를 유지했다.
- Spec: 테스트가 클라이언트·주소·빌더만 준비하고 실제 연결·전송·수신·assert를 하지 않는다. 다른 오류를 고친 뒤에는 기능 없이도 통과할 수 있다. `newWebSocketBuilder()`는 연결 준비이며 `buildAsync(uri, listener)` 호출로 연결을 시작한다.
- Spec: `WebSocketConfiguration`이 빈 클래스여서 `/ws/echo` 경로 등록이 없다. 설정 어노테이션과 Configurer 구현, 핸들러 객체 제공이 필요하다.
- Spec: `handleTextMessage`가 비어 있어 받은 문자열을 돌려주는 동작이 없다.
- 컴파일: `./gradlew compileJava` 실패. `EchoWebSocketHandler.java:17`에서 `reached end of file while parsing`을 확인했다. 메서드와 클래스를 닫을 중괄호 중 하나가 빠져 있다.
- 사용자 코드를 대신 고치지 않았다. 정상 실행 가능한 상태가 아니므로 테스트는 실행하지 않았다. 다음 수정은 먼저 중괄호를 맞추고, 실제 연결·수신·assert를 갖춘 첫 테스트가 기능 부재로 실패하도록 만드는 것이다.

## TDD로 echo를 시작하는 구체적인 순서

**질문:** TDD 스킬을 사용해 무엇을 해야 하는지 구체적인 힌트를 알려 달라.

**답변:** 앞서 제안한 핸들러 작성에 앞서, 이번에는 외부 동작을 확인하는 테스트 하나부터 시작한다. 제안한 테스트 경계는 실제 WebSocket `/ws/echo` 연결이다. 클라이언트가 `안녕`을 보내면 받은 응답이 `안녕`인지 확인한다. 이 경계는 사용자에게 확인을 요청했으며 아직 합의 전이라 테스트 코드를 작성하지 않았다.

첫 테스트의 준비는 실제 서버를 임의의 포트로 띄우고 테스트용 WebSocket 클라이언트가 연결하는 것이다. 테스트는 연결 → 문자열 전송 → 제한 시간 내 응답 수신 → 기대 문자열 비교 → 연결 정리를 수행한다. 경로가 아직 없으므로 최초 실패는 WebSocket 연결이 성립하지 않는 것이어야 한다. DB 연결 실패나 Java 문법 오류는 이 동작의 실패 증거가 아니다.

실패를 확인한 다음 필요한 구현은 두 파일이다. `chat/EchoWebSocketHandler.java`는 `TextWebSocketHandler`를 상속해 `handleTextMessage`에서 받은 메시지를 현재 세션에 보낸다. `config/WebSocketConfiguration.java`는 `@Configuration`, `@EnableWebSocket`, `WebSocketConfigurer`로 `/ws/echo`에 핸들러를 등록한다. 그 뒤 같은 테스트 하나를 다시 실행해 성공을 확인한다. echo는 학습용이며 이 단계에서 채팅 Service나 DB 저장을 호출하지 않는다.

비동기 응답이므로 테스트는 단순히 send 직후 응답을 읽을 수 없다. 응답을 수신하는 콜백과 제한 시간 있는 대기가 필요하다. 초보 학습자가 핵심 핸들러를 직접 작성할 수 있도록, 테스트 클라이언트 준비와 정리는 AI가 맡을 수 있는 반복 작업이다. 현재 요청은 설명과 힌트이므로 구현과 테스트 실행은 하지 않았다.

스킬 규칙: [tdd/SKILL.md](/Users/inchoi/.agents/skills/tdd/SKILL.md)의 “Before writing any test, write down the seams under test and confirm them with the user.”에 따라 테스트 경계를 먼저 확인한다.
