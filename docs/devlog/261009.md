# 2026-10-09 개발 기록

WebSocket을 직접 구현하면서 연결 설정과 메시지 송수신 흐름을 이해하는 것이 오늘의 목표다.

## 작업 시작

- 이전 작업의 다음 단계는 WebSocket이다. 송신을 기존 HTTP API로 유지할지, 방 종료 시 연결을 끊을지는 아직 결정하지 않았다.
- 세션 시작 절차에 따라 `make`를 실행했다. Docker Desktop 엔진이 준비되었고 PostgreSQL 컨테이너가 시작되었다.
- 기존 `MessageCleanup.java` 수정은 그대로 유지했다.

## WebSocket은 Gradle에 무엇부터 넣어야 할까?

**질문:** Java에서 WebSocket을 실제로 코딩해 본 적이 없다. 먼저 Gradle에 어떤 의존성을 넣어야 할까?

**답변:** 현재 프로젝트는 Spring MVC 기반이므로 `dependencies`에 다음 한 줄을 추가하면 된다.

```groovy
implementation 'org.springframework.boot:spring-boot-starter-websocket'
```

Spring Boot 플러그인과 dependency-management 설정이 이미 있으므로 의존성 버전은 별도로 적지 않는다. 기존 MVC 의존성은 유지한다. 지금 단계에서는 Redis나 메시지 브로커를 추가할 필요가 없다.

추가한 뒤 IntelliJ에서 Gradle 변경 사항을 불러온다. 처음에는 `TextWebSocketHandler`로 받은 문자열을 그대로 돌려주는 작은 echo 실습을 하고, `WebSocketConfigurer`로 접속 경로를 등록하는 흐름부터 익힌다. 이것은 학습용 첫 단계이며 실제 채팅의 송수신 방식이나 방 종료 정책을 확정하는 것은 아니다.

사용자가 직접 의존성을 추가하고 WebSocket 코드를 작성한다. AI는 환경 준비와 설명을 담당했다. 이번에는 애플리케이션 코드 변경이나 테스트 실행은 하지 않았다.

참고: [Spring Boot 공식 WebSocket 문서](https://docs.spring.io/spring-boot/reference/messaging/websockets.html)

## 전체 흐름과 다음 단계

**질문:** WebSocket을 도입할 때 전체 그림은 어떻게 될까?

**답변:** 지금은 클라이언트가 HTTP 요청을 보내면 Controller가 Service를 호출하고, Service가 사용자·방·본문을 검증한 뒤 Repository를 통해 PostgreSQL에 저장한다. WebSocket은 방에 연결된 다른 사용자에게 서버가 새 메시지를 즉시 보내는 통로를 추가한다. HTTP로 송신하든 WebSocket으로 송신하든 기존 Service의 검증과 저장을 재사용하고, DB 커밋에 성공한 메시지를 같은 방의 연결에 전달한다.

학습 순서는 echo → 두 연결 사이 전달 → 방별 연결 관리 → 기존 채팅 저장 흐름과 연결이다. 실제 채팅 전에는 쿠키 기반 연결 사용자 확인, Origin 검증, 차단·운영 시간 재검사, 연결 종료 처리를 정해야 한다. HTTP 송신을 유지할지와 방 종료 시 연결 종료 정책은 아직 미결정이다.

`TextWebSocketHandler`는 문자열 메시지 처리, `WebSocketConfigurer`는 접속 경로 등록을 맡는다. 이후 방별 `WebSocketSession` 관리는 애플리케이션에서 설계할 부분이다.

참고: [Spring Framework WebSocket API](https://docs.spring.io/spring-framework/reference/web/websocket/server.html)

## 세션 마무리

- 사용자가 WebSocket 스타터 의존성을 추가했다. 핸들러 구현은 아직 시작하지 않았다.
- `MessageCleanup` 클래스 이름에 들어간 불필요한 `S`를 제거해 파일명·생성자와 일치시켰다.
- `./gradlew compileJava`: BUILD SUCCESSFUL(UP-TO-DATE). 전체 테스트와 실제 WebSocket 연결 테스트는 이번에 실행하지 않았다.
- `make fclean`: PostgreSQL 컨테이너와 네트워크 제거, Docker Desktop 종료 성공. 데이터 볼륨은 유지했다.
- `NEXT.md`에 다음 시작 지점인 echo 실습을 기록했다.
- 삭제 요청의 날짜인 10월 8일 기록은 없으므로 삭제한 파일은 없다. 날짜가 다른 기존 기록과 오늘 기록은 유지했다.
