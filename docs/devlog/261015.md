# 2026-10-15 — 디자인 MCP 선택과 프런트 준비 인계

## 시작 상태와 목적

사용자가 MCP부터 찾아 확정하자고 요청했다. 이전에 요청한 준비 문서 커밋·푸시와 GitHub 티켓 발행은 중단된 턴에서 아직 수행되지 않았다. 로컬 상태를 다시 확인했고 기존 breakground.zip 삭제와 .DS_Store 미추적 변경은 유지했다. 오늘 기록은 261013.md에 덧붙이지 않고 새 날짜 파일로 작성한다.

이번에는 디자인 도구 선택을 먼저 진행했다. Plugin Management 지침으로 사용 가능한 도구를 검색하고 Stitch/Figma 공식 문서를 읽었다. 앱 구현·Docker 시작·계정 인증·도구 설치는 이 조사에 필요하지 않아 수행하지 않았다.

## MCP 조사와 질문·답변

Stitch 공식 문서에서 원격 MCP, API key/OAuth, 화면 생성·수정·변형안을 확인했다. Figma 공식 MCP도 현재 캔버스 쓰기를 지원하므로 읽기 전용이라고 비교하지 않았다. Figma는 도구 디렉터리에 미설치 상태로 나타났고 Stitch는 검색 결과에 없었다. Stitch 공식 원격 endpoint를 별도로 확인했다. 디렉터리에 없다고 MCP 자체가 없다고 결론내리지 않았다.

**질문:** 아직 시안이 없으니 설명으로 변형안을 만드는 Stitch부터 사용할까, Figma로 시작할까?

**사용자 답변:** Stitch부터 사용.

Stitch를 첫 디자인 MCP로 선택했다. 목적은 탁 트인 창문이 보이는 라운지 느낌을 화면으로 구체화하고 비교하는 것이다. Figma는 실제 편집·공유 필요가 생길 때 검토한다. 인증·등록·연결 검증은 다음 단계이며, 연결됐다고 말하지 않는다. 사용자 계정의 quota/요금은 아직 확인하지 않았다. 근거와 연결 완료 기준은 docs/research/design-mcp-comparison.md에 있다.

## 앞선 작업의 인계

도구 선택을 반영한 뒤 앞서 명시적으로 요청한 준비 문서의 커밋·푸시와 GitHub 티켓 발행을 진행한다. 이는 기존 '게시하지 말고 초안만' 제한을 해당 작업에 한해 변경한 사용자 요청이다. 첫 화면·HTTP/쿠키/WebSocket 접속 방식·triage 기본 라벨·세부 setup은 아직 미정이며 이슈를 발행해도 해결 완료로 바꾸지 않는다.

## 왜 티켓을 나누는가?

사용자는 티켓도 발행해야 한다고 요청한 뒤 '나눠야 하는구나'라고 했다. 설계 티켓은 선택·검증이 끝나면 해결되지만 기능 티켓은 구현과 사용자 동작 검증이 끝나야 완료된다. 둘을 섞으면 답변 없는 화면/접속 방식을 AI가 임의로 구현하기 쉽다. 부모 이슈는 큰 방향을, 자식은 한 결정 또는 독립적인 기능을 담는다. 하나의 자식 이슈 완료가 전체 프런트 완성을 의미하지 않는다.

## 발행 결과와 검증

설계 지도·MVP 명세 두 개와 설계/준비 다섯 개·기능 네 개를 합쳐 11개 이슈를 발행했다. 기존 이슈는 0개여서 중복 생성하지 않았다. Wayfinder 종류 라벨 네 개만 추가하고 기본 triage 라벨 선택은 미정으로 유지했다. 구현 이슈는 기존 enhancement를 사용하고 미결정 작업에 ready-for-agent를 붙이지 않았다.

시안은 첫 입장 흐름·Stitch 연결에 의존한다. 첫 방 목록 기능은 스킬 설정 범위·접속 경로·첫 입장 흐름에 의존하고 익명 입장 → 채팅 → 신고 순서로 이어진다. GitHub native parent/blockedBy를 사용했으며 모든 자식 9개를 다시 조회해 부모·선행 목록·OPEN 상태를 검증했다. 작업 착수·완료로 닫은 이슈는 없고 PR도 만들지 않았다. 실제 링크와 관계는 docs/frontend-issues.md에 기록했다.

앱/백엔드 소스 변경은 없으므로 이미 통과한 테스트를 다시 실행하지 않는다. 문서 링크·양식·공백 검사를 마친 뒤 준비 문서와 확정 정책·학습 기록을 커밋·푸시한다. 기존 ZIP 삭제와 .DS_Store는 스테이징하지 않는다.

문서 20개의 로컬 링크·코드 펜스·공백 검사와 세 이슈 양식의 YAML 검사가 통과했다. git diff --check도 통과했다. 커밋 전에 origin을 fetch해 원격 상태를 확인했다. 인증 정보 생성·공개나 앱 실행은 하지 않았다.

## Grilling — Stitch 연결 방식의 첫 라운드

사용자가 grilling 스킬로 계속 진행하자고 요청했다. 다음 경계는 실제 인증·등록 전에 사용자와 연결 범위를 정하는 것이다. 사실은 서브에이전트에게 읽기 전용으로 확인시켰고 현재 노출된 Stitch 도구, 사용자 설정의 알려진 Stitch 서버, 프로젝트 Codex 설정이 없음을 확인했다. 임의 이름의 프록시나 다른 관리 환경까지 없는 것으로 단정하지 않는다.

설치 CLI는 원격 HTTP MCP를 지원하며 공식 설정 문서에서 env_http_headers가 헤더 이름을 환경변수 이름으로 연결하는 방식임을 확인했다. 비밀값을 읽어 출력하거나 설정·인증을 변경하지 않았다. 앱 프로세스의 환경변수 전달, 실제 계정 접근과 사용량은 후속 검증이다. 근거: https://learn.chatgpt.com/docs/extend/mcp?surface=cli 및 https://learn.chatgpt.com/docs/config-file/config-reference.

이번에 질문할 현재 결정 경계는 두 개다. 답변 없이 확정하지 않는다.

1. API key로 인증할지 OAuth로 인증할지. 추천은 Stitch에서 발급한 API key를 비공개 환경값으로 참조하는 원격 연결이다. API key는 AI가 Stitch에 접근할 때 사용하는 열쇠이며 사용자가 직접 발급·안전하게 보관한다. 채팅에 원문을 붙이는 방식으로 받지 않는다.
2. 개인 Google 계정의 새 Breakground 전용 Stitch 디자인 프로젝트를 쓸지 다른 계정/기존 작업 공간을 쓸지. 추천은 이 서비스 시안만 모을 새 전용 공간이다. 여기서 프로젝트는 시안을 보관하는 Stitch 작업 공간을 뜻한다.

두 질문의 답변 뒤 필요한 인증·설정 준비와 계정 조건 확인으로 진행한다. 현재는 질문 단계이며 로그인·키 발급·MCP 등록·프로젝트 생성·시안 생성은 실행하지 않았다. 작업 재개 규칙에 따라 make를 실행했고 Docker 엔진 준비와 PostgreSQL 컨테이너 생성·시작이 성공했다. 이는 Stitch 연결 완료나 Spring 앱 실행과 별개다.

## frontend-design 스킬부터 시작할까?

**사용자 질문:** MCP 대신 Anthropic의 frontend-design 같은 스킬을 설치하는 건 어떨까?

**답변:** 공식 frontend-design 지침을 확인했다. 스킬은 AI가 디자인을 판단하고 구현하는 방법을 안내하는 문서이고, Stitch MCP는 외부 서비스에서 시안을 생성·수정하는 연결이다. 스킬 자체에 별도 디자인 서비스 인증은 필요하지 않지만, 설치만으로 좋은 결과가 보장되지는 않는다. 현재 공식 지침은 색상·글꼴·배치 계획과 검토를 거쳐 코딩하도록 안내한다.

지금은 스킬로 '탁 트인 창문이 보이는 라운지'의 디자인 방향을 먼저 구체화하고, 외부 시안 도구가 필요해지면 Stitch를 연결하는 순서를 추천했다. 이는 제안이며 기존 Stitch 선택을 취소하거나 연결 보류를 확정하지 않았다. 설치·프런트 코드 작성·GitHub 이슈 변경은 수행하지 않았다.

근거: [Anthropic 공식 frontend-design](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md), [스킬 디렉터리](https://skills.sh/anthropics/skills/frontend-design). find-skills 지침으로 출처를 확인했고, 조회한 로컬 스킬 경로에서는 frontend-design을 찾지 못했다.

**후속 결정:** 사용자가 스킬부터 추가하고 Stitch 연결을 보류하는 방향에 동의했다. skill-installer 공식 설치 스크립트로 `/Users/inchoi/.codex/skills/frontend-design`에 설치했고 성공 결과와 SKILL.md 존재를 확인했다. 다음 턴부터 사용할 수 있다. 사용자는 별도로 설치 중이라고 알려왔으므로 중복 설치·덮어쓰기·삭제는 하지 않는다. 사용자 전역 설치이므로 저장소를 받는 다른 AI 환경에 자동 설치되는 것은 아니다.

**추가로 생각할 사항:** 첫 화면에서 열린 방을 먼저 보여줄지, 닉네임 입력을 먼저 받을지 정해야 한다. 열린 방이 없을 때의 화면과 모바일에서 라운지 분위기·채팅 가독성을 함께 유지할 방법도 디자인 계획에 포함한다. 브라우저의 HTTP·쿠키·WebSocket 접속 경로는 구현 전 별도 검증 대상이다. AI 추천은 방 목록 먼저, 닉네임 선택 입력이며 아직 사용자가 확정하지 않았다. 프런트 구현이나 외부 이슈 변경은 하지 않았다.

## 디자인 질문의 속도 조절

사용자는 방 선택과 닉네임 입력을 함께 해야 한다고 정정했다. 원하는 분위기는 개방된 오피스 사이의 사내 카페다. 이를 별도의 닉네임 선행 화면으로 해석하지 않는다. 한 화면의 구체적 배치와 재방문 사용자 처리는 아직 정하지 않았다.

**질문:** 어렵다. 오늘 안에 다 정해야 할까?

**답변:** 오늘 모두 확정할 필요는 없다. 현재 방향을 바탕으로 다음에는 코드 없이 간단한 화면 구성안 두 개를 비교하면 된다. 색상·글꼴·창문 표현은 실제 구성을 보며 다듬고, 열린 방이 없는 상태는 '운영 시간 안내'를 추천 후보로 남긴다. 질문을 한꺼번에 늘리지 않고 결정에 필요한 구체적인 안부터 보여준다. grilling의 공유된 이해 확인은 구현 전에 하며, 오늘 모든 디자인을 끝내야 한다는 뜻은 아니다.

## 추가 스킬과 세션 마무리

사용자는 종료 절차 중 Web Interface Guidelines와 React Best Practices도 설치해 달라고 요청했다. skill-installer로 Vercel 공식 vercel-labs/agent-skills의 두 디렉터리를 설치했다. SKILL.md의 이름은 각각 web-design-guidelines, vercel-react-best-practices이며 사용자 Codex 스킬 폴더에 존재함을 확인했다. 다음 턴부터 사용할 수 있다. UI 검토와 React/Next.js 성능 검토에 활용하고 설치만으로 프런트 구현을 시작하지 않는다.

make fclean이 성공했다. PostgreSQL 컨테이너와 프로젝트 네트워크를 제거하고 Docker Desktop 종료 성공 응답을 확인했다. 데이터 볼륨 삭제나 임의 강제 종료는 하지 않았다. 오늘은 문서와 스킬 설치만 변경했으므로 백엔드 테스트는 다시 실행하지 않았다. 다음 시작 지점은 방 선택·닉네임을 함께 제공하는 사내 카페 화면 구성안 두 개 비교다. 이번 문서 변경만 커밋·푸시하며 기존 breakground.zip 삭제와 .DS_Store는 제외한다.

**추가 질문:** create-design-system-rules는 어떨까?

**답변:** Figma 공식 문서의 create_design_system_rules는 디자인을 저장소의 구현 방식에 맞춰 옮기도록 프로젝트 규칙 파일을 만드는 프롬프트다. 스킬 이름과 MCP 기능을 구분해야 한다. 지금은 Figma 연결과 프런트 컴포넌트·디자인 규칙이 없으므로 추가 도입은 보류하는 것을 추천한다. 화면 방향을 선택한 뒤 색상·간격·버튼 등 합의한 규칙을 문서로 남기는 작업은 별도로 할 수 있다. 설치나 계정 연결은 하지 않았다. 근거: https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/.

## to-spec — 최신 합의 반영

사용자가 to-spec을 요청했다. 기존 GitHub 프런트 MVP 명세 #2의 본문·라벨·OPEN 상태를 조회하고 중복 명세를 만들지 않기로 했다. 로컬 명세에 방 선택·닉네임 동시 표시, 사내 카페 방향, 설치한 세 스킬과 Stitch 연결 보류를 반영했다. 공백 검사를 통과했다. triage 매핑은 여전히 미승인 초안이므로 스킬의 설정 전제와 테스트 경계 확인을 마치기 전 ready-for-agent 생성·적용 및 외부 명세 갱신은 수행하지 않았다. 종료한 개발 환경은 다시 시작하지 않았다.

## to-tickets — 미결정과 구현 준비 상태 구분

사용자가 to-tickets를 요청해 기존 네 기능 티켓과 현재 GitHub OPEN 목록을 확인했다. 새 티켓을 발행하거나 기존 이슈·부모·라벨·의존 관계를 변경하지 않았다.

**질문:** 정하지 않은 부분이 있는데 이슈·티켓을 쪼개는 것이 성급한가?

**답변:** 큰 기능을 분할 초안으로 정리하는 것은 가능하지만, 세부 정책이 열려 있는 구현 티켓을 ready-for-agent로 표시하는 것은 성급하다. 미결정은 디자인·접속 경로 같은 결정 이슈로 유지하고, 구현 티켓은 실제 선행 조건이 해결된 뒤 범위·완료 기준을 확정한다. 현재는 기존 이슈를 중복 생성하지 않고 기능 분할을 잠정적인 지도로 사용한다. 모든 세부 사항을 결정할 필요는 없으며, 첫 기능을 구현하는 데 필요한 결정부터 해결하면 된다.

## 사내 카페 구성안 두 개

사용자가 구성안을 요청했다. frontend-design 지침으로 색상·한글 글꼴·정렬·배치와 ASCII 구조를 먼저 작성하고 검토했다. 창가 라운지는 상단 풍경 아래 입장 영역, 오피스 사이 카페는 좌측 풍경·우측 입장 영역이다. 추천은 두 번째이며 아직 사용자가 선택하지 않았다. 비교 계획은 docs/drafts/frontend/lounge-layout-options.md에 있다.

대화에서 두 안을 바꿔보고 방 선택·닉네임 입력을 확인할 수 있는 시안을 준비했다. 신규 방문·평일 10:30 점심메뉴방 예시라고 명시하고 실제 API·쿠키·WebSocket에는 연결하지 않았다. 실제 frontend 디렉터리와 의존성은 생성하지 않았다. 열린 방 없음·목록 실패 상태도 비교할 수 있고, 닫힌 방·다음 개장 시간·참가자 수를 가짜 데이터로 제시하지 않는다. JavaScript 구문 검사와 시안 파일 구조 검사가 통과했으며 실제 서비스 접속 테스트와 다르다.

### 사용자 피드백 — 공간이 중심이어야 한다

사용자는 두 구성안이 뻔한 게시판처럼 느껴져 선호하지 않는다고 했다. AI는 창가를 장식으로 처리하고 실제 화면을 목록·폼으로 둔 점을 인정했다. 이후 사용자는 평면 일러스트보다 '공간을 바라보는 듯한 느낌'에 가깝다고 답했다. 기존 구성안을 승인한 것으로 취급하지 않는다.

카페 입구에서 창가·긴 공용 테이블·주변 오피스가 보이는 원근감 있는 장면을 중심으로 다시 탐색한다. 대화 주제 선택 시 같은 화면에서 닉네임과 입장 영역이 펼쳐지는 방식은 AI 제안이며 아직 확정된 상호작용이 아니다. 아바타·좌석 이동은 도입하지 않는다. imagegen 스킬의 기본 이미지 생성 도구로 공간감 검토용 이미지 시안을 요청했다. 이는 이미지 탐색이며 서비스 프런트 구현·실제 입장 기능 검증이 아니다.

이미지 생성이 완료되어 대화에 표시됐다. 유리로 구분된 오피스·넓은 창·긴 테이블을 원근감 있게 표현하고, 입장 영역은 오른쪽에 작게 배치한 신규 방문 예시다. 사용자 검토 전으로 확정 자산이 아니며 이미지 자체는 클릭 가능한 UI가 아니다. 특히 입장 영역을 실제 화면에서 얼마나 눈에 띄게 할지와 모바일 구도는 후속 검토가 필요하다.

**추가 피드백:** 사용자는 '탁자에 앉아 있는 느낌'을 원한다고 설명했다. 카페 입구의 관찰자 시점보다, 사용자가 이미 창가 탁자에 앉아 짧게 쉬는 1인칭 시점으로 이해했다. 가까운 탁자 면을 화면 아래에 두고 앉은 눈높이에서 창과 오피스를 바라보는 수정 시안을 요청했다. 아바타나 실제 좌석 선택 기능을 추가한다는 뜻은 아니다. 공간감 방향을 확인하는 단계이며 상호작용·입장 패널 위치는 아직 확정하지 않는다.

**시선 방향 수정:** 사용자는 앉은 공간감은 맞지만 시선은 햇살과 반대쪽이어야 한다고 했다. AI는 햇살·창을 등 뒤에 두고 카페 안쪽과 그 너머 오피스를 바라보는 방향으로 해석해 수정 시안을 요청했다. 탁자와 앉은 눈높이는 유지한다. 이미지의 입장 패널이나 최종 UI 승인과는 별개다.
