## 실행 결과

- 기존 Spring 전체 검사는 97개 통과했다. 이후 UTC 시간대 회귀 검사 한 개를 추가한 최종 실행은 총 98개 중 97개 통과, 1개 실패다. 중간 안내에서 107개라고 한 수치는 잘못 합산한 것으로 XML 결과 기준으로 바로잡았다.
- `./gradlew test --rerun-tasks`의 유일한 실패는 `RoomTimeZoneTest.roomListUsesTheSameSeoulTimeAsChatWhenServerDefaultsToUtc`다. 서울 시간에 열려 있는 방 하나를 기대했으나 목록은 빈 배열이었다.
- 원인은 `RoomController.getRooms()`의 `LocalDateTime.now()`와 채팅에서 사용하는 `Asia/Seoul` Clock의 차이다. 서버 기본 시간대가 UTC이면 9시간 차이가 생긴다. 다음 수정은 컨트롤러에도 기존 Clock을 주입하는 것이다. 익명 사용자 서비스의 시스템 시간 직접 사용도 확인이 필요하다. 이번 작업은 테스트와 재현 기록까지 진행했다.

- 재방문 사용자의 ID·닉네임·쿠키 유지, 인증 없는 접속 401, 외부 Origin 거절 403, 잘못된 JSON·본문 타입·빈 문자열·NUL·141자 입력 거절을 확인했다. 오류 뒤에도 같은 연결에서 140자 이모지 포함 메시지를 보낼 수 있었다. 작성자와 방을 클라이언트가 위조한 필드는 서버가 신뢰하지 않았다.

## 재현과 다음 작업

```sh
./gradlew test --tests com.breakground.room.RoomTimeZoneTest --rerun-tasks
```

이 명령은 현재 시간대 결함 때문에 실패한다. 운영 코드 수정 후 통과해야 한다. 회귀 검사는 JVM 기본 시간대를 UTC로 바꾸고 종료 시 원래 시간대로 복구하며, 다른 테스트와 동시 실행되지 않게 설정했다.

프런트 깊은 검사는 PostgreSQL·Spring·프런트가 실행 중이고 기존 방이 운영 중일 때 frontend 디렉터리에서 실행한다.

```sh
RUN_LIVE_TESTS=1 RUN_LIVE_DEPTH_TESTS=1 npm test
```

실제 연동으로 만든 테스트 사용자·메시지·신고는 로컬 DB에 남는다. PostgreSQL·Spring·프런트를 실행한 상태로 유지했다. 실제 휴대전화 키보드, HTTPS와 프록시 뒤 Secure 쿠키, 느린 수신자, 장시간 실행, 운영 규모 부하, 각 게임의 브라우저 조작과 WebGL 성능은 이번 자동 검사에서 검증하지 않았다.

## 시간대 결함을 어떻게 개선할까

첫 수정은 RoomController가 기존 applicationClock 빈을 생성자로 주입받고 LocalDateTime.now(clock)으로 방 목록 조회 시각을 구하도록 하는 것이다. @RequiredArgsConstructor가 있으므로 final Clock 필드를 추가하면 Lombok이 생성자에 포함하고 Spring이 등록된 Clock 빈을 전달한다. 이 Clock은 Asia/Seoul로 설정되어 있어 서버 기본 시간대가 UTC여도 채팅과 동일한 기준을 사용한다.

컨트롤러 생성자가 바뀌면 RoomTimeZoneTest의 직접 생성 코드에도 같은 Clock을 전달해야 한다. 기대하는 열린 방 목록은 유지하고, 해당 테스트를 먼저 실행한 뒤 전체 검사를 수행한다. 다음 작은 작업은 AnonymousUserService.getOrCreateAnonymousUser의 시스템 시각 사용도 기존 Clock으로 맞추는 것이다. 이번 답변에서는 사용자가 먼저 수정할 수 있도록 위치와 작은 코드 조각을 안내했다.
