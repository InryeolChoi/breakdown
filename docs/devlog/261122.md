# 2026-11-22

## 목표

AWS CLI로 서울 리전 Lightsail 인스턴스를 만들고 Breakground를 HTTPS로 띄운다.

## 시작 상태

- 로컬 Compose는 개발용 PostgreSQL만 실행한다. 세션 시작 시 Docker Desktop과 PostgreSQL을 시작했다.
- AWS CLI는 설치되어 있었다. 브라우저 로그인 이후 STS로 인증을 확인했다.

## 배포 구성

- Ubuntu 24.04, 2GB Lightsail 한 대를 선택했다. 기본료는 월 $12다.
- Docker Compose에서 Caddy가 HTTPS를 받고, 브라우저와 같은 출처의 API 및 WebSocket을 Spring으로 전달한다. PostgreSQL은 내부 네트워크에 두고 데이터를 볼륨에 저장한다.
- Spring이 프록시 뒤의 원래 HTTPS 요청을 인식하도록 전달 헤더를 처리한다. 익명 쿠키의 Secure 속성과 WebSocket의 Origin 검사에 필요하다.

## 배포 결과

- 서울 리전의 `breakground` 인스턴스에 고정 IPv4 `43.202.20.1`을 연결했다. HTTP와 HTTPS는 공개하고 SSH는 작업자 IP와 Lightsail 브라우저 콘솔에 허용했다.
- Mac의 Docker에서 Linux amd64 이미지를 빌드하고 임시 SSH 인증서로 서버에 전송했다. 서버의 `~/breakground`에서 `sudo docker compose -f compose.production.yml up -d --no-build`로 실행한다. DB 비밀번호는 서버의 `.env`에만 저장했다.
- 도메인 없이 Let’s Encrypt의 짧은 수명 IP 인증서를 Caddy가 자동 발급·갱신하도록 설정했다. IP 접속 시 SNI를 보내지 않는 클라이언트에도 인증서를 제공하도록 Caddy 기본 SNI를 지정했다.
- 외부에서 HTTPS 홈·미니멀 화면·게임 목록·방 API 200, HTTP→HTTPS 308, 익명 쿠키 Secure·HttpOnly, 쿠키 없는 WSS 요청 401을 확인했다. Flyway V1~V10이 적용됐다.
- 로컬의 격리된 PostgreSQL에만 주말 운영 시간을 열어 HTTPS 채팅 왕복·신고·중복 신고를 확인했다. 운영 DB의 방 시간표는 그대로 사용하므로 주말에는 열린 방이 없고, 운영 WSS 메시지 왕복은 평일 운영 시간에 확인한다.
- GitHub Actions에서도 두 Dockerfile을 그대로 빌드해 커밋별 이미지를 배포할 수 있다. 첫 배포는 수동으로 진행했다. GitHub 호스팅 러너에서 운영 서버로 접근하는 방식과 자동 배포 후 검증은 다음 작업이다.

## 로컬 재실행과 운영 버전 비교

로컬 PostgreSQL과 Spring을 실행하고 현재 main의 `fcde071`에서 프런트 production 빌드를 새로 띄웠다. Lightsail은 running 상태였고, 운영 PostgreSQL은 Compose에서 healthy로 표시됐다. 운영 HTTPS의 미니멀 화면, 게임 목록, 미니어처 철거, 방 API가 모두 200을 반환했다.

비교한 세 프런트 화면이 불러오는 JS·CSS는 로컬과 운영에서 바이트가 모두 일치했다. 운영 Spring 컨테이너의 JAR와 로컬 `bootJar`를 비교한 결과 클래스·리소스 55개와 의존 라이브러리 77개도 모두 일치했다. 운영 Compose와 Caddyfile의 SHA-256은 로컬 파일과 같았다.

로컬 루트는 디자인 비교 화면이고 운영 루트는 Caddy의 302 응답으로 미니멀 화면에 들어간다. 같은 미니멀 화면을 비교하려면 양쪽 모두 `/minimal`로 접속한다. 로컬과 운영의 방 목록은 일요일에 모두 빈 배열이었고, 쿠키 없는 WebSocket 연결은 양쪽 모두 401로 거절됐다. 운영에서 인증된 사용자의 채팅 왕복은 평일 방 운영 시간에 확인한다.

테스트 버전의 완료 기준은 수정한 UI가 운영 HTTPS에 올라가고, 운영 중인 방에서 실제 휴대폰과 PC로 입장부터 채팅 왕복·신고까지 성공하는 것이다. GitHub Actions 자동 배포, 신고 관리자 화면·자동 차단, 게임 점수 저장·랭킹, 운영 규모 부하는 후속 작업으로 제안한다.

사용자는 현재 UI가 아쉽다고 했다. 구체적으로 어떤 요소가 문제인지는 아직 정하지 않았다. 첫 시안에서는 초기 진입 화면을 우선 살핀다. 열린 방과 입장 버튼에 시선이 모이고, 닫힌 시간에도 다음 운영 시간과 체험 진입을 찾을 수 있는 구성을 제안한다.

## UI 방향, 채팅 입력, 테스트 버전 후보

첫 화면은 단순한 2D, 색과 타이포그래피를 강조한 2D, 카페 공간을 보여주는 3D 구도로 비교했다. 제안은 방의 열림 여부와 입장 버튼이 먼저 보이는 2D를 기본으로 하고, 저녁과 야근 등 운영 시간대의 분위기는 색과 정적인 배경으로 표현하는 것이다. 닫힌 상태에는 다음 운영 시각과 체험 링크를 둔다. 3D는 미니어처 철거처럼 공간이 조작에 직접 쓰이는 게임에 잘 맞는다. 첫 화면 시안은 아직 선택하지 않았다.

게임은 점심 카페 러시를 먼저 개선하는 방향을 제안한다. 첫 주문은 버튼을 익힐 수 있도록 하나씩 내고, 이후에는 한꺼번에 들어오는 주문 때문에 먼저 준비할 메뉴를 선택하게 한다. 라운드 결과에 놓친 이유를 보여주고 같은 주문표로 즉시 재도전할 수 있게 하면 두 번째 판에서 다른 순서를 시험할 수 있다. 새 게임 개발에 앞서 연속 두 판을 하는지와 어디에서 조작을 놓치는지 본다.

추가 서비스 후보는 3분 쉬는 타이머와 오늘의 한 표다. 타이머는 브라우저에서 시작·정지하고, 방이 닫혀 있거나 혼자 왔을 때도 쓸 수 있다. 오늘의 한 표는 점심 메뉴처럼 선택지가 정해진 질문에 기존 익명 세션당 하루 한 번 응답하고 합계를 보여준다. 먼저 타이머 한 화면을 제안하고, 투표는 날짜 기준과 중복 투표 처리를 설계한 뒤 검토한다.

채팅에서는 작성 중 텍스트 상태를 별도 입력 컴포넌트로 옮겼다. 한 글자를 입력할 때 채팅 화면 전체와 최대 200개 메시지 목록을 다시 렌더링하던 경로를 제거했다. 로컬 브라우저에서 141자 거절 후 작성 내용 유지, 한글과 Shift+Enter 줄바꿈, Enter 전송과 서버 응답 표시, 전송 후 입력 초기화를 확인했다. production 빌드와 타입 검사도 통과했다. 휴대전화 입력 지연의 전후 시간과 한글 IME 조합 중 동작은 실기기에서 확인해야 한다.

격리된 PostgreSQL 스키마와 프록시에서 24개 연결이 각각 20개씩 입력해 총 480개 메시지를 모든 연결에서 누락·중복 없이 받는지 확인했다. 다른 방이 메시지를 받지 않는지, 같은 방에 다섯 번 연속 재접속해도 다음 메시지를 받는지, 동시 중복 신고 12개 중 하나만 접수되는지도 검증했다. 새 production 프런트 빌드에서 전체 17개를 세 번 반복 실행했고 모두 통과했다. 이는 로컬에서 짧게 실행한 동시성 검사다. 운영 HTTPS 채팅 왕복과 실제 휴대폰 입력 확인은 테스트 버전의 완료 기준에 남아 있다.

수정본은 일반 로컬 주소 `http://127.0.0.1:3000/minimal`과 열린 테스트 방이 있는 격리 주소 `http://127.0.0.1:13000/minimal`에서 실행 중이다. 격리 주소에서 실제 서버 모드로 바꾸면 운영 시간과 무관하게 테스트 방에 들어갈 수 있다. 격리 스키마와 테스트 데이터는 이 확인을 위해 남겨뒀다. 채팅 수정은 운영에 배포하지 않았다.

### 첫 화면 정리와 테마 선택

로컬 첫 화면을 실제 방 목록부터 보여주는 흐름으로 바꿨다. 방이 열렸을 때만 닉네임과 입장 버튼을 보여주고, 닫혔을 때는 평일 운영 안내와 채팅 체험으로 이어진다. 배경 조작은 하단의 화면 분위기 안에 모았다. 로컬 루트도 운영의 진입 흐름에 맞게 미니멀 화면으로 보낸다. 기본 테마는 온기로 바꾸고 한글 글꼴은 고운 돋움 WOFF2를 사용한다.

화면 분위기를 누르면 빙하·온기·대나무숲·블랙이 왼쪽에서 오른쪽으로 커튼처럼 0.36초에 걸쳐 한 줄로 펼쳐진다. 모션 감소 설정에서는 즉시 표시한다. 브라우저 360·760·1280px에서 가로 넘침이 없었고, 360px에서 테마 한 줄 배치와 대나무숲 적용을 확인했다. 체험 입장과 복귀, 실제 로컬 테스트 방 닉네임 입장 및 전송도 확인했다. 프런트 빌드·타입 검사와 기본 테스트 9개가 통과했다. 현재 수정본은 로컬에서 볼 수 있다.

### 간식 고르는 느낌의 첫 화면

사용자는 게임의 위치를 고민하며 게임·채팅방·명상이 간식을 고르듯 느껴지길 원했다. 첫 화면 제목 아래에 '이야기 · 게임 · 명상'을 같은 높이의 세 선택지로 배치하는 방향을 제안한다. 현재 헤더의 게임 링크는 첫 화면의 선택지로 옮기는 안이다. 각 선택지에는 이름과 작은 그림을 두고, 고른 활동의 시작 UI를 바로 아래에 표시한다. 채팅은 열린 방과 상태, 게임은 바로 할 수 있는 한 판과 게임 목록, 명상은 3분 시작으로 이어지는 안이다. 모바일에서도 세 선택지를 한 줄로 유지하고 상세 영역은 아래로 쌓는다. 명상은 신규 기능 후보이며 이번 논의는 화면 배치 제안이다.

첫 화면 제목 아래에 찻잔·쿠키·사탕으로 채팅·게임·명상을 고르는 선반을 구현했다. 기본값은 채팅이다. 게임은 점심 카페 러시와 전체 게임 목록을 연결했다. 명상은 브라우저에서 3분 타이머를 시작·일시정지·재개할 수 있게 했다. 다른 활동을 선택하면 타이머가 초기화된다. 로컬 브라우저에서 세 선택지의 한 줄 배치와 전환, 카페 러시 링크, 타이머 카운트다운과 일시정지를 확인했다. 프런트 빌드와 타입 검사, 기본 테스트 9개가 통과했다.

선반을 처음에 보여주고 채팅·게임·명상 중 하나를 고르면 위로 접히면서 활동 화면이 나오게 바꿨다. 목록을 내려 보다가도 찾도록 헤더 오른쪽에 선반 열기 버튼을 고정했다. 이 버튼으로 돌아오면 선반이 위에서 아래로 펼쳐진다. 채팅방은 선택 행에 방 이름과 운영 시간을 나누고, 선택한 행을 테두리와 배경으로 강조했다. 게임은 기존 게임 목록과 목록 데이터를 공유하며 첫 화면에서 8개를 모두 선택할 수 있다.

360px 브라우저에서 게임 8개, 스크롤 중에도 보이는 선반 열기, 채팅의 빈 상태와 체험 전환을 확인했다. 열린 방이 있는 격리 환경에서는 두 번째 방을 선택해 입장하고 방 목록으로 돌아왔다. 빌드·타입 검사와 기본 테스트 9개가 통과했다.

### 하단 선반, 빙하 미스트, 메일비행기

선반을 첫 화면 아래쪽에 놓았다. 활동을 고르면 찻잔·쿠키·사탕이 함께 높이를 줄이며 화면 위로 말려 올라간다. 선반을 접었을 때만 오른쪽 하단에 선반 열기가 보인다. 로고 주변 헤더의 배경과 선을 제거하고 테마 강조색으로 글자를 표시한다. 로고를 누르면 채팅에서 나와 첫 선반으로 돌아온다. 게임의 게임 목록 링크는 초기 화면에 통합한 게임 목록으로 복귀한다.

빙하 테마를 천장 채광, 벽과 바닥 원근, 반투명 UI로 바꿨다. 원형 안개를 겹친 첫 버전의 모양이 참고 이미지와 달라, 여러 크기의 질감을 섞은 캔버스 미스트를 사용했다. 안개는 뒤에서 천천히 내려와 바닥에서 옆으로 퍼지고, 전경에는 낮은 투명도로 흐른다. 마우스에 배경·패널·앞쪽 미스트가 다른 정도로 움직이며 모션 감소 설정과 수동 정지를 지원한다.

종이비행기 이름을 메일비행기로 변경했다. 시작 후 메일이 자동으로 나오고, 한 번 날릴 때마다 다음 메일도 자동으로 접힌다. 동료가 시선을 돌린 사이 뒤로 당겼다가 놓아 발사한다. 동료가 쳐다보면 옆으로 숨기고, 노출되는 시간이 길거나 보이는 중 발사하면 게임 오버다. 방향키·Space·H 입력도 지원한다.

로컬 브라우저에서 선반 위치와 헤더 배경 제거, 채팅 중 로고로 홈 복귀, 게임 목록 복귀, 빙하 앞뒤 미스트, 메일 자동 접힘·숨기기·들켰을 때 게임 오버·키보드 발사를 확인했다. 프런트 타입 검사와 빌드, 기본 테스트 9개가 통과했다. 실제 휴대폰의 터치 조작과 성능은 아직 확인하지 않았다.

화면 분위기를 누를 때 글자가 위로 이동하지 않고 같은 높이에서 '화면'과 '분위기'가 양옆으로 벌어지며 그 사이에 테마 네 가지가 나타나도록 수정했다. 빙하에서는 입체 벽·바닥을 제거하고 밝은 2D 그라데이션 위에 기존 캔버스 미스트를 유지했다. 메일비행기 동료 네 명에게 서로 다른 키·색과 얼굴·옷·팔다리 형태를 적용했다. 360px에서 메뉴가 글자 사이 한 줄에 들어가는 점, 빙하의 앞뒤 안개와 게임의 WebGL 렌더링·메일 숨기기 동작을 로컬에서 확인했다. 프런트 빌드·타입 검사와 기본 테스트 9개가 통과했다.

화면 분위기 글자는 열 때 양옆으로 찢어지듯 흩어져 사라지고, 배경을 누르거나 Escape를 누르면 메뉴가 닫히며 글자가 복원된다. 첫 화면 선반의 얇은 구분선을 없애고 둥근 받침과 그림자를 넣었다. 빙하에서 마우스 위치를 사용하던 효과를 제거했다. 두 캔버스의 아래로 흐르는 미스트는 유지한다. 로컬 브라우저에서 글자 숨김·복원, 바깥 클릭 닫힘, 정지된 미스트 레이어 위치와 새 받침을 확인했다. 빌드·타입 검사와 기본 테스트 9개가 통과했다.

사용자는 빙하 테마에 만족했고 냉기 켜기·멈추기 버튼을 없애길 원했다. 빙하를 선택하면 미스트가 자동으로 흐르고, 시스템에서 모션 감소를 선택한 경우에는 정적인 안개를 보여준다. 로컬 브라우저에서 빙하 선택 시 안개 캔버스 두 개가 표시되고 관련 버튼이 사라진 것을 확인했다.

### 메일비행기 조작 개선과 게임 정리

사무실에 책상 구역, 통로, 유리 회의실을 추가했다. 동료가 걷는 방향에 맞춰 몸을 돌리고 시선과 팔·다리가 따로 움직이도록 했다. 모니터 버튼을 누르면 메일을 숨기고 업무 진행표를 띄운다. 동료를 길게 누르면 강도 조절이 열리며, 15~100%의 강도가 발사 속도와 예상 궤적에 반영된다. 로컬 브라우저에서 업무 화면 전환, 길게 누르기, 강도를 100%로 조절해 발사하는 흐름을 확인했다.

사용자는 게임을 다시 구상하기 위해 메일비행기만 남기기로 했다. 나머지 시제품 7개의 페이지와 전용 코드, 규칙 테스트를 제거했다. 프런트 빌드와 타입 검사, 채팅 계약 검사 4개가 통과했다. 로컬 HTTP 확인에서 게임 목록에는 메일비행기 링크 하나만 나왔고, 메일비행기는 200, 제거한 7개 주소는 404를 반환했다.

### 직원 시점과 동료 20명

플레이어의 자리를 중앙 대형 책상에서 옆줄의 일반 직원 책상으로 옮겼다. 20명의 동료가 다섯 통로를 서로 다른 속도로 걷고, 가까운 통로는 플레이어의 책상 옆을 지난다. 가시 범위에 있는 동료는 잠시 멈춰 플레이어를 바라볼 수 있다. 두 가지 CC0 인물 모델의 얼굴·옷 텍스처와 보행·정지 애니메이션을 사용했다. 멀리 있는 통로에는 더 가벼운 모델을 적용했고 출처와 라이선스는 게임 자산 디렉터리에 남겼다.

메일 제목은 모니터의 편지함에 표시한다. 화면 위에 뜨던 별도 메일 카드는 없앴고, 접힌 종이비행기가 모니터 옆에서 책상 위로 나온다. 브라우저에서 가까이 걸어오는 동료, 길게 눌러 발사, 업무 화면 전환, 노출 시 게임 오버를 확인했다. 360px에서도 업무 버튼이 모니터 위에 표시됐다. 프런트 타입 검사·빌드와 기본 테스트 4개가 통과했다. 실제 휴대전화에서 렌더링 성능은 확인하지 않았다.

## 운영 주소와 GitHub Actions

첫 배포에서 기본 주소 `/`가 예전 디자인 비교 화면을 보여줬다. 개선한 미니멀 UI는 이미 `/minimal`에 있었다. 운영 Caddy에 `/`를 `/minimal`로 보내는 302 리디렉션을 적용했다. 외부에서 302를 따라가 미니멀 화면이 200으로 열리고, 게임 목록과 방 API도 각각 200을 반환하는 것을 확인했다. 이후 일지에서 다룬 추가 UI와 게임 개선은 로컬 검증 기준이다.

운영 흐름은 브라우저 → Caddy → Next.js 또는 Spring Boot다. 브라우저는 한 주소에서 페이지와 게임을 받고, 같은 주소의 `/api/*`와 `/ws/rooms/*`로 방 목록과 채팅에 접속한다. Spring은 Docker 내부 네트워크에서 PostgreSQL에 연결하고, 데이터는 Docker 볼륨에 남는다. Ubuntu 24.04의 서울 Lightsail 2GB 한 대에서 네 컨테이너를 실행한다.

GitHub Actions는 PR에서 테스트·빌드를 실행하고, 검증한 `main` 커밋의 이미지를 SHA 태그로 GHCR에 발행한 뒤, 운영자가 방이 닫힌 시간에 배포를 실행하는 방식을 논의했다. 현재 SSH는 작업자 IP와 Lightsail 콘솔에만 열려 있다. Actions가 배포 명령을 전달할 인증 경로와 배포 후 확인 절차는 아직 설정하지 않았다. 배포 시 Spring이 재시작되면 열린 채팅 연결이 끊어진다.

## AWS와 코드 보안 점검

AWS CLI 세션 만료로 첫 조회가 막혔다. 브라우저에서 재인증한 뒤 서울 리전의 Lightsail, AWS 계정 설정, 운영 컨테이너와 공개 HTTPS 응답을 확인했다. 당시 호출 주체는 계정 root였다. root MFA는 활성화되어 있고 장기 액세스 키는 0개였다. 80·443만 전체 공개하고 SSH는 제한했다. IMDSv2 토큰 필수, 운영 `.env` 권한 `600`, 운영 DB 내부 네트워크 설정도 확인했다.

운영 Spring이 PostgreSQL의 슈퍼유저로 연결하고 있었다. 익명 세션 발급, 채팅 연결, 메시지·신고 빈도에 서비스 차원의 한도가 없었다. 순차 WebSocket 방송은 느린 수신자가 다른 사용자에게도 영향을 줄 수 있었다. 개발 DB는 5432를 모든 호스트 인터페이스에 게시했다. 운영에서는 스냅샷·경보·CloudTrail trail·서울 AWS Backup 계획을 찾지 못했다. Ubuntu는 보안 자동 업데이트가 활성화됐고 재부팅 필요 상태였다.

실행 중인 이미지 네 개를 Trivy로 검사했다. Critical/High 패키지 권고는 Spring Boot 4/5, Next.js 1/43, Caddy 0/2, PostgreSQL 2/151이었다. 운영 Spring에서 Tomcat 11.0.24와 Jackson 3.1.5를 확인했다. 이 숫자는 **패치 전** 이미지의 패키지 버전 대조 결과다. 항목별 수정 버전과 영향 범위는 별도 보고서에 있다. ## 운영 보안 설정 변경과 확인

- AWS 계정의 S3 버킷이 0개인 것을 확인하고 계정 수준 S3 공개 차단 네 항목을 활성화했다. 변경 후 재조회에서 모두 `true`였다.
- 운영 Caddy의 Spring HTTP API 경로를 허용 목록으로 좁히고 본문 크기를 16KB로 제한했다. CSP로 프레임·object 삽입과 base URI를 제한하고, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`도 추가했다. 운영에서 익명 쿠키 없는 채팅 연결 401, 초과 본문 413, 개발용 Echo의 API 경로 404를 확인했다.
- 운영 미니멀 화면과 방 API를 각각 20회 조회했다. 최대 동시 요청은 4개였고 40회 모두 HTTP 200이었다. 외부 클라이언트에서 새 HTTPS 연결로 측정한 중앙값은 47.4ms, p95는 1,142.7ms, 최대는 1,147.2ms였다. 단일 저부하 측정이다. 운영 채팅의 수용 인원이나 지연 원인은 확인하지 않았다.
- 개발 DB를 `127.0.0.1:5432`에만 게시했다. Gradle 9.7.1 배포 ZIP의 공식 SHA-256을 Wrapper에 저장했고 빈 캐시에서 다운로드와 실행을 확인했다.
- Spring Boot를 4.1.3으로 올렸다. Tomcat 11.0.27과 Jackson core·databind 3.1.8을 포함한 JAR를 만들었고 Spring 테스트 101개가 통과했다.
- 격리 DB에서 `breakground_app`과 `breakground_flyway`를 분리하고 Spring 시작과 익명 세션 발급을 확인했다. 앱 역할은 스키마 생성과 Flyway 이력 조회 권한이 없다. 메시지 만료 삭제와 신고 삽입 권한을 확인했다.
- Lightsail 스냅샷 `breakground-before-db-hardening-20261122`가 `available`이 된 뒤, 열린 방이 없는 시간에 운영 백엔드 패치와 DB 역할 전환을 적용했다. 운영 연결 10개가 앱 역할을 썼고 새 역할 두 개 모두 슈퍼유저·역할 생성 권한이 없었다. 컨테이너 네 개에서 최대 10MB 로그 파일 3개로 회전하도록 설정했다. 외부 미니멀 화면과 방 API는 HTTP 200을 반환했다.

스냅샷 대기 중 검토한 Mac 임시 파일 백업은 운영 메시지·신고 증거가 포함될 수 있어 자동 승인 검토에서 거절됐다. DB 데이터는 전송하지 않았다. 수동 스냅샷은 저장 요금이 발생하고 복원 훈련은 아직 하지 않았다. Spring 시작 시 Flyway가 실행되므로 백엔드 컨테이너가 두 DB 자격 증명을 모두 받는다.

## 이어서 확인할 보안 작업

1. AWS 운영자를 최소 권한 역할과 임시 자격 증명으로 전환하고 배포·접속을 검증한다. GitHub Actions에는 별도 OIDC 역할과 운영 배포 경로가 필요하다.
2. 정기 암호화 백업과 만료를 설정하고 격리 환경에 실제 복원한다. 신고·일반 메시지의 보관 기한을 백업에도 적용한다.
3. 세션 발급·WebSocket 연결·채팅·신고에 한도를 두고, 느린 수신자의 전송 시간과 버퍼를 제한한다. 공유 IP에서 정상 사용자가 함께 접속하는 경우를 검증한다.
4. Flyway를 별도 배포 단계로 옮기고, 프런트·Caddy·PostgreSQL 이미지를 패치한 뒤 운영 이미지를 다시 검사한다. 호스트 재부팅, 디스크·백업 실패 경보, 평일 운영 채팅의 실제 왕복과 신고 검증도 남아 있다.

### 메일비행기 한 번 누르기

움직이는 대상을 조준하면서 강도·방향·동료의 시선까지 동시에 다루는 조작이 어려웠다. 매번 배달 대상 한 명을 머리 위 화살표로 표시하고, 화살표를 누르면 그 동료에게 자동으로 날아간다. 게임 화면에 포커스를 두고 Enter와 Space로도 발사할 수 있다. 대상이 이쪽을 보는 동안에는 잠시 기다리면 되며, 자동 게임 오버는 제거했다. 업무 화면과 숨기기 조작도 제거했고 모니터에는 파란색 사내 메일함을 표시한다.

가까이 있는 고해상도 인물 모델을 우선 배달 대상으로 고르고, 대상이 멈춰 비스듬히 서도록 했다. 얼굴을 비추는 조명을 추가했다. 인물 모델 자체는 기존 두 가지를 사용한다.

로컬 브라우저에서 다른 동료를 눌러도 발사하지 않는 점, 시선이 돌아왔을 때 발사가 막히는 점, 화살표와 Enter로 메일 5통 배달을 완료하는 흐름을 확인했다. 프런트 빌드·타입 검사와 기본 테스트 4개가 통과했다.

### 계속 움직이는 배달 대상과 시선 피하기

배달 대상으로 골라도 동료가 하던 보행이나 착석은 그대로 이어진다. 내 책상 옆 통로를 지나며 가까운 의자에 잠깐 앉았다 일어나는 동료가 있다. 화살표는 머리 위치를 따라가고, 비행기는 발사 이후에도 움직이는 배달 대상으로 날아간다. 대상이 화면에서 벗어나면 화면 안의 다른 동료를 표시한다.

대상이 돌아보기 직전에는 화살표가 빨갛게 바뀐다. 이때 먼저 발사하거나 일하는 척 버튼을 한 번 눌러 피할 수 있다. 업무 화면으로 전환하면 비행기가 숨겨지고 시선이 지나간 뒤 편지함과 발사 조작이 자동 복구된다. 메일을 들고 있다가 눈이 마주치면 게임이 끝난다. 로컬 브라우저에서 화살표 이동과 자동 조준, 업무 화면 전환 뒤 발사 재개, 대응하지 않았을 때 게임 오버를 확인했다. 프런트 빌드·타입 검사와 기본 테스트 4개가 통과했다.

### 빈도 제한

단일 서버이므로 Redis 없이 Spring 메모리의 토큰 버킷(`RateLimiter`)으로 구현했다. 재시작하면 카운트가 초기화되고, 서버를 늘리면 공유 저장소가 필요하다. 다 찬 버킷은 1분마다 지운다.

| 대상 | 키 | 한도 | 초과 시 |
| --- | --- | --- | --- |
| 새 익명 사용자 발급 | IP | 분당 20 | HTTP 429 |
| WebSocket 연결 | IP | 분당 60 | 핸드셰이크 429 |
| 방 동시 연결 | 방 | 200 | 핸드셰이크 503 |
| 메시지 | 사용자 | 10초에 5 | 429 안내, 연결 유지 |
| 신고 | 사용자 | 10분에 10 | HTTP 429 |

- 회사 공유 IP를 고려해 IP 한도는 넉넉히 두고, 유효한 쿠키로 재방문하는 요청은 발급 한도에 세지 않는다. 점심 시작에 한 사무실이 동시에 접속해도 기존 사용자는 막히지 않는다.
- 이전에는 400 이외의 WebSocket 오류에서 연결을 끊었다. 429는 안내만 보내고 연결을 유지하도록 바꿨다. 프런트는 401·403 이외 오류를 안내 문구로만 표시하므로 수정이 필요 없었다.
- 한도 값은 `application.yml`의 `rate-limit`에 있다. 통합 테스트는 고정 시계를 써서 토큰이 다시 차지 않으므로 `src/test/resources/config/application.yml`에서 한도를 크게 덮어쓴다.
- 새 테스트 7개(버킷 충전·키 분리·정리, IP별 발급 제한과 재방문 제외, WebSocket 429 연결 유지와 차단 시 종료)를 포함해 108개가 통과했다.

운영 배포: 스냅샷 `breakground-before-rate-limit-20261123`이 `available`이 된 뒤, 방이 없는 00:06에 백엔드만 `breakground-backend:ratelimit-e179c8b`로 교체했다. 이전 `.env`는 서버에 `.env.bak-20261123`으로 남겼다. 외부에서 쿠키 없는 WebSocket 연결을 64회 시도해 401 이후 429를 받았고, 같은 시각 서버 IP에서 보낸 요청은 401이었다. Spring이 Caddy 내부 주소가 아니라 실제 클라이언트 IP로 한도를 계산한다는 뜻이다. 미니멀 화면과 방 API는 200이었다. 운영에서 메시지·신고·발급 한도는 실제 데이터를 만들지 않기 위해 시험하지 않았고 단위 테스트로만 확인했다. 평일 방 운영 중에 확인한다.

### AWS root 대신 운영자 IAM 사용자

root는 역할을 맡을 수 없으므로 IAM 사용자 `breakground-operator`를 만들었다. 인라인 정책 `BreakgroundOperator`는 서울 리전 Lightsail의 조회·SSH 임시 인증서·스냅샷·방화벽·재부팅과 자신의 비밀번호·MFA 관리만 허용한다. `aws login`을 위해 관리형 정책 `SignInLocalDevelopmentAccess`, 첫 비밀번호 변경을 위해 `IAMUserChangePassword`를 붙였다. 콘솔 비밀번호와 MFA 등록은 사용자가 직접 한다. 새 사용자로 로그인해 배포 경로가 동작하는지 확인한 뒤 root CLI 사용을 멈춘다. IAM 변경·결제 등은 이 사용자에게 없으므로 그런 작업은 root로 콘솔에서 한다.
