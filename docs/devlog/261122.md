# 2026-11-22

## 목표

AWS CLI로 서울 리전 Lightsail 인스턴스를 만들고 Breakground를 HTTPS로 띄운다.

## 시작 상태

- 로컬 Compose는 개발용 PostgreSQL만 실행한다. 세션 시작 시 Docker Desktop과 PostgreSQL을 시작했다.
- AWS CLI는 설치되어 있었다. 브라우저 로그인 이후 STS로 인증을 확인했다.

## 배포 구성

- Ubuntu 24.04, 2GB Lightsail 한 대를 선택했다. 기본료는 월 $12다.
- Docker Compose에서 Caddy가 HTTPS를 받고, 브라우저와 같은 출처의 API 및 WebSocket을 Spring으로 전달한다. PostgreSQL은 내부 네트워크에 두고 데이터를 볼륨에 저장한다.
- Spring이 프록시 뒤의 원래 HTTPS 요청을 인식하도록 전달 헤더를 처리한다. 익명 쿠키의 Secure 속성과 WebSocket의 Origin 검사에 필요하다.

## 배포 결과

- 서울 리전의 `breakground` 인스턴스에 고정 IPv4 `43.202.20.1`을 연결했다. HTTP와 HTTPS는 공개하고 SSH는 작업자 IP와 Lightsail 브라우저 콘솔에 허용했다.
- Mac의 Docker에서 Linux amd64 이미지를 빌드하고 임시 SSH 인증서로 서버에 전송했다. 서버의 `~/breakground`에서 `sudo docker compose -f compose.production.yml up -d --no-build`로 실행한다. DB 비밀번호는 서버의 `.env`에만 저장했다.
- 도메인 없이 Let’s Encrypt의 짧은 수명 IP 인증서를 Caddy가 자동 발급·갱신하도록 설정했다. IP 접속 시 SNI를 보내지 않는 클라이언트에도 인증서를 제공하도록 Caddy 기본 SNI를 지정했다.
- 외부에서 HTTPS 홈·미니멀 화면·게임 목록·방 API 200, HTTP→HTTPS 308, 익명 쿠키 Secure·HttpOnly, 쿠키 없는 WSS 요청 401을 확인했다. Flyway V1~V10이 적용됐다.
- 로컬의 격리된 PostgreSQL에만 주말 운영 시간을 열어 HTTPS 채팅 왕복·신고·중복 신고를 확인했다. 운영 DB의 방 시간표는 그대로 사용하므로 주말에는 열린 방이 없고, 운영 WSS 메시지 왕복은 평일 운영 시간에 확인한다.
- GitHub Actions에서도 두 Dockerfile을 그대로 빌드해 커밋별 이미지를 배포할 수 있다. 첫 배포는 수동으로 진행했다. GitHub 호스팅 러너에서 운영 서버로 접근하는 방식과 자동 배포 후 검증은 다음 작업이다.
