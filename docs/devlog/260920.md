# 2026-09-20 — Flyway V2 적용 확인

## V2 migration은 실제 DB에 적용됐을까?

`flyway_schema_history`를 조회해 다음 두 migration이 모두 성공(`success = true`)한 것을 확인했다.

| Version | Description |
| --- | --- |
| 1 | create room |
| 2 | add room operating time constraint |

V2가 성공으로 기록됐다는 것은 PostgreSQL의 `room` 테이블에 `CHECK (open_at <> close_at)` 제약이 적용됐다는 뜻이다. 이제 시작 시각과 종료 시각이 같은 Room은 데이터베이스 단계에서 저장할 수 없다.

Spring Boot가 기동할 때 Flyway가 먼저 migration을 적용하고, 이어 JPA의 `ddl-auto: validate`가 Entity와 실제 스키마의 호환성을 검증한다. 따라서 이 확인으로 Room의 기본 테이블, Entity, 운영 시간 제약이 한 흐름으로 연결됐음을 확인했다.

## 다음으로

- 초기 Room의 이름과 운영 시간을 정한다.
- 확정한 데이터를 별도 `V3` Flyway migration으로 넣는다.
- `GET /rooms`가 현재 시각에 열린 Room만 `RoomResponse`로 반환하는지 실제 데이터로 확인한다.

## 초기 Room은 무엇으로 시작할까?

초기 방은 아래 세 개로 제한한다. 기능을 넓히기보다 Room 조회 API와 운영 시간 정책을 실제 데이터로 먼저 검증하기 위한 선택이다.

- 점심메뉴방: 10:00~11:30 제안
- 저녁메뉴방: 4:00~5:30 제안
- 야근메뉴방: 9:00~다음 날 2:00 제안

V3 migration에 넣기 전에는 저녁·야근 시간이 각각 16:00~17:30, 21:00~02:00을 뜻하는지 확인한다. PostgreSQL `time`에는 오전·오후가 따로 없으므로 SQL에는 24시간 형식으로 명확히 적어야 한다. 야근메뉴방은 `open_at > close_at`인 자정 통과 구간이며, 현재 `Room.isOpen()`이 이 경우를 처리하도록 설계돼 있다.

### V3 SQL을 검토하며 무엇을 고쳤을까?

초안에는 `id`와 이름·시간 값을 직접 적었다. 다음 세 가지를 고쳤다.

- `id`는 INSERT 대상에서 제외했다. `id` 컬럼은 PostgreSQL의 `GENERATED ALWAYS AS IDENTITY`이므로 DB가 값을 생성하며, 일반 INSERT가 임의 값을 넣으면 거절한다.
- 방 이름은 SQL 문자열이므로 작은따옴표로 감쌌다.
- `time` 값도 `'10:00'`처럼 작은따옴표로 감쌌다. PostgreSQL이 문자열을 `time` 컬럼 타입으로 변환한다.

수정한 V3 migration을 포함해 `./gradlew test`를 실행했고 성공했다. 이후 PostgreSQL을 직접 조회해 아래를 확인했다.

| id | name | open_at | close_at |
| --- | --- | --- | --- |
| 1 | 점심메뉴방 | 10:00:00 | 11:30:00 |
| 2 | 저녁메뉴방 | 16:00:00 | 17:30:00 |
| 3 | 야근메뉴방 | 21:00:00 | 02:00:00 |

`flyway_schema_history`에도 V1, V2, V3이 모두 성공으로 기록됐다. 이제 Room 스키마, 운영 시간 제약, 초기 데이터가 Flyway migration으로 재현 가능한 상태다.

## 오늘 마무리와 다음 시작점

오늘은 Room의 운영 시간 제약과 초기 데이터까지 DB에 적용·검증했다. 다음에는 실제 현재 시각을 기준으로 `GET /rooms`를 호출해, 열린 방만 `RoomResponse` 형태로 반환되는지 확인한다.

이후에도 Room 도메인에서 필요한 검증이나 테스트를 정리한 뒤, AnonymousUser와 Message 설계로 확장한다.

### 취침 전 테스트를 다시 실행해도 될까?

커밋·푸시와 Docker 종료 뒤에도 확인을 위해 `make && ./gradlew test`를 다시 실행했다. Docker Desktop과 PostgreSQL을 다시 시작한 뒤 Gradle 테스트가 `BUILD SUCCESSFUL`로 통과했다. 이 실행에서는 소스가 바뀌지 않아 Gradle이 이전 결과를 재사용했고 `test UP-TO-DATE`로 표시됐다.

테스트 직후 `make fclean`을 다시 실행해 PostgreSQL 컨테이너·네트워크와 Docker Desktop을 종료했다. 따라서 오늘 종료 시점에는 로컬 개발 환경이 이미 정리된 상태다.

## 실제 `/rooms` API는 어떻게 확인할까?

일요일 오전 08:26에 Spring Boot를 실행하고 `GET /rooms`를 호출했다. 초기 세 방은 모두 운영 시간 밖이라 응답은 빈 배열 `[]`이었다. 이는 현재 시각 기준으로 열린 방만 고르는 `RoomService.findOpenRooms()`의 정상 결과다.

Service부터 Controller까지의 흐름을 실제로 확인하기 위해, Flyway migration에는 넣지 않는 로컬 임시 row `주말테스트방(00:00~23:59)`을 추가했다. 같은 API 호출 결과는 다음과 같았다.

```json
[{"closeAt":"23:59:00","id":4,"name":"주말테스트방","openAt":"00:00:00"}]
```

이 결과로 `Room` Entity를 읽고, `isOpen()`으로 필터링하고, `RoomResponse`로 변환한 뒤 JSON으로 반환하는 흐름을 확인했다. 검증 직후 임시 row를 삭제했고, DB에는 초기 세 방만 남아 있다.

### 주말에 기존 방이 열리면 안 된다면?

초기 세 방은 평일에만 운영한다는 정책을 확정했다. 하지만 현재 Room에는 `open_at`, `close_at`만 있어 요일을 판단할 정보가 없다. 따라서 지금 구현은 특정 시각이 되면 토요일·일요일에도 초기 세 방을 열게 된다.

다음 구현에서는 요일 운영 정책을 Room 모델에 어떻게 저장할지 먼저 정한다. 이후 Flyway migration으로 스키마를 확장하고, `Room.isOpen()`이 현재 시각뿐 아니라 현재 요일까지 함께 판단하게 만든다.

## 테스트는 어떻게 역할을 나눌까?

Spring Boot 기동, Flyway 적용 여부 확인, PostgreSQL 조회, HTTP API 호출처럼 반복 가능한 검증은 AI에게 요청해도 된다. 사람이 직접 판단하고 구현할 핵심은 서비스 정책과 도메인 모델의 선택이다.

이 프로젝트에서는 사용자가 Room의 요일 운영 정책과 데이터 구조를 먼저 설계하고 코드를 작성한다. AI는 그 뒤 실제 DB·API·경계 조건을 빠르게 검증하고, Spring·JPA·PostgreSQL 관점에서 코드 리뷰를 제공한다.

### RoomOperatingDay 테이블을 꼭 새로 만들어야 할까?

아니다. `RoomOperatingDay`는 월·수·금처럼 임의의 요일 조합을 여러 방에서 유연하게 표현하려는 확장형 설계다. 현재 요구사항은 초기 세 방을 평일에만 열고 주말에는 닫는 것이므로, Room 테이블에 요일 운영 정보를 추가하는 더 작은 설계도 가능하다.

예를 들어 `open_on_weekdays`, `open_on_weekends` 두 Boolean 컬럼을 Room에 둔다면 평일 전용·주말 전용·매일 운영을 모두 표현할 수 있다. 두 값이 모두 false인 방은 운영하지 않는 방이므로 DB `CHECK` 제약으로 막아야 한다.

반면 특정 요일만 운영하는 방이 필요해지면 RoomOperatingDay 같은 별도 테이블이 자연스럽다. 현재 기능 범위와 앞으로 만들 방의 종류를 기준으로 둘 중 하나를 먼저 선택한다.

### `isOpen()`은 요일을 어떻게 함께 판단할까?

`isOpen()`은 현재 시각이 방의 운영 구간에 들어오는지뿐 아니라, 그 구간을 시작한 날짜가 운영 가능한 날인지 확인해야 한다.

- 일반 구간(예: 10:00~11:30)은 현재 날짜가 운영 가능하고 `open_at <= now < close_at`일 때 열린다.
- 자정 통과 구간(예: 21:00~02:00)은 21:00 이후에는 현재 날짜의 운영 여부를 확인한다.
- 같은 자정 통과 구간에서 02:00 전에는 전날의 운영 여부를 확인한다. 금요일 21:00~토요일 02:00 방은 토요일 01:00에도 금요일에 시작한 운영 구간으로 열린다.

따라서 `LocalDate`에서 `DayOfWeek`를 얻어 주말인지 판단하고, 평일·주말 Boolean 값을 선택하는 작은 helper를 먼저 만드는 방식이 읽기 쉽다. `java.util.Date`는 필요하지 않으며, 이미 사용한 `java.time.LocalDate`와 `LocalTime`만 사용한다.

### V4에 주의할 점

이미 row가 있는 Room 테이블에 `NOT NULL` 컬럼을 추가할 때는 기존 row가 즉시 값을 가져야 한다. 초기 세 방이 평일 전용이라는 정책이 확정됐으므로, 컬럼에 `DEFAULT true`와 `DEFAULT false`를 설정하면 별도 CASE UPDATE 없이 기존 row까지 같은 정책으로 채울 수 있다.

현재 V4 초안의 `CASE` 구문에는 각 조건 뒤 세미콜론이 들어가 있고 `WEEKDAU_OPEN` 오타도 있다. 기본값으로 초기 데이터를 채우는 설계를 선택하면 이 복잡한 UPDATE 자체가 필요 없다.

### 평일·주말 정책을 실제 코드와 DB에 적용

요일 정보는 별도 테이블 대신 Room의 `weekday_open`, `weekend_open` Boolean 컬럼으로 저장하도록 구현했다. Java 필드는 `weekdayOpen`, `weekendOpen`의 camelCase와 primitive `boolean`을 사용하고, `@Column`으로 PostgreSQL snake_case 컬럼에 연결했다.

`isOpen()`은 `LocalDateTime` 하나를 받아 날짜와 시간을 같은 순간에서 추출한다. 일반 구간은 당일 운영 여부와 시간 구간을 함께 확인한다. 자정 통과 구간은 21:00 이후에는 당일 운영 여부를, 02:00 전에는 `date.minusDays(1)`로 전날 운영 여부를 확인한다.

V4 migration은 기존 Room row에 두 nullable 컬럼을 먼저 추가하고, 초기 세 방을 `weekday_open = true`, `weekend_open = false`로 채운 뒤 `NOT NULL`을 적용했다. 마지막 `CHECK (weekday_open OR weekend_open)`은 운영하는 요일이 전혀 없는 Room을 막는다.

`./gradlew test`가 통과했고, PostgreSQL의 `flyway_schema_history`에서 V4 성공을 확인했다. Room 세 건 모두 평일 true·주말 false로 저장된 것도 확인했다. 일요일에 새 코드로 실행한 `GET /rooms`는 HTTP 200과 빈 배열 `[]`를 반환했다.

## 초기 Room을 어떻게 구성할까?

메뉴를 주제로 한 짧은 대화방을 초기 데이터로 둔다. 제안된 방은 점심메뉴방, 저녁메뉴방, 야근메뉴방이다. 각각의 대화 목적이 분명하고, 야근메뉴방은 자정을 넘는 운영 시간을 실제로 검증할 수 있다.

다만 "4개"라는 목표와 실제로 나열된 세 방의 수가 다르다. 또 `4:00~5:30`, `9:00~다음 2:00`는 오전·오후가 분명해야 Flyway에 정확한 PostgreSQL `time` 값으로 저장할 수 있다. 이 두 지점을 확정한 뒤 V3 data migration을 작성한다.
