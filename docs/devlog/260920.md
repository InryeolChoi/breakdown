# 2026-09-20 — Flyway V2 적용 확인

## V2 migration은 실제 DB에 적용됐을까?

`flyway_schema_history`를 조회해 다음 두 migration이 모두 성공(`success = true`)한 것을 확인했다.

| Version | Description |
| --- | --- |
| 1 | create room |
| 2 | add room operating time constraint |

V2가 성공으로 기록됐다는 것은 PostgreSQL의 `room` 테이블에 `CHECK (open_at <> close_at)` 제약이 적용됐다는 뜻이다. 이제 시작 시각과 종료 시각이 같은 Room은 데이터베이스 단계에서 저장할 수 없다.

Spring Boot가 기동할 때 Flyway가 먼저 migration을 적용하고, 이어 JPA의 `ddl-auto: validate`가 Entity와 실제 스키마의 호환성을 검증한다. 따라서 이 확인으로 Room의 기본 테이블, Entity, 운영 시간 제약이 한 흐름으로 연결됐음을 확인했다.

## 다음으로

- 초기 Room의 이름과 운영 시간을 정한다.
- 확정한 데이터를 별도 `V3` Flyway migration으로 넣는다.
- `GET /rooms`가 현재 시각에 열린 Room만 `RoomResponse`로 반환하는지 실제 데이터로 확인한다.

## 초기 Room은 무엇으로 시작할까?

초기 방은 아래 세 개로 제한한다. 기능을 넓히기보다 Room 조회 API와 운영 시간 정책을 실제 데이터로 먼저 검증하기 위한 선택이다.

- 점심메뉴방: 10:00~11:30 제안
- 저녁메뉴방: 4:00~5:30 제안
- 야근메뉴방: 9:00~다음 날 2:00 제안

V3 migration에 넣기 전에는 저녁·야근 시간이 각각 16:00~17:30, 21:00~02:00을 뜻하는지 확인한다. PostgreSQL `time`에는 오전·오후가 따로 없으므로 SQL에는 24시간 형식으로 명확히 적어야 한다. 야근메뉴방은 `open_at > close_at`인 자정 통과 구간이며, 현재 `Room.isOpen()`이 이 경우를 처리하도록 설계돼 있다.

### V3 SQL을 검토하며 무엇을 고쳤을까?

초안에는 `id`와 이름·시간 값을 직접 적었다. 다음 세 가지를 고쳤다.

- `id`는 INSERT 대상에서 제외했다. `id` 컬럼은 PostgreSQL의 `GENERATED ALWAYS AS IDENTITY`이므로 DB가 값을 생성하며, 일반 INSERT가 임의 값을 넣으면 거절한다.
- 방 이름은 SQL 문자열이므로 작은따옴표로 감쌌다.
- `time` 값도 `'10:00'`처럼 작은따옴표로 감쌌다. PostgreSQL이 문자열을 `time` 컬럼 타입으로 변환한다.

수정한 V3 migration을 포함해 `./gradlew test`를 실행했고 성공했다. 이후 PostgreSQL을 직접 조회해 아래를 확인했다.

| id | name | open_at | close_at |
| --- | --- | --- | --- |
| 1 | 점심메뉴방 | 10:00:00 | 11:30:00 |
| 2 | 저녁메뉴방 | 16:00:00 | 17:30:00 |
| 3 | 야근메뉴방 | 21:00:00 | 02:00:00 |

`flyway_schema_history`에도 V1, V2, V3이 모두 성공으로 기록됐다. 이제 Room 스키마, 운영 시간 제약, 초기 데이터가 Flyway migration으로 재현 가능한 상태다.

## 실제 `/rooms` API는 어떻게 확인할까?

일요일 오전 08:26에 Spring Boot를 실행하고 `GET /rooms`를 호출했다. 초기 세 방은 모두 운영 시간 밖이라 응답은 빈 배열 `[]`이었다. 이는 현재 시각 기준으로 열린 방만 고르는 `RoomService.findOpenRooms()`의 정상 결과다.

Service부터 Controller까지의 흐름을 실제로 확인하기 위해, Flyway migration에는 넣지 않는 로컬 임시 row `주말테스트방(00:00~23:59)`을 추가했다. 같은 API 호출 결과는 다음과 같았다.

```json
[{"closeAt":"23:59:00","id":4,"name":"주말테스트방","openAt":"00:00:00"}]
```

이 결과로 `Room` Entity를 읽고, `isOpen()`으로 필터링하고, `RoomResponse`로 변환한 뒤 JSON으로 반환하는 흐름을 확인했다. 검증 직후 임시 row를 삭제했고, DB에는 초기 세 방만 남아 있다.

### 주말에 기존 방이 열리면 안 된다면?

초기 세 방은 평일에만 운영한다는 정책을 확정했다. 하지만 현재 Room에는 `open_at`, `close_at`만 있어 요일을 판단할 정보가 없다. 따라서 지금 구현은 특정 시각이 되면 토요일·일요일에도 초기 세 방을 열게 된다.

다음 구현에서는 요일 운영 정책을 Room 모델에 어떻게 저장할지 먼저 정한다. 이후 Flyway migration으로 스키마를 확장하고, `Room.isOpen()`이 현재 시각뿐 아니라 현재 요일까지 함께 판단하게 만든다.

Spring Boot 기동, Flyway 적용 여부 확인, PostgreSQL 조회, HTTP API 호출처럼 반복 가능한 검증은 AI에게 요청해도 된다. 사람이 직접 판단하고 구현할 핵심은 서비스 정책과 도메인 모델의 선택이다.

이 프로젝트에서는 사용자가 Room의 요일 운영 정책과 데이터 구조를 먼저 설계하고 코드를 작성한다. AI는 그 뒤 실제 DB·API·경계 조건을 빠르게 검증하고, Spring·JPA·PostgreSQL 관점에서 코드 리뷰를 제공한다.

### RoomOperatingDay 테이블을 꼭 새로 만들어야 할까?

아니다. `RoomOperatingDay`는 월·수·금처럼 임의의 요일 조합을 여러 방에서 유연하게 표현하려는 확장형 설계다. 현재 요구사항은 초기 세 방을 평일에만 열고 주말에는 닫는 것이므로, Room 테이블에 요일 운영 정보를 추가하는 더 작은 설계도 가능하다.

예를 들어 `open_on_weekdays`, `open_on_weekends` 두 Boolean 컬럼을 Room에 둔다면 평일 전용·주말 전용·매일 운영을 모두 표현할 수 있다. 두 값이 모두 false인 방은 운영하지 않는 방이므로 DB `CHECK` 제약으로 막아야 한다.

반면 특정 요일만 운영하는 방이 필요해지면 RoomOperatingDay 같은 별도 테이블이 자연스럽다. 현재 기능 범위와 앞으로 만들 방의 종류를 기준으로 둘 중 하나를 먼저 선택한다.

### `isOpen()`은 요일을 어떻게 함께 판단할까?

`isOpen()`은 현재 시각이 방의 운영 구간에 들어오는지뿐 아니라, 그 구간을 시작한 날짜가 운영 가능한 날인지 확인해야 한다.

- 일반 구간(예: 10:00~11:30)은 현재 날짜가 운영 가능하고 `open_at <= now < close_at`일 때 열린다.
- 자정 통과 구간(예: 21:00~02:00)은 21:00 이후에는 현재 날짜의 운영 여부를 확인한다.
- 같은 자정 통과 구간에서 02:00 전에는 전날의 운영 여부를 확인한다. 금요일 21:00~토요일 02:00 방은 토요일 01:00에도 금요일에 시작한 운영 구간으로 열린다.

따라서 `LocalDate`에서 `DayOfWeek`를 얻어 주말인지 판단하고, 평일·주말 Boolean 값을 선택하는 작은 helper를 먼저 만드는 방식이 읽기 쉽다. `java.util.Date`는 필요하지 않으며, 이미 사용한 `java.time.LocalDate`와 `LocalTime`만 사용한다.

### V4에 주의할 점

이미 row가 있는 Room 테이블에 `NOT NULL` 컬럼을 추가할 때는 기존 row가 즉시 값을 가져야 한다. 초기 세 방이 평일 전용이라는 정책이 확정됐으므로, 컬럼에 `DEFAULT true`와 `DEFAULT false`를 설정하면 별도 CASE UPDATE 없이 기존 row까지 같은 정책으로 채울 수 있다.

현재 V4 초안의 `CASE` 구문에는 각 조건 뒤 세미콜론이 들어가 있고 `WEEKDAU_OPEN` 오타도 있다. 기본값으로 초기 데이터를 채우는 설계를 선택하면 이 복잡한 UPDATE 자체가 필요 없다.

### 평일·주말 정책을 실제 코드와 DB에 적용

요일 정보는 별도 테이블 대신 Room의 `weekday_open`, `weekend_open` Boolean 컬럼으로 저장하도록 구현했다. Java 필드는 `weekdayOpen`, `weekendOpen`의 camelCase와 primitive `boolean`을 사용하고, `@Column`으로 PostgreSQL snake_case 컬럼에 연결했다.

`isOpen()`은 `LocalDateTime` 하나를 받아 날짜와 시간을 같은 순간에서 추출한다. 일반 구간은 당일 운영 여부와 시간 구간을 함께 확인한다. 자정 통과 구간은 21:00 이후에는 당일 운영 여부를, 02:00 전에는 `date.minusDays(1)`로 전날 운영 여부를 확인한다.

V4 migration은 기존 Room row에 두 nullable 컬럼을 먼저 추가하고, 초기 세 방을 `weekday_open = true`, `weekend_open = false`로 채운 뒤 `NOT NULL`을 적용했다. 마지막 `CHECK (weekday_open OR weekend_open)`은 운영하는 요일이 전혀 없는 Room을 막는다.

`./gradlew test`가 통과했고, PostgreSQL의 `flyway_schema_history`에서 V4 성공을 확인했다. Room 세 건 모두 평일 true·주말 false로 저장된 것도 확인했다. 일요일에 새 코드로 실행한 `GET /rooms`는 HTTP 200과 빈 배열 `[]`를 반환했다.

테스트 후보는 평일 시작 시각 포함, 종료 시각 제외, 금요일 밤 자정 통과, 토요일 새벽의 전날 기준 열림, 토요일 밤의 주말 닫힘이다. 이를 직접 만들려면 JPA가 요구하는 no-argument 생성자와 별개로, Room의 이름·시간·운영 요일을 받는 도메인 생성자를 어떻게 둘지 먼저 정한다.

### 테스트 클래스와 Entity 생성자는 어디에 둘까?

테스트 클래스는 운영 코드가 있는 `src/main/java`가 아니라 `src/test/java/com/breakground/room/RoomTest.java`에 둔다. 패키지 이름을 `com.breakground.room`으로 맞추면 Room과 같은 도메인 단위로 코드를 읽을 수 있고, 테스트 전용 코드가 JAR 결과물에 포함되지 않는다.

Room의 생성자는 운영 코드인 `src/main/java`의 Room Entity에 추가한다. `@AllArgsConstructor`는 id까지 포함한 모든 필드를 받는 생성자를 만들기 때문에 적합하지 않다. id는 `GENERATED ALWAYS AS IDENTITY`로 DB가 생성하며, 테스트나 Room 생성 코드가 지정하면 안 된다.

또한 현재 Room은 생성자를 선언하지 않아 Java가 public no-argument 생성자를 암묵적으로 제공한다. 원하는 생성자를 하나 추가하면 그 기본 생성자가 사라진다. Hibernate가 Entity를 DB row에서 복원할 때 쓸 `protected` no-argument 생성자를 명시적으로 남기고, id를 제외한 name·시간·운영 요일을 받는 별도 생성자를 직접 둔다.

### Room 생성자를 직접 만들며 확인한 점

Room 생성자는 id 없이 name·운영 시간·평일·주말 여부를 받아 필드를 채우도록 작성했다. DB가 id를 생성한다는 책임과 맞는 설계다.

기본 생성자도 남겨 Hibernate가 Entity를 복원할 수 있다. 다만 일반 애플리케이션 코드가 빈 Room을 만들지 못하도록, 이 생성자의 접근 제어자는 public보다 `protected`가 적합하다. JPA는 public 또는 protected no-argument 생성자를 요구한다.

생성자 선언 뒤의 세미콜론은 Java 문법상 허용되지만 필요하지 않다. 제거하고 중괄호를 선언문과 같은 줄에 두면 프로젝트의 일반적인 Java 형식과 맞는다.

### 왜 JPA용 기본 생성자는 따로 둘까?

`protected`로 바꾸는 대상은 name·시간·운영 요일을 받는 생성자가 아니라 매개변수가 없는 생성자다. Java는 접근 제어자가 달라도 생성자 이름과 매개변수 타입·순서가 같으면 중복 선언으로 본다. 따라서 같은 다섯 인자 생성자를 public과 protected로 동시에 둘 수 없다.

Room에는 두 생성자가 역할별로 필요하다. `public Room(name, openAt, closeAt, weekdayOpen, weekendOpen)`은 테스트와 이후 Room 생성 로직이 유효한 상태를 만들 때 사용한다. `protected Room()`은 Hibernate가 DB row를 Entity로 복원할 때 사용한다.

JPA는 Entity에 public 또는 protected no-argument 생성자를 요구한다. Hibernate는 Room의 같은 패키지나 하위 클래스가 아니다. JPA provider로서 reflection을 이용해 인자 없이 Room 인스턴스를 만들고, 이 프로젝트처럼 필드에 JPA annotation이 있는 field access 방식에서는 reflection으로 각 필드를 DB 값으로 채운다. protected 기본 생성자는 다른 패키지의 일반 애플리케이션 코드에 빈 Room 생성을 노출하지 않는다.

`protected`는 Hibernate 전용 접근 제어자가 아니다. Java에서 protected 멤버는 같은 패키지의 코드와, 다른 패키지에 있더라도 상속한 하위 클래스에서 접근할 수 있다. 따라서 `com.breakground.room` 패키지 안의 테스트·서비스는 기본 생성자에 접근할 수 있지만, 다른 패키지의 일반 코드는 접근할 수 없다.

Hibernate는 일반 코드가 생성자를 직접 호출하는 방식이 아니라 JPA provider로서 reflection을 이용한다. JPA 명세가 Entity의 public 또는 protected no-argument 생성자를 요구하므로, Hibernate는 이 생성자로 인스턴스를 만든 뒤 DB 값을 채울 수 있다. protected는 외부 코드의 실수를 완전히 막는 보안 장치가 아니라, 빈 Entity 생성을 덜 노출하는 설계 의도 표현이다.

### Reflection은 무엇일까?

Reflection은 Java 프로그램이 실행 중에 클래스의 생성자·필드·메서드 정보를 조사하고 다룰 수 있게 하는 기능이다. Hibernate는 개발자가 작성한 Room 생성자 호출을 코드에 직접 적지 않는다. 실행 중에 `@Entity`, `@Id`, `@Column` annotation을 읽고 Room의 기본 생성자로 객체를 만든 다음, 조회한 DB row의 값을 필드에 채운다.

따라서 protected 기본 생성자는 Hibernate라는 특정 패키지에만 요구되는 규칙이 아니다. JPA 명세가 모든 JPA provider에게 Entity의 public 또는 protected no-argument 생성자를 요구한다. Hibernate는 그 명세를 구현한 라이브러리이며, 그 생성자와 reflection을 이용해 Entity를 복원한다.

생성자 정리는 `public Room(name, openAt, closeAt, weekdayOpen, weekendOpen)`과 `protected Room()`의 두 형태로 완료했다. 이제 `src/test/java/com/breakground/room/RoomTest.java`에서 DB 없이 Room을 직접 만들어 `isOpen()`의 반환값을 검사할 수 있다.

### 첫 JUnit 테스트는 어떻게 실행할까?

JUnit 테스트는 애플리케이션을 실행해 Postman으로 호출하는 방식이 아니다. `@Test`가 붙은 메서드를 JUnit이 실행하고, `assertTrue` 같은 assertion이 기대값과 실제값을 비교한다. 조건이 true면 통과하고 false면 어떤 assertion이 실패했는지 알려 준다.

RoomTest는 Spring Context나 PostgreSQL이 필요 없는 순수 단위 테스트다. IntelliJ에서는 `@Test` 왼쪽의 초록색 실행 아이콘을 누르거나, 터미널에서 `./gradlew test --tests com.breakground.room.RoomTest`를 실행해 이 클래스만 검사할 수 있다. 전체 `./gradlew test`는 Spring Context 테스트도 함께 실행한다.

첫 초안에서는 Java 문법도 함께 확인했다. Java 문자열은 작은따옴표가 아닌 큰따옴표를 사용하고, `10:00`은 Java 표현식이 아니므로 `LocalTime.of(10, 0)`처럼 LocalTime 객체로 만들어 Room 생성자에 전달해야 한다.

JUnit은 `@Test`가 붙은 메서드 하나를 테스트 한 건으로 인식한다. IntelliJ에서 특정 메서드 옆 실행 아이콘을 누르면 그 메서드만 실행하고, 클래스 이름 옆 실행 아이콘이나 `./gradlew test --tests com.breakground.room.RoomTest`를 실행하면 RoomTest 안의 모든 `@Test` 메서드를 실행한다.

JUnit 5의 기본 방식에서는 각 테스트 메서드마다 새 테스트 클래스 인스턴스를 만들어 실행한다. 따라서 한 테스트의 지역 변수나 객체 상태가 다른 테스트에 남지 않는다. 각 테스트는 한 가지 규칙만 검증하도록 작게 쓰는 이유다.

### Spring Boot를 실행하면 테스트도 자동으로 실행될까?

아니다. 애플리케이션 실행과 테스트 실행은 Gradle의 서로 다른 작업이다. IntelliJ에서 BreakgroundApplication을 실행하거나 `./gradlew bootRun`을 실행하면 Spring Boot 서버를 띄운다. `@Test` 메서드는 실행하지 않는다.

`./gradlew test`는 JUnit 테스트를 실행한다. RoomTest처럼 Spring annotation이 없는 테스트는 순수 Java 객체만 만들어 빠르게 실행한다. `@SpringBootTest`가 붙은 BreakgroundApplicationTests는 test 작업 안에서 Spring Context를 띄우고 DB 연결·Flyway·JPA 설정까지 함께 확인한다.

따라서 전체 Spring을 켜는 테스트와 순수 도메인 테스트를 함께 두면, 빠른 규칙 검증과 실제 설정 검증을 각각 할 수 있다. Django에도 테스트 기능은 있지만, Spring/Gradle에서는 `test` 작업과 `@Test` 메서드의 구분이 더 눈에 보이는 편이다.

### 이것도 Spring의 장점일까?

테스트 자체는 Django를 포함한 많은 프레임워크가 제공한다. Spring의 장점은 Java·JUnit·Gradle과 결합해 테스트 범위를 선택하기 쉽다는 점이다. RoomTest처럼 Spring을 전혀 띄우지 않는 빠른 단위 테스트와, `@SpringBootTest`로 실제 설정을 검증하는 통합 테스트를 같은 `test` 작업 안에서 함께 운영할 수 있다.

나중에는 Controller만 검증하는 `@WebMvcTest`, JPA Repository만 검증하는 `@DataJpaTest`처럼 필요한 Spring 부분만 올리는 테스트도 쓸 수 있다. 모든 테스트에 서버와 DB를 항상 띄우지 않아도 되므로 피드백이 빠르고, CI에서도 같은 Gradle 명령으로 반복 검증하기 좋다.

첫 RoomTest는 평일 전용 점심방이 월요일 10:00에 열린다는 규칙을 `assertTrue`로 확인했고 통과했다. 이로써 Room 생성자와 `isOpen(LocalDateTime)`을 Spring·DB 없이 직접 실행하는 첫 단위 테스트를 완료했다.

같은 점심방에 월요일 11:30을 전달한 테스트도 `assertFalse`로 통과했다. 시작 시각은 포함하고 종료 시각은 제외한다는 `[open_at, close_at)` 정책의 양쪽 경계를 단위 테스트로 고정했다.

평일 전용 야근방(21:00~02:00)이 금요일 21:00에 열린다는 테스트도 `assertTrue`로 통과했다. 자정 통과 구간에서 시작 시각을 포함하는 규칙을 검증했다.

### 테스트가 왜 필요한지 조금 보이기 시작한 지점

처음에는 Spring의 구조와 테스트가 복잡하고 반복적인 절차처럼 보일 수 있다. 그러나 Room처럼 시간·요일·자정 통과 규칙이 쌓이면, 기능을 한 번 실행해 보는 것만으로 모든 경우가 계속 맞는지 보장하기 어렵다.

테스트는 문제를 어렵게 만드는 별도 과제가 아니라, 이미 정한 서비스 규칙을 짧은 문장으로 남기고 이후 변경이 그 규칙을 깨뜨리지 않는지 확인하는 장치다. 규칙 하나를 코드로 만들고 테스트 하나로 확인하는 흐름이 보이기 시작하면 Spring의 여러 계층도 각각 무엇을 지키는지 이해하기 쉬워진다.

### 테스트는 어느 패키지에 둘까?

테스트 클래스는 `src/test/java/com/breakground/room/RoomTest.java`에 둔다. production 코드와 같은 `com.breakground.room` 패키지 구조를 따라가면 Room 도메인 테스트라는 위치가 명확해진다.

다만 테스트가 Room을 만들기 위해 사용하는 생성자는 테스트 전용 기능이 아니다. 실제 애플리케이션에서도 Room을 유효한 상태로 만들 때 쓰는 도메인 코드이므로 `src/main/java/com/breakground/room/Room.java`에 둔다. JPA/Hibernate가 DB row를 객체로 복원할 때 쓰는 no-argument 생성자와, 애플리케이션·테스트가 새 Room을 만들 때 쓰는 생성자의 책임을 구분한다.

## 초기 Room을 어떻게 구성할까?

메뉴를 주제로 한 짧은 대화방을 초기 데이터로 둔다. 제안된 방은 점심메뉴방, 저녁메뉴방, 야근메뉴방이다. 각각의 대화 목적이 분명하고, 야근메뉴방은 자정을 넘는 운영 시간을 실제로 검증할 수 있다.

다만 "4개"라는 목표와 실제로 나열된 세 방의 수가 다르다. 또 `4:00~5:30`, `9:00~다음 2:00`는 오전·오후가 분명해야 Flyway에 정확한 PostgreSQL `time` 값으로 저장할 수 있다. 이 두 지점을 확정한 뒤 V3 data migration을 작성한다.
