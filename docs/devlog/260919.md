# 2026-09-19 — Room API 응답 설계부터

## 시작 전 상태

Room을 중심으로 Repository, Service, Controller까지 연결했다. 현재 `GET /rooms`는 `Room` 엔티티를 직접 반환한다.

다음에는 API 응답에 엔티티를 그대로 사용해도 되는지, 방 목록에 어떤 정보를 보여줄지부터 고민하려고 한다. 필요하다면 `RoomResponse` DTO를 설계하고 적용한다.

## 오늘 한 것

- `GET /rooms`가 `Room` 엔티티를 직접 반환하는 현재 상태를 확인했다.
- 다음 구현 단위를 DTO 응답 설계로 정했다. 새 테이블이나 다음 도메인을 추가하는 일은 아직 시작하지 않는다.

## 질문과 답변

### DTO를 만든다는 건 새 테이블을 만든다는 뜻인가?

아니다. DTO는 DB 테이블이 아니라 Java 객체다.

현재 흐름은 다음과 같다.

```text
room 테이블 → Room 엔티티 → 그대로 JSON 응답
```

DTO를 적용하면 엔티티와 API 응답을 분리한다.

```text
room 테이블 → Room 엔티티 → RoomResponse → JSON 응답
```

`Room`은 DB와 JPA 매핑을 위한 객체이고, `RoomResponse`는 프론트에 어떤 정보를 보일지 정한 응답용 객체다.
DTO를 만든다고 DB 구조가 바뀌는 것은 아니다.

### 그럼 다른 테이블을 먼저 만들어야 하나?

지금은 아니다. Room 목록 API의 응답 모양을 먼저 정하면 된다.
AnonymousUser나 Message 테이블은 방 목록 API가 한 단위로 마무리된 다음 확장한다.

현재 `room` 테이블에는 구조만 있고 기본 방 데이터는 아직 없다. 이것은 새 테이블 문제가 아니라 기존 `room` 테이블에 점심방, 간식방, 야근방 같은 행을 넣는 문제다.

### 초기 방 데이터도 Flyway로 넣어야 하나?

넣는 쪽이 맞다. 이미 적용한 V1을 수정하지 않고 새 migration을 추가한다.

```text
V1__create_room.sql
V2__insert_initial_rooms.sql
```

V2의 INSERT는 로컬과 AWS에서 같은 기본 방 데이터를 만들 수 있게 한다.
다만 어떤 방을 제공하고 각 방의 운영 시간이 무엇인지가 아직 확정되지 않았으므로, V2를 바로 작성하지는 않는다.

### DTO를 만들기 전에 정할 것

방 목록 화면이 실제로 필요한 정보를 먼저 정한다. 현재 후보는 `id`, `name`, `openAt`, `closeAt`이다.
`GET /rooms`는 이미 열린 방만 반환하므로, `isOpen`을 응답에 넣으면 항상 true가 된다. 이 값이 필요한지는 API의 역할을 바꾸는 시점에 다시 판단한다.

### 왜 이름에 DTO를 직접 붙이지 않나?

`RoomResponseDto`도 틀린 이름은 아니다. 다만 `dto` 패키지 안에 두면 DTO라는 분류는 이미 위치로 드러난다.

`RoomResponse`라는 이름은 이 객체가 무엇을 하는지 더 구체적으로 말해 준다. Room을 조회한 HTTP 응답이라는 뜻이다.
나중에 요청 데이터는 `RoomCreateRequest`, 목록 응답은 `RoomResponse`처럼 역할을 이름으로 구분할 수 있다.

```text
com.breakground.room.dto.RoomResponse
```

이름에 `Dto`를 붙이는 스타일도 프로젝트마다 존재한다. 이번 프로젝트에서는 패키지가 분류를, 클래스 이름이 API에서의 역할을 표현하도록 해 보기로 했다.

### RoomResponse를 처음 작성한 뒤 확인한 것

`com.breakground.room.dto` 패키지에 `RoomResponse`를 만들었다.
처음에는 record 대신 일반 클래스를 선택하고 Lombok의 `@Getter`를 붙였다.

```java
public RoomResponse(Room room) {
    this.id = room.getId();
    this.name = room.getName();
    this.openAt = room.getOpenAt();
    this.closeAt = room.getCloseAt();
}
```

Room 엔티티의 필드 타입과 응답 DTO의 필드 타입이 맞고, 생성자에서 엔티티 한 개를 응답 객체 한 개로 변환하는 것도 자연스럽다.
DTO에는 setter를 만들지 않았다. 다만 응답 값이 생성 뒤에 바뀌지 않는다는 의도를 더 강하게 표현하려면 다음 단계에서 필드를 `final`로 둘지 검토할 수 있다.

`LocalTime`은 불변 객체라 엔티티의 `openAt`, `closeAt` 값을 DTO로 넘겨도 값이 공유되어 변경되는 문제는 없다.

다음 결정은 이 생성자를 어디에서 호출할지다. Service가 Room을 DTO로 바꿔 반환할지, Controller가 변환할지 비교해 본다.

### RoomService.findOpenRooms()는 무엇인가?

`findOpenRooms()`는 Spring이 자동으로 제공한 메서드가 아니라, 앞에서 직접 `RoomService`에 작성한 일반 Java 메서드다.

```java
public List<Room> findOpenRooms(LocalTime now) {
    return roomRepository.findAll()
            .stream()
            .filter(room -> room.isOpen(now))
            .toList();
}
```

현재 시각 `now`를 받아서 모든 Room을 조회하고, `Room.isOpen(now)`가 true인 방만 골라 `List<Room>`으로 돌려준다.

요청 흐름은 다음과 같다.

```text
GET /rooms → RoomController → roomService.findOpenRooms(now)
           → RoomRepository.findAll() → DB
```

DTO를 적용하는 다음 변경은 이 메서드가 현재 돌려주는 `List<Room>`을 `List<RoomResponse>`로 바꾸는 일이다.
열린 방을 고르는 책임은 그대로 Service에 두고, 골라진 Room을 응답 객체로 변환하는 단계를 추가한다.

### DTO 변환을 어디에 어떻게 추가할까?

현재 Stream은 모든 Room을 가져온 뒤 filter로 열린 방만 남기고 끝난다.
DTO를 적용하려면 filter 다음에 각 `Room`을 `RoomResponse`로 바꾸는 `map` 단계를 추가한다.

```text
모든 Room → 열린 Room만 filter → 각 Room을 RoomResponse로 map → 목록 반환
```

이때 `map(RoomResponse::new)`은 각 Room을 `new RoomResponse(room)`으로 변환하라는 메서드 참조다.
JPA 매핑과는 다른 Stream API의 map이다.

따라서 Service의 반환 타입도 `List<Room>`에서 `List<RoomResponse>`로 바뀌고,
그 결과를 받는 Controller의 반환 타입도 같은 타입으로 맞춰야 한다.

### Stream 변환을 직접 적용하며 놓친 연결 지점

Service에는 아래 변경을 직접 적용했다.

```java
.filter(room -> room.isOpen(now))
.map(RoomResponse::new)
.toList();
```

`RoomResponse::new`은 각 Room에 대해 `new RoomResponse(room)`를 실행하는 생성자 메서드 참조다.
filter와 map을 이어 쓰는 것이 Stream API를 활용하는 방식이다.

Service의 반환 타입도 `List<RoomResponse>`로 올바르게 바꿨다.
Controller의 반환 타입도 `List<RoomResponse>`로 함께 바꿨다.
Service가 공개하는 결과 타입이 바뀌면 그 메서드를 호출하는 Controller의 타입도 함께 맞춰야 한다.

컴파일은 통과했다.
Spring 기동 테스트는 PostgreSQL 연결 실패로 통과하지 못했다. DTO 코드 문제가 아니라 Docker Desktop이 꺼져 있어 Docker API 소켓과 로컬 PostgreSQL에 연결할 수 없었던 환경 문제였다.
Docker를 실행한 뒤 다시 `./gradlew test`를 실행했고 테스트가 통과했다.
Spring이 PostgreSQL에 연결하고 JPA와 Flyway를 초기화한 뒤 정상 종료한 것을 확인했다.

### Room 운영 시간의 경계는 어떻게 정할까?

다음 정책을 확정했다.

- `open_at`은 포함한다. 12:00에 시작하면 정확히 12:00부터 열린다.
- `close_at`은 제외한다. 13:00에 닫히면 정확히 13:00부터 닫힌 상태다.
- `open_at`과 `close_at`이 같은 방은 허용하지 않는다. 24시간 방은 제공하지 않는다.

따라서 일반적인 운영 시간은 `[open_at, close_at)` 구간으로 본다.
12:00~13:00 방은 `12:00 <= now < 13:00`일 때 열린 상태다.

자정을 넘는 18:00~02:00 방은 `now >= 18:00` 또는 `now < 02:00`일 때 열린 상태다.

`isOpen()`은 시작 시각에 `!now.isBefore(openAt)`를 사용하고, 종료 시각에는 `now.isBefore(closeAt)`를 사용하도록 수정했다. 이로써 시작 시각을 포함하고 종료 시각을 제외하는 정책과 맞는다.
같은 시각 금지는 DB에도 남겨야 한다. V1은 이미 적용됐으므로 수정하지 않고, 다음 Flyway migration에서 `CHECK (open_at <> close_at)` 제약조건으로 추가한다.

## 다음으로

- `Room.isOpen()` 경계 조건 수정은 완료했다.
- 같은 시작·종료 시각을 막는 V2 migration을 작성했다. `time_check` 제약은 `open_at <> close_at`일 때만 Room row 저장을 허용한다.
- 초기 Room 데이터를 어떤 정책과 운영 시간으로 넣을지 정한다.
- 확정된 초기 데이터가 있으면 이후 migration으로 추가한다.
