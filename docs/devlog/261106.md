# 2026-11-06 — 공간형의 현실감 개선

## 사용자 피드백과 변경 이유

사용자는 공간형을 3D처럼 만들되 현실감과 몰입감이 있어야 한다고 지적했다. 기본 도형으로 만든 직전 시안은 구조 확인 수준이어서 원하는 시각 품질과 달랐다. 사용자가 원하는 고정 좌석·고개 회전 범위에 맞춰 실사형 이미지를 3D 구면에 투영하는 방식으로 바꿨다. 이는 가구를 모델링한 방이나 자유 이동형 3D와 다르다고 설명했다.

## 이미지와 렌더링

기본 이미지 생성 도구에 승인 공간을 참조로 주고 파노라마를 요청했다. 핵심 지시는 앉은 눈높이·등 뒤 햇살·막힌 뒷벽·셀프바 유지, 식물·업무공간·UI 제외, 실제 재질과 부드러운 접지 그림자다. 결과는 1774×887의 실사형 와이드 이미지였으며 frontend/public/images/cafe-panorama.png에 저장했다. 기존 기준 이미지와 정지 배경은 덮어쓰지 않았다.

요청한 360도 이음새가 검증된 촬영물로 볼 수 없어 정면 180도·수직 90도 구면 일부에 매핑하고 좌우 회전 범위를 제한했다. 원근 방향 변화로 둘러보는 느낌을 만들지만 자리 이동에 따른 시차·가구 상호작용은 없다. 텍스처 해상도 때문에 큰 화면에서는 선명도 한계가 있다. 이를 완성된 고정밀 3D 모델이라고 주장하지 않는다.

## 유지한 동작과 검증

미니멀형과 서버 계약은 유지했다. 공간형의 드래그·방향 버튼·정면 복귀, 입장·대화 전환과 체험 전송을 브라우저에서 확인했다. 입력 중에는 시선 조작을 멈춘다. 360px에서 파노라마 로드 완료·가로 넘침 없음과 1280px 구도를 확인했다. 새 스크린샷은 대화용 시각화 폴더의 cafe-immersive-browser.jpg에 보관했다. WebGL/이미지 실패 시 정지 배경 안내는 구현했지만 실패 주입 검증은 하지 않았다.

렌더는 변화가 있을 때만 요청하고 페이지 이탈 시 구면 geometry·material·texture·renderer·이벤트를 정리한다. 타입 검사와 production build를 실행해 결과를 확인한다. 실제 사용자 서버 연동은 전날 검증한 공통 코드를 유지하므로 이번 렌더링 교체만으로 같은 연동 검사를 반복하지 않는다. 서버는 사용자가 계속 비교할 수 있게 유지한다. 커밋·푸시·외부 배포는 하지 않았다.

## 파노라마 중단과 세 테마 비교

사용자는 파노라마 결과가 이상하다고 했고 AI는 평면 이미지를 구면에 투영한 왜곡 문제를 인정했다. 사용자는 정지 시안에서 3차원 느낌을 살리는 방향에 동의하고, 미니멀에는 아주 차가운 분위기·따뜻한 분위기·검은 분위기 세 가지를 제안했다.

공간형은 승인한 정지 사진의 원근감과 전경 탁자, 햇살·명암을 사용하는 방식으로 돌아왔다. 시선 회전·구면 투영 코드를 제거하고 Three.js 의존성도 제거했다. 새 3D 모델을 완성한 것으로 설명하지 않는다.

미니멀은 '빙하 / 온기 / 블랙' 버튼으로 배경·본문·보조 글·구분선·강조·신고창 색이 함께 바뀐다. 빙하는 청백색과 푸른 계열, 온기는 따뜻한 밝은 색과 갈색, 블랙은 기존의 어두운 배경을 사용한다. 후보 비교용이며 최종 디자인이나 기본 테마 정책은 아직 미정이다. 초기값은 빙하로 두고 선택을 영구 저장하지 않는다.

브라우저에서 세 테마를 전환하고 체험 대화와 입력 중 문장이 유지되는 것을 확인했다. 360px에서 테마 이름이 줄바꿈되던 부분을 수정해 버튼 높이 44px·이름 한 줄·가로 넘침 없음으로 확인했다. 정지 공간형에는 canvas가 없고 승인된 cafe-spatial.png가 배경으로 사용됨을 확인했다. 타입 검사·production build가 통과했고 마지막 표시 보정은 브라우저에서 확인했다. 서버 계약을 바꾸지 않았으며 실제 서버 연동 검사를 반복하지 않았다.

스크린샷은 대화용 시각화 폴더의 minimal-ice-browser.jpg, minimal-warm-browser.jpg, minimal-black-browser.jpg, spatial-still-browser.jpg에 저장했다. 두 비교 페이지는 로컬에서 계속 사용할 수 있게 유지한다.

## 냉기·햇살의 감각과 공간형이 어울리지 않는 이유

사용자는 빙하에 냉장고처럼 바람이 흐르는 배경, 온기에는 앉은 시점에서 오른쪽 위 햇살과 왼쪽 아래 그림자, 모든 테마의 글씨체 통일을 요청했다. 냉기는 느리면 안 되고 빠르게 흘러야 한다고 정정했다.

빙하 배경에 낮은 대비의 두 냉기 층을 2.6초·3.1초 주기의 transform 애니메이션으로 넣었다. 멈춤·켜기 버튼과 prefers-reduced-motion 정지를 제공했다. 온기 배경은 오른쪽 위를 밝히고 왼쪽 아래에 부드러운 그림자를 둔다. 외부 글꼴 로드와 온기 제목만 다르게 쓰던 글꼴을 제거해 시스템 한글 글꼴로 통일했다. 브라우저에서 애니메이션 주기·running/paused 전환과 빙하/온기의 동일 font-family를 확인했다. 360px에서 새 조절 버튼이 제목과 겹치지 않는 배치를 확인했다. 타입 검사와 빌드가 통과했다. 서버 로직은 변경하지 않았다.

**사용자 질문:** 공간형이 생각한 느낌과 어울리지 않는 이유는 무엇일까?

**AI 해석:** 원하는 휴식감을 가구·기계의 목록으로만 번역해 카페를 관찰하는 이미지에 머물렀다. 사진/도형/파노라마를 바꾸면서 공간과 대화 UI가 한 경험으로 연결되지 못한 점도 있었다. 창을 등지는 구도에서는 고층이라는 단서를 전달하기 어렵고, 빈 의자와 설비가 중심에 남아 장소가 평범한 휴게실로 읽힐 수 있다. 사용자가 요청한 냉기와 햇살은 사물보다 바로 느껴지는 감각이므로 미니멀이 의도에 더 가까울 가능성이 있다는 의견이다. 이는 사용자 선호에 대한 가설이며 공간형을 삭제하거나 미니멀을 최종 확정한 것은 아니다.

배경 보정 스크린샷은 minimal-cold-air-browser.jpg, minimal-sunlight-browser.jpg로 대화용 시각화 폴더에 저장했다.

## 사용자 부재 중 후속 정리

사용자가 계속 작업해 달라고 하고 잠자리에 들었다. 세션 종료 요청으로 처리하지 않고 미니멀 세 테마의 표시·동작 검증을 이어갔다. 새로운 제품 정책이나 최종 디자인을 대신 결정하지 않았다.

- 빙하 냉기의 반복 시작/끝에서 불연속이 드러나지 않도록 경계만 옅어지게 하고 빠른 횡방향 흐름은 유지했다.
- 보조 글자가 어두운 배경 부분에서도 읽히도록 빙하/온기의 색을 조정했다. 대표 배경색을 기준으로 계산한 보조 글자 대비는 빙하 5.03:1, 온기 4.73:1이다. 이는 모든 배경 픽셀의 자동 접근성 검사를 의미하지 않는다.
- 블랙 선택 시 문서 color-scheme도 dark로 바꿔 기본 스크롤바/폼 색이 밝게 튀는 것을 줄였다. 브라우저 계산값 dark를 확인했다.
- 실제 Spring 연결로 야근메뉴방에 입장한 뒤, 입력 중 문장을 둔 채 빙하→온기로 전환하고 전송해 서버 메시지를 수신했다. 블랙 전환 후에도 같은 사용자·방·메시지·연결됨 표시가 유지됐다. 냉기 멈춤/켜기와 실제 연결 유지도 확인했다.
- 모바일 360px에서 실제 채팅과 배경 조절 버튼을 확인했고 가로 넘침이 없었다. 검사 후 실제 연결을 닫고 체험 모드로 되돌렸다. 비교 페이지와 로컬 서버는 계속 사용할 수 있게 유지한다.
- 타입 검사, 프런트 계약 검사 4개, production build, git diff --check가 통과했다. 기본 테스트 실행의 별도 live 검사는 의도적으로 skip이며 앞서 직접 수행한 브라우저 실제 연결 검증과 구분한다.

최종 비교 스크린샷은 minimal-ready-ice.jpg, minimal-ready-warm.jpg, minimal-ready-black.jpg다. 선택 기준은 docs/drafts/frontend/visual-direction-review.md에 정리했다. 기본 테마·세 테마 모두 채택할지·공간형 유지 여부는 여전히 사용자 결정이다. 커밋·푸시·외부 게시·계정 연결은 하지 않았다.


## 빙하 재수정: 구름 대신 어두운 배경의 냉기

**사용자 피드백:** 냉기처럼 보이지 않는다. 안개를 넓히자 구름이 흐르는 것 같다. 차갑게 느껴지도록 조정하거나 배경을 어둡게 해보자.

**조정:** 첫 수정의 넓은 타원형 안개는 구름으로 읽혔다. 빙하만 짙은 청남색 배경과 옅은 청백색 글자로 변경하고, 둥근 덩어리를 제거했다. cold-mist.svg의 가늘고 불규칙한 수증기 줄기를 두 층으로 빠르게 이동시킨다. 온기·블랙의 시각과 채팅 로직은 변경하지 않았다.

**검증:** 브라우저에서 데스크톱과 360px 화면을 확인했다. 가로 넘침 없음, 두 층의 paused/running 전환, 빙하 문서 color-scheme dark를 확인했다. reduced-motion 정지 규칙은 유지했지만 이번에 OS 설정으로 별도 실행하지 않았다. CSS·SVG 변경으로 백엔드/채팅 회귀 검사는 반복하지 않았다. 최종 냉기 느낌은 사용자의 재검토가 필요하다. 스크린샷: minimal-dark-cold.jpg.


## 연기가 아니라 에어컨 바람, 하단에 남는 햇살 그림자

**사용자 정정:** 어두운 냉기 역시 담배처럼 보인다. 냉기는 에어컨 바람이 확 와서 보기만 해도 시원한 느낌이어야 한다. 온기는 건물 아래에 앉아 창밖 태양빛을 받고, 그림자가 아래에 있는 느낌을 원한다.

**변경:** 냉기에서 연기/구름 SVG를 제거하고 밝은 청백색 바탕으로 되돌렸다. 위에서 앞으로 넓어지는 공기 띠를 1.8초 주기로 이동시킨다. 온기는 화면 밖 오른쪽 위 창에서 들어오는 넓은 햇살과 아래 바닥에 드리운 창틀 그림자를 별도 SVG로 표현했다. 글꼴·배치·채팅 코드는 유지했다.

**확인:** 데스크톱에서 두 테마를 직접 보고 냉기 두 층의 멈춤·재생, light color-scheme, 연기 이미지 미사용을 확인했다. 360px 냉기 화면에서 가로 넘침 없음을 확인했다. 모바일 온기 최종 캡처 전 탭이 닫혀 해당 시각 검토는 완료하지 못했다. 브라우저 크기 설정은 복원했다. 냉기/온기의 체감은 사용자 재검토가 필요하다. 기록 스크린샷: cool-air-front.jpg, warm-window-floor.jpg.


## 그림이 아닌 공간의 감각, 건물위·대나무숲 추가

사용자는 온기 표현에 만족했고 건물위(공원·빌딩숲 전망과 햇살), 대나무숲을 추가 요청했다. AI가 건물과 이글루를 SVG로 그리자 사용자는 “그림이 아니라 느낌”이라고 정정했다. 그 시안은 제거했다. 최종 후보는 건물위의 하늘빛·녹색 반사광·햇살, 대나무숲의 녹색 그늘·가느다란 투과광이다. 온기는 유지했다.

냉기는 화면 전체의 질감 이동이 아닌 오른쪽 위에서 시작해 왼쪽 아래로 내려오는 별도 바람 요소로 변경했다. 사용자가 가는 바람을 비 같다고 하고 빠르다고 지적해, 최종 4개 넓은 공기 층(높이 70~190px)과 4.8초 이동 주기로 수정했다. 얼음 블록 그림 대신 주변의 둥근 음영·밝은 안쪽·하단 반사광으로 공간감을 시도했다. 체감은 사용자 검토 사항이다.

브라우저에서 바람 시작점이 화면 오른쪽 위인지, 넓이·높이·4.8초 주기·재생을 계산 스타일로 확인했다. 360px에서 다섯 테마 버튼과 가로 넘침 없음, 수정 전후 멈춤 기능을 확인했다. 화면 크기 설정을 복원했다. 타입 검사 통과, 프런트 계약 테스트 4개 통과(live 1개는 기본 실행에서 skip). 이번 배경 작업에서 실제 서버 회귀 검사는 반복하지 않았다. 대표 화면: bamboo-atmosphere.jpg, cold-wide-slow.jpg.


## 냉기 가시성·공간감 보강, 건물위 제거

사용자는 냉기와 공간감이 잘 보이지 않는다고 했고 건물위 삭제를 요청했다. 선택 목록과 관련 CSS에서 건물위를 제거했다. 현재 후보는 빙하·온기·대나무숲·블랙이다. 냉기는 주변 푸른 벽 음영, 밝은 안쪽, 하단 타원형 반사광과 접지 음영을 보강했다. 바람은 흰 중심부 대비를 높이고 흐림을 줄였으며, 장식 음영 위에서 보이게 배치했다. 넓은 폭·4.8초·오른쪽 위→왼쪽 아래 방향은 유지했다. 타입 검사와 diff 공백 검사를 통과했다. 브라우저에서 건물위 제거, 네 테마 목록, 4.8초, 가로 넘침 없음을 확인했다. 공간감이 충분한지는 사용자의 재검토가 필요하다. 캡처: cold-depth-visible.jpg.


## 긴 바람이 햇살로 보인다는 피드백

짧은 바람을 넓히는 것만으로는 유성처럼 보였고, 길이를 180vmax·7초로 바꾸자 사용자는 햇살 같다고 지적했다. 발광 띠가 공기의 움직임으로 읽히지 않는 것이 문제였다. 넓은 세 흐름의 방향과 느린 이동은 유지하고, 흰 띠/발광 중심부를 제거했다. 현재는 미세한 청회색 성에 입자가 같이 이동하는 표현을 비교한다. 브라우저에서 빛띠가 제거된 화면을 확인했고 체감에 대한 긍정 피드백은 아직 없다. 캡처: cold-air-no-light.jpg. 이전 long-air 시안은 현재 화면이 아니다.


사용자는 성에 입자도 원한 바람 표현이 아니라고 정정했다. 입자 파일을 제거하고 긴 곡선 경로를 따라 넓은 공기 결이 이동하는 방식으로 교체했다. 발광 없이 공간과 같은 청회색으로 세 흐름이 오른쪽 위에서 왼쪽 아래로 진행한다. 브라우저에서 입자 없음·곡선 흐름 3개와 이동 중 offset을 확인했다. 타입 검사 통과. 이 시안도 사용자 승인을 받지 않은 비교 후보이며, 원하는 감각과 다르면 추가 구현보다 기준을 다시 맞출 필요가 있다. 캡처: cold-curved-airflow.jpg.


## 넓은 흰 구름 형태로 변경

사용자가 곡선 바람은 스파게티 같다고 하고 넓은 흰 구름 형태를 명시했다. 이전 곡선 띠를 제거하고, 넓은 타원형 구름이 겹친 두 냉기 층으로 변경했다. 흰색·부드러운 가장자리·오른쪽 위→왼쪽 아래·11초의 느린 이동으로 구성한다. 이전 구름 제외 방향보다 최신 사용자 요청을 우선했다. 타입 검사 통과, 브라우저 표시와 두 층의 멈춤·켜기를 확인했다. 캡처 cold-white-cloud.jpg. 최종 체감은 사용자 검토 대상이다.


## 넓은 흰 구름층으로 변경

사용자가 곡선 바람을 스파게티처럼 보인다고 지적하고 “넓은 흰 구름이 흐르는 것처럼” 변경을 요청했다. 기존 곡선 경로를 제거하고 불규칙하고 부드러운 흰 구름 두 층으로 변경했다. 오른쪽 위→왼쪽 아래로 13초 주기로 흘러가며 두 층은 반 주기 어긋나게 배치했다. 둥근 공간 음영은 유지했다. 타입 검사 통과, 브라우저에서 넓은 흰 구름 화면과 두 층의 멈춤/재생을 확인했다. 검토 중 프런트 서버가 꺼져 있어 npm run dev로 다시 시작했다. 캡처: cold-wide-clouds.jpg.


## 2D 구름의 깊이와 사각 경계

사용자는 흰 구름 표현을 괜찮다고 했고 더 빠른 오른쪽 위→왼쪽 아래 흐름과 2D 공간감을 요청했다. 기존 구름 모양을 유지하면서 먼 층은 7초·낮은 농도, 가까운 큰 층은 4.8초·높은 농도로 조정했다. 벽과 바닥은 고정하고 겹침·속도 차로 깊이를 시도한다.

**사용자 질문:** 처음에 왜 사각형이 옆으로 이동하는 것처럼 보이나?
**설명/수정:** 이미지의 구름 일부가 SVG 캔버스 끝에서 잘린 채 이동해 사각 레이어 경계가 노출될 수 있었다. 구름 레이어 네 가장자리를 타원형 투명 마스크로 부드럽게 없앴다. 브라우저 계산값으로 두 층의 마스크 적용과 화면을 확인했다. reduced-motion 선택자도 실제 cloud-layer에 맞게 보정했다. 캡처: cold-cloud-soft-edges.jpg.


## 미니멀 방향과 서비스의 적합성

**사용자:** 이제 괜찮다. 공간형은 없어도 되겠다. 서비스가 이 화면에 잘 들어갈 수 있나?

**검토:** 짧은 익명 대화를 중심에 두고 배경은 쉬는 분위기를 주는 역할로 쓰는 방향이 서비스의 짧은 이용 시간·낮은 진입 장벽에 맞는다. 현재 프런트에는 방 선택·선택 닉네임·입장·메시지·신고·연결 종료가 이미 같은 컴포넌트에 있다. 다만 디자인 비교용 화면으로, 공개 서비스 완성 상태는 아니다. 다음에는 입장 후 제목/여백을 줄이고 대화/입력 영역을 넓히는 실제 채팅 화면 검토를 제안했다. 공간형은 제외 방향으로 기록하고 현재 라우트/비교 링크 삭제는 아직 하지 않았다.


## 글씨 굵기와 문구 정리

사용자가 글씨를 굵게 하고 군더더기 문구를 줄이자고 제안했다. 제목·방 이름·주요 버튼은 600, 본문·입력은 500으로 정리했다. 분위기 설명·소개 부제·하단 슬로건·디자인 비교 링크·입장 전 중복 상태 표시·반복 로그인 안내를 제거했다. 닉네임 선택 입력, 자동 생성 설명, 체험 모드 구분, 연결/오류, 신고와 입력 도움말은 유지했다. 브랜드 링크는 /minimal로 이동한다. 공간형 라우트와 비교 홈 자체는 아직 남아 있다.

타입 검사 통과. 브라우저에서 제목/방 이름 600과 체험 입장→대화/상태 안내→나가기 흐름을 확인했다. 문구와 스타일 작업이라 실제 서버 테스트는 반복하지 않았다. 스크린샷: minimal-clear-type.jpg.


**글씨 굵기 정정:** 사용자는 제목 위주가 아니라 전반적인 글씨를 굵게 해달라는 뜻이었다. 안내·테마 이름·운영 시간·입력·채팅 본문까지 600으로 통일했다. 브라우저 입장 화면의 관련 텍스트 요소 25개 모두 계산값 600을 확인했다. 이전 본문 500은 현재 기준이 아니다. 캡처: minimal-all-semibold.jpg.


## 채팅에 들어가면 대화가 중심이 되도록

미니멀 방향과 전체 글씨 굵기를 유지하면서, 이번 범위는 입장 이후 채팅 배치 하나로 제한했다. 정상 입장 시 소개 제목을 접고 채팅 영역을 넓힌다. 긴 문장은 가로로 넘치지 않고 줄바꿈하며, 입력창을 유지한 채 대화 목록만 스크롤된다. 신고창과 나가기는 그대로 동작해야 한다.

구현은 data-phase에 따른 CSS 배치로 처리했다. 데스크톱 대화 폭은 최대 760px, 남은 높이를 목록에 배분하고 모바일은 화면 높이에 맞춰 조정한다. 대화 중 냉기 배경 농도를 낮춰 글과 경쟁하지 않게 했다. 서비스 정책과 메시지 전송 로직은 변경하지 않았다.

검증: 타입 검사와 프런트 계약 검사 4개 통과(live 검사는 기본 실행에서 skip). 브라우저 체험 모드에서 입장→140자 공백 없는 문장 전송→모바일 360px 줄바꿈/가로 넘침 없음→신고창 열기/취소→나가기/재입장을 확인했다. 채팅 본문 굵기 600 유지. 실제 휴대전화 키보드는 검증하지 않았다. 캡처: chat-layout-desktop.jpg, chat-layout-mobile-360.jpg.

환경: 시작 스킬에 따라 make를 실행했으나 Docker 앱을 찾지 못해 docker-start에서 실패했다. 설치/Makefile 변경은 하지 않았다. 프런트 체험 모드는 정상 동작하므로 화면 작업을 계속했다. 실제 Spring·PostgreSQL 연동은 이번 회차에서 확인하지 못했다.


## 하단 테마·실제 서버 검증·게임 후보 조사

사용자가 Docker 실행과 실제 연동, 하단 테마 배치, 게임 후보 조사, 지금까지 작업의 커밋·푸시를 요청했다. Docker 접근을 허용한 실행에서 make가 성공했고 PostgreSQL은 기존 볼륨 그대로 실행됐다. 앞선 Docker 앱 미발견은 권한 제한 영향을 받은 것으로 확인했다. Spring 8080을 시작하고 Flyway V10 최신 상태와 스키마 검증을 확인했다.

테마는 대화 아래 footer로 옮겼다. 실제 야근메뉴방에 브라우저 쿠키로 입장→메시지 전송/수신→온기 전환 후 같은 연결과 대화 유지를 확인했다. 360px에서 테마가 입력창 아래에 있고 가로 넘침이 없는 것을 확인했다. 캡처: live-chat-bottom-themes.jpg. 실제 연동 포함 테스트 5개 모두 통과, 타입 검사·production build 통과. 사용자 요청대로 서버는 켜둔다.

research 스킬로 별도 조사 에이전트에 게임 후보를 맡겼다. 패턴 순서 기억 우선, 작은 SameGame 다음을 추천하되 사용자가 선택한 것은 아니다. 반응속도·슬라이딩·2048까지 비교했고, 점수 변조와 공개 순위는 별도 설계임을 명시했다. 보고서: docs/research/minigame-candidates-2026-11-06.md. 게임 코드는 구현하지 않았다.

커밋 범위는 프런트와 디자인/개발 기록·게임 조사다. 기존 breakground.zip 삭제와 .DS_Store는 이번 작업과 무관해 제외한다.


## 게임 후보의 방향 정정: 플래시게임 같은 깊이

사용자는 패턴 기억·단순 퍼즐보다 더 심도 있는, 플래시게임 같은 종류를 원한다고 정정했다. AI가 짧은 체류 시간을 너무 작은 게임 규칙으로 좁혀 해석했다. 새 조사 기준은 짧은 스테이지 안에서도 조작 숙련·자원 선택·성장·실패 후 재도전이 있는 액션/타이쿤/디펜스다. 실제 첫 게임 장르는 아직 선택하지 않았다. 한 판 목표 시간은 설계 제안이지 실측값이 아니다.

공식 제작자 자료를 다시 조사한 보고서는 docs/research/flash-style-game-candidates-2026-11-06.md다. Kingdom Rush식 배치/강화 디펜스, Papa 계열 주문/설비 타이쿤, N 계열 플랫폼 조작, Twin Shot 계열 방 단위 전투를 비교했다. AI 추천은 작은 웨이브 디펜스이며 사용자 선택은 미정이다. 원작 플레이·개발 시간·재미는 검증하지 않았고 시간/콘텐츠 양은 가정이다.


## 게임 취향 확정: 간단한 조작과 액션·물리 퍼즐

사용자는 선택 질문에서 “액션·물리 퍼즐 — 조작과 타격감”을 골랐고 빠르고 쉽게 할 수 있어야 한다고 덧붙였다. 앞선 AI의 디펜스 우선 추천보다 이 사용자 선호를 우선한다. 짧은 스테이지·즉시 재도전·단순 입력을 기준으로 조준/튕기기, 원버튼 대시 같은 독자 후보를 다음 논의로 제안한다. 후보별 시간은 실측이 아닌 제안이고 첫 게임은 아직 선택하지 않았다. 게임 구현은 시작하지 않았다.


## 사용자 게임 아이디어: 회사 스트레스 해소 묶음

사용자가 상사 때리기·퇴사 내버리기·회사 컴퓨터 박살내기를 묶는 아이디어를 제안했다. 단순 테스트보다 짧은 조작과 타격감·물리 반응이 있는 게임을 원한다는 앞선 선호와 연결된다. 공통 화면/조작/결과 틀을 공유하되 세 게임의 핵심 재미를 타격·투척·파괴로 구분하고, 첫 시제품은 하나만 만드는 방향을 AI가 제안했다. 만화풍 과장·게임명·점수식·해금·상점 등은 확정하지 않았고 게임 코드는 구현하지 않았다.


**게임 3D 허용:** 사용자는 게임 종류에 따라 3D를 전면적으로 사용해도 된다고 했다. 메인 화면은 미니멀 방향을 유지하고 게임별 시각/조작 효과로 2D·3D를 판단한다. AI는 컴퓨터 파괴의 충격·부품 분리·낙하가 첫 3D 후보로 적합하다고 제안했다. 첫 게임 선택이나 3D 엔진 도입을 확정한 것은 아니다.


## 사용자 게임 구상: 짜증나는 메일을 종이비행기로 던지기

사용자는 모니터에 온 짜증나는 이메일을 꺼내 종이비행기로 접고 사람들에게 던지며, 잘 맞출수록 점수가 오르는 게임을 제안했다. 이는 첫 구체 게임 후보로 다음 검토의 중심이다. AI는 3D 비행 궤적과 거리감, 짧은 자동 접기 연출과 직접 조준/던지기 조작을 제안했다. 자동 접기·조작 방식·점수식·시간 제한은 아직 사용자 합의 전이다. 원본 사용자 이메일을 읽는 기능이 아니라 게임 안의 가상 이메일 연출로 해석한다. 구현과 엔진 도입은 시작하지 않았다.


## 종이비행기 첫 시제품과 카드게임 후보

사용자가 종이비행기 구상에 ㄱㄱ로 구현을 맡겼다. 게임은 `/games/mail-plane`에 별도 시제품으로 만들고 메인에 진입 링크를 추가했다. Three.js와 타입 정의만 설치했고 물리 엔진이나 백엔드/DB 기능을 추가하지 않았다. 자체 도형의 사무실·움직이는 표적, 메일 클릭/접기, 드래그/키보드 조준, 예상 궤적, 단순 중력 비행, 명중 정확도/거리/연속 점수, 5회 종료, 재시작, 일시정지를 구현했다. 시간 제한·점수식·5회는 최종 정책이 아닌 체험값이다. 시제품 상태·점수는 브라우저 메모리뿐이다.

브라우저 검증: 기본 투척 빗나감, 방향키 조준과 Space 투척으로 명중 +58, 추가 투척 명중 +80, 5회 종료와 138점 결과, 다시 하기에서 0점/0회 복귀를 확인했다. 360px에서 가로 넘침 없음과 드래그 투척을 확인했다. 일시정지 때 던지기 비활성화 후 재개를 확인하고 화면 크기 설정을 복원했다. 타입 검사·기존 채팅 계약 검사 4개·production build 통과(live 검사는 기본 실행에서 skip). 채팅 검사를 게임 자동 테스트로 보지 않는다. 실제 휴대전화 성능, WebGL 미지원 분기, 재미·난이도는 검증하지 않았다. 캡처: mail-plane-prototype.jpg.

사용자가 추가 게임 3개와 간단한 카드게임도 생각해달라고 했다. 추가 창작 아이디어는 의자 컬링·서류 도미노·고무줄 당구로 정리했다. research 스킬의 조사 에이전트가 골프 솔리테어·피라미드·포커 스퀘어·독자 퇴근 정리 카드퍼즐을 공식 규칙과 제안으로 구분해 docs/research/short-card-games-2026-11-06.md에 남겼다. 카드게임은 구현/정책 확정하지 않았다. 잠자는 동안 계속하라는 요청은 세션 종료로 처리하지 않았고 Docker/서버를 내리거나 자동 커밋·푸시하지 않았다.
