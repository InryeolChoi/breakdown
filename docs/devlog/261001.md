# 2026-10-01 — AnonymousUser 식별 정책 시작

## 출근 전 10분 미션

Room 도메인은 schema, API, 단위 테스트까지 마무리됐다. 다음 AnonymousUser 구현에 앞서, 로그인 없는 서비스가 같은 브라우저를 어떻게 최소한으로 식별할지 정책부터 정한다.

후보는 서버가 예측하기 어려운 임의 토큰을 만들고, 브라우저 cookie와 AnonymousUser DB row에 함께 보관하는 방식이다. 이후 cookie가 있으면 해당 사용자를 다시 찾고 마지막 활동 시각을 갱신한다. 이 정책이 정해지면 ERD, Flyway V5, Entity부터 Controller까지 한 수직 슬라이스로 구현한다.

## AnonymousUser 코드는 어떤 흐름으로 나눌까?

코드가 막막할 때는 먼저 HTTP 요청에서 DB까지의 한 흐름을 그린다.

```text
브라우저 요청 + cookie
  → Controller가 cookie 확인
  → Service가 사용자 찾기 또는 생성 결정
  → Repository가 PostgreSQL 조회·저장
  → Entity가 AnonymousUser 상태 표현
  → Response DTO가 필요한 값만 반환
```

첫 진입에서 서버가 임의 토큰을 만들고 cookie로 내려주는 흐름과, 다음 요청에서 cookie로 기존 사용자를 찾는 흐름을 설계해야 한다. 브라우저 식별 토큰은 비밀번호처럼 취급할 수 있으므로 토큰 원문을 DB에 저장할지 해시를 저장할지도 결정 대상이다.

`AGENTS.md`의 기존 도메인 원칙에 따르면 닉네임은 입력 가능하고, 없으면 서버가 임의 생성한다. 따라서 우선 논의할 정책은 cookie 수명과 토큰 저장 방식이다.
