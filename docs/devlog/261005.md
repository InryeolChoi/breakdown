# 2026-10-05 — 익명 사용자 재방문 구현 이해

## AnonymousUserSession은 무엇인가?

Service가 Controller에 사용자와 쿠키 원문 토큰이라는 두 값을 함께 반환하기 위한 내부 전달 객체다. Java 메서드 반환값 하나에 둘을 묶기 위해 record를 사용했다. `session.user()`는 HTTP 응답 DTO를 만드는 데 쓰고 `session.rawToken()`은 Set-Cookie에 쓴다. 이것 자체는 JPA Entity, DB 테이블 또는 Servlet HttpSession이 아니다. 기존 AnonymousUserResponse에 원문 토큰을 넣으면 JSON에 비밀값이 노출되므로 내부 결과 객체와 외부 응답 DTO를 구분했다. record가 두 필드의 생성자와 접근자 등을 제공하고, toString은 원문 토큰이 로그에 찍히지 않게 가린다.

## 테스트 보완 및 실행 결과

쿠키의 원문 전달·HttpOnly·SameSite·Path·7일 Max-Age·HTTPS Secure, 닉네임 30/31자 경계, 잘못된 JSON, 응답 본문에 토큰이 없는지를 Controller 테스트에 추가했다. PostgreSQL 테스트는 모르는 토큰의 신규 발급, 방문 시각 UPDATE 후 재조회, 차단 만료 상태 복원을 확인하고, Entity 테스트는 차단 해제 시각 직전에도 차단이 유지되는지를 확인한다. `./gradlew test`는 전체 24개 통과, 실패·오류·건너뜀 모두 0이다.

## HttpServletRequest를 Controller 파라미터로 받는 이유

`@RestController` 어노테이션의 파라미터가 아니라 요청 처리 메서드의 파라미터다. Spring MVC가 현재 HTTP 요청 객체를 전달한다. 이번 구현에서 사용한 목적은 `servletRequest.isSecure()`로 요청이 HTTPS인지 확인하고 ResponseCookie의 Secure 속성을 정하는 것이다. 로컬 HTTP 요청에서는 false, 직접 HTTPS 요청에서는 true로 설정된다. Secure 쿠키는 브라우저가 HTTPS 요청에만 전달하도록 제한한다. JSON 요청 DTO는 본문 입력을 나타내고 HttpServletRequest는 전송 방식·헤더 등 HTTP 요청 정보를 나타낸다. 향후 AWS ALB처럼 HTTPS를 종료하는 프록시 뒤에서는 전달 헤더 처리 및 신뢰하는 프록시 설정을 확인해야 isSecure가 원래 HTTPS 요청을 정확히 반영한다.

## 학습 진행과 개발 속도에 대한 점검

현재 대화와 코드에서 반복된 어려움은 타입·반환값·제어 흐름을 함께 추적하는 것이다. Optional<AnonymousUser>와 AnonymousUser를 구분하고, map이 반환값을 요구하며 void 메서드는 상태 변경이라는 점, orElseThrow 뒤의 null 분기가 실행되지 않는 점에서 막혔다. Spring에서는 요청 본문·쿠키·내부 결과 객체의 책임 구분과 트랜잭션/영속 상태를 연결하는 경험이 아직 적다. 이 관찰만으로 Java/Spring 전체 역량이나 다른 개발 경험까지 평가할 수는 없다.

속도를 위해 먼저 메서드 입력·출력과 분기별 결과를 글로 정리하고, Optional은 조회 경계에서만 쓰고 내부 로직은 단순 if/return으로 작성한다. 한 번에 한 흐름을 완성하고 컴파일/테스트로 확인한다. AI가 초기에 새 개념과 정책을 계속 추가하거나 여러 계층을 동시에 구현해주는 방식도 사용자의 이해와 진행을 분리시키므로 범위를 줄인다. 토큰 생성 같은 표준 기능과 반복 작업은 AI에 맡길 수 있지만, 전체 흐름을 사용자가 설명하고 작은 변경을 직접 수행할 수 있는지로 이해를 확인한다.

## 다음 단계는 Message 테이블과 HTTP API

AnonymousUser 작업을 GitHub에 반영하고 Message로 진행하기로 했다. 현재 Message는 ERD 초안에만 있으므로 실제 PostgreSQL 테이블을 만드는 Flyway V9이 필요하다. 기존 Room과 AnonymousUser를 외래 키로 연결하고, id 자동 생성·content 최대 140자·내용과 작성 시각 NOT NULL을 ERD/DDL에 맞춰 반영하는 것이 사용자의 첫 작업이다. 작성자는 클라이언트가 보낸 user id가 아니라 쿠키 token 검증으로 서버에서 결정한다.

WebSocket 도입 전에 HTTP 작성/조회 API로 메시지 내용 검증, 방 운영 시간, 차단 상태, 저장/조회 흐름을 확인한다. 이후 실시간 전달을 붙이되 검증과 저장 로직은 Service에서 공유한다. 현재 익명 사용자 API가 성공했다고 메시지 작성 권한까지 보장하는 것은 아니므로, Message 작성 유스케이스가 방과 차단 여부를 검사해야 한다.

## 과거 메시지를 보존하지 않는데 왜 Message 테이블이 필요한가?

우리 정책은 메시지를 전혀 저장하지 않는 것이 아니라 방이 열린 동안 보관하고 방이 닫히면 삭제하는 것이다. Message row는 방·작성자·내용·작성 시각을 연결하고, 새로 들어온 사용자에게 현재 방의 메시지를 조회해 주며, 신고 대상 메시지를 id로 식별하는 데 쓰인다. WebSocket은 연결된 사용자에게 데이터를 전달하는 수단이라 메시지 저장 수명이나 신고 대상을 관리해 주지 않는다. 채팅을 DB 없이 구현하는 것도 가능하지만 현재 ERD와 신고/조회 정책을 실현하려면 Message 테이블이 적합하다. 방 종료 삭제는 별도 로직으로 구현해야 하며 테이블이 있다고 자동 삭제되는 것은 아니다.

## 기존 AI 협업 문서와 새 프롬프트 비교

기존 AGENTS.md에도 설계 결정을 대신하지 않기, 힌트 우선, 사용자 코드 리뷰, Spring/JPA/DB 내부 동작 설명, 이해 우선 원칙이 이미 있었다. CLAUDE.md는 AGENTS.md를 공통 기준으로 참조하고 변경 전 설계 의도/영향 범위를 설명하도록 보완한다. 따라서 새 프롬프트 전체를 반복해서 붙일 필요는 없다. 새로 보완할 실질적인 내용은 작은 기능으로 작업 범위 제한, 정상·실패·경계 상황부터 정하기, AI와 사용자의 구현 책임 구분, 검증 결과와 미확인 사항 보고, 가벼운 이해 확인이다.

기존 규칙도 AI 구현을 전면 금지하지 않으므로 새 방향과 충돌하지 않는다. 반복 작업을 AI에 맡기고 사용자는 정책 판단·결과 검증·작은 수정 능력을 갖추는 목표를 명시하면 협업 의도가 더 분명해진다. 문서 부족 외에도 실제 진행에서 한 기능의 범위를 늘리고 여러 계층을 한꺼번에 구현한 방식이 학습 속도에 영향을 주었다. 공통 규칙은 AGENTS.md에 모으고 CLAUDE.md는 참조 문서로 유지하는 편이 중복과 불일치를 줄인다. 이번 요청은 비교이므로 두 지침 파일은 수정하지 않았다.

## 일반 채팅은 임시 메모리, 신고 증거만 DB에 저장하는 제안 검토

늦게 입장한 사용자에게 과거 대화를 제공할 요구는 없다는 사용자 설명으로 기존 Message 테이블/V9 계획을 보류했다. 새 제안은 서버가 messageId와 작성자·방·내용·작성 시각을 묶어 짧게 메모리에 유지하고, 신고 요청의 ID로 원본을 찾아 Report에 증거를 복사하는 것이다. 신고자는 cookie로 확인하며, 신고 대상과 내용은 서버 원본에서 결정한다. 이는 PostgreSQL Message 테이블 없이 구현할 수 있으며 Java 메시지 객체는 여전히 필요하다.

초기 단일 서버에는 적합하지만 임시 보관 기간이 신고 가능한 시간을 제한한다. 만료/방 종료/서버 재시작으로 원본이 없으면 검증할 수 없는 브라우저 내용을 대신 저장하지 않는다. TTL과 총 보관량 상한, 동시 접근·신고 복사와 삭제의 경합을 처리해야 한다. 다중 서버로 확장할 때 메모리 공유 문제가 생기면 그때 저장 방식을 재검토한다. 중복 기준은 동일 메시지인지 동일 대상 사용자인지 별도 결정이 필요하며 메시지 ID는 Message 테이블 FK 없이 Report에 저장할 수 있다. 또한 일반 채팅을 남기지 않는 정책에 신고 증거 보존 예외와 보존 기간을 명시해야 한다. 현재는 제안 평가 단계로 ERD/정책 확정 변경은 하지 않았다.

## 메시지 ID와 임시 메모리 보관을 구체화하기

Redis를 먼저 도입할 필요는 없다. 단일 Spring 서버가 관리하는 객체의 필드에 ConcurrentHashMap<UUID, ChatMessage>를 두고 서버가 받은 메시지를 저장할 수 있다. 메시지 ID는 DB 자동 생성값이 아니라 서버의 UUID.randomUUID()로 만들고, Java record 같은 객체에 방·작성자·내용·작성 시각과 함께 담는다. WebSocket으로 보낼 때 ID도 전달하고, 신고할 때 서버는 ID로 Map에서 원본을 찾는다. 작성자는 브라우저가 지정한 id를 신뢰하지 않고 서버가 쿠키/연결에서 확인한 사용자다.

Map은 실행 중인 Java 프로세스의 RAM에 있을 뿐 PostgreSQL에 저장되지 않으며 재시작하면 사라진다. 일정 시간 이후 자동으로 삭제되는 기능은 일반 Map에 없으므로 별도 만료 확인과 정리가 필요하다. 예를 들어 5분 보관은 설명용 후보이며 아직 정책으로 확정하지 않았다. 보관 시간·최대 용량·방 종료 시 정리 정책을 결정한 뒤 구현한다. Redis 같은 공유 보관소는 다중 서버 등 실제 필요가 생기면 검토한다.

비교 결과를 반영해 AGENTS.md의 AI Collaboration에 학습 목표와 작업 범위·구현 역할 분담·설명 방식·실행 검증·가벼운 이해 확인 기준을 추가했다. 사용자가 AI에 구현을 맡기는 경우에는 요청 범위를 완성하고 핵심 흐름을 설명하도록 명시했다. CLAUDE.md는 공통 기준을 참조하는 구조를 유지한다.

## 다음 기능에 어떤 Skill을 쓸까?

설치된 grill-with-docs, to-spec, to-tickets, implement, wayfinder의 실제 SKILL.md를 읽어 비교했다. Message HTTP 작성/조회 기능처럼 작은 범위는 grill-with-docs로 남은 정책만 짧게 확인한 뒤, 필요하면 to-spec으로 합의 사항을 정리하는 흐름이 적합하다. to-tickets는 여러 개의 검증 가능한 기능 단위로 나눌 일이 있을 때 사용한다. implement는 AI가 구현·테스트·리뷰·커밋까지 수행하는 절차이므로 사용자가 핵심 코드를 직접 작성하는 단계에서는 적용 범위를 명시한다. wayfinder는 여러 세션이 필요한 큰 결정들을 추적하는 도구라 현재 작은 기능에는 필요하지 않다. to-spec/to-tickets는 트래커와 라벨 설정을 전제로 하고, 실제 호출 시 문서/티켓 게시도 수행할 수 있다는 점을 확인했다. 이번에는 선택 비교만 수행했고 해당 워크플로를 실행하거나 티켓을 게시하지 않았다.

## 사용자에게 정책을 확인하고 AI가 전체 구현

사용자는 이번 메시지 임시 보관·신고 기능을 AI가 작성하고 직접 리뷰하기로 했다. 확인된 정책은 메시지 최대 15분(방 종료가 더 빠르면 그때 만료), 같은 신고자의 같은 메시지 중복 금지, 신고 증거 30일 보관이다. 서버 메모리에는 UUID·작성자·방·내용·작성 시각·만료 시각을 보관하며 10,000개 상한을 설정했다. HTTP 메시지 작성/신고 API를 구현했고 서버 쿠키로 사용자를 검증한다. 아직 실시간 브로드캐스트는 구현하지 않았다.

V9는 Report만 만들며 Message 테이블은 없다. Report의 대상 사용자와 증거 내용은 서버 메모리 원본에서 가져온다. 과거 입력 내용을 브라우저가 바꿔 보내도 증거는 바뀌지 않는다. PostgreSQL UNIQUE로 동시 중복 신고도 방어한다. 신고 원본이 없으면 410, 닫힌 방/차단은 403, 쿠키 없음/만료는 401이다. 메시지 만료는 접근을 즉시 막고 물리 정리는 1초 간격, Report 삭제는 30일 기한이 지난 row를 1분 간격 정리한다. JPA 트랜잭션으로 Map이 자동 롤백되지 않으므로 실패 시 메시지를 제거하는 콜백을 추가했다.

전체 검증 과정에서 30일 삭제 직전 테스트를 1나노초 차이로 만들면 PostgreSQL timestamp의 마이크로초 정밀도 때문에 경계가 반올림될 수 있음을 확인했다. DB 경계 테스트를 마이크로초 단위로 수정했다. ERD/정책/프로젝트 지침을 새 모델에 맞췄고, 기존 AI 협업 원칙 수정은 보존했다.

최종 `./gradlew test`: 39개, 실패 0, 오류 0, 건너뜀 0. 검토 순서는 `docs/reviews/chat-report.md`에 기록했다.

## Wayfinder와 설계→명세→티켓→구현 스킬의 적용 시점

사용자가 질문한 Wayfinder와 grill-with-docs/to-spec/to-tickets/implement의 실제 SKILL.md를 읽었다. Wayfinder는 큰 미해결 설계를 여러 세션의 결정 이슈로 탐색한다. 후자의 흐름은 정책을 사용자와 구체화하고, 명세에 완료 기준을 고정하며, 검증 가능한 작은 기능 단위로 나눈 다음 승인된 구현을 수행하기에 적합하다. 다음 실시간 채팅 단계부터 적용하는 것을 권했다. 현재 질문은 흐름 평가이므로 이슈 발행이나 자동 실행을 하지 않았다. 작성자 주도권을 유지하는 지점은 정책 결정·티켓 검토·구현 흐름 설명이며, 코드 리뷰 체크포인트 하나를 남겼다.

## 채팅·신고 코드를 읽으며 생긴 질문

사용자는 Controller 주소, 트랜잭션 종료 콜백, DB 없는 채팅 구조, LAZY/JoinColumn, Modifying, ReportCleanup의 역할을 질문했다. 추가로 놓친 검토 질문도 요청했다.

- ChatController에는 클래스의 RequestMapping에 `/rooms/{roomId}/messages`가 있다. 메서드의 인자 없는 PostMapping은 그 주소에 POST를 연결한다. RestController 자체는 주소 설정이 아니라 컨트롤러 등록과 응답 본문 변환을 담당한다.
- registerSynchronization은 현재 트랜잭션에 종료 후 실행할 콜백을 등록한다. ChatService는 사용자의 lastSeenAt을 DB에서 갱신하지만 메시지는 Map에 넣는다. PostgreSQL 롤백으로 Map은 복구되지 않으므로 커밋되지 않으면 Map에서 메시지를 제거한다. 이것은 DB와 Map을 완전히 원자적으로 묶는 기능은 아니다. 커밋 전 다른 요청이 Map 메시지를 읽을 수 있는 문제는 별도의 검토 항목이다.
- chat은 Controller/DTO/Service와 일반 Java record, 메모리 저장소를 갖는다. JPA Entity와 채팅용 JpaRepository만 없다. DB 테이블이 없어도 도메인 객체와 저장 역할은 필요하다.
- Report의 ManyToOne은 여러 신고가 한 사용자/방을 참조한다는 객체 관계다. JoinColumn은 이 관계를 report의 외래 키 컬럼에 연결한다. LAZY는 연결된 객체의 상태를 필요할 때 불러오도록 요청한다. Hibernate에서는 보통 프록시를 사용하고 접근 시 추가 SQL이 발생할 수 있다. 초기화되지 않은 관계를 영속성 컨텍스트 밖에서 읽는 문제와 목록 조회의 N+1도 검토해야 한다.
- Modifying은 직접 Query로 선언한 UPDATE/DELETE 등을 변경 쿼리로 실행하게 한다. save나 기본 delete 메서드마다 붙이는 것이 아니다. deleteExpired는 JPQL 벌크 삭제라 영속성 컨텍스트의 객체를 하나씩 삭제하는 것과 달라, 메모리 상태가 자동 동기화되지 않고 엔티티별 삭제 콜백도 수행하지 않는다. 호출 측 트랜잭션이 필요하다.
- ReportCleanup은 클라이언트 요청 없이 30일이 지난 신고 증거 row를 지운다. Scheduled fixedDelay 60000은 이전 작업 완료 후 60초를 기다린다. 애플리케이션이 정지해 있으면 작업도 멈추므로 정확히 30일 순간에 물리 삭제되는 것은 아니다.

놓친 질문을 시험처럼 취급하기보다 구현 검토 기준으로 정리했다. 서버 재시작/다중 서버에서 메모리 증거가 유지되는지, 트랜잭션 커밋 전 Map 공개가 안전한지, 스케줄 정지 시 보관 기한은 어떻게 보장하는지, LAZY 목록 조회가 몇 개 SQL을 만드는지, 클라이언트가 작성자/증거를 조작할 수 있는지 등을 우선 확인한다. 현재 단일 서버·임시 메모리라는 한계를 설명하고 코드 변경은 하지 않았다.

참고: Spring 공식 Request Mapping, TransactionSynchronization, Scheduling 문서와 Spring Data JPA Modifying API, Jakarta Persistence 관계 매핑 문서를 확인했다.

## 오늘 마무리와 다음 학습 방식

사용자는 Report 코드를 직접 쳐봤다면 더 기억에 남았을 것 같다고 말했다. 이번 전체 구현은 명시적으로 맡겼지만, 다음 세션은 새 기능의 대량 구현보다 Report의 작은 메서드를 직접 다시 작성하는 복습부터 시작한다. AI는 힌트와 코드 리뷰를 제공한다. 이어 DB 커밋 전에 Map 메시지가 노출되는 한계를 검토한다. NEXT.md에 두 항목을 우선순위로 남겼다.

기능 코드의 마지막 전체 테스트 결과는 39개 통과이며 이후에는 문서만 수정했다. 공백 검사 통과, 추가 파일에 빌드 산출물이 없는지와 대표적인 비밀키 패턴을 확인했다. make fclean은 성공하여 PostgreSQL 컨테이너·네트워크를 제거하고 Docker Desktop 종료 명령을 완료했다. 이번 구현과 학습 기록은 종료 절차에 따라 커밋·푸시한다.
