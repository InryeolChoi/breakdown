# 2026-09-18 — RoomRepository 하려다가 Docker부터

다시 시작하려고 make를 실행했는데, 지난번과 같은 네트워크 오류가 났다.
RoomRepository에 집중하려 했는데 왜 또 Docker인가... 일단 복구하면서 어떤 문제였는지 정리했다.
블로그에 옮길 때도 확인한 사실과 아직 모르는 원인은 구분해 두려고 한다.

## 1. Makefile은 왜 맨날 실패하지?

**Q. Docker Desktop은 켜졌는데 왜 DB가 안 뜨는가?**

```text
Docker daemon is ready.
Error response from daemon: failed to set up container networking:
network ... not found
make: *** [up] Error 1
```

컨테이너가 참조하는 예전 네트워크 ID와 현재 네트워크 ID가 달랐다.
네트워크 이름이 `breakground_default`로 같아도 새로 만들어지면 ID는 다르다.

```text
남아 있는 컨테이너 → 예전 네트워크 A를 찾음
현재 Docker       → 새 네트워크 B만 있음
```

`make`는 Docker 명령이 실패했다는 결과를 보여준 것이다.
Makefile 문법이 원인은 아니었고, 네트워크가 왜 없어졌는지는 아직 확인하지 못했다.

**Q. 어떻게 고친다는 건지 잘 모르겠는데?**

컨테이너를 다시 만들면 현재 네트워크에 연결할 수 있다.

```bash
docker compose up -d --force-recreate postgres
```

현재 PostgreSQL 데이터는 컨테이너 안의 임시 공간이 아니라 `postgres_data`라는 named volume에 저장한다.
위 명령은 그 볼륨을 삭제하지 않고 컨테이너를 재생성한다.
복구 후 DB 실행, 기존 Flyway V1 이력, room 테이블 조회까지 확인했다.
다만 실행 중인 DB도 재시작하므로 평소 시작마다 무조건 사용할 명령은 아니다.

## 2. Docker Desktop을 직접 종료해서 그런 건가?

**Q. 지난번에는 Docker Desktop을 직접 종료했다. 그게 문제인가?**

직접 종료하는 것은 정상적인 사용 방법이다.
그것만으로 이번 오류의 원인이라고 단정할 수 없다.
처음에는 `make fclean`으로 컨테이너와 네트워크를 함께 정리하면 재발을 피할 수 있다고 안내받았다.
그런데 실제로는 정리·종료 과정도 멈췄다. 그 설명만으로 충분하지 않았다.

**Q. make fclean을 실행했는데 왜 GUI가 안 닫히지?**

원래 순서는 Compose 정리 후 macOS에 앱 종료를 요청하는 것이었다.

```text
docker-compose down
→ osascript -e 'quit app "Docker"'
```

처음에는 앱 종료 요청 방식 때문일 가능성을 이야기했다.
이후 확인한 상황에서는 앞의 `docker-compose down` 자체가 대기 중이었다.
앞 명령이 끝나지 않으면 다음 종료 명령까지 가지 못한다.

로그에 Container와 Network가 `Removed`로 표시됐다고 해서 명령 전체의 완료나 다음 재시작 상태까지 보장할 수는 없었다.
처음 실행은 프롬프트로 돌아왔고 다음 실행은 down에서 멈췄으므로, 모든 실행을 같은 상태였다고 묶어서 설명하는 것도 조심해야 한다.

**Q. Docker 전용 종료 명령을 쓰면 되는가?**

```bash
docker desktop stop --timeout 30
```

이 명령도 30초 뒤 실패했다. 오류에는 GUI Helper, Docker Desktop, `com.docker.backend` 등의 프로세스가 남아 있다고 나왔다.
적어도 정상 종료 요청으로 제한 시간 안에 종료되지 않았다는 것은 확인했다.
정확히 내부 어디서 멈췄는지는 아직 모른다.

수동 강제 종료는 성공했다.

```bash
docker desktop stop --force --timeout 30
```

그런데 다시 make를 실행하니 오래된 네트워크를 찾는 오류는 남아 있었다.
프로세스 강제 종료와 컨테이너 연결 정보 복구는 별개의 일이었다.
결국 컨테이너를 재생성해서 복구했다.
강제 종료는 다른 프로젝트의 작업에도 영향을 줄 수 있으므로 자동 처리하지 않기로 했다.

## 3. 그러면 Makefile은 어떻게 바꾸나?

일반 시작, 복구, 종료 명령을 나눴다.

| 명령 | 역할 |
| --- | --- |
| `make` | Docker 실행 → 엔진 준비 대기 → DB 실행 |
| `make repair-db` | 볼륨을 유지하고 DB 컨테이너 재생성 |
| `make down` | 컨테이너와 네트워크 정리. 데이터 볼륨 유지 |
| `make fclean` | down 성공 후 Docker Desktop 종료 |

시작 순서는 `up → wait-for-docker → docker-start` 의존 관계로 표현했다.
fclean은 down이 성공한 뒤 recipe에서 docker-stop을 호출한다.
그래서 `make -j`로 실행해도 이 흐름 안에서 준비와 실행, 정리와 종료가 동시에 진행되지 않도록 했다.

앱 종료에는 `docker desktop stop --timeout 30`을 사용한다.
실패하면 복구 방법을 출력하고, 강제 종료는 사용자가 직접 판단한다.
`reset-db`, `nuke-db`는 `down -v`를 사용하므로 데이터까지 지운다. 복구 명령과 혼동하면 안 된다.

이 변경은 Docker 내부 문제를 고친 것이 아니다.
프로젝트에서 실행 순서와 실패 후 대응을 명확하게 만든 것이다.

## 4. 꼭 Python까지 넣어야 하나? justfile은?

**Q. 시간 제한 때문에 Python을 넣었는데, 꼭 필요한가? 차라리 justfile로 바꿔야 하나?**

처음 수정에서는 명령 전체가 멈췄을 때 끊기 위해 Python 시간 제한 스크립트를 추가했다.
그런데 Docker 명령 몇 개 실행하려고 별도 스크립트를 관리하는 건 지금 프로젝트에는 과하다고 느꼈다.
그래서 Python 스크립트와 관련 설정은 제거했다.

just도 프로젝트 명령을 관리하는 도구로 쓸 수 있지만, 바꾼다고 Docker의 멈춤 자체가 해결되지는 않는다.
지금은 Makefile을 유지하고 필요한 명령만 작게 두기로 했다.

대신 포기한 기능도 있다.
Docker Desktop 종료의 30초 제한은 유지하지만, Docker 준비 대기와 Compose 명령 전체에는 별도 시간 제한이 없다.
거기서 멈추면 `Ctrl+C`로 중단한 뒤 Docker 상태를 확인해야 한다.

## 오늘 남겨둘 점

- Make가 실패했다고 Makefile 문법 문제인 것은 아니다. 실패한 실제 명령부터 본다.
- 컨테이너, 네트워크, 데이터 볼륨은 따로 생각해야 한다.
- 진행 메시지와 명령의 종료, 다시 실행했을 때의 상태는 구분해서 확인한다.
- 복구에 성공한 것과 근본 원인을 찾은 것은 다르다. 반복 오류의 내부 원인은 아직 미확인이다.
- 편의 도구를 고치다가 의존성과 관리할 코드를 너무 늘리지 않기로 했다.

## 5. Repository부터 다시 이해하기

**Q. 문법부터 쓰기 전에 Repository가 뭘 하는지부터 알아야 하지 않나?**

Room은 방 하나의 상태와 규칙을 표현하고, RoomRepository는 Room을 저장하거나 조회하는 역할이다.
@Entity는 테이블과 연결할 매핑 정보이지, 객체가 스스로 조회하도록 만드는 기능은 아니다.
Java_101에서 MemberDao.findAll()을 호출했듯이 방 목록 조회를 Repository에 요청하게 된다.
이번에는 Spring Data JPA가 제공하는 기본 구현을 사용한다.
저장된 방 목록을 가져오는 일과 현재 시각에 방이 열려 있는지 판단하는 정책은 구분해서 생각한다.

**Q. DTO, DAO, VO를 다 만들던데 Repository와 다른 건가?**

저장·조회하는 역할과 데이터를 표현하는 객체가 섞여 있어서 헷갈렸다.

| 구분 | 역할 | 이 프로젝트에서의 예 |
| --- | --- | --- |
| DAO | 데이터 접근 방법을 감춤 | 예전에 JDBC로 만든 MemberDao |
| Repository | 도메인 객체를 저장하고 찾는 통로 | RoomRepository |
| Entity | 식별자로 구분되는 도메인 객체, JPA에서는 테이블에 매핑 | Room |
| DTO | 경계를 넘어 전달할 데이터 구조 | 향후 방 목록 응답용 RoomResponse |
| VO(Value Object) | 식별자보다 값 자체로 의미와 동등성을 판단 | LocalTime, 필요할 경우 운영 시간 값 객체 |

DAO와 Repository는 역할이 겹친다. DAO는 데이터 접근 기술을 감추는 데, Repository는 도메인 객체를 모아 둔 저장소처럼 사용하는 데 초점이 있다.
DAO는 JDBC 전용, Repository는 JPA 전용이라는 규칙은 아니다.
현재는 RoomRepository로 충분하므로 같은 CRUD를 하는 RoomDao를 추가할 이유가 없다.

DTO는 DB에 접근하지 않는다. 예를 들어 방 목록 API에서 필요한 id, name, isOpen만 담는 응답 구조를 만들 수 있다.
Entity의 필드 구성과 API의 응답 구성을 독립적으로 바꿀 수 있게 하는 의미가 있다. 아직 이 DTO는 구현하지 않았다.

VO는 문맥을 확인해야 한다. 일부 자료에서는 DTO 같은 데이터 운반 객체를 VO라고 부르기도 한다.
도메인 설계에서 말하는 Value Object는 값으로 비교하고 보통 불변으로 만든다.
LocalTime.of(12, 0)을 두 번 만들어도 equals로 같은 시각이라고 판단하는 것이 예다.
반면 이름과 운영 시간이 같더라도 ID가 다른 Room은 별개의 방일 수 있다.
DTO도 불변으로 만들 수 있으므로 setter 유무만으로 DTO와 VO를 구분하면 안 된다.

DTO, DAO, VO를 모두 하나씩 만들어야 하는 공식은 없다.
지금은 Room과 RoomRepository에 집중하고, API 응답을 설계할 때 DTO를, 값과 규칙을 묶을 필요가 생길 때 VO를 검토한다.

참고: [DAO](https://www.oracle.com/java/technologies/dataaccessobject.html), [DTO](https://martinfowler.com/eaaCatalog/dataTransferObject.html), [Value Object](https://martinfowler.com/bliki/ValueObject.html)

## 다음으로

이제 RoomRepository 작성으로 돌아왔다.
`com.breakground.room`에 빈 `RoomRepository` 클래스를 만들었다. 위치는 맞지만 아직 데이터 접근 기능은 없다.
리뷰에서는 Spring Data JPA를 사용하려면 class를 interface로 바꾸고 `JpaRepository<T, ID>`를 상속해 보라는 힌트를 받았다.
T에는 관리할 엔티티 타입, ID에는 그 엔티티 식별자의 Java 타입을 넣는다.
아직 메서드나 구현은 작성하지 않았다. 이 부분은 직접 이어서 해볼 예정이다.

오늘 나오는 질문과 답변도 이 문서에 이어서 정리하되, 아직 구현하거나 검증하지 않은 내용을 완료한 것처럼 적지는 않는다.

## 6. DAO, Repository, DTO, VO — 왜 다들 네 개를 다 만드는 것처럼 보이지?

**Q. Repository와 DAO/DTO/VO 차이가 뭔지 모르겠다. 사람들은 네 개를 다 만드는 것 같던데?**

네 개 중 절반은 "책임(역할)"이고 절반은 "데이터를 담는 그릇"이라는 축으로 구분하면 헷갈림이 줄어든다.

역할(뭘 하는가):
- DAO — SQL/JDBC 같은 기술적인 접근 방법을 숨긴다는 관점. 예: `MemberDao`.
- Repository — 도메인 객체들이 컬렉션처럼 존재한다는 관점. 예: `RoomRepository.findAll()`.
- 실무에서는 둘이 거의 같은 일을 하므로 한 프로젝트에 둘 다 만들 필요는 없다. JPA를 쓰는 현재는 Repository 하나로 충분하다.

그릇(뭘 담는가):
- Entity(`Room`) — DB 테이블과 매핑된 도메인 객체. id로 구분한다.
- DTO — 계층 경계를 넘길 때 필요한 데이터만 담는 상자. 예: 방 목록 API 응답에서 `isOpen` 같은 계산 결과까지 얹어 내려줄 `RoomResponse`.
- VO — id가 아니라 값 자체로 동일성을 판단하는 객체. 예: `LocalTime.of(12, 0)`.

현재 프로젝트 기준:
- Entity `Room` — 있음
- Repository — 작성 중
- DTO, DAO, VO — 아직 필요 없음 (API 응답 설계 시 DTO, 값·규칙을 묶을 필요가 생기면 VO 검토)

"네 개를 다 만드는 것처럼 보인다"는 인상은 프로젝트가 커지면서 각자 다른 시점에 자연스럽게 등장하기 때문이지, 처음부터 세트로 만드는 공식이 있는 것은 아니다.

## 7. RoomRepository 작성 — JpaRepository의 타입 파라미터와 추상 메소드

`RoomRepository`를 다음과 같이 작성했다.

```java
package com.breakground.room;

import org.springframework.data.jpa.repository.JpaRepository;

public interface RoomRepository extends JpaRepository<Room, Long> {

}
```

**Q. JpaRepository는 왜 항상 타입을 두 개 받고, 왜 흔히 Long을 쓰는가?**

두 개를 받는 이유는 "어떤 Entity를, 어떤 타입의 식별자로 찾을지"를 컴파일 타임에 명시해야 하기 때문이다.
Long이 고정값은 아니고, DB PK로 BIGINT를 많이 써서 관습적으로 Long을 쓰는 경우가 많을 뿐이다.

다만 `Room.id`는 `Integer`인데 `JpaRepository<Room, Long>`으로 선언해서 타입이 어긋나 있다.
지금은 메소드를 하나도 호출하지 않아 컴파일은 되지만, 이후 `findById()` 등을 호출할 때 인자 타입 문제가 드러날 것으로 예상된다. 아직 실제로 확인하지 않았다.

**Q. DB에서 뭔가를 가져오는 인터페이스인데 왜 추상 메소드가 하나도 없는가?**

`JpaRepository`는 빈 인터페이스가 아니라 `PagingAndSortingRepository`, `CrudRepository` 등을 상속하고 있고, 그 안에 `save()`, `findAll()`, `findById()`, `deleteById()` 같은 추상 메소드가 이미 선언돼 있다. `RoomRepository`는 이를 그대로 물려받는다.
이 추상 메소드들의 구현체는 Spring이 애플리케이션 실행 시점에 인터페이스를 보고 동적 프록시로 자동 생성한다.

**Q. 프록시를 자동 생성한다는 게 스프링 핵심 원리인 IoC인가?**

IoC(제어의 역전)는 "객체 생성·관리 책임을 개발자가 아니라 프레임워크(Spring 컨테이너)가 갖는다"는 더 큰 원칙이다. `@Autowired` 의존성 주입도, Repository 구현체를 Spring이 대신 만들어주는 것도 모두 IoC의 사례다.
동적 프록시 생성은 그 IoC 원칙을 Repository 케이스에 적용한 구체적인 기술이다. Spring이 `RoomRepository` 인터페이스를 보고 실행 시점에 실제 구현 클래스를 바이트코드로 생성하고(JDK Dynamic Proxy 또는 CGLIB), 그 객체를 IoC 컨테이너에 빈으로 등록한다. 이후 `@Autowired`나 생성자 주입으로 이 빈을 받아 쓴다.

정리하면 IoC는 "누가 객체 생성/관리를 책임지는가"에 대한 원칙이고, 동적 프록시는 그 원칙이 Repository에 적용된 구체적인 수단이다.

빌드는 정상적으로 됐다. Integer/Long 타입 불일치는 서비스 코드에서 실제로 메소드를 호출할 때 다시 확인할 예정이다.

이후 `RoomRepository`를 `JpaRepository<Room, Integer>`로 직접 수정해서 `Room.id`(Integer)와 타입을 맞췄다.

## 8. JpaRepository의 두 번째 타입 인자와 Service 계층 설계

**Q. JpaRepository의 두 번째 타입 인자가 PK를 식별해주는 건가?**

맞다. 정확히는 "이 Repository가 관리하는 Entity의 `@Id` 필드 타입"을 컴파일러에게 알려주는 역할이다.
Entity는 `@Id`로 "이 필드가 PK다"를 표시하고, Repository의 두 번째 타입 파라미터는 그 PK의 Java 타입을 지정해서 `findById(Integer id)` 같은 메소드 시그니처를 만들 수 있게 한다.

**Q. "현재 시각에 방이 열려있는지" 판단을 왜 Room 엔티티가 아니라 Service에 둬야 하는가?**

Room에 두면 안 되는 것은 아니다. 두 가지 방식이 있고 트레이드오프가 다르다.

- Room에 두는 방식(Rich Domain Model): `openAt`, `closeAt`을 가진 Room 자신이 `isOpen(now)`를 판단. 데이터와 그 데이터로 할 수 있는 행동이 한 곳에 있어 응집도가 높다.
- Service에 두는 방식(Anemic Domain Model 쪽): Entity는 데이터만 갖고, 판단은 Service가 담당. 판단에 DB의 다른 상태(예: 관리자가 강제로 닫은 플래그)나 여러 Room을 동시에 다루는 로직이 필요해지면 유리하다.

**Q. 답이 정해진 건 아니지?**

그렇다. 정답이 하나로 고정된 문제는 아니다. 판단 기준은 "isOpen 계산이 Room 자신의 필드만으로 끝나는 순수 계산인가, 외부 정보가 더 필요한가"이다.
현재는 `openAt`, `closeAt`만으로 끝나는 순수 계산이라 `Room.isOpen(now)`로 두는 쪽이 자연스럽다. 다만 이는 현재 설계 기준의 판단이며, 이후 관리자가 방을 강제로 닫는 정책 등이 추가되면 Service가 조율하는 방식으로 재검토할 수 있다.

## 9. Room.isOpen() — 자정을 넘는 운영 시간 처리

`docs/decisions.md`에는 이미 "자정을 넘는 운영 시간을 허용한다. 예: 23:00~02:00"라는 결정이 있었지만, 처음 작성한 `isOpen()`은 이 케이스를 처리하지 못했다.

```java
public boolean isOpen() {
    LocalTime now = LocalTime.now();
    return now.isAfter(openAt) && now.isBefore(closeAt);
}
```

**Q. openAt=18:00, closeAt=02:00, now=23:00이면 now.isBefore(closeAt)는 true인가 false인가?**

false다. `LocalTime`은 날짜 정보 없이 하루(00:00~23:59) 안에서만 비교하기 때문에, 23:00은 02:00보다 항상 "이후"로 취급된다.

**Q. 그러면 LocalDateTime으로 바꾸고 SQL도 바꿔야 하나?**

아니다. 컬럼 타입(`LocalTime`)과 스키마는 그대로 두고, `openAt`과 `closeAt`의 대소 관계로 두 케이스를 나눠 비교 로직만 분기하면 된다.

- 일반적인 방(`openAt < closeAt`, 예: 11:30~13:00): `now`가 `openAt` 이후이면서 `closeAt` 이전이면 열림 (AND).
- 자정을 넘는 방(`openAt > closeAt`, 예: 18:00~02:00): `now`가 `openAt` 이후이거나 `closeAt` 이전이면 열림 (OR).

구현 중 두 차례 조건이 뒤바뀌는 실수가 있었다.
- 일반 방 분기에서 `isBefore`/`isAfter`를 반대로 써서 열려있어야 할 시각(12:00, 11:30~13:00 방)에 false를 반환.
- 자정 분기를 고치다가 `now.isBefore(openAt) || now.isAfter(closeAt)`로 잘못 바꿔, 닫혀있어야 할 시각(10:00)에 true를 반환.

각각 구체적인 시각을 대입해 손으로 검증하면서 잡았다. 최종 코드:

```java
public boolean isOpen() {
    LocalTime now = LocalTime.now();
    if (openAt.compareTo(closeAt) < 0)
        return now.isAfter(openAt) && now.isBefore(closeAt);
    else
        return now.isAfter(openAt) || now.isBefore(closeAt);
}
```

검증: `openAt=18:00, closeAt=02:00, now=23:00` → true(열림, 정상). `now=10:00` → false(닫힘, 정상).

다음은 Service 계층으로 이어간다.
