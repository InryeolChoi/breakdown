# 2026-10-03 — AnonymousUser 정책 이어가기

## 오늘 시작 상태

Room 도메인은 Entity, Repository, DTO, Service, Controller, Flyway V1~V4, 시간·요일 단위 테스트까지 완료했다. 다음 도메인은 AnonymousUser다.

지난 논의에서 로그인 없는 브라우저 식별을 위해 임의 토큰을 cookie로 전달하고, cookie가 있으면 기존 AnonymousUser를 찾는 방향을 잡았다. 구현 구조가 막막해 `ask-matt` 흐름의 `grill-with-docs` 방식으로 설계 결정을 먼저 좁히기로 했다.

아직 정하지 않은 사항은 cookie 유지 기간과 DB에 식별 토큰 원문 또는 해시 중 무엇을 저장할지다. 닉네임은 사용자가 입력할 수 있고 없으면 서버가 생성한다는 기존 프로젝트 정책을 따른다.

## 프로젝트의 전체 목표를 다시 정리

이 프로젝트는 직장인이 로그인이나 설치 없이 접속해 3~10분 동안 시간대별 채팅방과 짧은 미니게임을 즐기고 나가는 익명 웹 서비스다. 메시지 기록은 방이 닫힌 뒤 보존하지 않는다.

기술 학습의 목표는 Java 21, Spring Boot 4, PostgreSQL 기반 서비스를 직접 설계하고 실제 사용자에게 운영하는 것이다. ERD, Spring MVC, JPA/JDBC, transaction, validation, 익명 세션, 실시간 통신, moderation, Docker, AWS 배포, 모니터링과 로그를 실제 기능 안에서 경험한다. MSA, Kafka, Kubernetes 등은 목적에 필요해질 때만 검토한다.

진행 순서는 Room 기반과 API를 완성한 뒤 AnonymousUser 생성·식별을 구현하고, 최소 프론트 화면으로 연결한다. 그다음 Message와 채팅, 신고·moderation, 게임·점수 기록을 붙이고, 마지막으로 AWS에 배포해 실제 사용자 피드백과 운영 지표를 확인한다. 사용자가 핵심 정책과 주요 Java 구현을 직접 만들고 AI가 리뷰와 반복 검증을 맡는다.

## V5에서 user_status와 브라우저 식별 키는 어떻게 표현할까?

ERD에는 PostgreSQL enum으로 `user_status`가 있고 값은 `ACTIVE`, `BANNED`다. 현재 Flyway V1~V4는 이 DB 타입을 만들지 않았으므로, V5에서 테이블보다 먼저 `CREATE TYPE user_status AS ENUM ('ACTIVE', 'BANNED')`로 선언해야 한다. 그 뒤 status 컬럼은 `user_status NOT NULL DEFAULT 'ACTIVE'`로 둘 수 있다. Java에는 `UserStatus` enum을 만들고 Entity 필드에 `@Enumerated(EnumType.STRING)`을 써 이름 그대로 저장한다. ORDINAL은 enum 순서를 숫자로 저장해 항목 순서 변경에 취약하므로 피한다.

브라우저 식별 컬럼은 AnonymousUser의 DB primary key인 `id`와 목적이 다르다. id는 테이블 내부 관계에 쓰고, cookie는 같은 브라우저가 다음 요청에서 제시할 예측하기 어려운 bearer token을 담는다. 추천 형태는 cookie에 임의 token 원문을 보내고 DB에는 SHA-256 해시를 `identifier_hash` 같은 unique 컬럼에 저장하는 것이다. 그러려면 ERD와 V5 양쪽에 그 컬럼을 추가해야 한다.

Cookie의 Max-Age 30일은 브라우저가 cookie를 보관하는 기간이다. 그것만으로 서버가 복사된 토큰을 30일 뒤 거부하지는 않는다. 서버에서도 만료를 강제하려면 token 만료 시각을 DB에 두고 검사하거나, last_seen_at 기준 유휴 만료 정책을 정해야 한다. 그러므로 cookie 30일과 서버 토큰 만료 의미를 같은 결정으로 취급하지 않는다.

확인한 V5 초안에는 실행 전 점검할 항목이 있다. id에 primary key와 identity 생성이 선언되지 않았고, `user_status` 타입이 먼저 생성되지 않았다. 현재 ERD/정책과 맞추려면 created_at·last_seen_at은 날짜+시간을 보존하는 timestamp 계열이어야 하며, 초안의 `time`은 시각만 저장한다. `last_seen__at` 컬럼명도 ERD의 `last_seen_at`과 맞춰야 한다. 그리고 브라우저 식별을 구현하려면 token hash 컬럼이 빠져 있다.

## 프론트엔드는 언제 시작할까?

Room 조회 API는 이미 있으므로 프론트 프로젝트를 지금 시작해도 된다. 다만 AnonymousUser API의 요청·응답과 cookie 처리 계약을 먼저 정하고, 그 계약이 생기는 즉시 최소 화면을 구현하는 순서가 안정적이다. Message/실시간 채팅까지 기다릴 필요는 없다.

첫 프론트 범위는 열린 Room 목록, 닉네임 입력, 익명 사용자 생성·복귀 흐름으로 제한한다. 이 화면이 API 계약을 실제로 사용하는지 확인한 다음 Message와 채팅 UI로 확장한다.

## V5의 status와 브라우저 식별 키

ERD의 `Enum user_status { ACTIVE, BANNED }`는 PostgreSQL enum 타입으로 구현할 수 있다. Flyway V5에서 테이블 생성 전에 `CREATE TYPE user_status AS ENUM ('ACTIVE', 'BANNED')`를 실행하고, 테이블 컬럼은 `status user_status NOT NULL DEFAULT 'ACTIVE'`로 둔다.

Java에는 `UserStatus` enum을 만들고 `@Enumerated(EnumType.STRING)`을 사용해야 enum 이름을 저장한다. PostgreSQL native named enum으로 매핑하려면 Hibernate의 `@JdbcTypeCode(SqlTypes.NAMED_ENUM)`도 함께 필요하다. 단순 `@Enumerated(STRING)`은 기본적으로 VARCHAR 계열 저장을 뜻하므로, ERD의 native enum과 실제 JDBC 매핑을 구분한다. 대안은 ERD를 VARCHAR + CHECK로 바꾸는 것이지만 현재 ERD를 유지한다면 native enum 방식이 일치한다.

브라우저 식별은 DB 관계용 `id`와 별개다. 쿠키에 담긴 임의 토큰으로 같은 브라우저를 찾을 수 있어야 하므로 V5와 ERD에 unique 식별 컬럼이 필요하다. 권장안은 쿠키에는 token 원문, DB에는 64자리 SHA-256 hex 해시를 저장하는 `identifier_hash` 컬럼이다. 원문은 bearer credential처럼 취급한다.

30일 쿠키 유지 정책은 브라우저 저장 기간만 정한다. 서버에서도 idle 30일 뒤 토큰을 무효화하려면 `last_seen_at` 기준으로 만료 여부를 판단하고, 유효 요청 때 쿠키 Max-Age와 `last_seen_at`을 갱신하는 정책을 함께 구현해야 한다.

현재 V5 초안에는 `user_status` 타입 선언, identity primary key, 식별 hash 컬럼이 빠져 있고 시간 컬럼이 `time`으로 되어 있다. Migration을 적용하기 전에 ERD와 시간 의미를 정리해야 한다.

## 프론트 작업 시점

프론트는 AnonymousUser API의 생성·복귀 계약이 정해지고 최소 구현이 끝난 직후 시작한다. Room 목록 API도 이미 있으므로 Message 구현을 기다릴 이유는 없다. Next.js 화면에서 방 목록, 닉네임 입력, 익명 사용자 cookie 흐름을 연결해 보고, 이후 Message API에 맞춰 채팅 화면을 확장한다.

## AnonymousUser 구현은 어떤 순서로 진행할까?

AnonymousUser는 먼저 식별 정책과 ERD를 정하고, 그 다음 Flyway V5로 DB schema를 추가한다. Java 코드는 프로젝트의 기존 base package `com.breakground` 아래에 `anonymoususer` 도메인 패키지를 만들고, Entity → Repository → DTO → Service → Controller 순으로 구현하는 편이 의존 관계를 따라가기 쉽다.

사용자가 제안한 `com.breakdown`은 현재 프로젝트 base package와 다르므로 `com.breakground`를 사용한다. V5의 토큰 컬럼과 HTTP cookie 처리 방식은 cookie 유지 기간과 DB 저장 형태가 결정된 뒤 확정한다.

## 익명 브라우저 식별에는 어떤 보안 문제가 있을까?

쿠키의 임의 토큰은 그 자체가 권한 증표(bearer token)다. 토큰을 훔친 쪽은 해당 브라우저 사용자처럼 요청할 수 있으므로, 토큰 원문을 로그나 DB에 남기지 않고 HTTPS와 `Secure`, `HttpOnly`, 적절한 `SameSite` 쿠키 속성을 사용해야 한다. OWASP는 세션 식별자를 충분히 예측 불가능하게 만들고 쿠키 속성을 통해 노출 위험을 줄이도록 권고한다. DB에는 고엔트로피 난수 토큰의 SHA-256 해시를 저장하면 DB만 유출됐을 때 원문 재사용 위험을 줄일 수 있다. 이는 사람이 기억하는 비밀번호 해시와 다른 상황이다.

브라우저가 쿠키를 자동으로 붙이므로 상태를 바꾸는 요청에는 CSRF도 고려해야 한다. GET으로 상태를 변경하지 않고, 실제 배포 환경에서 Origin 검증이나 Spring의 CSRF 방어를 검토한다. `SameSite`만으로 모든 CSRF 위험이 해결된다고 가정하지 않는다.

이 식별은 사람의 신원을 확인하지 않는다. 사용자가 쿠키를 지우거나 시크릿 창·다른 기기를 쓰면 새 AnonymousUser가 생길 수 있어 차단을 우회할 수 있다. 낮은 진입 장벽을 우선하는 현재 서비스에서는 브라우저 단위의 best-effort 식별로 받아들이고, IP 추적이나 fingerprinting처럼 개인정보 침해와 복잡성을 키우는 수단은 실제 악용 문제가 확인되기 전에는 추가하지 않는 방향이 합리적이다. 30일 쿠키를 택한다면 브라우저 보관 기간뿐 아니라 서버가 토큰을 언제 만료·폐기할지도 함께 정해야 한다.

## 프론트는 언제 바이브코딩을 시작할까?

Room 목록 API가 이미 있으므로 프론트의 화면 골격과 Room 목록은 지금 시작할 수 있다. 다만 AnonymousUser의 생성·재방문 API 계약이 정해지기 전까지 그 부분은 임시 화면이나 mock으로 두고, 계약과 백엔드 테스트가 준비되면 연결한다. Message API와 실시간 채팅을 기다릴 필요는 없다.

프론트 구현은 별도 프롬프트나 작업으로 시작하면 집중하기 좋다. 그 프롬프트에는 프로젝트 목표, 사용할 프론트 기술, 실제 API 주소·요청/응답 예시, 지금 만들 화면 범위, 백엔드에서 확정되지 않은 동작을 mock 처리하라는 경계를 적는다. 지금 이 대화에서는 보안·API 정책을 같이 정하고, 실제 프론트 코드를 만들 시점에 맥락을 짧게 넘기면 된다.

## 이 서비스는 어떤 보안부터 적용할까?

익명 서비스를 안전하게 만든다는 것은 사용자의 실제 신원을 알아내는 것이 아니다. 브라우저 토큰은 해당 브라우저의 권한 증표이므로 충분히 긴 암호학적 난수로 만들고, 원문은 HttpOnly 쿠키로만 전달하며, 서버 DB에는 해시를 저장한다. 운영에서는 HTTPS와 `Secure`, `SameSite` 속성을 적용하고 토큰 원문이나 쿠키를 로그에 남기지 않는다. 쿠키를 쓰는 변경 요청은 CSRF 방어도 필요하며, GET은 상태를 변경하지 않아야 한다.

서비스 남용 방어는 별도로 서버에서 입력 길이·요청 빈도·신고 중복을 검증하고, 신고 누적에 따른 제한과 차단을 적용한다. 다만 쿠키 삭제나 다른 기기 사용으로 새 익명 사용자를 만들 수 있는 한계는 남는다. 이를 막으려고 IP 저장이나 브라우저 fingerprinting을 곧바로 도입하지 않고, 우선 최소 개인정보를 쓰는 브라우저 단위 식별로 시작한다.

개발 순서는 식별 토큰 생성·저장·복귀·폐기 정책을 정하고 테스트한 뒤, 요청 검증과 moderation 규칙을 적용하는 것이다. HTTPS 쿠키 속성은 운영 환경에서 필수이며, 로컬 HTTP 개발 환경 설정은 운영 설정과 구분한다.

## V5 초안 리뷰: 적용 전에 고칠 점

현재 저장소에는 AnonymousUser Java 수직 슬라이스가 아직 없고, V5 migration만 초안으로 추가되어 있다. 초안 SQL은 `status ... default 'ACTIVE';`에서 테이블 정의가 끝나기 전에 세미콜론을 써 문법 오류가 난다. `id`에는 primary key와 identity가 없고, `last_seen_at time`은 시각만 저장해 ERD의 timestamp와 다르다. ERD는 `nickname`을 nullable text로 선언하지만 SQL 초안은 not null varchar(10)이므로 정책을 정해 양쪽을 맞춰야 한다.

PostgreSQL에서 따옴표 없는 `AnonymousUser`는 소문자 `anonymoususer`로 접힌다. JPA의 기본 naming 전략은 Java의 `AnonymousUser`를 `anonymous_user`로 매핑할 수 있으므로, 실제 Entity의 명시적 테이블명과 migration을 일치시켜야 한다.

쿠키 보안 속성은 DB 컬럼이 아니다. 다만 쿠키 토큰으로 같은 브라우저의 AnonymousUser를 다시 찾는 기능을 구현하려면 식별자(권장: 토큰 해시)를 저장할 위치가 필요하다. 토큰 만료 컬럼은 서버 측 만료 정책을 선택할 때 추가할 수 있으며, 아직 확정되지 않은 상태에서 필수로 넣을 필요는 없다.

Migration 문법과 모델 불일치가 남아 있어 이번 변경은 테스트·DB 적용·커밋·푸시하지 않는다. 다음 미션은 V5만 ERD와 정책에 맞게 사용자가 고쳐서 리뷰받고, 통과한 후 적용 여부를 검증하는 것이다.

## 닉네임과 id를 ERD에서 어떻게 표현할까?

사용자가 닉네임을 생략하면 서버가 자동 생성해 저장한다는 정책이라면, 최종 DB row에는 닉네임이 항상 있어야 한다. 따라서 DBML 컬럼에 `[not null]`을 표시하고 실제 컬럼에도 `NOT NULL`을 둔다. 선택 입력은 API 요청의 정책이고, DB의 not-null은 저장된 데이터의 불변 조건이므로 서로 모순되지 않는다. ERD 타입을 `varchar(10)`으로 제한할지 `text`로 둘지는 실제 닉네임 길이 제한 정책에 맞춰 양쪽에서 동일하게 정한다.

각 테이블의 `id`는 그 테이블 행을 구분하는 primary key다. 다른 테이블의 `anonymous_user_id` 같은 컬럼이 `AnonymousUser.id`를 가리킬 때 그쪽 컬럼이 foreign key다. 즉 AnonymousUser.id는 자기 테이블에서 PK이면서 다른 테이블들이 참조하는 대상이다. DBML에서 자동 증가를 표현하려면 Room처럼 `[primary key, increment]`를 붙이고, PostgreSQL에서는 `GENERATED ... AS IDENTITY`로 구현한다. 단순 `PRIMARY KEY`만으로는 자동 증가가 되지 않는다.

수정된 V5에서는 SQL 구문 오류는 고쳐졌다. 다만 `CREATE TABLE "AnonymousUser"`처럼 따옴표를 쓰면 PostgreSQL에 대소문자 구분 테이블명이 만들어진다. Java/Hibernate의 기본 naming과 충돌을 피하려면 보통 `anonymous_user`처럼 소문자 snake_case 이름을 명시적으로 사용하는 편이 안전하다.

이후 ERD와 V5를 맞췄다. AnonymousUser.id는 DB identity primary key이고, 닉네임은 생략 입력 시 서버가 생성하되 저장값은 `varchar(10) NOT NULL`이다. created_at·last_seen_at은 현재 ERD와 동일한 date/timestamp 타입이며, status는 PostgreSQL named enum에 ACTIVE 기본값을 둔다. migration 파일 이름도 `V5__create_anonymous_user.sql`로 정리했다.

검증은 `./gradlew compileJava test --tests com.breakground.room.RoomTest`와 전체 `./gradlew test`가 성공했다. 전체 Spring context 테스트는 Flyway V5를 로컬 PostgreSQL에 적용하고 JPA context 검증까지 통과했다. 다음은 Java `UserStatus`와 AnonymousUser Entity를 만들어 DB 컬럼과 매핑하는 단계다.

## AnonymousUser Entity 초안 리뷰

`UserStatus`의 `ACTIVE`, `BANNED` 값은 정책과 일치한다. Entity 초안은 아직 컴파일되지 않는다. `AnonymousUser anonymousUser(...)`는 생성자가 아니라 반환 타입이 빠진 일반 메서드라서 `missing return statement`가 난다. 생성자는 클래스와 같은 이름이며 반환 타입을 쓰지 않는다. JPA용 protected 기본 생성자도 필요하다.

V5와 필드 매핑도 맞춰야 한다. DB 컬럼은 `created_at`인데 코드에는 `date`라고 지정되어 있고, DB status 컬럼은 `status`이지 `user_status`가 아니다. Java 필드는 snake_case보다 `createdAt`, `lastSeenAt`, `status`처럼 camelCase로 두고, 컬럼명 변환은 naming strategy 또는 `@Column`에서 명시한다. PostgreSQL `date`에는 `LocalDate`, `timestamp`에는 `LocalDateTime`이 맞으며, 현재 초안의 `java.util.Date`와 `LocalTime`은 해당 SQL 의미와 맞지 않는다.

`@Setter`를 Entity 전체에 열어두면 id나 status 등 불변 규칙과 무관한 값을 어디서든 바꿀 수 있다. 필요한 읽기 접근만 열고 상태 변경은 의미 있는 도메인 메서드로 제한하는 방향을 검토한다. id는 identity로 DB가 만드므로 신규 Entity 생성 시 전달하거나 직접 설정하지 않는다. 컴파일과 DB 매핑 검증은 수정 후 다시 수행한다.

## AnonymousUser 이름 길이와 JPA 매핑을 정리하다

닉네임 최대 길이를 10자에서 30자로 늘렸다. V5는 이미 로컬 DB에 적용된 migration이므로 수정하지 않고, V6에서 `anonymous_user.nickname`을 `varchar(30)`으로 확장했다. ERD와 decisions도 30자 정책으로 맞췄다.

Entity는 DB 컬럼 이름에 맞춰 `createdAt`/`LocalDate`, `lastSeenAt`/`LocalDateTime`, `status`/`UserStatus`로 정리했다. `UserStatus`는 PostgreSQL native enum이므로 Hibernate에 named enum JDBC 타입임을 지정했다. Entity 전체 setter를 제공하지 않고 id는 identity 생성에 맡긴다. Repository도 추가했다.

`./gradlew test`가 통과했다. 별도 DB 조회에서도 Flyway V1~V6가 모두 성공했고, `anonymous_user.nickname`의 실제 타입이 `varchar(30)`임을 확인했다. Repository 저장·조회 테스트는 30자 닉네임과 ACTIVE enum 값을 왕복 검증한다. 다음은 생성 요청 DTO에서 닉네임 선택 입력·길이 검증 정책을 표현하고, Service에서 생략 시 서버 생성 규칙을 구현하는 단계다.

## 한국어 닉네임 생성과 JSON DTO 검증은 무엇일까?

런타임에 AI API를 불러 닉네임을 만들 필요는 없다. 수식어와 동물 이름 같은 로컬 단어 목록을 조합하면 지연·비용·외부 장애 없이 일정한 정책으로 만들 수 있다. 초기 목록은 6개 수식어와 7개 명사라 조합이 42개뿐이었다. 이후 50개 수식어 × 40개 명사와 000~999 숫자 접미사를 붙여 명목상 2,000,000가지 조합으로 늘렸다. 무작위 생성은 중복을 줄일 뿐 유일성을 보장하지 않는다. 닉네임은 표시용 이름이므로 보안 토큰처럼 비밀일 필요도 없다.

현재 Controller는 `@RequestParam`으로 URL query parameter를 받는다. 예를 들어 `POST /anonymoususer?nickname=...` 형태다. JSON 요청 DTO를 쓰면 요청 본문 `{"nickname":"..."}`을 전용 Java 객체로 변환한다. `@RequestBody`는 JSON을 DTO로 읽고, DTO 필드의 `@Size(max=30)`은 최대 길이 규칙을 선언하며, Controller 파라미터의 `@Valid`가 그 규칙을 실행한다. 닉네임이 선택값이면 `@Size`는 null을 허용하므로, 생략 시 Service가 자동 생성할 수 있다. `@NotBlank`는 null과 공백도 거부하므로 이 선택 정책과는 다르다.

길이 검증에 실패하면 Controller가 Service를 호출하기 전에 Spring MVC가 요청 오류로 처리해 HTTP 400을 반환한다. 응답 본문 메시지 형식을 일관되게 하려면 예외 처리기를 추가한다. Service의 명시적 예외는 다른 호출 경로를 보호하고, HTTP에서는 같은 오류를 400으로 변환해야 한다.

요청 DTO와 `AnonymousUserResponse`는 방향이 서로 다르다. `AnonymousUserResponse`는 서버에서 사용자에게 보내는 응답 모델이므로 그대로 둔다. 클라이언트가 보내는 JSON에는 `AnonymousUserCreateRequest` 같은 별도의 요청 DTO를 만든다. Controller 매개변수에서 `@RequestBody`와 `@Valid`를 붙이고, 요청 DTO의 nickname에 `@Size(max=30)`을 선언한다. 그러면 검증 실패는 Service 호출 전에 HTTP 400이 된다. 현재 Controller는 query parameter를 받으므로 JSON 요청으로 바꿀 때 그 위치를 교체한다.

닉네임 생성 코드는 `KoreanNicknameGenerator`로 분리했다. 수식어 50개 × 명사 40개가 2,000개 기본 조합이고, 000~999 접미사를 붙여 명목상 2,000,000개를 만든다. 전체 테스트가 통과했다.

## Service는 무엇을 맡을까?

Service는 하나의 애플리케이션 사용 사례를 완성한다. AnonymousUser 생성에서는 요청에서 받은 선택 닉네임을 사용하거나 생략 시 서버가 생성하고, ACTIVE 상태와 생성·활동 시각을 정해 Entity를 만든 다음 Repository에 저장한다. 저장된 Entity를 응답 DTO로 바꿔 Controller에 돌려준다. DB 조회/저장은 Repository, HTTP 요청·응답 처리는 Controller의 책임이다. 여러 DB 작업이 하나의 변경으로 묶이면 Service 경계에 `@Transactional`을 둔다.

현재 사용자 작성 Service 초안은 Repository 필드만 있고 생성자 주입과 메서드가 아직 없어 미완성이다. 응답 DTO도 getter가 없어 아직 Jackson 응답으로 쓰기 전이다. 다음에는 요청·응답에서 브라우저에 내부 DB id, status, lastSeenAt까지 노출할 필요가 있는지 먼저 정하고, 생성 use case 하나를 Service 메서드로 구현한다.

## 무작위 한국어 닉네임과 생성 시각은 어디서 정할까?

한국어 닉네임은 실제 사람 이름이나 무작위 한글 음절을 만들기보다, 관리된 단어 목록의 형용사·상태 표현과 동물·사물 명사를 조합하는 방식이 읽기 쉽고 안전하다. 예: `졸린참새`, `퇴근기다리는고양이`. 목록에서 난수 인덱스를 선택하면 되고, 표시용 닉네임은 인증 토큰이 아니므로 보안용 암호 난수 생성기를 쓸 필요는 없다. 조합이 중복될 수 있으므로 중복 허용 여부는 제품 정책으로 따로 정한다.

`created_at`은 DB `date`라 Java `LocalDate`, `last_seen_at`은 DB `timestamp`라 `LocalDateTime`에 대응한다. Service에서 한 번만 현재 시각을 구해 그 값에서 날짜와 시간을 나눠 Entity 생성자에 넘기면 둘이 같은 생성 시점을 가리킨다. 시스템 시각을 Entity 생성자 안에서 직접 읽으면 테스트에서 시간을 고정하기 어렵고 환경 시간대가 도메인에 숨어든다. 필요해지면 `Clock`을 Service에 주입해 테스트와 운영 시간대를 명시할 수 있다.

현재 Service 초안은 `isBlank()` 호출 전에 null 여부를 처리해야 하며, 빈 값에 빈 문자열을 저장하는 대신 닉네임 생성 규칙을 실행해야 한다. 길이 초과 시 void 메서드에서 조용히 return하면 호출자가 실패 이유를 알 수 없으므로 요청 DTO의 validation이나 명시적 예외로 표현한다. 응답을 돌려줄 메서드라면 저장한 Entity를 응답 DTO로 변환해 반환한다.

### 생성 Service에 자동 닉네임과 입력 오류를 적용하다

빈 값과 null이면 한국어 수식어·동물 이름 목록에서 각각 하나를 골라 조합하도록 했다. 직접 입력된 닉네임은 앞뒤 공백을 제거하고 30자를 넘으면 `IllegalArgumentException`을 던진다. 조용한 `return`은 호출자에게 성공과 실패를 구분할 결과를 주지 못하므로 쓰지 않는다. Controller/예외 처리에서 이 입력 오류를 HTTP 400으로 변환하는 부분은 다음 검증 단계에서 연결한다.

생성 시각은 Service에서 한 번 구해 `createdAt`과 `lastSeenAt`에 같은 시점을 전달한다. Service는 생성된 Entity를 반환하고 Controller가 응답 DTO로 변환한다. Repository 생성자 주입과 Controller 주입도 추가했으며, 빈 입력 자동 생성과 30자 초과 예외를 테스트했다. `./gradlew test`가 통과했다. 현재 Controller 입력은 간단한 선택 query parameter이고, 이후 JSON 요청 DTO와 `@Valid` 검증으로 정리할 수 있다.

### 한국어 임의 닉네임을 만들고 Service 20번째 줄을 어떻게 볼까?

닉네임은 보안 토큰이 아니므로 `SecureRandom`이 필요하지 않다. 관리 가능한 형용사 목록과 명사 목록에서 각각 하나를 뽑아 조합하면 쉬운 첫 버전이 된다. `ThreadLocalRandom` 또는 `Random`으로 목록 인덱스를 선택할 수 있다. 조합 결과가 중복될 수 있으므로 닉네임에 unique 제약을 두지 않는 한 문제는 아니다. 중복이 허용되지 않는 정책이면 별도 설계와 저장 충돌 처리가 필요하다.

Service 안에서 `new AnonymousUser(...)`로 도메인 객체를 만드는 것은 책임에 맞다. 다만 nickname이 null 또는 공백이면 빈 문자열로 저장하지 말고 임의 닉네임을 만들며, 너무 긴 입력은 조용히 return하지 말고 DTO validation 또는 명시적 예외로 거부해야 한다. 생성 시각은 `LocalDateTime.now()`를 한 번만 읽어 그 값과 `toLocalDate()`를 Entity 생성자에 전달하면 자정 경계에서 created_at과 last_seen_at 날짜가 어긋나는 것을 막는다. 저장 결과에는 DB 생성 id가 채워지므로 Service 반환값/응답 DTO를 만들 때 저장된 Entity를 사용한다.

혹시 20번째 줄이 `AnonymousUserResponse`의 `lastSeenAt = anonymousUser.getLastSeenAt()`을 가리킨다면, 이는 단순 필드 복사로는 맞다. 다만 lastSeenAt과 status, 내부 DB id가 최초 생성 응답에 필요한지는 API 계약에서 별도로 정한다.

## 무엇을 먼저 만들어야 할지 막막할 때

AnonymousUser 다음에 다른 도메인으로 넘어가기보다, 이미 만든 Entity와 Repository를 사용 사례 하나로 연결하는 것이 다음 학습 단위다. Service 전체를 한 번에 생각하지 않고 `생성 요청을 받는다 → 닉네임 생략 여부를 판단한다 → Entity를 만든다 → Repository에 저장한다 → 응답으로 돌려준다` 순서로 나눈다.

첫 단계는 코드를 바로 완성하는 것이 아니라 Service의 메서드 이름과 입력·출력을 정하고, 각 단계에 필요한 책임이 어느 계층에 있는지 표시하는 것이다. 사용자가 그 초안을 작성하면 다음에 Repository 호출·기본값·transaction 경계가 적절한지 리뷰한다. 현재 devlog 기록도 갱신한다.

### Controller를 먼저 만들어야 할까?

요청이 실행될 때는 Controller가 HTTP 진입점으로 가장 먼저 호출된다. 하지만 코드를 작성하는 순서가 반드시 런타임 호출 순서와 같을 필요는 없다. 먼저 `POST /anonymous-users`의 요청·응답 계약을 정하고, Controller는 입력 DTO를 받아 Service에 위임하며, Service는 닉네임 기본값·ACTIVE 상태·시간·저장을 조율한다. Controller부터 뼈대를 만들 수도 있지만, Service 메서드의 입력과 반환값이 정해지지 않으면 Controller도 연결할 대상이 없다.

현재 단계에서는 Controller 로직보다 생성 요청 DTO의 모양과 Service 메서드 계약을 먼저 정하고, 그 다음 Controller가 이를 HTTP로 연결하는 순서가 학습하기 쉽다. Controller 안에 Repository 호출이나 익명 닉네임 생성 규칙을 넣지 않는다.

Service를 어디서 시작할지 막막할 때는 모든 기능을 한 번에 설계하지 않고, 한 요청이 데이터베이스에 저장되어 응답으로 돌아오는 흐름 하나만 따라간다. 첫 use case는 익명 사용자 생성이다. 입력 닉네임을 정리하거나 없으면 생성하고, 생성 날짜·마지막 활동 시각을 정해 Entity를 만들고, Repository에 저장하고, 저장 결과를 응답 DTO로 변환한다. Entity가 이미 ACTIVE 상태를 기본으로 설정하므로 Service가 id나 status를 직접 만들 필요는 없다.

구현 순서는 Service에 `@Service`를 붙이고 Repository를 생성자 주입한 뒤, `create...` 메서드 하나를 작성하는 것이다. 그 메서드 내부에서 입력 처리 → Entity 생성 → `repository.save` → 응답 DTO 변환 순서로 나눈다. 쿠키와 HTTP 응답 처리는 이 첫 Service 메서드에 넣지 않고 후속 단계로 둔다. 요청 DTO의 선택 입력/30자 검증과 Response DTO의 직렬화 접근자도 이 흐름을 테스트하기 전에 정리한다.

## 요청 DTO를 별도로 추가하다

기존 `AnonymousUserResponse`는 서버가 응답으로 보내는 모델이고 이미 Entity에서 값을 복사한다. JSON 요청을 받는 클래스는 별개이므로 빈 `AnonymousUserCreateRequest` 클래스를 추가했다. 다음 단계에서 optional nickname 필드와 `@Size(max=30)` 검증을 넣는다.

## 왜 생성 요청이 필요하고 Request DTO는 꼭 필요할까?

HTTP Controller의 Service는 클라이언트 요청에 응답해 실행되므로, 익명 사용자를 만들려면 진입 시점에 POST 요청이 필요하다. 다만 POST 요청에 JSON body가 반드시 필요한 것은 아니다. 서버가 항상 임의 닉네임을 정한다면 body 없이 생성할 수 있다.

현재 제품 정책은 사용자가 닉네임을 입력하거나 생략할 수 있고, 생략하면 서버가 만든다는 것이다. 따라서 한 번의 생성 요청에 닉네임을 optional 필드로 담으면 사용자가 고른 값을 함께 전달할 수 있고, 생략 시 Service가 기본 생성 규칙을 적용한다. Request DTO는 이 입력을 표현하고 `@Size(max=30)` 검증을 두는 역할이다. 대안으로 먼저 생성 후 닉네임 수정 API를 둘 수 있지만, 별도 요청과 수정 정책이 더 필요해진다.

여기서 사용자는 미리 제시된 닉네임 중 하나를 고르는 것이 아니라, 원하는 문자열을 직접 입력하거나 입력을 생략한다. 따라서 Request DTO는 선택 목록을 전달하기 위한 것이 아니라 선택적 자유 입력값을 받기 위한 것이다. 공백만 입력한 경우도 생략과 같이 취급해 Service에서 자동 생성한다는 정책으로 정리했다.

## AnonymousUser 생성 요청은 GET일까 POST일까?

현재 Controller에는 `@PostMapping("/anonymoususer")`가 있으므로 HTTP 요청은 POST다. Java 메서드 이름이나 `@RequestParam`이 GET/POST를 결정하지 않는다. `@RequestParam`은 URL query parameter를 읽는 바인딩 방식이고 POST에서도 사용할 수 있다.

AnonymousUser 생성은 DB row를 추가하는 상태 변경이므로 POST가 맞다. GET은 조회처럼 서버 상태를 바꾸지 않는 요청이어야 한다. 브라우저와 중간 시스템은 GET을 사전 요청하거나 캐시할 수 있으므로, GET으로 생성하면 의도하지 않은 row가 생길 위험이 있다. `/rooms` 조회는 GET이고, 새 AnonymousUser 생성은 POST로 구분한다.
