# Breakground 미니게임 후보

확인일: 2026-11-06. 게임 선택을 위한 조사이며 구현·정책 확정은 아니다. `AGENTS.md`, `CLAUDE.md`, `docs/decisions.md`, `docs/erd.dbml`, `docs/devlog/NEXT.md`를 읽었다. 현재 합의는 브라우저에서 게임 상태 처리, 새로고침 시 초기화, 서버에 Game 목록과 GamePlay 결과 저장이다. 게임은 첫 공개 채팅 범위 이후의 후속 기능이다.

## 추천

첫 게임은 **패턴 순서 기억**, 다음 게임은 **작은 SameGame 보드**를 추천한다. 혼자 즉시 시작하고 소리 없이 클릭·탭으로 끝낼 수 있으며, 실시간 대전·매칭·새 인프라가 필요 없다는 판단이다. 먼저 하나만 구현한다. 아래 시간과 보드 크기는 Breakground용 제안이며 실제 플레이 측정값이나 원작의 평균 소요 시간이 아니다. 3~10분을 한 판으로 채우기보다 짧은 한 판을 원하는 만큼 반복하게 한다.

| 후보 | 확인한 원형과 Breakground용 작은 범위 | 한 판 목표 | 적합성·주의점 |
| --- | --- | --- | --- |
| **패턴 순서 기억** | 점점 길어지는 버튼 입력 순서를 기억하는 [Human Benchmark의 Sequence Memory 소개](https://humanbenchmark.com/)를 참고. 3×3 버튼이 켜진 순서를 그대로 입력하고 오답 또는 상한 단계에서 종료하는 방식 제안 | 약 1~3분, 단계 상한으로 길이 제한 | 규칙 설명이 짧고 키보드·탭을 함께 지원하기 쉽다. 버튼 식별에 위치·테두리도 사용하고 소리는 필수로 삼지 않는다. 화면을 떠났을 때 처리와 단계 상한은 선택 필요 |
| **같은 블록 묶음 지우기(SameGame)** | 연결된 같은 색 블록을 지우고 중력·열 압축을 적용하는 [공식 규칙](https://www.chiark.greenend.org.uk/~sgtatham/puzzles/doc/samegame.html). 6×6·3종류 보드 한 장, 상하좌우 연결, 새 블록 추가 없음으로 시작하는 제안 | 약 2~5분 | 서두르지 않고 생각할 수 있다. 모두 지우거나 더 지울 묶음이 없으면 자연스럽게 끝난다. 색마다 기호를 병기한다. 첫 버전에서 항상 전부 지울 수 있는 보드 생성까지 요구하지 않는다 |
| **반응속도** | 신호가 바뀌면 클릭하는 [Human Benchmark 원형](https://humanbenchmark.com/tests/reactiontime). 무작위 대기 후 문자·색 신호, 유효한 5회 결과를 묶는 제안 | 약 30~60초 | 가장 작은 체험 후보. 조기 입력은 해당 시도 실패로 안내한다. 원형도 컴퓨터·모니터 지연이 결과에 영향을 준다고 설명하므로 공개 순위용 첫 게임으로는 우선순위를 낮춘다 |
| **숫자 슬라이딩 퍼즐** | 빈칸 옆 타일을 움직여 번호순으로 정렬하는 [Fifteen 공식 규칙](https://www.chiark.greenend.org.uk/~sgtatham/puzzles/doc/fifteen.html). 첫 버전은 3×3으로 축소하고 완성 상태에서 합법 이동으로 섞는 제안 | 약 2~5분 목표, 미보장 | 탭·방향키와 잘 맞고 소리 불필요. 섞기 횟수가 실제 풀이 난이도를 보장하지 않으며 익숙하지 않으면 오래 걸린다. 중도 종료를 쉽게 제공한다 |
| **숫자 합치기(2048 계열)** | 같은 숫자를 합치는 [제작자의 게임](https://gabrielecirulli.github.io/2048/). 작은 보드와 이동·합치기만 먼저 검토 | 기본 규칙만으로 짧은 종료 미보장 | 키보드·스와이프를 함께 설계할 수 있으나 숙련자는 오래 지속한다. 3분 도전으로 바꾸면 별도 시간 종료·최종 점수 정책이 생기므로 후순위 |

웹 문서와 공식 소개를 확인했다. 게임을 직접 플레이하거나 모바일 조작을 검증하지는 않았다. Human Benchmark 개별 페이지 일부는 본문 추출이 비어 공식 홈 소개와 검색에 노출된 원문으로 보완했다. 공식 사이트와 이름이 비슷한 다른 도메인의 설명은 근거로 사용하지 않았다.

## 첫 구현의 정상·실패·경계

패턴 순서 기억의 작은 범위는 시작 → 시범 표시 → 입력 → 정답이면 다음 단계 → 결과 → 다시 시작이다. 점수는 완료한 단계 수를 후보로 둔다. 최고 단계와 시범 속도는 구현 전 사용자와 정한다. 난이도 선택·아이템·연속 출석·공개 랭킹은 첫 게임에 묶지 않는다.

| 상황 | 확인할 동작 또는 정할 정책 |
| --- | --- |
| 정상 | 정확한 순서의 마지막 입력 후 한 번만 단계 상승. 결과 화면에서 한 번만 저장 요청 |
| 오답·잘못된 조작 | 오답이면 결과 표시. 시범 표시 중 입력 무시. 빠른 연속 탭이 두 이벤트로 중복 반영되지 않는지 확인 |
| 경계 | 마지막 단계 완료, 첫 단계 오답, 창 크기 변경·360px 화면, 키보드 입력과 탭 입력 혼용 확인 |
| 중단 | 새로고침은 기존 합의대로 초기화. 탭 숨김·포커스 이탈 때 중단/재시작/계속 중 어떤 동작을 할지는 선택 필요 |
| 저장 실패 | 결과는 화면에 남기고 실패·재시도 안내. 재전송으로 동일 판이 중복 저장되지 않도록 하는 계약은 별도 설계 필요 |

SameGame을 다음에 만든다면 연결 묶음 판정 → 삭제 → 아래로 낙하 → 빈 열 압축 → 종료 판정 순서가 핵심이다. 1개 블록 선택, 모서리 연결, 마지막 묶음 제거, 전부 제거, 고립 블록만 남음, 애니메이션 중 추가 입력을 확인한다. 원형의 점수식도 복수이므로 특정 공식을 이미 결정한 것으로 취급하지 않는다. [SameGame 공식 점수·종료 규칙](https://www.chiark.greenend.org.uk/~sgtatham/puzzles/doc/samegame.html).

## 결과 저장과 순위는 별도 결정

현재 `GamePlay.score`는 정수 하나다. 단계 수와 SameGame 점수는 높은 값이 좋지만 반응속도·풀이 시간은 낮은 값이 좋다. 게임 간 점수를 합산하지 않고 게임별 단위와 정렬 방향부터 정해야 한다. SameGame의 무작위 보드마다 난이도가 다르므로 단순 최고점이 같은 조건의 실력을 뜻하지도 않는다. 공통 보드·날짜별 문제는 가능한 후속 선택이며 현재 정책이 아니다.

브라우저가 계산해 보낸 점수는 사용자가 바꿀 수 있다. 서버는 익명 사용자 식별을 기존 쿠키로 판단하고 활성 게임·정수 타입·허용 범위를 검증해야 하지만, 범위 안의 조작 점수까지 진짜 플레이로 입증하지는 못한다. OWASP도 클라이언트 검증을 우회할 수 있어 서버 검증이 필요하다고 설명한다. [OWASP Input Validation](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html).

선택지는 다음과 같다. 이는 추천 비교이며 합의된 정책 추가가 아니다.

- **첫 체험:** 판 결과와 브라우저 내 최고점부터 제공하고 공개 경쟁 순위는 보류한다. 서버 결과 저장을 연결해도 미검증 기록이라는 성격은 같다. 브라우저 최고점 보존 여부는 새로고침 시 판 초기화와 구분해 정한다.
- **가벼운 공개 순위:** 쿠키 기준 사용자별 최고점과 입력 범위 검증을 적용할 수 있다. 쿠키 삭제·다른 브라우저로 새 익명 사용자가 될 수 있고 자동 입력·점수 변조를 막는 보장은 없다.
- **검증을 강화한 퍼즐 기록:** 서버가 발급한 보드·난수 시드와 제한된 이동 기록으로 결과를 재계산하는 방법이 있다. 현재 ERD에는 발급 판·중복 제출 키·이동 기록이 없어 저장 계약과 스키마 범위가 늘어난다. 자동 풀이까지 막지는 못한다. 반응속도의 실제 화면 표시 시점과 사람의 입력은 이런 재계산으로 입증하기 어렵다.

`played_at`의 날짜 기준, 동점 처리, 한 사용자 여러 기록의 집계, 중도 종료를 GamePlay로 셀지, 저장 재시도의 중복 방지, 익명 사용자 만료·차단 시 게임 결과 저장 허용 여부는 아직 정해지지 않았다. 기존 채팅 정책을 게임에 자동 적용하지 않는다. 공개 랭킹보다 먼저 **어떤 한 판을 완료된 기록으로 셀지** 사용자가 정하면 GamePlay 학습 범위가 작아진다.

## 판단의 한계

재미·반복 의향·실제 소요 시간은 대상 사용자 테스트가 필요하다. 이번 추천은 규칙과 현재 아키텍처의 적합성에 대한 추론이다. 외부 게임의 디자인·코드·자산을 복사하는 승인은 포함하지 않으며, 구현 전 별도 확인 없이 외부 코드를 가져오지 않는다. 이 조사에서는 파일 한 개만 추가했고 게임 구현·패키지 설치·정책 문서 수정은 하지 않았다.
