# 베타 이미지 릴리스와 운영 배포

## GitHub 검사

CI는 작업 브랜치와 main 대상으로 열린 PR, main 푸시에서 실행된다. PostgreSQL 17에 Spring 전체 테스트를 실행한다. 별도 일회용 DB에 동일 Spring 아티팩트를 띄우고 운영 시간과 무관하게 열리는 테스트 방을 준비한다. 기존 Node 계약 검사와 HTTP/WSS 연동 검사를 실행하고 Chromium 데스크톱·모바일에서 카페 진입과 메일비행기 배달을 확인한다. 테스트 보고서가 없거나 필수 테스트가 건너뛰어져도 실패한다. `Required CI`는 테스트·저장소 검사·두 이미지의 Critical 검사가 모두 성공해야 통과한다.

main 보호는 GitHub Actions의 `Required CI`를 필수로 지정한다. 최신 main을 기준으로 확인된 PR을 요구하고 관리자 우회, 강제 푸시, 브랜치 삭제를 막는다. 자동 머지를 활성화하기 전에 실제 PR에서 검사 이름과 발행 주체를 확인한다. 성능 수치와 5~10인 제품 실험 결과는 별도로 기록한다.

## 이미지 릴리스

main push의 CI가 성공한 경우에만 해당 SHA를 체크아웃한다. Linux amd64 프런트·백엔드 이미지를 빌드하고 Critical 이미지 검사를 통과한 뒤 GHCR에 게시한다. SHA 태그는 워크플로에서 덮어쓰지 않는다. 배포 입력은 `release.json`의 SHA와 두 `@sha256:` digest다. 이전 검증 릴리스는 비교용이며, 실제 롤백 대상은 운영자가 마지막으로 정상임을 확인한 서버의 배포 기록이다.

검증 작업은 읽기 전용 GitHub 토큰을 사용한다. 이미지 게시 작업에는 `packages: write`, 체크아웃에는 `contents: read`, 직전 릴리스 매니페스트 조회에는 `actions: read`를 사용한다. 외부 PR에서는 운영 비밀값이나 AWS 권한을 쓰지 않는다. 첫 GHCR 게시 후 패키지 공개 범위와 저장소 연결을 확인한다. 공개 이미지면 서버 pull에 레지스트리 비밀값이 필요 없다. 비공개이면 승인 후 운영 서버에 해당 패키지의 읽기 권한만 있는 자격 증명을 등록한다.

## Lightsail 경로 선택

| 방식 | 권한과 접속 | 비용과 운영 |
| --- | --- | --- |
| 서버에서 Pull | Lightsail이 승인된 릴리스 세트만 outbound HTTPS로 조회한다. SSH 허용 IP를 바꾸지 않는다. 호스트에서 검증된 고정 명령이 Compose의 앱 이미지 두 개만 교체한다. | 기존 호스트에서 타이머와 잠금으로 시작할 수 있다. 레지스트리·전송·디스크 비용과 이미지 보존 범위는 확인한다. |
| 제한된 원격 실행 | SSM 하이브리드 관리 노드와 전용 Run Command 문서 하나를 사용한다. 운영 승인 뒤 OIDC 역할을 정확한 저장소·환경과 문서·노드에 제한한다. SSM Agent와 노드 권한을 별도로 관리한다. | 고정 문서 실행·감사 추적이 가능하다. 하이브리드 노드에서 Run Command는 요청량 기반 비용이 발생할 수 있다. [AWS Hybrid Activations](https://docs.aws.amazon.com/systems-manager/latest/userguide/activations.html) |

베타는 **승인 전에는 수동 배포를 유지**한다. 시험을 통과한 뒤 서버 Pull을 우선한다. GHCR에 새 이미지가 올라왔다는 사실만으로 배포하지 않는다. 서버는 운영자가 승인한 SHA·digest와 백업 ID를 읽고, 동일 SHA의 성공한 CI 및 릴리스 기록과 일치할 때만 진행하도록 설계한다. 기존 SSH 경계를 유지하며, 이 단계에서는 운영 서버용 스크립트나 자격 증명을 프로비저닝하지 않는다.

## 승인된 시험 배포 한 번과 복구 훈련

1. 격리 환경에서 운영과 동일한 Compose·Caddy 구성을 준비한다. 호스트 아키텍처를 확인하고, 정상 버전과 시험 이미지의 digest를 기록한다. 백업을 별도 DB에 복원해 애플리케이션이 읽는지 확인한다.
2. 운영자가 승인한 변경 창에서 Asia/Seoul 운영 시간과 방 API를 확인한다. 다음 개장까지 시험·복구 시간을 확보하고 최신 DB 백업 상태와 사용 가능한 디스크를 확인한다. 운영 수동 배포와 미래 Pull 작업은 같은 서버 잠금을 사용한다.
3. Flyway 마이그레이션 파일 및 운영 DB 구성의 변화가 있는 릴리스는 중단한다. 자동 경로에서는 `SPRING_FLYWAY_ENABLED=false`로 운영 앱 기동 시 스키마 변경을 막고, Hibernate 스키마 검증이 실패하면 복구한다. 스키마·데이터 변경은 별도 승인 절차로 처리한다.
4. 정상 버전 두 digest와 Compose 설정을 기록한 뒤 `--no-deps`로 프런트와 백엔드만 교체한다. HTTPS 홈·방 목록·프록시 경로·쿠키 및 컨테이너 상태를 확인한다. 운영 방이 닫혀 있는 동안의 WSS는 정상적인 거절까지 확인할 수 있다. 채팅 왕복은 격리 환경 또는 승인된 운영 방에서 검증한다.
5. 시험용 검증 실패를 한 번 유도해 이전 두 digest로 복구하고 같은 점검을 반복한다. 시험 단계에서 DB는 제자리 복원하지 않는다. 승인자, 시각, 배포·복구 SHA, digest 및 결과를 비밀값과 채팅 내용 없이 남긴다.
6. 운영자가 시험 결과와 수동 배포 충돌 여부를 검토한 뒤 자동 실행 활성화를 별도로 승인한다.
