# Project Decisions

## Product
- 직장인이 3~10분 잠깐 놀다 가는 익명 웹 서비스
- 로그인 없음
- 모바일 앱보다 웹 우선
- 일반 채팅은 PostgreSQL에 임시 저장하며, 해당 방 운영 구간 종료 10분 후부터 정리 작업이 삭제한다. 과거 대화는 제공하지 않는다.
- 메시지의 신고 가능 기한은 작성 후 15분과 방 종료 중 빠른 시각이다. 원본의 실제 삭제 기한과 구분한다. 신고된 증거는 신고 후 30일 보관한다.
- 메시지 최대 140자
- 수정/삭제 불가
- 닉네임은 사용자가 정하거나 자동 생성

## Anonymous User
- 개인정보 식별이 목적이 아님
- 동일 브라우저를 구분할 최소 식별자 필요
- 닉네임은 사용자가 원하는 문자열을 직접 입력할 수 있고, 미리 준비된 닉네임 목록에서 고르는 방식은 아니다. 입력은 선택이며 생략하거나 공백만 입력하면 서버가 생성한다. 저장된 닉네임은 필수이며 최대 30자다.
- AnonymousUser의 id는 데이터베이스가 생성하는 primary key다.
- 동일 브라우저 재방문 식별에는 서버가 생성한 예측하기 어려운 토큰을 HttpOnly cookie로 전달한다. DB에는 토큰 원문을 저장하지 않고 SHA-256 해시만 저장한다.
- 같은 브라우저의 익명 식별은 마지막 방문 후 7일 동안 유효하다. 유효한 재방문 때 `last_seen_at`을 갱신하고 쿠키 유효 기간도 7일로 다시 설정한다.
- 익명 사용자의 차단은 영구 차단이 아니라 7일 임시 차단으로 한다. `banned_until`에 차단 해제 시각을 저장하며, 마지막 방문 시각과 분리한다.
- 운영에서는 HTTPS와 `Secure`, `SameSite` cookie 속성을 사용하고 원문 토큰을 로그에 남기지 않는다.
- ACTIVE / BANNED 상태 관리
- 신고 3회 누적 시 차단 정책 고려

## Chat
- 늦게 입장한 사용자에게 이전 대화를 제공하지 않는다.
- 일반 메시지는 서버가 UUID를 부여해 Message 테이블에 임시 저장한다. 본문은 varchar(140) 문자열이며 JSONB나 별도 NoSQL을 도입하지 않는다.
- `expires_at`은 min(작성 시각 + 15분, 해당 운영 구간 종료)이며 이 시각부터 신고 원본으로 사용할 수 없다.
- `delete_after`는 해당 운영 구간 종료 + 10분이다. 날짜가 바뀌어도 메시지를 작성한 운영 구간의 종료를 기준으로 계산한다.
- 메시지 삭제 작업은 실행 완료 후 1분 간격으로 `delete_after <= 현재 시각`인 row를 삭제한다. 실제 삭제는 다음 정리 실행까지 지연될 수 있으며 앱 정지 중에는 실행되지 않는다.
- DB 저장으로 전환하면서 기존 Map 보호용 전역 10,000개 상한은 제거한다. 사용자별 전송 제한과 DB 용량 모니터링은 운영 준비에서 별도 검토한다.
- 재시작 후에도 DB 원본이 남아 있고 `expires_at` 이전이면 신고할 수 있다. 재시작이 기한을 연장하지 않는다.
- 작성 당시 닉네임을 Message에 복사해 저장한다. 작성자 ID는 서버 쿠키로 확인한다.
- 메시지 길이는 Unicode 코드 포인트 기준 최대 140자다. 공백만 있는 내용은 거절하고 앞뒤 공백을 제거한다.
- Room은 반복적으로 열림
- 점심/간식/저녁 방을 별도 테이블로 만들지 않고 Room row로 관리
- open_at / close_at은 DB에 저장
- 방이 열려 있는지 판단하는 로직은 Spring에서 처리
- 자정을 넘는 운영 시간을 허용한다. 예: 23:00~02:00
- open_at은 포함하고 close_at은 제외한다. 예: 12:00~13:00 방은 12:00부터 열리고 13:00부터 닫힌다.
- open_at과 close_at이 같은 방은 허용하지 않는다. 24시간 방은 제공하지 않는다.
- 초기 Room은 점심메뉴방(10:00~11:30), 저녁메뉴방(16:00~17:30), 야근메뉴방(21:00~다음 날 02:00) 세 개로 시작한다.
- 초기 세 Room은 평일에만 운영하며, 주말에는 열리지 않는다.
- Room은 weekday_open, weekend_open으로 평일·주말 운영 여부를 저장한다. 두 값이 모두 false인 Room은 허용하지 않는다.
- 자정을 넘는 Room은 자정 전에는 당일 운영 여부를, 자정 후에는 전날 운영 여부를 기준으로 연다.

## Report
- 신고 대상은 AnonymousUser이며 Message 원본에서 복사한 내용은 신고 증거다.
- 신고자는 AnonymousUser
- 같은 사용자가 같은 메시지를 중복 신고할 수 없으며, DB UNIQUE 제약으로 동시 요청도 막는다.
- 신고자는 쿠키로 검증하고 대상 사용자·방·내용·작성 시각은 DB Message 원본에서 가져온다.
- 원본이 없거나 신고 가능 기한이 지났으면 신고를 거절한다. 브라우저가 보낸 내용을 대체 증거로 쓰지 않는다.
- 원본을 확인할 때 기준 시각을 정해 유효성을 판단한다. 그때 유효했다면 신고 커밋이 만료 시각 이후 끝나거나 정리 작업이 원본을 삭제해도 접수를 허용한다.
- `Report.message_event_id`는 원본 UUID를 복사한 추적 식별자이며 Message FK를 걸지 않는다. Message 삭제와 무관하게 Report 증거와 중복 신고 기준을 유지한다.
- 자신이 작성한 메시지는 신고할 수 없다. 신고 사유는 필수이며 최대 500자다.
- 신고 증거는 신고 후 30일을 보존 기한으로 기록하고 정리 작업이 만료된 Report row를 삭제한다.
- 신고 누적에 따른 자동 차단 기준은 아직 확정되지 않았으며 이번 구현에는 포함하지 않는다.
- warning_count는 별도 저장하지 않고 Report 기준 계산
- 관리자 증거 검토·자동 차단은 향후 기능이며 이번 Message 저장 전환에는 포함하지 않는다.

## Message DB 전환 상태 (2026-10-05)
- V10과 Entity/Repository 및 채팅·신고 Service의 DB 저장/조회 전환을 완료했다(2026-10-06).
- 원본 정리는 MessageCleanup, 신고 증거 정리는 ReportCleanup이 담당한다. Map·10,000개 상한·Map 실패 제거 콜백을 삭제했다. 적용된 V9/V10은 수정하지 않는다.
- 채팅 작성과 실시간 수신은 모두 WebSocket을 사용하는 양방향 방식으로 진행한다(2026-10-10 사용자 결정). 기존 ChatService의 검증·DB 저장은 재사용한다. 기존 HTTP 작성 API의 유지·제거 여부는 아직 확정하지 않았다.
- WebSocket 구현은 사용자와 AI가 분담한다. 핵심 연결·메시지 처리 흐름은 사용자 작성 기회를 우선하고, AI는 반복 코드·표준 라이브러리 연결·테스트를 지원한다. 구체 분담은 다음 학습 단계에서 합의한다.
- 방문 시각과 메시지 INSERT를 같은 DB 트랜잭션에 묶고, 향후 실시간 전달은 커밋 이후 수행한다.
- WebSocket 접속 전 기존 HTTP 익명 사용자 API로 쿠키를 준비한다. 핸드셰이크에서는 새 사용자를 생성하지 않으며 유효한 익명 쿠키와 운영 중인 방을 확인한다(2026-10-11).
- 클라이언트의 WebSocket 작성 요청은 본문만 담은 JSON으로 한다. 방은 접속 주소, 작성자는 쿠키로 판단하고 응답에는 서버가 생성한 메시지 ID·닉네임·본문·시각을 포함한다(2026-10-11).
- 방 운영 종료 시 서버가 종료 안내 후 연결을 종료한다. 작성 시 운영 시간 재검증도 유지한다(2026-10-11). 기존 HTTP 작성 API 유지 여부는 계속 미정이다.
- 유휴 연결의 운영 종료 확인은 정상 실행 중 1초 주기로 한다. 연결은 입장한 운영 구간의 종료 시각을 따르며 다음 운영 구간으로 연장하지 않는다. 방 종료를 우선하므로 종료 직전에 수락했어도 종료 시각 이후 커밋된 메시지의 전달을 기다리지 않으며, 종료 시각 이후 새 방송 전송을 시작하지 않는다. 이미 시작된 전송을 회수하는 의미는 아니다. 확인 주기는 엄격한 최대 지연 보장이 아니다. 유휴 연결의 자동 안내·종료는 실제 두 연결로 검증했고 방송 직전 세션 잠금 안의 종료 시각 검사도 구현해 종료 전·정각·종료 후 Registry 경계로 검증했다. 실제 DB 커밋 지연·잠금 대기 중 만료를 재현하는 검증은 남아 있다(2026-10-11).
- 연결 후 잘못된 JSON·빈 본문·140자 초과 등 입력 오류는 보낸 연결에만 오류 JSON으로 안내하고 연결을 유지한다. 익명 사용자 만료·차단·방 종료는 안내 후 연결을 종료한다(2026-10-11).
- 오류 JSON은 `{"type":"ERROR","status":400,"message":"..."}` 형태다. status는 오류 분류값이며 연결 후 HTTP 응답을 보내는 것은 아니다. 입력 오류는 400, 익명 사용자 만료는 401, 차단·방 종료는 403이며 종료가 필요한 경우 안내 후 WebSocket 종료 코드 1008을 보낸다. 메시지 처리 시의 오류·종료와 유휴 연결의 방 종료 자동 안내·종료를 구현·검증했다(2026-10-11).
- 각 방 접속 전 기존 HTTP 익명 사용자 API로 7일 쿠키를 갱신한다. 채팅 작성 시 DB 방문 시각은 기존 트랜잭션에서 갱신하며 WebSocket 메시지에 쿠키 원문을 실어 보내지 않는다(2026-10-11).
- TTL 삭제는 백업/WAL의 즉시 삭제를 보장하지 않는다. AWS 운영 시 백업 보존 정책을 별도로 정한다.

## Game
- 게임 내부 상태는 브라우저에서 처리
- 새로고침 시 초기화
- 서버는 Game 목록과 GamePlay 결과만 저장
- 플레이 1회 = GamePlay 1 row
- 랭킹/최고점/인기 게임 계산 가능

## Architecture
- Java 21
- Spring Boot 4
- PostgreSQL
- Docker
- 프런트는 Next.js + TypeScript로 진행하며 기존 Spring 서버 정책을 유지한다. 프런트 구현은 AI 활용 비중을 높인다(2026-10-13 사용자 결정).
- Redis는 필요할 때만
- Kafka / RabbitMQ / K8s / MSA는 이번 프로젝트에서 제외
- AI 기능은 부가 기능으로만 고려

## Frontend Direction (2026-10-13)
- 접속 직후 서비스 경험과 할 수 있는 행동이 직관적으로 보여야 한다. 사내 카페에서 잠깐 쉬는 분위기를 목표로 한다.
- 게시판 중심 구성과 메타버스 방식은 피한다.
- 추가 MCP는 디자인 관련 도구에 한정한다. Stitch를 먼저 사용하기로 선택했다(2026-10-15). 공식 원격 MCP를 연결 대상으로 하며 아직 인증·등록·설치·연결 검증은 하지 않았다. Figma는 실제 편집/공유 필요가 생길 때 검토한다. 조사 근거는 docs/research/design-mcp-comparison.md에 있다.
- 디자인은 커피 컵 중심이 아니라 탁 트인 창문이 보이는 라운지에 들어온 듯한 느낌을 목표로 한다(2026-10-13 사용자 수정). 구체적인 첫 화면·레이아웃·자산은 아직 확정하지 않았다.
- 프런트는 같은 저장소 루트의 `frontend/`에 둔다. 기존 Spring의 src/main·src/test·Gradle 구조는 유지한다(2026-10-13 사용자 결정). 실제 생성은 구현 단계에서 진행한다.
- HTTP/쿠키/WebSocket 접속 경로, 첫 화면 진입 순서와 디자인 세부는 미확정이다. 같은 저장소 배치가 같은 출처 접속을 확정하는 것은 아니다.
- 기본 구현 흐름은 작은 기능 이슈 하나당 PR 하나로 한다(2026-10-13 사용자 승인). implement-spec의 전체 통합 PR 방식과 구분한다. 이는 GitHub 설정 변경·게시·머지 권한을 추가로 승인한 것이 아니다.
- 모바일 360px와 데스크톱 1280px를 함께 검토한다. 첫 공개 범위는 채팅과 기존 신고 API에 연결한 신고 버튼까지이며 게임·관리자·자동 차단은 후속 범위다(2026-10-13 사용자 승인).
- 첫 기능은 열린 방 목록과 로딩·빈 상태·실패 후 재시도이며 브라우저 사용자 동작을 첫 테스트 경계로 삼는다. 작은 기능 분할 방향에 사용자 동의를 받았다. 화면 진입 흐름·접속 경로를 확정한 뒤 구현한다(2026-10-13).
- GitHub Issues 기준의 스킬·이슈·PR 준비 문서는 docs/drafts/frontend에 있다. 기본 triage 라벨과 세부 저장소 설정은 확인 전이다. 2026-10-15 사용자 요청으로 설계/준비·기능 티켓을 발행하고 native 부모·선행 관계를 연결했다. 인계는 docs/frontend-issues.md를 따른다. 설정 활성화·프런트 구현·MCP 실제 연결은 아직 하지 않았다.
