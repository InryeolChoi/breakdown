# Breakground 보안 점검 · 2026-11-22

서울 Lightsail의 운영 인스턴스, Docker의 실제 실행 설정과 이미지, AWS 계정 요약, 운영 URL 응답, 로컬 소스와 배포 설정을 읽기 전용으로 점검했다. 취약점 악용과 운영 부하 시험은 수행하지 않았다. Git 작업 트리에 배포 이후의 프런트 변경이 있어 소스와 운영 이미지 결과를 구분한다.

## 추가 발견

- 채팅 방송은 수신자별 잠금 안에서 순차적으로 전송한다. 느린 연결 하나가 다른 사용자 전달과 방 종료 처리를 지연시킬 수 있다. 연결별 전송 시간과 대기 버퍼에 한도를 둔다.
- 차단 상태는 메시지 작성 때 확인하지만 이미 연결된 수신자에게 방송할 때는 방 종료 시각만 확인한다. 운영자가 차단한 기존 연결에도 읽기 제한이 필요하다면 해당 사용자의 연결을 함께 종료한다.
- 7일 세션 만료는 인증 판단에 적용된다. 만료 익명 사용자 행 정리 작업은 찾지 못했다. 새 세션이 늘수록 테이블이 커진다. 신고 증거 등의 외래 키와 보관 정책을 고려해 정리한다. 중복 신고 방지는 신고자 ID 기준이므로 신규 익명 신원을 서로 다른 사람으로 간주할 수 없다.
- Caddy가 /api/ 아래의 경로를 일괄적으로 Spring에 넘긴다. Spring의 개발용 Echo WebSocket은 모든 Origin을 허용하고 채팅방 인증 인터셉터를 사용하지 않는다. API 프록시가 WebSocket 업그레이드도 처리하는 구성이다. 배포 프로필에서 Echo 등록을 제거하고, API와 WebSocket 공개 경로를 명시한다. 운영 채팅방 자체의 Origin 설정은 Echo와 별개다.
- 운영 미니멀 페이지 응답에는 CSP, frame-ancestors 또는 X-Frame-Options, X-Content-Type-Options가 없었다. 외부 프레임 삽입 방지를 우선하고 CSP는 Next.js 스크립트와 호환되도록 Report-Only로 검증한다.
- 네 컨테이너 모두 Docker 메모리 상한이 0(무제한)이며 json-file 로그에 개별 회전 설정이 없다. 컨테이너·DB가 같은 디스크와 메모리를 사용한다. 로그 회전, 디스크 경보, 실측에 따른 메모리 예산을 정한다.
- 조회한 CloudTrail trail, 서울 CloudTrail Lake 이벤트 저장소, Lightsail·CloudWatch 경보가 모두 0건이다. 기본 CloudTrail 이벤트 이력은 별도로 제공된다. root 사용, 방화벽·백업 변경과 자원 고갈에 대한 장기 기록과 알림 경로를 정한다. 예산은 1개였고 실제 알림 수신 여부는 검증하지 않았다.
- Ubuntu는 unattended-upgrades가 활성화됐지만 재부팅 필요 표시가 있다. 유지보수 시간에 재부팅 후 컨테이너·API·DB를 확인한다. SSH 암호 인증은 꺼져 있고 root 공개키 로그인은 SSH 정책상 가능하다. 실제 root 승인 키가 있는지는 확인하지 않았다.
- 이미지 태그가 가변이고 Gradle Wrapper 배포 SHA-256과 Gradle 의존성 검증 메타데이터가 없다. 배포 식별에는 이미지 digest를 기록하고 빌드 입력 검증을 도입한다. Next.js 최종 이미지에는 빌드 단계의 node_modules 전체가 복사돼 개발 의존성도 포함된다.
- 계정 수준 S3 Block Public Access 설정이 없고 조회된 버킷은 0개다. 향후 백업 버킷 생성 시 계정·버킷 공개 차단을 확인한다. 서울 GuardDuty 탐지기와 Access Analyzer 분석기는 0개였다. 유료 탐지 도입은 비용과 운영 필요에 따라 판단한다.

## 확인한 보호 설정과 한계

- Lightsail은 80·443만 모든 IPv4에 허용하며 22는 제한한다. IMDSv2 토큰 필수, 응답 hop limit 2다. 운영 .env는 권한 600이고 네 컨테이너 모두 privileged가 꺼져 있다.
- 익명 토큰은 SecureRandom 32바이트로 만들고 DB에는 SHA-256 해시를 저장한다. 쿠키에 HttpOnly, SameSite=Lax를 설정하며 운영 HTTPS에서 Secure가 붙는 것을 첫 배포에서 확인했다. 신고는 서버 원본을 복사하고 DB 유일 제약으로 같은 신고자의 중복을 방지한다.
- 로컬 npm audit --omit=dev 결과는 0건이었다. Git 이력에서 검사한 일부 AWS 키·개인키·GitHub 토큰 패턴은 0건이었다. 다른 형식의 비밀이나 과거 노출을 배제하지 않는다.
- 점검 범위는 Breakground, 해당 서울 리전, 열거한 계정 API다. 조직 SCP·다른 리전 전체 자원·외부 백업·복원 성공·실제 침해 여부는 별도 확인 대상이다. 이미지 검출은 패키지 버전 대조이며 취약 기능 호출과 서비스 침해를 입증하지 않는다.

근거 파일은 compose.production.yml, docker-compose.yml, deploy/Caddyfile, frontend/Dockerfile, WebSocketConfiguration.java, AnonymousUserService.java, ChatService.java, ReportService.java, RoomSessionRegistry.java다.

## 운영 변경 후 검증

- 계정에 S3 버킷이 0개임을 재확인한 뒤 계정 수준 S3 공개 차단 네 항목을 활성화했다. 변경 전파 후 다시 조회해 모두 true임을 확인했다.
- 운영 Caddy 설정을 백업하고 현재 Spring HTTP API 경로만 허용했다. API 본문 한도는 16KB로 정했다. 운영 응답에서 초과 요청 413, 개발용 Echo의 API 경로 404, 쿠키 없는 채팅 연결 401을 확인했다.
- 운영 페이지에서 프레임 삽입·object 삽입·base URI를 제한하는 CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy를 확인했다. 기본 주소는 302, 게임과 방 목록은 200이었다.
- 외부 클라이언트 한 곳에서 HTTPS 페이지와 방 목록을 각 20회 조회했다. 최대 동시 4개씩 10묶음, 묶음 사이 1초 간격, 총 10.87초였다. 40회 모두 200, 중앙값 47.4ms, p95 1142.7ms, 최댓값 1147.2ms였다. 각 요청은 새 curl 연결을 사용했다. 별도 요청에서 페이지 문구와 API 배열 응답을 확인했다. 단일 저부하 측정으로 채팅 처리 한계나 지연 원인은 판단할 수 없다.

## DB 역할 분리 적용 절차

운영 스키마가 있는 DB에서 관리자 역할로 `deploy/limit-db-roles.sql`을 실행한다. 이 스크립트는 `BREAKGROUND_APP_DB_PASSWORD`와 `BREAKGROUND_FLYWAY_DB_PASSWORD`를 psql 프로세스 환경에서 읽는다. 새 환경은 기존 마이그레이션으로 스키마를 만든 후 같은 절차를 적용한다. 운영에서는 서버의 보호된 `.env`에 두 역할의 사용자명과 비밀번호를 설정한다. 새 테이블을 만드는 마이그레이션에서 앱이 실제로 필요한 권한을 명시적으로 추가한다.

- `breakground_app`은 방 조회, 익명 세션 관리, 메시지·신고 저장과 만료 삭제에 필요한 권한을 가진다.
- `breakground_flyway`는 프로젝트 스키마 객체를 소유하고 마이그레이션을 실행한다. 두 역할 모두 PostgreSQL 슈퍼유저나 역할 관리자가 아니다.
- 롤백 시 이전 Compose와 환경 파일로 컨테이너를 시작하면 기존 관리자 연결로 앱이 다시 실행된다. 스키마 소유권 이전은 그대로 두고 서비스 회복을 먼저 확인한다.

로컬 PostgreSQL 포트를 loopback으로 제한했다. Spring Boot 4.1.3으로 테스트 101개를 통과했고, 로컬 배포 JAR의 Tomcat은 11.0.27, Jackson core·databind는 3.1.8이다. 별도 PostgreSQL에서 역할 전환 후 서버 시작과 익명 세션 발급을 확인했다. 런타임 역할의 스키마 생성·Flyway 이력 조회는 허용되지 않으며 메시지 만료 삭제와 신고 삽입 권한은 확인됐다.

## 후속 조치 순서

1. 운영자 인증을 임시 자격 증명의 최소 권한 역할로 전환한다. 새 역할이 인스턴스 상태 조회와 운영 접속을 할 수 있는지 확인한 뒤 root CLI 사용을 중단한다. GitHub Actions에는 별도의 OIDC 역할을 사용한다.
2. PostgreSQL 논리 백업을 운영 서버 외부에 두고 암호화·자동 만료를 설정한다. 월별 비용과 증거 보관 기간을 정한 뒤 복원된 별도 DB에서 마이그레이션 이력과 필요한 테이블을 확인한다. 배포 직전 인스턴스 스냅샷은 롤백용이다.
3. 세션 발급과 WebSocket 연결에 IP당 한도를, 채팅·신고에는 세션당 한도를 적용한다. 회사 공유 IP의 여러 사용자를 수용하고, 느린 연결의 전송·버퍼를 제한한다. 격리 환경에서 정상 사용자 동작과 제한 응답을 확인한다.
4. Flyway를 별도 배포 작업으로 이동해 앱 프로세스에는 앱 DB 자격 증명만 전달한다. 이어서 나머지 운영 이미지를 업데이트하고 각 이미지의 수정 가능한 권고를 재검사한다. 호스트는 유지보수 시간에 재부팅하고 CPU·디스크·백업 실패 경보를 검증한다.

Gradle 9.7.1 배포 ZIP의 공식 SHA-256 값을 Wrapper 설정에 추가했다. 프로젝트의 Wrapper JAR 해시도 공식 목록과 일치하며, 빈 캐시에서 배포 ZIP을 내려받고 Gradle이 기동하는 것을 확인했다.

## 후속 운영 반영 결과

Lightsail 수동 스냅샷 `breakground-before-db-hardening-20261122`가 사용 가능해진 뒤, 열린 방이 없는 것을 확인하고 백엔드 보안 패치와 DB 역할 전환을 적용했다. 네 컨테이너를 재생성해 각각 최대 10MB 파일 3개로 Docker 로그를 회전한다. 운영 미니멀 페이지와 방 API는 HTTP 200이었고, PostgreSQL에서 `breakground_app` 연결 10개를 확인했다. 신규 두 역할에 SUPERUSER와 CREATEROLE 권한은 없다.

스냅샷은 복구에 사용할 수 있는 상태다. 이 스냅샷으로 새 인스턴스를 만들어 복원하는 작업은 별도로 남아 있다. 수동 스냅샷은 삭제할 때까지 저장 비용이 발생하며 디스크에 있던 신고 증거와 비밀 설정이 보존될 수 있다. Spring 시작 시 Flyway가 실행되므로 두 DB 역할의 자격 증명을 백엔드 컨테이너가 함께 받는다. 자격 증명 격리를 끝내려면 Flyway를 별도 배포 단계에서 실행해야 한다.
